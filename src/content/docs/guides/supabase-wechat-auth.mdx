import { Aside } from "@astrojs/starlight/components";

WeChat login uses two different protocols that do not match standard OAuth 2.0 or OpenID Connect. Mini Program login (`wx.login()`) returns a one-time code that a backend exchanges at `GET /sns/jscode2session` with no browser redirect. Website QR login (`snsapi_login`) redirects the browser to `/connect/qrconnect`, but its token endpoint (`GET /sns/oauth2/access_token`) expects `appid` and `secret` query parameters instead of RFC 6749 `client_id` and `client_secret`[^rfc-6749], its profile endpoint (`GET /sns/userinfo`) requires both `access_token` and `openid`, it does not support PKCE, and it returns no email address.

This guide builds four Supabase Edge Functions and two PostgreSQL tables that adapt both WeChat login flows to Supabase Auth, decrypt Mini Program encrypted payloads (`wx.getPhoneNumber`) server-side, and provide a deterministic `wechat-mock` replacement for `api.weixin.qq.com` so the entire stack can be tested on a throwaway Supabase project without a WeChat developer account. For the platform's custom OIDC, passkey, and SAML behaviour, see [Supabase Auth providers: custom OIDC, passkeys, SAML and a sign-in canary](/reference/supabase-auth-providers/). For token signing, JWKS caching, and Data API verification, see [Supabase Auth end to end](/reference/supabase-auth-end-to-end/).

<Aside type="caution" title="Proven against wechat-mock, not live api.weixin.qq.com">
Every automated test in this guide runs against `wechat-mock` on a live Supabase project (verified 2026-06-26 and 2026-06-30) or in-process unit mocks. No test in the source repository has exchanged a token with real `api.weixin.qq.com`. The [Proven versus assumed matrix](#proven-versus-assumed-matrix) below separates what is verified against Supabase Auth and the mock from the protocol details transcribed from WeChat documentation.
</Aside>

## Prerequisites

- A Supabase project with the project reference (`<project-ref>`), anon key (`SUPABASE_ANON_KEY`), and service-role key (`SUPABASE_SERVICE_ROLE_KEY`).
- Deno 2.x and the Supabase CLI (`supabase` v2.108.0 or newer; `supabase db push` requires the Go binary).
- For production use only: a WeChat Mini Program (`wx...` AppID and AppSecret from `mp.weixin.qq.com`) and/or a WeChat Open Platform Website Application (`wx...` AppID and AppSecret from `open.weixin.qq.com`). Neither is needed to deploy and run the mock test suites.

## Architecture overview

The adapter splits WeChat integration into four Edge Functions and two `public` tables protected by Row Level Security (RLS) with no client policies:

| Function | What it does |
|---|---|
| `wechat-miniprogram` | Accepts `{ code }` from `wx.login()`, calls `GET /sns/jscode2session`, maps `unionid` and `openid` to `auth.users` via `wechat_identities`, stores `session_key` in `wechat_session_keys` with a 2-hour expiry, and issues a Supabase session using `admin.generateLink({ type: "magiclink" })` followed by `verifyOtp({ token_hash, type: "magiclink" })`. |
| `wechat-decrypt` | Validates the caller's Supabase Bearer JWT via `auth.getUser(jwt)`, reads `openid` from `user_metadata`, loads the stored `session_key` from `wechat_session_keys`, decrypts AES-128-CBC `encryptedData` and `iv` payloads using `node:crypto` with manual PKCS#7 padding removal, and checks `watermark.appid`. |
| `wechat-web-proxy` | Exposes `POST /wechat-web-proxy/token` and `GET /wechat-web-proxy/userinfo` as an RFC 6749 bridge for a Supabase Auth `custom:wechat-web` OAuth2 provider[^sb-custom-oauth]. Translates `client_id` and `client_secret` to `appid` and `secret`, packs WeChat's `access_token`, `openid`, and `unionid` into a base64 JSON opaque token so no key-value store is needed between `/token` and `/userinfo`, and maps `unionid ?? openid` to `sub`. |
| `wechat-mock` | Implements `GET /sns/jscode2session`, `GET /sns/oauth2/access_token`, `GET /sns/userinfo`, and `GET /connect/qrconnect`. Setting `WECHAT_API_BASE_URL` to the deployed `wechat-mock` URL routes all server-side WeChat calls to the mock. |

| Path | Flow |
|---|---|
| Mini Program login | The Mini Program client sends `POST /functions/v1/wechat-miniprogram` with `{ code }`. The function calls `/sns/jscode2session` on `api.weixin.qq.com` (or `wechat-mock`), upserts the user mapping in `wechat_identities` and `session_key` in `wechat_session_keys`, and calls `generateLink` + `verifyOtp` on Supabase Auth to return a session. |
| Mini Program decrypt | The Mini Program client sends `POST /functions/v1/wechat-decrypt` with `{ encryptedData, iv }` and `Authorization: Bearer <access_token>`. The function resolves the user via `getUser(jwt)`, reads `session_key` from `wechat_session_keys`, and returns the decrypted JSON payload. |
| Web QR OAuth2 | The browser calls `supabase.auth.signInWithOAuth({ provider: "custom:wechat-web" })`. Supabase Auth redirects to `/connect/qrconnect`, receives the callback `code`, calls `POST /wechat-web-proxy/token` and `GET /wechat-web-proxy/userinfo`, and persists the resulting identity in `auth.identities`. |

## Part 1: Database schema and shared modules

### Step 1: Create the identity and session-key migrations

Create three migrations under `supabase/migrations/`. The first table, `wechat_identities`, maps each app-scoped `openid` (and optional cross-app `unionid`) to `auth.users(id)`:

```sql
-- supabase/migrations/20240601000000_wechat_identities.sql
CREATE TABLE IF NOT EXISTS wechat_identities (
  openid           TEXT        NOT NULL,
  unionid          TEXT,
  app_type         TEXT        NOT NULL
                   CHECK (app_type IN ('miniprogram', 'web', 'mobile')),
  supabase_user_id UUID        NOT NULL
                   REFERENCES auth.users (id) ON DELETE CASCADE,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),

  PRIMARY KEY (openid)
);

CREATE INDEX IF NOT EXISTS wechat_identities_unionid_idx
  ON wechat_identities (unionid)
  WHERE unionid IS NOT NULL;

CREATE INDEX IF NOT EXISTS wechat_identities_user_id_idx
  ON wechat_identities (supabase_user_id);

ALTER TABLE wechat_identities ENABLE ROW LEVEL SECURITY;
```

The second migration creates `wechat_session_keys` to hold the Mini Program `session_key` server-side and defines a cleanup function with an empty `search_path`:

```sql
-- supabase/migrations/20240601000001_wechat_session_keys.sql
CREATE TABLE IF NOT EXISTS wechat_session_keys (
  openid      TEXT        NOT NULL PRIMARY KEY,
  session_key TEXT        NOT NULL,
  expires_at  TIMESTAMPTZ NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

ALTER TABLE wechat_session_keys ENABLE ROW LEVEL SECURITY;

CREATE OR REPLACE FUNCTION cleanup_expired_wechat_session_keys()
  RETURNS void
  LANGUAGE sql
  SET search_path = ''
AS $$
  DELETE FROM public.wechat_session_keys WHERE expires_at < now();
$$;
```

The third migration schedules hourly pruning via `pg_cron` so expired keys do not accumulate:

```sql
-- supabase/migrations/20240601000002_schedule_session_key_cleanup.sql
CREATE EXTENSION IF NOT EXISTS pg_cron;

DO $$
BEGIN
  IF EXISTS (SELECT 1 FROM cron.job WHERE jobname = 'cleanup-wechat-session-keys') THEN
    PERFORM cron.unschedule('cleanup-wechat-session-keys');
  END IF;
END $$;

SELECT cron.schedule(
  'cleanup-wechat-session-keys',
  '0 * * * *',
  $$ SELECT cleanup_expired_wechat_session_keys(); $$
);
```

### Step 2: Disable platform JWT verification in config.toml

All four Edge Functions receive requests that do not carry a standard Supabase client JWT at the gateway layer:

| Function | What arrives instead |
|---|---|
| `wechat-miniprogram` | A WeChat `code` |
| `wechat-web-proxy` | Server-to-server calls from Supabase Auth |
| `wechat-decrypt` | A Bearer JWT validated inside the handler via `adminClient.auth.getUser(jwt)` |
| `wechat-mock` | A sandbox endpoint |

Declare `verify_jwt = false` in `supabase/config.toml` so a single-function deploy never re-enables the gateway check:

```toml
# supabase/config.toml
project_id = "your-project-ref"

[functions.wechat-miniprogram]
verify_jwt = false

[functions.wechat-web-proxy]
verify_jwt = false

[functions.wechat-decrypt]
verify_jwt = false

[functions.wechat-mock]
verify_jwt = false
```

Create `supabase/functions/_shared/wechat.ts` with the WeChat client and opaque token helpers (the three API wrappers are in the code below). `WeChatClient` defaults to `https://api.weixin.qq.com` and switches to `wechat-mock` when `baseUrl` (`WECHAT_API_BASE_URL`) is passed:

```ts
// supabase/functions/_shared/wechat.ts
import {
  Code2SessionSchema,
  OpaqueTokenSchema,
  UserInfoSchema,
  WebTokenSchema,
} from "./types.ts";
import type {
  Code2SessionResponse,
  OpaqueTokenPayload,
  UserInfoResponse,
  WeChatConfig,
  WebTokenResponse,
} from "./types.ts";

export const WECHAT_ERROR_HINTS: Record<number, string> = {
  [-1]: "WeChat system busy - retry shortly",
  40013: "invalid appid",
  40029: "invalid code - expired or already used (codes are single-use, ~5 min TTL)",
  40125: "invalid appsecret - check WECHAT_*_SECRET",
  40163: "code already used - request a fresh wx.login() / authorize code",
  41008: "missing code parameter",
  42001: "code expired - request a fresh one",
  45011: "API rate limit hit (100/min per user) - back off and retry",
  40226: "high-risk user blocked by WeChat risk control",
  48001: "API unauthorized for this account - check Open Platform binding/scopes",
};

export class WeChatError extends Error {
  constructor(public readonly code: number, message: string) {
    const hint = WECHAT_ERROR_HINTS[code];
    super(`WeChat error ${code}: ${message}${hint ? ` - ${hint}` : ""}`);
    this.name = "WeChatError";
  }
}

const DEFAULT_BASE_URL = "https://api.weixin.qq.com";

export class WeChatClient {
  private readonly _fetch: typeof fetch;
  private readonly baseUrl: string;

  constructor(
    private readonly config: WeChatConfig,
    fetchFn: typeof fetch = globalThis.fetch,
  ) {
    this._fetch = fetchFn;
    this.baseUrl = config.baseUrl ?? DEFAULT_BASE_URL;
  }

  async code2Session(jsCode: string): Promise<Code2SessionResponse> {
    const url = new URL(`${this.baseUrl}/sns/jscode2session`);
    url.searchParams.set("appid", this.config.appid);
    url.searchParams.set("secret", this.config.secret);
    url.searchParams.set("js_code", jsCode);
    url.searchParams.set("grant_type", "authorization_code");

    const res = await this._fetch(url.toString());
    if (!res.ok) throw new WeChatError(res.status, `HTTP ${res.status}`);
    const data = Code2SessionSchema.parse(await res.json());
    if (data.errcode) throw new WeChatError(data.errcode, data.errmsg ?? "unknown error");
    return data;
  }

  async exchangeWebToken(code: string): Promise<WebTokenResponse> {
    const url = new URL(`${this.baseUrl}/sns/oauth2/access_token`);
    url.searchParams.set("appid", this.config.appid);
    url.searchParams.set("secret", this.config.secret);
    url.searchParams.set("code", code);
    url.searchParams.set("grant_type", "authorization_code");

    const res = await this._fetch(url.toString());
    if (!res.ok) throw new WeChatError(res.status, `HTTP ${res.status}`);
    const data = WebTokenSchema.parse(await res.json());
    if (data.errcode) throw new WeChatError(data.errcode, data.errmsg ?? "unknown error");
    return data;
  }

  async getUserInfo(accessToken: string, openid: string): Promise<UserInfoResponse> {
    const url = new URL(`${this.baseUrl}/sns/userinfo`);
    url.searchParams.set("access_token", accessToken);
    url.searchParams.set("openid", openid);
    url.searchParams.set("lang", "zh_CN");

    const res = await this._fetch(url.toString());
    if (!res.ok) throw new WeChatError(res.status, `HTTP ${res.status}`);
    const data = UserInfoSchema.parse(await res.json());
    if (data.errcode) throw new WeChatError(data.errcode, data.errmsg ?? "unknown error");
    return data;
  }
}

export function encodeOpaqueToken(payload: OpaqueTokenPayload): string {
  return btoa(JSON.stringify(payload));
}

export function decodeOpaqueToken(token: string): OpaqueTokenPayload | null {
  try {
    const parsed = OpaqueTokenSchema.safeParse(JSON.parse(atob(token)));
    return parsed.success ? parsed.data : null;
  } catch {
    return null;
  }
}
```

## Part 2: Configure the Web QR OAuth2 proxy and custom provider

### Step 1: Implement wechat-web-proxy

| Request | Supabase Auth custom provider (RFC 6749) | WeChat |
|---|---|---|
| Token exchange | `POST` with form-encoded `grant_type=authorization_code`, `code`, `client_id`, and `client_secret`, or HTTP Basic authentication headers per RFC 6749 Section 2.3.1[^rfc-6749] | `GET /sns/oauth2/access_token?appid=...&secret=...&code=...&grant_type=authorization_code` |
| Profile lookup | `GET /userinfo` with `Authorization: Bearer <access_token>` | `GET /sns/userinfo` requiring both `access_token` and `openid` |

`supabase/functions/wechat-web-proxy/index.ts` bridges the two protocols:

| Endpoint | Behaviour |
|---|---|
| `POST /wechat-web-proxy/token` | Parses form-encoded or HTTP Basic credentials, verifies `client_id === WECHAT_WEB_APPID` when `WECHAT_WEB_APPID` is set (so the `--no-verify-jwt` endpoint cannot be used as an open relay), calls `wechat.exchangeWebToken(code)`, and returns `{ access_token: encodeOpaqueToken({ wat, oid, uid }), token_type: "Bearer", expires_in }`. |
| `GET /wechat-web-proxy/userinfo` | Decodes the Bearer opaque token back into `{ wat, oid, uid }`, calls `wechat.getUserInfo(wat, oid)`, and returns `{ sub: userInfo.unionid ?? userInfo.openid, openid, unionid, name: userInfo.nickname, picture: userInfo.headimgurl \|\| null }`. |

```ts
// supabase/functions/wechat-web-proxy/index.ts
import { Hono } from "hono";
import { WebTokenRequestSchema } from "../_shared/types.ts";
import {
  decodeOpaqueToken,
  encodeOpaqueToken,
  WeChatClient,
  WeChatError,
} from "../_shared/wechat.ts";

export const app = new Hono().basePath("/wechat-web-proxy");

function parseBasicAuth(header?: string): { id: string; secret: string } | null {
  if (!header?.startsWith("Basic ")) return null;
  try {
    const decoded = atob(header.slice(6).trim());
    const idx = decoded.indexOf(":");
    if (idx === -1) return null;
    return { id: decoded.slice(0, idx), secret: decoded.slice(idx + 1) };
  } catch {
    return null;
  }
}

app.post("/token", async (c) => {
  const raw = await c.req.parseBody();
  const basic = parseBasicAuth(c.req.header("Authorization"));
  const merged = basic
    ? { client_id: basic.id, client_secret: basic.secret, ...raw }
    : raw;

  const parsed = WebTokenRequestSchema.safeParse(merged);
  if (!parsed.success) {
    return c.json(
      {
        error: "invalid_request",
        error_description: parsed.error.issues[0]?.message ?? "Missing required parameters",
      },
      400,
    );
  }

  const { code, client_id, client_secret } = parsed.data;
  const expectedAppId = Deno.env.get("WECHAT_WEB_APPID");
  if (expectedAppId && client_id !== expectedAppId) {
    return c.json(
      { error: "invalid_client", error_description: "Unrecognised client_id" },
      401,
    );
  }

  const wechat = new WeChatClient({
    appid: client_id,
    secret: client_secret,
    baseUrl: Deno.env.get("WECHAT_API_BASE_URL"),
  });

  let tokenData;
  try {
    tokenData = await wechat.exchangeWebToken(code);
  } catch (err) {
    const msg = err instanceof WeChatError ? err.message : "WeChat API error";
    return c.json({ error: "wechat_error", error_description: msg }, 400);
  }

  const opaqueToken = encodeOpaqueToken({
    wat: tokenData.access_token,
    oid: tokenData.openid,
    ...(tokenData.unionid ? { uid: tokenData.unionid } : {}),
  });

  return c.json({
    access_token: opaqueToken,
    token_type: "Bearer",
    expires_in: tokenData.expires_in,
  });
});

app.get("/userinfo", async (c) => {
  const authHeader = c.req.header("Authorization");
  if (!authHeader?.startsWith("Bearer ")) {
    return c.json(
      { error: "unauthorized", error_description: "Missing or invalid Authorization header" },
      401,
    );
  }

  const tokenData = decodeOpaqueToken(authHeader.slice(7));
  if (!tokenData) {
    return c.json(
      { error: "invalid_token", error_description: "Malformed or invalid opaque token" },
      401,
    );
  }

  const wechat = new WeChatClient({
    appid: "",
    secret: "",
    baseUrl: Deno.env.get("WECHAT_API_BASE_URL"),
  });

  let userInfo;
  try {
    userInfo = await wechat.getUserInfo(tokenData.wat, tokenData.oid);
  } catch (err) {
    const msg = err instanceof WeChatError ? err.message : "WeChat API error";
    return c.json({ error: "wechat_error", error_description: msg }, 400);
  }

  return c.json({
    sub: userInfo.unionid ?? userInfo.openid,
    openid: userInfo.openid,
    ...(userInfo.unionid ? { unionid: userInfo.unionid } : {}),
    name: userInfo.nickname,
    picture: userInfo.headimgurl || null,
  });
});

if (import.meta.main) {
  Deno.serve(app.fetch);
}
```

### Step 2: Register the custom:wechat-web provider

Deploy `wechat-web-proxy` before registering the provider. Supabase Auth checks that the hostnames in `authorization_url`, `token_url`, and `userinfo_url` resolve via DNS during registration and returns HTTP `400` (`validation_failed: "Unable to resolve hostname"`) if a host does not resolve.

Register `custom:wechat-web` via `POST /auth/v1/admin/custom-providers`[^sb-custom-oauth]:

```bash
curl -X POST "https://<project-ref>.supabase.co/auth/v1/admin/custom-providers" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" \
  -H "apikey: $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "provider_type": "oauth2",
    "identifier": "custom:wechat-web",
    "name": "WeChat",
    "client_id": "wx_placeholder_web_appid",
    "client_secret": "placeholder_web_secret",
    "authorization_url": "https://open.weixin.qq.com/connect/qrconnect",
    "token_url": "https://<project-ref>.supabase.co/functions/v1/wechat-web-proxy/token",
    "userinfo_url": "https://<project-ref>.supabase.co/functions/v1/wechat-web-proxy/userinfo",
    "scopes": ["snsapi_login"],
    "pkce_enabled": false,
    "email_optional": true,
    "authorization_params": {
      "appid": "wx_placeholder_web_appid"
    }
  }'
```

WeChat needs three registration fields set as follows:

- `pkce_enabled: false` stops Supabase Auth from sending `code_challenge` to WeChat's authorize endpoint (client-to-Supabase PKCE still works independently).
- `email_optional: true` allows sign-in when `/userinfo` returns no `email` claim.
- `authorization_params: { "appid": "wx_placeholder_web_appid" }` injects `appid` onto the authorize redirect alongside the standard `client_id` parameter that Supabase Auth always appends.

To delete and recreate the provider, pass the identifier (`custom:wechat-web`), not the UUID, to `DELETE /auth/v1/admin/custom-providers/custom:wechat-web`.

## Part 3: Wire the Mini Program flow and encrypted-data decryption

### Step 1: Resolve or create users deterministically

In `supabase/functions/_shared/identity.ts`, `findOrCreateUser` resolves a Mini Program login in three stages:

| Stage | Behaviour |
|---|---|
| Lookup by `unionid` | If `jscode2session` returned a `unionid`, query `wechat_identities` by `unionid`. When found, upsert the current `(openid, unionid, app_type, supabase_user_id)` row so a second Mini Program or mobile app under the same Open Platform account attaches to the same `supabase_user_id`. |
| Lookup by `openid` | Query `wechat_identities` by `openid`. If the user existed without a `unionid` and now has one, backfill `unionid`. |
| Deterministic creation | Compute `UUIDv5(WECHAT_USER_NAMESPACE, openid)` (`WECHAT_USER_NAMESPACE = "9f7c3e2a-5b1d-4c8e-a6f0-1d2e3f4a5b6c"`) and call `adminClient.auth.admin.createUser({ id: computedId, email: "${openid}@wechat.local", email_confirm: true, ... })`. |

Two concurrent first-time requests for the same `openid` compute the same `computedId`. If the second request receives HTTP `409` or a `422` whose code or message matches `/already.*(registered|exists)|email_exists|user_already_exists|duplicate/`, `isDuplicateUserError` treats it as a concurrent winner and continues with `computedId`. Other `422` validation errors throw immediately so `wechat_identities` never writes a foreign key to a nonexistent user.

For returning users, `resolveUserEmail` reads the canonical email from `auth.users` via `getUserById(userId)` instead of reconstructing `${openid}@wechat.local`. A user reached via `unionid` across two apps has a different `openid` on the second app than the creator `openid` stored in `auth.users.email`; guessing a reconstructed email and passing it to `generateLink` would mint a second user. If `getUserById` fails or returns no email, `resolveUserEmail` fails closed and throws.

### Step 2: Issue sessions in wechat-miniprogram

The function exchanges `code` via `wechat.code2Session(code)`, calls `findOrCreateUser` before touching `wechat_session_keys` (so a failed user lookup leaves no orphan `session_key` row), upserts `wechat_session_keys` with a 2-hour TTL, and mints a Supabase session using `generateLink` + `verifyOtp` wrapped in `withRetry`:

```ts
// Session issuance excerpt from supabase/functions/wechat-miniprogram/index.ts
const { data: linkData, error: linkError } = await withRetry(() =>
  adminClient.auth.admin.generateLink({
    type: "magiclink",
    email: identity.placeholderEmail,
  })
);

const { data: verifyData, error: verifyError } = await withRetry(() =>
  anonClient.auth.verifyOtp({
    token_hash: linkData.properties.hashed_token,
    type: "magiclink",
  })
);
```

`withRetry` (`supabase/functions/_shared/retry.ts`) retries up to 3 times with exponential backoff (200 ms, 400 ms, 800 ms) **only** when `result.error?.status === 429`. Because GoTrue's rate limiter rejects HTTP `429` before processing the request, the single-use `hashed_token` is not consumed on a `429` and is safe to retry.

From the Mini Program client, call `wx.login()` and post `res.code` to the function:

```js
wx.login({
  success(res) {
    if (!res.code) return;
    wx.request({
      url: "https://<project-ref>.supabase.co/functions/v1/wechat-miniprogram",
      method: "POST",
      header: { "content-type": "application/json" },
      data: { code: res.code },
      success({ data }) {
        wx.setStorageSync("sb_access_token", data.access_token);
        wx.setStorageSync("sb_refresh_token", data.refresh_token);
      },
    });
  },
});
```

### Step 3: Decrypt Mini Program payloads in wechat-decrypt

| Concern | Behaviour |
|---|---|
| Payload | WeChat Mini Program APIs such as `<button open-type="getPhoneNumber">` return `{ encryptedData, iv }` encrypted with AES-128-CBC using the user's 16-byte `session_key`. |
| Padding | Deno's Web Crypto `AES-CBC` implementation rejects WeChat's padding in practice, so `supabase/functions/_shared/crypto.ts` uses `node:crypto` (`createDecipheriv("aes-128-cbc", key, iv)`) with `decipher.setAutoPadding(false)` and strips PKCS#7 padding manually (`stripPkcs7` verifies that the last byte `pad` is in `1..16` and that all trailing `pad` bytes equal `pad`). |
| Watermark | When `WECHAT_MINIPROGRAM_APPID` is set, `decryptWeChatData` also verifies `parsed.watermark.appid === expectedAppId` to block cross-app ciphertext replay. |
| Endpoint | `supabase/functions/wechat-decrypt/index.ts` authenticates the caller via `Authorization: Bearer <access_token>`, resolves `user.user_metadata.openid` via `adminClient.auth.getUser(jwt)`, fetches `{ session_key, expires_at }` from `wechat_session_keys`, returns HTTP `409` (`no_session_key` or `session_key_expired`) when the key is missing or past `expires_at`, and otherwise returns `{ data: decrypted }`. |

## Gotchas and lessons learned

- `session_key` is plaintext at rest in `wechat_session_keys`. RLS blocks client queries, but the service role, database administrators, and database backups can read the `TEXT` column, and each key decrypts that user's WeChat payloads (`wx.getPhoneNumber`). The 2-hour `expires_at` TTL and hourly `pg_cron` job (`cleanup-wechat-session-keys`) bound the window; for encryption at rest, store the secret through Supabase Vault (`pgsodium`).
| Gotcha | Detail |
|---|---|
| Mini Program and Web QR flows create separate `auth.users` rows | `wechat-miniprogram` creates users via `admin.createUser` and tracks them in `public.wechat_identities`, whereas `custom:wechat-web` creates users inside Supabase Auth's OAuth callback and records `unionid` as `auth.identities.identity_data->>'sub'`. Because the `auth` schema is not exposed via PostgREST, cross-flow linking requires a `SECURITY DEFINER` RPC with `SET search_path = ''` that queries `auth.identities` where `provider = 'custom:wechat-web'` and `identity_data->>'sub' = p_unionid`, granted only to `service_role`. |
| `WECHAT_WEB_APPID` gates the open-relay check on `wechat-web-proxy/token` | Because `wechat-web-proxy` runs with `verify_jwt = false`, anyone who knows the function URL can POST to `/token`. The handler checks `client_id === WECHAT_WEB_APPID` only when `WECHAT_WEB_APPID` is set in the environment; always set `WECHAT_WEB_APPID` in production. |
| WeChat omits `errcode` on success | On a valid response from `jscode2session`, `oauth2/access_token`, or `sns/userinfo`, `errcode` is absent (or `0`), and on failure WeChat still returns HTTP `200` with a non-zero `errcode` JSON body (such as `40029` for an expired or reused code). Check `data.errcode` after parsing HTTP `200`. |
- Supabase `.single()` returns HTTP `406` (`PGRST116`) when zero rows match. When writing `globalThis.fetch` mocks for `wechat_identities` lookups, return HTTP `406` with `{ code: "PGRST116" }` on a cache miss rather than HTTP `200` with `[]`.
