import { Aside, Steps } from '@astrojs/starlight/components';

Bringing up SWD and a MOSFET crowbar on a live peripheral has several independent failure layers: broken pogo contact, a debug adapter that answers without providing memory access, back-power through probe ESD diodes, an invalid halted-CPU context, and pulses too fast for the selected measurement device. Each needs its own control before a flash-lock result means anything.

This guide is the current physical procedure for a locked `M483SIDAE`. It covers wiring, rail ownership, safe OpenOCD transport, direct glitch-controller reads and run control, RAM evidence, and the measured crowbar pulse ladder. The interpretation and full evidence timeline are in [Nuvoton M483 flash locks and the glitch-oracle trap](/reference/m483-flash-locks-and-glitch-oracles/).

<Aside type="caution" title="Current boundary">
Direct `DPIDR`, `SYS_PDID`, and SRAM reads are live-qualified. APROM/LDROM/SPROM remain `0xFF` through the direct ICE path. Application-plus-config backup and restoration work; `LDROM`, `CONFIG`, and `OTP` are outside that recovery scope. The 2026-11-18 review-fixed rerun qualified 8/16-bit and bit-band `CLK` controls while SRAM stayed blocked; an in-SRAM LDR gadget executed with advancing PC, and a CPU STR gadget landed on `CLK` but not SRAM. CPU-issued FMC returned `fmc-fail` before CID. The bounded app-mode HID command sweep found no hidden raw-image command; one config-writing power command was restored. No physical per-instruction RAM-diff series, SPA/CPA capture, real synchronized crowbar-read pulse, plaintext recovery, or key recovery has run.
</Aside>

|---|---|

The official ICP tool description and M483 system block identify the relevant pins.[^icp][^m480ds] A Sensepeek SWD pin-map was drawn from the datasheet for the actual probe seating.

## Safety and rail ownership

<Aside type="danger" title="Exactly one rail owner and one SWD master">
The target's own USB supply or the glitcher target-VCC output can power `VDD`, never both together with a probe that also sources target power. Keep the Nu-Link target-power output off. Disconnect the crowbar from a rail during passive power measurements. Only one SWD master may be attached at a time.
</Aside>

A probe supplying 3.3 V while the glitcher crowbar shares that rail can back-feed the controller through RP2040 GPIO ESD diodes. The observed result was a Windows code-10 composite-device failure: descriptors visible, no function. The safe sequence is:

<Steps>

1. **Disconnect both target USB cables and all probe power.** Check `SWDIO-SWCLK` and `SWCLK-GND` for shorts. Near-zero resistance is a hard short, not a valid SWD state.
2. **Verify continuity and the debug map.** Use the current board's annotated map and continuity evidence. Do not infer a pad from a visually similar board.
3. **Connect the glitcher USB first if it is present.** Confirm clean enumeration before wiring its harness to the target.
4. **Power the target from its own USB for the USB-powered SWD procedure.** Then attach the sense-only probe. The later glitcher-owned-VDD campaign topology is a separate, not-yet-live-qualified configuration.
5. **Run read-only identification first.** Flash writes, update commands, glitch outputs, and configuration changes are separate decisions with separate gates.
6. **Tear down in reverse.** Remove target power before disconnecting the harness. Restore any peripheral mode the measurement changed.

</Steps>

## Phase 1: qualify safe SWD observation

### Use the patched non-resetting Nu-Link path

Stock `interface/nulink.cfg` initialization can reset the target and enable target power. The patched `nulink-safe` path uses connect-only reset type 5, which performs the `CONNECT_NORMAL` AP power-up while suppressing hardware reset and keeping `supply=0`.

```tcl
set workarea 0x20000000
set _CHIPNAME m483
transport select swd
adapter driver hla
hla layout nulink_safe
hla reset_type 5 nulink
adapter speed 200
reset_config none
```

Do not replace this with the stock Nu-Link layout. A successful OpenOCD exit alone is also not an identification result: require the expected `DPIDR` and then qualify memory access separately.

### Separate DP contact from AHB-AP memory access

`DPIDR = 0x2ba01477` establishes physical debug-port contact. On this HLA transport, normal `mdw` can take a different access path. Use adapter commands and `raw_mdw` for the memory qualification:

```tcl
adapter assert srst 0
adapter deassert srst 0
cortex_m reset_config none
cortex_m_poll off
raw_mdw 0xE000ED00
raw_mdw 0x40000000
raw_mdw 0x20000000
raw_mdw 0x20000400
raw_mdw 0x00000000
raw_mdw 0x00100000
```

Expected qualified observations on the tested locked board:

| Observation | Interpretation |
|---|---|
| `SYS_PDID = 0x00d48310` | Real M483SIDAE part ID through the AHB-AP |
| Distinct, address-dependent SRAM words | Address-sensitive memory observation |
| `APROM`, `LDROM`, `SPROM = 0xFFFFFFFF` | Direct ICE flash reads blocked in the measured state |
| Every address repeats `0x2ba01477` | Dead transport echo; stop and repair the probe path |
| Every address is `0xFFFFFFFF` without the `SYS_PDID`/SRAM controls | Unqualified read; do not call it a lock signature |

The safe-connect bug came from skipping the reset command without replacing its bundled `CONNECT_NORMAL` operation in the Nu-Link driver sequence.[^openocdnuvoton] The vendor CPU-versus-ICE access split is documented in the M480 TRM.[^m480trm] The DP answered while the AHB-AP stayed unpowered, so memory reads echoed the adapter's stale `DPIDR`. The lock model and chronological evidence are in the companion reference.

`CONFIG0` and `CONFIG2` do not have a same-run positive control proving that their stored values reach this read path. Their `0xFFFFFFFF` responses are blocked-read masks, not configuration dumps.

## Phase 2: direct glitch-controller reads and run control

The direct `SWD helper` path is the alternative to starting a fresh OpenOCD process for each observation.[^faultierfw] Direct `DPIDR`, `SYS_PDID`, SRAM, and register reads are live-qualified. The synchronized `GLITCH_READ` path is qualified with `OUT_NONE`; it has not fired a real crowbar pulse.

Run control needs explicit state labels:

| State | Recorded result | Allowed conclusion |
|---|---|---|
| Reset/vector catch | Can avoid the initial connect LOCKUP; `PC` can still be `0xFFFFFFFE` | Debug observation only; not valid execution |
| Resume from reset catch | Faults instead of running the updater | Resume not demonstrated |
| Running-halted update mode | SRAM/peripheral reads work; tested resume entered LOCKUP | Halted snapshot, not running CPU readout |
| DP power-down plus target reset | Normal USB enumeration returns | Target recovered after the session, not successful resume |
| Single-step | Tested attempts faulted | No valid per-instruction execution series |
| `GLITCH_READ` with `OUT_NONE` | Matching reads and clean disarm | Control path qualified without a real pulse |

Do not describe vector catch as a working resume path. Do not generalize the recorded faults into a global rule that every halted-CPU flash read is lock-gated. The exact fault mechanism remains unresolved.

For the direct Tcl RPC transport used by the capture tooling:

- Call `init` before `targets`.
- Wait for `Target ... examined` after `init`/`reset halt`.
- Set `cortex_m_poll off` after examination and before re-halt operations.
- Keep a persistent session when timing matters.
- Send DP power-down before the final close reset when restoring normal USB.

## Phase 3: RAM dumps and the per-instruction experiment

The completed RAM work includes full general-SRAM dumps, corrected bank-2 dumps, running-halted update-mode snapshots, post-read snapshots, and HID-overread mapping. Bank 2 requires the existing SPIM clock/cache-mode switch and verified restore. These snapshots found no plaintext application code or identified key/decrypt buffer. They remain useful for memory mapping and for detecting future changes; they do not exclude transient plaintext between capture instants.

The exact sequence below has not run on hardware:

```text
halt -> dump RAM -> single-step -> dump the same RAM -> diff -> repeat
```

Slow dumps are acceptable. With the CPU halted after each step, RAM written by that instruction remains available for the following AHB-AP read. The prerequisite is a real PC and a qualified single-step, not faster capture.

The step-ram-diff command implements the bounded experiment. It requires:

- the current instruction PC and expected next PC;
- an aligned SRAM word that the control instruction changes from a declared value to another;
- a fresh hash-verified recovery manifest and explicit `--yes`;
- a new or empty evidence directory.

The control runs first. A series starts only if both the PC and RAM-word transitions match. Frames, diffs, hashes, and a journal are preserved on later faults. Bank-2 capture is optional. The implementation and 14 fake-target tests are offline evidence; a control-only live probe rejected the initial state (`PC=0xFFFFFFFE`, zero frames). No physical collection series has run. Use the local step-ram-diff runbook for the live command procedure.

The command's help can be inspected without opening hardware:

```bash
python3 <path-to-step-ram-diff> --help
```

A known store-to-RAM instruction is the positive control. Without it, a re-halted core and unchanged RAM do not prove that one instruction executed.

## Phase 4: backup and recovery scope

The update-mode HID reader captured `65` application pages (66,560 bytes) plus a separate config image on the tested boards. Bind the backup to a physical `board_id`, verify artifact hashes, and record omitted regions in the manifest.

The measured restoration sequence is:

<Steps>

1. Rewrite all `65` application pages from the same board's fresh backup.
2. Verify every page against that backup.
3. Use the official vendor updater to return the device to application mode.

</Steps>

That is app-plus-config recovery scope. It does not restore `LDROM`, `CONFIG`, or `OTP`. Hash equality proves file integrity, not board identity or full-chip coverage. Do not authorize firmware-write fuzzing, LDROM mutation, or configuration writes on the strength of the application backup alone.

## Phase 5: measured crowbar behaviour

The following ladder is physical harness evidence from the `fx2lafw` captures and glitcher ADC. Its readback column predates the qualified transport and is retained only as campaign history.

| Target | Pulse width | `VDD`/`LDO_CAP` behaviour | `nRESET` behaviour | Campaign readback |
|---|---:|---|---|---|
| `LDO_CAP` | `4-128 ns`, cap installed | ADC could not resolve pulse shape | N/A | `locked-response` echo |
| `VDD` | `1-35 us` | Rail droop measured | `nRESET` stayed high | `locked-response` echo |
| `VDD` | `40-100 us` | Rail droop measured | `nRESET` asserted `35-37 us` after `VDD` falling edge | `locked-response` echo |
| `VDD` | `250 us-1 ms` | Rail droop measured | `nRESET` followed | `locked-response` echo |

The glitcher ADC sample rate was 2.604 MS/s, about 384 ns/sample. It can resolve the microsecond `VDD` envelope but cannot qualify a `4-128 ns` pulse shape. Nanosecond pulse verification requires an oscilloscope with suitable bandwidth and triggering.

A real fault campaign additionally needs:

- an unlocked reference board proving that the same readback path can return real flash;
- a target-event trigger tied to POR/reset/configuration reload rather than host-command timing;
- an address-sensitive persistent readback session;
- a fresh board-bound recovery manifest and readiness manifest;
- a measured pulse that does not unintentionally assert `nRESET` outside the intended window.

`trigger=none` varies delay relative to a host command, not relative to a hardware reset event. Spawning OpenOCD seconds after a pulse cannot detect a transient configuration window. These two facts invalidated the old large timing grids independently of the transport bug.

## Pre-experiment checklist

Before using any negative result, confirm:

- [ ] Both USB cables were disconnected for continuity checks; shorts were excluded.
- [ ] Exactly one rail owner and one SWD master are present.
- [ ] `DPIDR`, `SYS_PDID`, and address-sensitive SRAM controls passed in the same run.
- [ ] Flash, SRAM, configuration, and peripheral controls are not being substituted for one another.
- [ ] USB application/update PID is recorded for every HID probe.
- [ ] Halt state includes PC, SP, LR, `DHCSR`, `CFSR`, `HFSR`, and `DFSR` where run control matters.
- [ ] A known store-to-RAM control passed before any per-instruction RAM series.
- [ ] Backup scope, `board_id`, hashes, and restoration coverage are explicit.
- [ ] Analog/logic measurement resolution matches the pulse width being claimed.
- [ ] Any fault output has a hardware trigger, persistent readback, disarm evidence, and a positive control.

## Gotchas

- **DP contact proves the debug port answers; the AHB-AP must be qualified separately.** The repeated `0x2ba01477` response was an adapter-buffer echo.
- **A halted target can still hold an invalid CPU context.** `PC = 0xFFFFFFFE` is LOCKUP, not an instruction address.
- **SRAM observation and flash observation are separate gates.** A readable SRAM positive control leaves the flash lock untested.
- **Application and update modes enumerate as different USB devices.** Older notes reversed them and invalidated mode-specific probes.
- **Bank 2 needs its SPIM mode controlled and restored.** A raw banked read without that setup is not a qualified second-bank dump.
- **Reset recovery restores USB after a failed run-control experiment; it does not prove the core resumed.** DP power-down plus reset is the recovery path.
- **The LDO_CAP capacitor state must be checked physically.** Existing notes conflict; keep the stability capacitor installed by default and do not infer its state from an old photograph.
- **Logic-analyzer activity shows transitions; protocol success needs decoded responses.** Transition counts alone cannot distinguish probe output from target responses.
- **Treat status 1 as accepted only when the response report ID matches the request.** The app-mode sweep originally marked a command accepted when the response report ID belonged to a different request; the tool now requires the report ID to match.
