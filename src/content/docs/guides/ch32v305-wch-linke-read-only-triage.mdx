This is a separate CH32V305 RISC-V (reduced instruction set computer) target. The WCH-LinkE probe (`1a86:8010`, RV mode, firmware `v3.6(v42)`) can see the chip's 2-wire SDI (serial debug interface) at the electrical level - logic-analyzer activity confirms both SWCLK (serial wire clock) and SWDIO (serial wire debug input/output) transition during attach - but `wlink v0.1.3`'s `AttachChip` command fails with protocol error `0x55` (`[0x81, 0x55, 0x01, 0x01]`). This error occurs before `ChipID` and `RDPR` status are available; it does not confirm that the chip's option bytes lock the debug interface.

## WCH-LinkE JP1 pinout (corrected)

The official WCH-LinkE-R0-1v3 schematic (page 1)[^wchlinke] confirms:

| JP1 pin | Signal |
|---|---|
| 1 | RX (receive) |
| 2 | SWCLK/TCK (test clock) |
| 3 | TX (transmit) |
| 4 | SWDIO/TMS (test mode select) |
| 5 | TDO (test data out) |
| 6 | GND |
| 7 | TDI (test data in) |
| 8 | 3V3 |
| 9 | RST (reset) |
| 10 | 5V |

A raw worker note that proposed a different order was wrong. Use the pinout above. For 2-wire SDI: JP1 pin 2 (SWCLK) to target PA14 (pin 22), JP1 pin 4 (SWDIO) to target PA13 (pin 19), JP1 pin 6 (GND) to target VSS (ground supply voltage) (pin 20).

## SDI vs SWD naming

WCH (WinChipHead) reuses the ARM (Advanced RISC Machines) pin names `SWDIO`/`SWCLK`, but the protocol is WCH-proprietary SDI (Serial Debug Interface). A standard ARM SWD debugger (CMSIS-DAP, J-Link in SWD mode) cannot talk to a CH32V305. The WCH-LinkE must be in RV mode (not ARM-DAP mode), and `wlink` implements the SDI protocol. The WCH-LinkRV bulk USB (Universal Serial Bus) protocol uses OUT endpoint `0x01` and IN endpoint `0x81`; normal responses begin with `0x82`, error responses with `0x81`.

## What the 0x55 error means at the wire level

In `wlink v0.1.3`, a session starts by opening the USB bulk interface and sending:

1. `GetProbeInfo` (`[0x81, 0x0d, 0x01, 0x01]`) - succeeds, probes the WCH-LinkE itself.
2. Up to 4 attempts (initial + 3 retries, 100 ms apart) of:
   - `SetSpeed` (`[0x81, 0x0c, 0x02, <riscvchip>, <speed>]`) - succeeds.
   - `AttachChip` (`[0x81, 0x0d, 0x01, 0x02]`) - **fails with `0x55`**.

`AttachChip` instructs the WCH-LinkE MCU (microcontroller unit) to initiate the 2-wire SDI handshake with the target RISC-V Debug Module and read its `ChipID`. When the probe cannot complete this handshake, it replies:

- `[0x81, 0x55, 0x01, 0x01]`
  - `0x81`: error response marker
  - `0x55`: error reason "failed to connect with riscvchip"[^wlinkproto]
  - `0x01`: payload length 1
  - `0x01`: failure subcode

The attach error happens during **Stage 1** (`AttachChip`). Stage 2 (`CheckReadProtect`, `[0x81, 0x06, 0x01, 0x01]`) runs only AFTER `AttachChip` succeeds and returns chip family + `ChipID`. Because `0x55` occurs in Stage 1, `ChipID` and `RDPR` status are unqueried. The error proves the SDI handshake did not complete. It does not confirm that option-byte locks are active.

### Possible causes of `0x55`

From the WCH official OpenOCD driver[^wlinkec] and `ch32-rs/wlink` issue reports[^wlink94]:

1. **Physical SDI connection or target power issue**: open/swapped `SWDIO` (PA13, pin 19) or `SWCLK` (PA14, pin 22), missing common GND, or unpowered target VDD (positive supply voltage). The live session eliminated these: all four wire runs were continuity-tested, and the target pad measured 3.3 V.
2. **Debug interface disabled or locked in option bytes / bootloader config (`RDPR != 0xA5`)**: on CH32V30x, the option-byte register `RDPR_USER` has reset/unprotected value `0x00FF5AA5` (`RDPR = 0xA5`). A chip whose 2-wire SDI is closed at boot or by ISP (in-system programming) config can refuse `AttachChip`. Debug-enable/configuration transitions may mass-erase code flash; do not attempt them without an independently protected backup.
3. **Application firmware reconfiguring PA13/PA14 or entering a tight loop after boot**: firmware can disable SDI on PA13/PA14 microseconds after reset release. `AttachChip` does not assert the hardware `nRST` pin; if the firmware disables SDI immediately, a USB-paced attach cannot catch the boot window.

## Logic-analyzer workflow and FX2 re-enumeration gotcha

The generic FX2 analyzer is attached through `usbipd` and driven by `sigrok-cli`. The capture workflow has a USB re-enumeration gotcha: when `sigrok` uploads firmware to the FX2, the USB device briefly disappears and re-appears. If the device is attached through `usbipd` when this happens, the attachment is dropped and must be re-attached. The workflow is now automated by a capture script and documented in the capture tooling's notes.

With CH0/D0 on target SWCLK (PA14, pin 22) and CH1/D1 on target SWDIO (PA13, pin 19):

| Capture | CH0 transitions | CH1 transitions | Attach result |
|---|---:|---:|---|
| First | 0 | 12,118 | `0x55` |
| Tool self-test | 49,782 | 11,838 | `0x55` |
| Repeat | 163,482 | 12,248 | `0x55` |

In the repeat capture both channels began transitioning at the same sample. The initial flat SWCLK is therefore not reliable evidence of a missing clock. The reproducible result is probe activity on both SDI lines while target attach still fails.

### Pin activity versus protocol decode

The logic-analyzer capture counts digital transitions. It does not decode the SDI protocol or verify that the target ever responds. The recorded activity is probe-driven (the WCH-LinkE sending the attach sequence). A silent target would still show probe-driven transitions on both lines. A full protocol decode or an `NRST`-controlled attach is required to separate the cases.

<Aside type="caution" title="No erase or unprotect without an independent backup">
Do not run `wchisp config enable-debug`, WCH-LinkE special erase commands, or any `EraseCodeFlash` variant without an independently protected backup covering application image, option bytes, and bootloader region. The live session ran read-only; flash was not read or erased.
</Aside>

## Read-only next steps

1. **Protocol-decode the existing captures.** Run a WCH SDI protocol decoder against the `sigrok` captures to determine whether the target ever sends a response or remains silent throughout the handshake. A silent target points at debug disable or firmware pin reconfiguration; a partial response points at a timing or electrical issue.
2. **`NRST`-controlled attach.** Target pad `P7` has now been continuity-confirmed to CH32 pin 3 `NRST`; JP1 pin 9 is the reset candidate. Verify that the selected driver actually asserts that pin before relying on the method - the recorded `wlink status` operation did not toggle it. A qualified held-reset attach prevents application firmware from reconfiguring PA13/PA14 during the attempt. Persistent `0x55` would still need the known-unprotected control before attribution.
3. **ISP backup over USB/UART.** The CH32V305 has a bootloader ISP that operates over USB or UART (universal asynchronous receiver-transmitter) before the application firmware runs. Check whether a read-only ISP backup path exists via `wchisp` or a similar tool. Do not issue any write, erase, or config-change command without a verified backup.
4. **Qualified `NRST`-controlled attach with a known-unprotected CH32V305.** The positive control: attach to a development board or unlocked sample with known-unprotected option bytes. Without it, a persistent `0x55` cannot be attributed to the target.
