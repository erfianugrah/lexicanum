---
title: GPU HDMI audio vs a USB DAC - measuring output latency through an HDMI audio extractor
description: Is audio from the GPU's HD Audio controller faster than the same DAC over USB? An HDMI audio extractor takes the RTX 5090's HDMI audio to the Topping D70 Pro Sabre's optical input, and the cable-loop method from the USB audio guide times both paths through the same recorder. At the default 10 ms shared-mode period the GPU path is 3.3-4.5 ms faster (43.73-44.43 ms against 47.58-48.40 ms), under the 5 ms bar set before the test; at the minimum period the USB path wins at 35.09-35.77 ms because NVIDIA's driver offers only 10 ms. Also covers the extractor's setup, the desktop cost of the extra display, why "Remove display from desktop" cannot hide it on Windows 10 with NVIDIA, where the community's 35 ms onboard-vs-USB gap could come from, and moving the DAC off a USB hub.
author: "Erfi Anugrah"
category: workstations
---

The [USB audio latency guide](/guides/usb-audio-loopback-latency-windows/) ended on an open question: would a non-USB output beat the D70 over USB? This page answers it for the one non-USB output I had, the GPU's HD Audio over HDMI, by putting an HDMI audio extractor between the GPU and the D70's optical input so the same DAC and the same recorder measure both paths. At the default shared-mode period, which is what most games get, the GPU path is 3.3-4.5 ms faster; at the minimum period, which apps get when they ask for small buffers, the USB path is 8.2-9.3 ms faster. I had set a 5 ms bar before measuring, so the verdict is a tie and the D70 stays on USB.

You'll need the loopback setup and `audio-loopback.ps1` from the USB guide, an HDMI audio extractor with a 2-channel EDID setting, a Toslink cable, and a DAC with an optical input. Everything was measured on one machine on 2026-11-03.

## Constants

### The rig

| Piece | Detail |
|---|---|
| OS | Windows 10 22H2 (build 19045), Enterprise edition during the test |
| GPU | NVIDIA GeForce RTX 5090, driver 617.42; primary display 2560x1440 at 360 Hz over DisplayPort |
| Extractor | J-Tech JTD18G-H5CH (HDMI 2.0b, optical out up to LPCM 2CH or Dolby Digital/DTS 5.1, EDID switch TV / 5ch / 2ch[^jtech]) on a spare HDMI port of the GPU, EDID switch on 2ch, HDMI Out empty, optical out into the D70 |
| DAC | Topping D70 Pro Sabre on Microsoft's USB Audio 2.0 class driver (`usbaudio2`), USB and optical inputs |
| Recorder | SSL 2, Input 2, buffer 128 samples, fed from the D70's left XLR output |
| USB | D70 and SSL 2 behind a VIA VL822 hub (`2109:0822`) on the chipset controller `1022:43F7` (not USB4) |
| Format | 48 kHz, 2 channels, WASAPI shared mode; the extractor's endpoint runs 16-bit, the D70's 32-bit float |

### The two endpoints

Windows names the extractor after its EDID. Read with `IAudioClient3::GetSharedModeEnginePeriod`, as in the USB guide:

| Endpoint | Driver | Default | Fundamental | Minimum |
|---|---|---|---|---|
| `Speakers (D70 Pro SABRE)` | `usbaudio2` | 480 frames (10 ms) | 1 | 336 frames (7 ms) |
| `HDMI SPLITTER (NVIDIA High Definition Audio)` | NVIDIA HD Audio | 480 frames (10 ms) | 480 | 480 frames (10 ms) |

The USB guide's period table showed 10 ms everywhere because it was measured with the D70 on Topping's driver; back on `usbaudio2` the 7 ms minimum is there again. Chromium reads each endpoint's minimum with `GetSharedModeEnginePeriod` and, when a smaller buffer is requested, opens the stream with `IAudioClient3::InitializeSharedAudioStream`[^ms-initshared] at that period[^chromium-coreaudio]; most games take the default. SDL added the same call to its WASAPI backend in May 2024[^sdl-9683], so games built on recent SDL can get the smaller period too.

### What the comparison holds fixed

The D70 is the DAC on both paths and the SSL 2's Input 2 records both, so the analog stage, the cable and the recorder's delay are common to both and cancel out of the difference. What changes is the Windows render path (the USB class driver against NVIDIA's HD Audio driver), the transport (USB against HDMI, the extractor and Toslink) and the D70's input receiver. The extractor's delay is inside the GPU number.

Text version: path A plays the click through the D70's USB endpoint; path B plays it through the GPU's HDMI endpoint, the extractor strips the audio onto Toslink, and the D70 takes it on its optical input. Either way the D70's XLR output goes into SSL 2 Input 2, and the script times the click from release to capture.

## Part 1: get the extractor's endpoint

1. Set the EDID switch to 2ch before connecting. In TV mode the extractor passes on the EDID of whatever is on its HDMI Out, and with nothing there the GPU gets no EDID and Windows sees no display.
2. Power the extractor (5 V barrel; HDMI does not power it), connect the GPU to HDMI In and the optical out to the DAC, leave HDMI Out empty.
3. If no display appears, unplug and replug the HDMI cable at the extractor to force a hotplug. Mine showed up after that as `HDMI SPLITTER` (manufacturer code HDC) at 1920x1080 at 60 Hz.
4. Extend the desktop to it (Win+P, Extend). The audio endpoint `HDMI SPLITTER (NVIDIA High Definition Audio)` exists only while that display is part of the desktop.
5. Play something to the new endpoint, switch the DAC to its optical input and check it locks and plays.

## Part 2: fix the verdict before measuring

I wrote the pass rule down before the extractor arrived, so the numbers could not shape it:

- Only the default period counts, because that is what games get.
- The GPU path wins only if its median is at least 5 ms lower than the USB path's and its p75 sits below the USB path's p25. Anything less is a tie, and a tie means staying on USB, which has no extra display to live with (Part 4).
- Runs alternate A, B, A, B so drift over the session lands on both paths.

5 ms was my judgement of a gap worth an extra display or a motherboard change, not a perceptual threshold.

## Part 3: measure both paths

With the USB guide's script, switching the DAC's input before each block:

```powershell
# D70 input on USB
.\audio-loopback.ps1 -Render 'D70' -Capture 'Input 2 (SSL 2' -Clicks 50
.\audio-loopback.ps1 -Render 'D70' -Capture 'Input 2 (SSL 2' -Clicks 50 -MinPeriod
# D70 input on OPT
.\audio-loopback.ps1 -Render 'HDMI SPLITTER' -Capture 'Input 2 (SSL 2' -Clicks 50
.\audio-loopback.ps1 -Render 'HDMI SPLITTER' -Capture 'Input 2 (SSL 2' -Clicks 50 -MinPeriod
```

Set both endpoints to 100 % in Windows; the optical level is fixed digital, so the DAC's volume sets the analog level on both paths. Watch the capture peak: one of my runs clipped at 1.0 and I re-ran it. Every run I kept peaked at 0.817.

Two sessions 40 minutes apart, two rounds each, 50 clicks per run, every click found. The first used the PowerShell script; the second a Go reimplementation of the same method, which also checks that the reimplementation measures the same thing. Medians in ms, p25-p75 in brackets:

| Path, period | Session 1, round 1 | Session 1, round 2 | Session 2, round 1 | Session 2, round 2 |
|---|---|---|---|---|
| USB, default | 47.58 (47.32-47.86) | 48.24 (47.97-48.52) | 48.13 (47.86-48.39) | 48.40 (48.10-48.64) |
| USB, minimum (7 ms) | 35.09 (34.83-35.33) | 35.19 (34.92-35.46) | 35.54 (35.27-35.78) | 35.77 (35.48-36.03) |
| GPU, default | 44.27 (44.13-44.38) | 43.79 (43.64-43.90) | 43.73 (43.57-43.86) | 44.43 (44.29-44.56) |
| GPU, minimum (10 ms) | 44.39 (44.25-44.53) | 44.27 (44.10-44.39) | 43.75 (43.59-43.88) | 44.42 (44.28-44.55) |

The script also splits each click at the moment the render stream's `IAudioClock` says it is playing:

| Path, period | App -> driver says playing | -> captured |
|---|---|---|
| USB, default | 42.96-42.97 ms | 4.63-5.42 ms |
| USB, minimum | 30.34-30.35 ms | 4.75-5.41 ms |
| GPU, default and minimum | 31.96-31.99 ms | 11.75-12.46 ms |

Per round, the GPU path at the default period came in 3.31, 4.45, 4.40 and 3.97 ms ahead. Both scripts' verdicts were TIE: 3.79 ms in session 1, 4.40 ms in session 2, each comparing the lower of the two rounds' medians on each side.

## Reading the numbers

- At the default period the distributions do not overlap (every GPU p75 is below every USB p25), so the GPU path is faster, by less than the bar.
- At the minimum period the order flips. The D70 drops 12.49-13.05 ms per round to 35.09-35.77 ms; the GPU path cannot move, because NVIDIA's driver offers one period. An app that asks for small buffers is 8.2-9.3 ms better off on USB.
- The split differs by driver: NVIDIA reports a click playing 11 ms sooner than `usbaudio2` does, then 7 ms more passes before it is recorded. Only the totals compare across drivers, as in the USB guide. Some of that 7 ms could be the extractor doing its own buffering, and some the D70's optical receiver, I haven't measured either. The extractor also has a 3.5 mm analog output, so looping that into the recorder instead of the D70 would at least split the extractor plus its DAC from the D70's optical input.
- The session 2 per-condition means moved -0.25 to +0.52 ms against session 1, and no round differed by more than 0.64 ms, so the reimplementation reproduces the script.
- This measured NVIDIA's HDMI audio driver, which offers one 10 ms period. Microsoft's inbox HD Audio driver can run periods down to 128 samples for apps that ask[^ms-lowlatency], and it can be installed on the GPU's HDMI audio controller as well as on an onboard codec, which is what most of the community GPU-audio results below used. Stock Realtek drivers tend to lock to 10 ms exact[^wasapi-relink], so an onboard codec on its vendor driver should look like this GPU path, and on the inbox driver more like the extrapolation below. Neither is measured here, so I'd treat the result as settling NVIDIA-driver HDMI audio as a daily path, not HD Audio in general.
- One asymmetry I have not removed: the NVIDIA endpoint carries Microsoft's default enhancement APOs (`WMALFXGFXDSP.dll`, LFX and GFX), the D70 endpoint none. I found no measurement of what they cost with no enhancement selected. If they cost more than 1.21 ms (the 5 ms bar minus the 3.79 ms verdict gap), the GPU path would clear the bar. The re-test is "Disable all enhancements" on the extractor's endpoint and one more GPU run.

### Where a 35 ms onboard-vs-USB gap could come from

The community numbers behind the claim that onboard audio is about 35 ms faster than any USB DAC come from a browser round-trip test: the page plays a beep through the speakers and listens for it on the microphone[^superpowered]. A browser asks for the endpoint's minimum period, so that test runs every output at the smallest buffer its driver allows, which a game at the default period never sees, and the number includes the microphone's capture path as well as the output.

The largest collection of these results, the ALTResults page from the Blur Busters forum[^altresults], lists the driver for most entries. The fast results are on Microsoft's "High Definition Audio Device" driver, including GPU audio: one entry has a GTX 1070's DisplayPort and HDMI audio on that driver at 34-47 ms round trip, while an RX 580's HDMI and DisplayPort audio, listed as "AMD High Definition Audio Device", came in at 75-108 ms on the same test. Another entry has the same Apple USB-C dongle at 67-76 ms on an ASMedia USB controller and 83-94 ms on a Renesas one. So the spread is driver and buffer first, and a USB controller can add on top, I don't see anything in it that isolates USB transport by itself.

The period matters more than its own length. On the D70, going from the 10 ms to the 7 ms period cut the time to "driver says playing" by 12.62 ms, about 4.2 ms per millisecond of period, because Windows keeps several periods queued ahead of the click. If that slope held down to the inbox HD Audio driver's 128 samples (2.67 ms), the period alone would be worth about 31 ms against an output whose driver offers only 10 ms, and many USB drivers do (Topping's and the SSL 2's in the USB guide). That is an extrapolation from two points on one driver, not a measurement. It does put a 35 ms browser gap within reach of the period difference, while a game at the default period would see a gap closer to the 4 ms measured here. The direct test on this machine is the GPU's HDMI audio on Microsoft's inbox driver through the same extractor, which is the setup the fast ALTResults GPU entries used; I haven't run it yet.

## Part 4: the cost of keeping it

The endpoint lives and dies with the display. Two consequences:

- An extra 60 Hz display next to a 360 Hz primary made the desktop visibly choppy: minimise and maximise animations stuttered while the extractor was attached and were smooth again after detaching it (Win+P, PC screen only). That is an eyeball check at 60 Hz only; the extractor supports 1080p at 120 and 144 Hz[^jtech], which I did not try.
- "Remove display from desktop" (Settings, Advanced display) would keep a display out of the desktop, but it needs driver support. NVIDIA's own sample says "the NVIDIA driver implementation of this feature is only supported on Windows 11 and later"[^nv-ddisplay]. On this machine `DisplayConfigGetDeviceInfo` with `DISPLAYCONFIG_DEVICE_INFO_GET_MONITOR_SPECIALIZATION` (type 12[^ms-devinfotype]) returns 87 (`ERROR_INVALID_PARAMETER`) for every display, the DisplayPort primary included, while other info types on the same targets succeed. Switching to Enterprise for the toggle bought nothing on Windows 10.

## Part 5: the USB port the DAC is on

The D70 had been behind a hub through all of this, so I moved it to a rear port with no external hub. It landed on the CPU's USB 2.0 controller (`1022:15B8`, one PCI bridge from the root complex against three for the chipset controller); the SSL 2 stayed on the chipset controller. Five rounds of default and minimum period, 50 clicks each:

| | Chipset controller behind the hub | CPU controller, no hub |
|---|---|---|
| Default period | 47.58-48.40 ms | 48.02-48.58 ms (steady runs) |
| Minimum period | 35.09-35.77 ms | 35.32-35.74 ms |
| Runs with a slip or lost clicks | 0 of 8 | 4 of 10 |

- Latency did not change, the hub and the extra bridges cost nothing I could measure, which fits the latency being mostly Windows' and the driver's buffering.
- Stability did. Three default runs on the new port started 6 ms early (41.80 ms at click 1, creeping to 42.30 ms), lost click 36, then ran at 47.92-48.15 ms for clicks 37-50, which pulled their medians to 42.15-42.41 ms. One minimum-period run found 28 of 50 clicks at a normal peak. A click lost at a normal level is a break in the stream, which you would hear as a tick or dropout. I have not isolated the cause: the controller, the board's own hub on that port, or the DAC and recorder now running on different controllers.
- The split moved with the port (31.93-31.97 + 16.11-16.62 ms in the steady default runs, instead of 42.97 + 5.14 ms) while the totals did not, so the split looks like each driver's position reporting more than hardware delay.

## Verification

| Check | How | Expected |
|---|---|---|
| Extractor display present | Win+P Extend, then Settings > Display | a second display named after the extractor's EDID |
| Extractor endpoint present | `audio-loopback.ps1 -List` | `HDMI SPLITTER (NVIDIA High Definition Audio)` |
| DAC on the class driver | `Get-PnpDevice -Class MEDIA`, driver service | `usbaudio2` |
| Right input for the block | capture peak in each run | about 0.8 with the volumes above; near zero means the DAC is on the other input |
| Clicks found | `RESULT n/50` | 50/50 |
| Display detached afterwards | Win+P, PC screen only | the endpoint shows as unplugged |

## Gotchas and lessons learned

- The EDID switch decides whether the GPU sees anything. TV mode with an empty HDMI Out gives no display and no endpoint; 2ch plus a replug did it.
- Prompts do not wait when the script is launched from WSL. A wrapper that asked me to switch the DAC's input with `Read-Host` got redirected stdin through WSL interop, skipped every prompt, and timed a USB block with the DAC still on optical. The capture peak was 0.002 and the "clicks" it found were noise. Run interactive measurements from a Windows terminal, and treat a peak under 0.02 as no signal.
- Windows asked for a restart halfway through. A removal of the USB root hub the DAC and recorder hang off had been vetoed by `audiodg.exe` and the SSL control panel (Kernel-PnP event 225 in the System log); no update or file-rename reboot was pending. A vetoed removal completes at the next restart and does not touch a running stream; the USB default-period numbers (47.58-48.40 ms) overlap the October baseline (47.33-47.88 ms in the USB guide).
- Do not compare the "driver says playing" column across drivers or USB ports; it moved by 11 ms between ports with the total unchanged.
- An idle extra display is not free. Detach the extractor when you are not measuring through it.
- Moving the DAC to a "better" port can make it worse. Check for lost clicks, not only the median.
