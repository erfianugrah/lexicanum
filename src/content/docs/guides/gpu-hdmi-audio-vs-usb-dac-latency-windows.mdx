The [USB audio latency guide](/guides/usb-audio-loopback-latency-windows/) ended on an open question: would a non-USB output beat the D70 over USB? This page answers it for the one non-USB output I had, the GPU's HD Audio over HDMI, by putting an HDMI audio extractor between the GPU and the D70's optical input so the same DAC and the same recorder measure both paths. At the default shared-mode period, which is what most games get, the GPU path is 3.3-4.6 ms faster whichever driver it runs on. I had set a 5 ms bar before measuring, so for games it's a tie and the D70 stays on USB. The bigger difference is the driver's smallest period. On NVIDIA's driver the GPU path can't go below 10 ms and the D70 wins at small buffers. Moved to Microsoft's inbox HD Audio driver, the same GPU output gets 20.28-20.55 ms for an app that asks for small buffers, against 35.75-35.76 ms for the D70 at its minimum in the same session. That is where the community's claim that onboard audio is much faster than USB comes from (Part 6).

Where it ended up (2026-11-09): the D70 stays on USB with Microsoft's driver, and a background stream holding the minimum period runs from logon, which takes default-period apps from 48.03 to 41.27 ms with no audible glitches (Part 5). The extra display made the GPU path too much hassle for daily use. I also built Microsoft's open-source USB Audio Class 2 driver for Windows 10 and the D70 to try for smaller periods; it ran, but slower than the inbox driver and with crackle (Part 9).

You'll need the loopback setup and `audio-loopback.ps1` from the USB guide, an HDMI audio extractor with a 2-channel EDID setting, a Toslink cable, and a DAC with an optical input. Everything was measured on one machine on 2026-11-03.

## Constants

### The rig

| Piece | Detail |
|---|---|
| OS | Windows 10 22H2 (build 19045), Enterprise edition during the test |
| GPU | NVIDIA GeForce RTX 5090, driver 617.42; primary display 2560x1440 at 360 Hz over DisplayPort |
| Extractor | J-Tech JTD18G-H5CH (HDMI 2.0b, optical out up to LPCM 2CH or Dolby Digital/DTS 5.1, EDID switch TV / 5ch / 2ch[^jtech]) on a spare HDMI port of the GPU, EDID switch on 2ch, HDMI Out empty, optical out into the D70 |
| DAC | Topping D70 Pro Sabre on Microsoft's USB Audio 2.0 class driver (`usbaudio2`), USB and optical inputs |
| Recorder | SSL 2, buffer 128 samples: Input 2 fed from the D70's left XLR output, Input 1 from the extractor's 3.5 mm output (left channel) |
| USB | D70 and SSL 2 behind a VIA VL822 hub (`2109:0822`) on the chipset controller `1022:43F7` (not USB4) |
| Format | 48 kHz, 2 channels, WASAPI shared mode; the extractor's endpoint at 16-bit (Part 4 explains why), the D70's at 32-bit |
| Interrupts | USB controller `1022:43F7` (D70 and SSL 2) pinned to CPU 4, the GPU to CPU 2, the GPU's HD Audio controller (`10DE:22E8`, line interrupt) on the default |

### The two endpoints

Windows names the extractor after its EDID. Read with `IAudioClient3::GetSharedModeEnginePeriod`, as in the USB guide:

| Endpoint | Driver | Default | Fundamental | Minimum |
|---|---|---|---|---|
| `Speakers (D70 Pro SABRE)` | `usbaudio2` | 480 frames (10 ms) | 1 | 336 frames (7 ms) |
| `HDMI SPLITTER (NVIDIA High Definition Audio)` | NVIDIA HD Audio | 480 frames (10 ms) | 480 | 480 frames (10 ms) |
| `HDMI SPLITTER (High Definition Audio Device)`, after Part 4 | Microsoft inbox HD Audio (`hdaudio.inf`) | 480 frames (10 ms) | 32 | 128 frames (2.67 ms) |

The USB guide's period table showed 10 ms everywhere because it was measured with the D70 on Topping's driver; back on `usbaudio2` the 7 ms minimum is there again. Chromium reads each endpoint's minimum with `GetSharedModeEnginePeriod` and, when a smaller buffer is requested, opens the stream with `IAudioClient3::InitializeSharedAudioStream`[^ms-initshared] at that period[^chromium-coreaudio]; most games take the default. SDL added the same call to its WASAPI backend in May 2024[^sdl-9683], so games built on recent SDL can get the smaller period too.

### What the comparison holds fixed

The D70 is the DAC on both paths and the SSL 2's Input 2 records both, so the analog stage, the cable and the recorder's delay are common to both and cancel out of the difference. What changes is the Windows render path (the USB class driver against NVIDIA's HD Audio driver), the transport (USB against HDMI, the extractor and Toslink) and the D70's input receiver. The extractor's delay is inside the GPU number. Input 1 records the extractor's own 3.5 mm output, which takes the D70's optical input out of the GPU path for comparison.

## Part 1: get the extractor's endpoint

1. Set the EDID switch to 2ch before connecting. In TV mode the extractor passes on the EDID of whatever is on its HDMI Out, and with nothing there the GPU gets no EDID and Windows sees no display.
2. Power the extractor (5 V barrel; HDMI does not power it), connect the GPU to HDMI In and the optical out to the DAC, leave HDMI Out empty.
3. If no display appears, unplug and replug the HDMI cable at the extractor to force a hotplug. Mine showed up after that as `HDMI SPLITTER` (manufacturer code HDC) at 1920x1080 at 60 Hz.
4. Extend the desktop to it (Win+P, Extend). The audio endpoint `HDMI SPLITTER (NVIDIA High Definition Audio)` exists only while that display is part of the desktop.
5. Play something to the new endpoint, switch the DAC to its optical input and check it locks and plays.

## Part 2: fix the verdict before measuring

I wrote the pass rule down before the extractor arrived, so the numbers could not shape it:

- Only the default period counts, because that is what games get.
- The GPU path wins only if its median is at least 5 ms lower than the USB path's and its p75 sits below the USB path's p25. Anything less is a tie, and a tie means staying on USB, which has no extra display to live with (Part 7).
- Runs alternate A, B, A, B so drift over the session lands on both paths.

5 ms was my judgement of a gap worth an extra display or a motherboard change, not a perceptual threshold.

## Part 3: measure both paths

With the USB guide's script, switching the DAC's input before each block:

```powershell
# D70 input on USB
.\audio-loopback.ps1 -Render 'D70' -Capture 'Input 2 (SSL 2' -Clicks 50
.\audio-loopback.ps1 -Render 'D70' -Capture 'Input 2 (SSL 2' -Clicks 50 -MinPeriod
# D70 input on OPT
.\audio-loopback.ps1 -Render 'HDMI SPLITTER' -Capture 'Input 2 (SSL 2' -Clicks 50
.\audio-loopback.ps1 -Render 'HDMI SPLITTER' -Capture 'Input 2 (SSL 2' -Clicks 50 -MinPeriod
```

Set both endpoints to 100 % in Windows; the optical level is fixed digital, so the DAC's volume sets the analog level on both paths. Watch the capture peak: one of my runs clipped at 1.0 and I re-ran it. Every run I kept peaked at 0.817.

Two sessions 40 minutes apart, two rounds each, 50 clicks per run, every click found. The first used the PowerShell script; the second a Go reimplementation of the same method, which also checks that the reimplementation measures the same thing. Medians in ms, p25-p75 in brackets:

| Path, period | Session 1, round 1 | Session 1, round 2 | Session 2, round 1 | Session 2, round 2 |
|---|---|---|---|---|
| USB, default | 47.58 (47.32-47.86) | 48.24 (47.97-48.52) | 48.13 (47.86-48.39) | 48.40 (48.10-48.64) |
| USB, minimum (7 ms) | 35.09 (34.83-35.33) | 35.19 (34.92-35.46) | 35.54 (35.27-35.78) | 35.77 (35.48-36.03) |
| GPU, default | 44.27 (44.13-44.38) | 43.79 (43.64-43.90) | 43.73 (43.57-43.86) | 44.43 (44.29-44.56) |
| GPU, minimum (10 ms) | 44.39 (44.25-44.53) | 44.27 (44.10-44.39) | 43.75 (43.59-43.88) | 44.42 (44.28-44.55) |

The script also splits each click at the moment the render stream's `IAudioClock` says it is playing:

| Path, period | App -> driver says playing | -> captured |
|---|---|---|
| USB, default | 42.96-42.97 ms | 4.63-5.42 ms |
| USB, minimum | 30.34-30.35 ms | 4.75-5.41 ms |
| GPU, default and minimum | 31.96-31.99 ms | 11.75-12.46 ms |

Per round, the GPU path at the default period came in 3.31, 4.45, 4.40 and 3.97 ms ahead. Both scripts' verdicts were TIE: 3.79 ms in session 1, 4.40 ms in session 2, each comparing the lower of the two rounds' medians on each side.

## Reading the numbers

- At the default period the distributions do not overlap (every GPU p75 is below every USB p25), so the GPU path is faster, by less than the bar.
- At the minimum period the order flips on NVIDIA's driver. The D70 drops 12.49-13.05 ms per round to 35.09-35.77 ms; the GPU path cannot move, because NVIDIA's driver offers one period. An app that asks for small buffers is 8.2-9.3 ms better off on USB. Part 4 changes that by changing the driver.
- The split differs by driver: NVIDIA reports a click playing 11 ms sooner than `usbaudio2` does, then 7 ms more passes before it is recorded. Only the totals compare across drivers, as in the USB guide. To see whether the D70's optical input accounts for that 7 ms, I looped the extractor's own 3.5 mm output into Input 1: 43.75 and 43.78 ms at the default period on NVIDIA's driver, against 43.73-44.43 ms through the D70, and the two outputs stay within a millisecond or two of each other on both drivers in Part 4. So the D70's optical receiver and DAC add nothing I could measure over the extractor's own DAC, and the extra time sits upstream of both: the driver, the HDMI link or the extractor's HDMI receiver.
- The session 2 per-condition means moved -0.25 to +0.52 ms against session 1, and no round differed by more than 0.64 ms, so the reimplementation reproduces the script.
- One asymmetry I have not removed: the NVIDIA endpoint carries Microsoft's default enhancement APOs (`WMALFXGFXDSP.dll`, LFX and GFX), the D70 endpoint none. I found no measurement of what they cost with no enhancement selected. If they cost more than 1.21 ms (the 5 ms bar minus the 3.79 ms verdict gap), the GPU path would clear the bar. The re-test is "Disable all enhancements" on the extractor's endpoint and one more GPU run.

## Part 4: swap the GPU's HDMI audio to Microsoft's inbox driver

Microsoft's inbox HD Audio driver supports small buffers for apps that ask[^ms-lowlatency], and it installs on the GPU's HDMI audio function as well as on an onboard codec. With the extractor's display attached:

1. Device Manager > Sound, video and game controllers > `NVIDIA High Definition Audio` (the GPU's) > Update driver > Browse my computer for drivers > Let me pick from a list of available drivers on my computer > `High Definition Audio Device` > Next, and accept the compatibility warning. Mine asked for a restart.
2. The swap reset the extractor's endpoint to 44.1 kHz. Set it back under Sound control panel > Playback > `HDMI SPLITTER` > Properties > Advanced. Use 16-bit, 48000 Hz: at 24-bit the extractor's 3.5 mm output went silent (capture peak 0.0003) while its optical output kept working, and 16-bit brought it back.
3. Check the periods with `GetSharedModeEnginePeriod`: the endpoint should report a 128-frame minimum, as in the endpoint table above.
4. To go back: Properties > Driver > Roll Back Driver. A GeForce driver install also puts NVIDIA's driver back.

Then the full set again in one sitting, with Discord, Telegram, the browser and a local model closed: the inbox driver first, then the D70 over USB, then NVIDIA's driver after the rollback and a restart. Two rounds per condition, 50 clicks per run, every click found. Medians in ms:

| Path | Default (480 frames) | Minimum period |
|---|---|---|
| GPU, inbox driver, optical into the D70 | 43.77 / 43.79 | 20.28 / 20.33 (128 frames) |
| GPU, inbox driver, extractor 3.5 mm | 42.20 / 44.02 | 20.50 / 20.55 (128 frames) |
| D70 over USB | 48.39 / 48.36 | 35.75 / 35.76 (336 frames) |
| GPU, NVIDIA driver, optical into the D70 | 44.38 / 44.32 | 44.33 / 44.33 (480 frames, the only period) |
| GPU, NVIDIA driver, extractor 3.5 mm | 44.34 / 44.35 | 44.36 / 44.12 (480 frames) |

| Path, period | App -> driver says playing | -> captured |
|---|---|---|
| GPU, inbox driver, default | 32.97-32.98 ms | 9.21-11.05 ms |
| GPU, inbox driver, minimum | 9.49-9.50 ms | 10.79-11.05 ms |
| GPU, NVIDIA driver, both | 33.18-33.25 ms | 10.88-11.20 ms |
| D70 over USB, default | 42.97 ms | 5.38-5.42 ms |
| D70 over USB, minimum | 30.35 ms | 5.42 ms |

- At the default period the driver makes no difference: the GPU path is 4.59 ms ahead of the D70 on the inbox driver and 4.02 ms on NVIDIA's (optical, mean of the two rounds). Still a tie for games.
- At the minimum period the inbox driver's 128 frames take the GPU path to 20.28-20.55 ms: 15.2-15.5 ms faster than the D70 at its minimum, 28.07 ms faster than the D70 at the default, and 24.05 ms faster than the same output on NVIDIA's driver.
- All of that is in the first column. Windows keeps a few periods queued ahead of the driver, so a smaller period saves a multiple of its own length: from how each total moved with the period, about 3.2 periods on the HD Audio path ((32.98 - 9.49) / (10 - 2.67)) and 4.2 on `usbaudio2` ((42.97 - 30.35) / (10 - 7)). After "playing", the USB path is the quicker one, 5.4 ms against about 11 ms.
- Two earlier inbox-driver sets, before the format fix: at 44.1 kHz the minimum-period runs gave 21.74-22.62 ms, and at 24-bit 48 kHz the optical runs gave 18.80 and 20.39 ms. The 16-bit set above is the one to compare.
- Closing the apps changed nothing I can see: the D70's default runs (48.36 and 48.39 ms) sit inside the morning's 47.58-48.40 ms with them open.

## Part 5: hold the small period for every app

Microsoft's low-latency page says that once one app requests small buffers, "all applications that use the same endpoint and mode will automatically switch to that small buffer size", until it exits[^ms-lowlatency]. REAL[^real] uses this: it opens a stream at the minimum period and keeps it open. The same thing in PowerShell, playing nothing:

```powershell
<#
hold-min-period.ps1 - open a WASAPI shared stream at the endpoint's minimum period and hold it,
the trick REAL (https://github.com/miniant-git/REAL) uses. Microsoft: once one app uses small
buffers, all apps on that endpoint and mode switch to that buffer size until it exits
(https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio, FAQ).
No admin. Plays nothing (silence). Usage: .\hold-min-period.ps1 -Render 'HDMI SPLITTER' -Seconds 120
#>
param([Parameter(Mandatory)][string]$Render, [int]$Seconds = 120)
$ErrorActionPreference = 'Stop'
Add-Type -TypeDefinition @"
```

I ran it in the background and measured normal default-period streams on the same endpoint, two rounds of 40 clicks:

| Path | Default, alone | Default with the hold running | Gain |
|---|---|---|---|
| GPU, inbox driver, optical into the D70 | 43.77 / 43.79 | 36.71 / 36.96 | 6.95 ms |
| GPU, inbox driver, extractor 3.5 mm | 42.20 / 44.02 | 37.04 / 37.03 | 6.08 ms |
| D70 over USB (hold at 336 frames) | 48.39 / 48.36 | 42.63 / 42.73 | 5.70 ms |

The gain is a fraction of what the minimum-period stream itself gets. The engine does run at the small period (the GPU path's "driver says playing" fell from 32.98 to 24.65 ms), but the default-period app still allocates its own 1056-frame (22 ms) buffer and keeps it filled, so most of that queue is still in front of each click. How much a particular game gains depends on how full it keeps its buffer, which this test doesn't cover. Microsoft's page also notes the trade-off: smaller buffers wake the CPU more often.

### Keeping the hold running

I kept the hold on the D70 over USB and moved it from the script into a small background program of my own that starts at logon. It opens the same `IAudioClient3` stream at the minimum period, starts it, and writes buffers flagged silent once per period (about 143 wakes a second at 7 ms), re-opening the stream if the device or the audio service goes away. The shared-mode mix format stays at 48 kHz float with or without it, and the hold only adds zero samples to the mix, so the audio itself is unchanged; the only cost is the extra wakes.

Re-measured 2026-11-08 on the D70 over USB, default-period stream, 30 clicks per run:

| Condition | Median | p25-p75 | Clicks back |
|---|---|---|---|
| No hold | 48.03 ms | 47.86-48.15 ms | 30/30 |
| Hold running (engine at 336 frames) | 41.27 ms | 41.11-41.42 ms | 30/30 |

That repeats the 5.70 ms gain in the table above (6.76 ms here). A listening session with music and a game while it held gave no clicks or dropouts. After the hold stopped, the engine read 336 frames at once and 480 frames (10 ms) again within 30 s, so a hold that dies takes the gain with it after a short delay.

## Part 6: where the community's onboard-vs-USB gap comes from

The community numbers behind the claim that onboard audio is about 35 ms faster than any USB DAC come from a browser round-trip test: the page plays a beep through the speakers and listens for it on the microphone[^superpowered]. A browser asks for the endpoint's minimum period, so that test runs every output at the smallest buffer its driver allows, which a game at the default period never sees, and the number includes the microphone's capture path as well as the output.

The largest collection of these results, the ALTResults page from the Blur Busters forum[^altresults], lists the driver for most entries. The fast results are on Microsoft's "High Definition Audio Device" driver, including GPU audio: one entry has a GTX 1070's DisplayPort and HDMI audio on that driver at 34-47 ms round trip, while an RX 580's HDMI and DisplayPort audio, listed as "AMD High Definition Audio Device", came in at 75-108 ms on the same test. Another entry has the same Apple USB-C dongle at 67-76 ms on an ASMedia USB controller and 83-94 ms on a Renesas one.

Part 4 measures the mechanism on one output. The same GPU output was 24.05 ms faster on the inbox driver's 128 frames than on NVIDIA's 10 ms, with the hardware unchanged. Many USB drivers also stop at 10 ms (Topping's and the SSL 2's in the USB guide), and stock Realtek drivers tend to lock to 10 ms exact[^wasapi-relink], so an onboard codec on Microsoft's driver against a USB DAC on a 10 ms driver would show a gap like that on the output alone, before the microphone side of a round trip. Against Microsoft's USB class driver, which goes to 7 ms, the gap here was 15.2-15.5 ms. None of it isolates USB transport: after the driver's queue, the USB path was the faster one.

## Part 7: the cost of keeping it

The endpoint lives and dies with the display. Two consequences:

- An extra 60 Hz display next to a 360 Hz primary made the desktop visibly choppy: minimise and maximise animations stuttered while the extractor was attached and were smooth again after detaching it (Win+P, PC screen only). That is an eyeball check at 60 Hz only; the extractor supports 1080p at 120 and 144 Hz[^jtech], which I did not try.
- "Remove display from desktop" (Settings, Advanced display) would keep a display out of the desktop, but it needs driver support. NVIDIA's own sample says "the NVIDIA driver implementation of this feature is only supported on Windows 11 and later"[^nv-ddisplay]. On this machine `DisplayConfigGetDeviceInfo` with `DISPLAYCONFIG_DEVICE_INFO_GET_MONITOR_SPECIALIZATION` (type 12[^ms-devinfotype]) returns 87 (`ERROR_INVALID_PARAMETER`) for every display, the DisplayPort primary included, while other info types on the same targets succeed. Switching to Enterprise for the toggle bought nothing on Windows 10.

## Part 8: the USB port the DAC is on

The D70 had been behind a hub through all of this, so I moved it to a rear port with no external hub. It landed on the CPU's USB 2.0 controller (`1022:15B8`, one PCI bridge from the root complex against three for the chipset controller); the SSL 2 stayed on the chipset controller. Five rounds of default and minimum period, 50 clicks each:

| | Chipset controller behind the hub | CPU controller, no hub |
|---|---|---|
| Default period | 47.58-48.40 ms | 48.02-48.58 ms (steady runs) |
| Minimum period | 35.09-35.77 ms | 35.32-35.74 ms |
| Runs with a slip or lost clicks | 0 of 8 | 4 of 10 |

- Latency did not change, the hub and the extra bridges cost nothing I could measure, which fits the latency being mostly Windows' and the driver's buffering.
- Stability did. Three default runs on the new port started 6 ms early (41.80 ms at click 1, creeping to 42.30 ms), lost click 36, then ran at 47.92-48.15 ms for clicks 37-50, which pulled their medians to 42.15-42.41 ms. One minimum-period run found 28 of 50 clicks at a normal peak. A click lost at a normal level is a break in the stream, which you would hear as a tick or dropout. I have not isolated the cause: the controller, the board's own hub on that port, or the DAC and recorder now running on different controllers.
- The split moved with the port (31.93-31.97 + 16.11-16.62 ms in the steady default runs, instead of 42.97 + 5.14 ms) while the totals did not, so the split looks like each driver's position reporting more than hardware delay.

## Part 9: what a faster USB driver would buy, and what building one gave

The gap in Part 4 is the driver's smallest period, so the obvious next question is whether a USB driver could offer the D70 small periods the way Microsoft's HD Audio driver does for the GPU. I haven't built one. This part is a desk review of what it would take, and the payoff it is capped at by the numbers above.

The ceiling comes from treating the inbox HD Audio path as the target:

| App type | D70 on usbaudio2 | GPU on the inbox HD Audio driver | Most a better USB driver could save |
|---|---|---|---|
| Asks for the smallest period (browsers) | 35.75-35.76 ms | 20.28-20.55 ms | about 15 ms |
| Default period, with a hold stream running (Part 5) | 42.63-42.73 ms | 36.71-37.04 ms | about 6 ms |
| Default period, nothing else | 48.36-48.39 ms | 42.20-44.02 ms | the default period does not change with the driver |

Games mostly sit in the last two rows, so for them a new driver is worth about 6 ms on top of the hold trick, and only while something holds the period.

Microsoft has published a USB Audio Class 2 driver built with Yamaha on its Audio Class Extensions (ACX) framework, MIT-licensed[^ms-lla]. Reading its source (checked 2026-11-06):

- The shared-mode floor is a constant: `s_PacketSizeConstraints` in `src/uac2-driver/CircuitHelper.h` sets a 7 ms minimum processing interval. That is the same 7 ms (336 frames at 48 kHz) Microsoft's inbox `usbaudio2` offers the D70.
- The USB scheduling is set from the registry: `ClassicFramesPerIrp` (default 4, so each transfer covers 4 ms), `MaxIrpNumber` (default 4 on x64), `OutputBufferOperationOffset` and `FirstPacketLatency`.
- Small shared-mode periods are not implemented yet. The open issue asking for them[^lla-22] quotes an answer from the project's Discord that latency would be "approximately on par with what native vendor-provided ASIO/UAC2 drivers can reach", and a Microsoft reply that Yamaha is investigating. Its fast path today is the ASIO side.
- It is still settling: an open fix addresses a bugcheck in the mixing thread[^lla-33], and an issue reports ASIO recording breakup on a recent build[^lla-44]. Its INF lists 25 hardware IDs by hardware ID and no Topping device, so the D70 would need adding.
- Windows 10 support is unconfirmed for this build. Microsoft lists ACX 1.1 as shipped with Windows 10 version 2004 on KMDF 1.31[^ms-acx-ver], and this machine has `Acx01000.sys` 10.0.19041.7725 and KMDF 1.31, but the project's globals ask for KMDF 1.33 while its compile defines say 1.31.

So the work would be a fork: add the D70, lower the 7 ms constant, set `ClassicFramesPerIrp` to 1, and tune the rest until the loop in Part 3 runs at a 2-3 ms period with no lost clicks. Lost clicks are the real test: the vendor driver in the [USB guide](/guides/usb-audio-loopback-latency-windows/) beat `usbaudio2` by 6.4 ms, and its intermittent crackle came back after that reinstall, so I went back to `usbaudio2`. Writing a driver from scratch would mean re-implementing about 30,000 lines of C++. A WinUSB user-mode driver avoids kernel signing but removes the D70 as a Windows audio endpoint, which leaves ASIO only.

Signing decides whether any of this is usable day to day:

- A test-signed driver loads only with test signing on, which needs Secure Boot off and puts a "Test Mode" watermark on the desktop[^ms-testsign]. Anti-cheat refuses it: FACEIT will not start until test signing is off[^faceit-testsign].
- A driver signed by Microsoft through attestation loads on Windows 10 desktop without HLK testing, but the submission needs an EV code-signing certificate and a Hardware Developer Program account, which is registered to an organisation with a legal contact[^ms-signing][^ms-hwreg].

The cheaper paths come first. One is to wait for Microsoft to ship small shared-mode periods in its own signed driver. The other needs no driver work: the GPU path on the inbox driver from Part 4 already reaches 20.28 ms, at the cost of the extra display in Part 7.

### Building it (2026-11-07 to 2026-11-09)

I built the fork anyway, test-signed, and loaded it from a second boot entry with test signing on, so the normal entry and its anti-cheat stayed untouched. The changes: KMDF 1.31, the D70's hardware ID in the INF, the lock proposed for the bugcheck in issue 33[^lla-33], and the 7 ms constant made a registry value so periods could be tried without a rebuild.

Getting it to start took three fixes:

1. The first build never reached its own code. The kernel debug output showed the framework stub's class bind for ACX returning `STATUS_INVALID_PARAMETER` (0xC000000D), and the device failed with code 37. The public symbols for this machine's `Acx01000.sys` (10.0.19041.7725) show its class library registering version 1.0.0 with 210 functions, while the driver asked for 1.1 with 221. Microsoft's version table lists ACX 1.1 on Windows 10 version 2004[^ms-acx-ver]; this build of Windows 10 has 1.0. Building against the WDK's ACX 1.0 headers, and replacing the three 1.1-only calls the driver made, got past the bind.
2. The D70 stalls a GET CUR request on its clock selector (entity 0x28), which the inbox driver either never sends or tolerates, and which this one treated as fatal (code 10). Logging and carrying on fixed that.
3. A pending reboot from the previous image (code 14).

Then it ran, as a new endpoint at 44.1 kHz with a 10 ms default and 7.01 ms minimum. Same loop, 30 clicks per run, all clicks back:

| Driver and settings | Minimum period | Default period |
|---|---|---|
| Inbox `usbaudio2`, 48 kHz (runs shortly before) | 34.95 ms | 48.03 ms |
| Fork, upstream defaults (4 ms per transfer, 4 transfers queued) | 41.87 ms | 51.58 ms |
| Fork, 1 ms per transfer, 2 queued, period value 7 / 3 / 2 / 1 ms | 41.32-41.99 ms | 51.24-51.90 ms |

- It was 7 ms slower at the minimum period and 3.5 ms slower at the default. The 44.1 kHz format explains 1-2 ms at most (see Gotchas).
- The period value never reached the audio engine: the driver wrote it to the endpoint's interface property (the trace shows the write succeeding), and the engine kept offering 7.01 ms at every setting.
- The transfer settings moved latency by under 1 ms.
- It crackled on everything at the upstream defaults, and short sounds came out with their start cut off.
- After this driver restarted the D70, the DAC stalled class requests (the clock selector read, then the sample-rate range on its clock source) until it was replugged, so 48 kHz and the smaller periods could not be tested past that point. The inbox driver restarts the same DAC without this.

I rolled it back and removed the test boot entry and certificate. On Windows 10 with this DAC, the fork as it stands loses to the inbox driver on latency and on stability, so signing it was never worth pursuing.

## Gotchas and lessons learned

- The EDID switch decides whether the GPU sees anything. TV mode with an empty HDMI Out gives no display and no endpoint; 2ch plus a replug did it.
- Prompts do not wait when the script is launched from WSL. A wrapper that asked me to switch the DAC's input with `Read-Host` got redirected stdin through WSL interop, skipped every prompt, and timed a USB block with the DAC still on optical. The capture peak was 0.002 and the "clicks" it found were noise. Run interactive measurements from a Windows terminal, and treat a peak under 0.02 as no signal.
- Windows asked for a restart halfway through. A removal of the USB root hub the DAC and recorder hang off had been vetoed by `audiodg.exe` and the SSL control panel (Kernel-PnP event 225 in the System log); no update or file-rename reboot was pending. A vetoed removal completes at the next restart and does not touch a running stream; the USB default-period numbers (47.58-48.40 ms) overlap the October baseline (47.33-47.88 ms in the USB guide).
- Do not compare the "driver says playing" column across drivers or USB ports; it moved by 11 ms between ports with the total unchanged.
- An idle extra display is not free. Detach the extractor when you are not measuring through it.
- Moving the DAC to a "better" port can make it worse. Check for lost clicks, not only the median.
- A driver swap resets the endpoint's format. Mine came back at 44.1 kHz, with a 448-frame (10.16 ms) default period and every number 1-2 ms off the 48 kHz set.
- The extractor's analog output mutes on a 24-bit stream while the optical output carries on. Check the capture peak on both inputs after any format change.
- The monitor's own headphone jack would have been a GPU test without the extractor, but it was silent even with headphones, while DDC/CI reported the monitor at volume 70, unmuted, on DisplayPort 1. I didn't find the cause.
- Windows 10 19041's in-box ACX is version 1.0, not the 1.1 that Microsoft's version table lists for Windows 10 version 2004. A driver built against ACX 1.1 fails before its entry point runs, with code 37 and nothing in its own trace; the kernel debug output with WDF loader diagnostics on is where the class-bind error shows.
- The D70 stalls GET CUR on its clock selector. A driver that treats a stalled class request as fatal will not start it.
- A hold stream only lasts while its process runs. Kill it before measuring anything else on that endpoint, or every later default-period run comes out 6-7 ms low.
