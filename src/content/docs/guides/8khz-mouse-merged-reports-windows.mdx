title: Fixing merged reports from an 8 kHz mouse on Windows
description: Fixing the count spikes an 8 kHz mouse shows in MousePlotter on Windows 10, reports that carry 2-4 polls of motion cause the PC got to the USB controller late. Count the merged reports from the export, take out USB filter drivers like USBPcap, trace DPCs and interrupts with WPR (and get past its 0x80010106 stop failure), read the trace with xperf, pin the mouse's xHCI controller interrupts to a CPU the GPU driver doesn't use, then reserve that CPU with ReservedCpuSets to get rid of the leftover jitter.
author: "Erfi Anugrah"
category: workstations
---

An 8 kHz mouse sends a report every 125 us. If Windows gets to the USB controller late, the mouse can't send on time and the next report carries the motion of two to four polls. In MousePlotter these show up as single dots way outside the counts band, and the counts axis stretches until the normal trace is a solid block. My machine went from 66.5 merged reports a minute to zero, this is how: count them from the export, take out a USB filter driver that made it worse, trace where the delay comes from, move the mouse's controller interrupts off the CPU the GPU driver uses, then reserve that CPU so nothing else gets scheduled on it, which got rid of the leftover timing jitter.

You'll need an admin PowerShell (Windows PowerShell 5.1 is fine, every snippet below was run on my machine), MousePlotter running elevated (it needs ETW for the kernel timestamps), DuckDB to count the results (`winget install DuckDB.cli`) and the Windows Performance Toolkit for the trace. All the numbers are from one machine, measured on 2026-10-16, 2026-10-24 and 2026-10-26, so treat them as one data point. The last few sections say what was and wasn't shown.

### What the export can tell you

Every MousePlotter HTML export has the raw CSV in it, per report `x`, `y`, `eventTime (ms)` (kernel, from ETW) and `userTime (ms)` (user space). Three numbers are enough to tell the failure modes apart:

| Number | Definition | Healthy 8 kHz |
|---|---|---|
| Merged reports | Moving reports (4+ counts) carrying more than 2.5x the median motion of the 21 reports around them | 0 |
| Bunched deliveries | Intervals under 40 % of the median interval (several reports delivered together) | about 1 a minute |
| Off-band intervals | Intervals outside the median +-20 % | about 30 a minute |

A merged report points the same way as the motion around it and carries 2.5-3.5x the local median. On my bad runs 97 % of the outliers looked like that and came right after a run of late (0.25-0.5 ms) or bunched deliveries. Both mice did it, so the delay was on the PC side.

### Why a late DPC means a merged report

| Constant | Value | Why it matters |
|---|---|---|
| Poll interval at 8 kHz | 125 us | Any delay longer than this misses a poll |
| DPC ordering | DPCs queued on one CPU run one after another | A long DPC from another driver delays the USB completion queued behind it |
| Where a DPC runs | Normally on the CPU that took the interrupt | Moving a device's interrupt moves its DPCs with it |
| Windows 10 raw input | Background raw-input listeners get every report | Windows 11 throttles background listeners to about 125 Hz (KB5028185); Windows 10 22H2 does not[^boosterx-raw] |

### The numbers to expect

OP1, 60 s of fast circles, with the browser, Discord and WSL closed:

| Config | Off-band /min | Bunched /min | Merged /min | Max counts in one report |
|---|---|---|---|---|
| Baseline 2026-10-16 | 31 | 1 | 0 | 15 |
| USBPcap filter installed | 769 | 135 | 66.5 | 75 |
| USBPcap removed from the mouse's hub | 251 | 46 | 16.8 | 50 |
| + reboot (filter gone from every hub), Windows Sandbox off | 126 | 19 | 10.1 | 38 |
| + controller pinned to CPU 4 | 112 | 32 | 0.0 | 31 |
| Controller pinned to CPU 6 | 123 | 13 | 0.0 | 17 |
| + CPUs 6 and 7 reserved, restart (two runs) | 16-23 | 0 | 0.0 | 13-26 |
| Same, BIOS Global C-state Control on Auto instead of Disabled | 35 | 2 | 0.0 | 28 |
| Same, usual apps open (Discord, browser, chat apps; WSL off), two runs | 16-24 | 0-1 | 0.0 | 14-33 |

The pin gets rid of the merged reports, reserving the pinned CPU then brings the timing back to the baseline or a bit better. Of the 16-35 off-band intervals left, 15-22 a minute are the mouse skipping a poll on its own (see [What is left](#what-is-left)).

Text version: the mouse's controller raised its interrupts on CPU 0, which is also where the NVIDIA driver's DPCs and the GPU's interrupts ran, so a long NVIDIA DPC held up the USB completion behind it. After the pin the controller's interrupts and DPCs run on CPU 6 and the GPU stays on CPU 0.

## Part 1: measure the merged reports

1. Close what you can, browsers, Discord, Steam, tray apps. On Windows 10 every one of them gets every raw mouse report. If you use WSL shut it down too (`wsl --shutdown`), its memory reclaim caused 5 s stalls on my machine before.
2. Run MousePlotter elevated, set its DPI field to the mouse's actual CPI, record 60 s of fast circles and sweeps without stopping, and Export.
3. Pull the CSV out of the export. MousePlotter puts it in a `<script type="application/csv" id="embeddedCsv">` block, the first two lines are the device name and the DPI field and then it's a normal header (`xCount,yCount,eventTime (ms),userTime (ms),timestampSource`). In PowerShell, from an empty folder:

```powershell
$export = "$env:USERPROFILE\Downloads\<your export>.html"
$html = Get-Content -Raw -Encoding UTF8 $export
$m = [regex]::Match($html, '(?s)<script type="application/csv" id="embeddedCsv">(.*?)</script>')
$lines = $m.Groups[1].Value.Trim() -split "`r?`n"
"device: $($lines[0]), DPI field: $($lines[1])"
$lines | Select-Object -Skip 2 | Set-Content -Encoding ascii run.csv
```

4. Start `duckdb` in the same folder and count (the first and last second are left out, that's just lift-off and stopping):

```sql
-- gaps over 0.4 ms, off-band and bunched intervals, merged reports, per minute
create table d as select row_number() over () i, xCount x, yCount y,
  "eventTime (ms)" t,
  "eventTime (ms)" - lag("eventTime (ms)") over () dt,
  sqrt(xCount*xCount + yCount*yCount) cnt
  from read_csv('run.csv');
create table f as select *, median(cnt) over (order by i rows between 10 preceding and 10 following) loc
  from d where t > 1000 and t < (select max(t) - 1000 from d);
select
  round(count(*) filter (where dt > 0.4) * 60000.0 / any_value(span), 1) gaps_over_04ms_per_min,
  round(count(*) filter (where dt < 0.8*m or dt > 1.2*m) * 60000.0 / any_value(span)) off_band_per_min,
  round(count(*) filter (where dt < 0.4*m) * 60000.0 / any_value(span)) bunched_per_min,
  round(count(*) filter (where cnt >= 4 and cnt > 2.5 * greatest(loc, 4)) * 60000.0 / any_value(span), 1) merged_per_min,
  round(max(cnt)) max_counts
from f, (select median(dt) m, max(t) - min(t) span from f) q;
```

On a clean run (2026-10-26 10:01) I get 0.0, 16, 0, 0.0 and 14.

If merged reports are above zero while gaps over 0.4 ms stay rare, the PC is getting to the controller late. Big gaps (1-6 ms) on a fixed period are something else, that's a timer stalling the whole system.

## Part 2: remove USB filter drivers

A class filter on the USB host-controller class ends up in the stack of every root hub and every USB device. In my case USBPcap (installed for protocol captures) was the only non-Microsoft one, and taking it out cut merged reports from 66.5 to 16.8 a minute.

Check what is registered:

```powershell
(Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Class\{36FC9E60-C465-11CF-8056-444553540000}').UpperFilters
```

To take USBPcap out without uninstalling it, remove it from that value and restart each root hub that has it (devices behind the hub drop for about a second):

```powershell
$k = 'HKLM:\SYSTEM\CurrentControlSet\Control\Class\{36FC9E60-C465-11CF-8056-444553540000}'
$rest = @((Get-ItemProperty $k).UpperFilters | Where-Object { $_ -ne 'USBPcap' })
if ($rest) { Set-ItemProperty $k UpperFilters $rest } else { Remove-ItemProperty $k UpperFilters }
Get-PnpDevice -PresentOnly | Where-Object InstanceId -like 'USB\ROOT_HUB*' | ForEach-Object { pnputil /restart-device $_.InstanceId }
```

Windows can refuse the restart if a device behind the hub is in use (my audio interface was), then that hub keeps the filter until a reboot. The System log tells you what blocked it, Kernel-PnP event 225, for me `audiodg.exe` and the audio interface's control panel. Check a hub's stack with `Get-PnpDeviceProperty -InstanceId <hub> DEVPKEY_Device_Stack`. The entries are driver object paths like `\Driver\USBPcap`, so a script has to match the last part of the path. My first check compared the whole entry with `USBPcap`, never matched, never restarted a hub and still said the filter was gone.

:::caution
Do not disable the USBPcap service while it is still listed in UpperFilters. Windows then cannot load the filter and the USB stack fails to start, which can leave you without keyboard and mouse. Change the registry value, not the service.
:::

## Part 3: trace the DPCs and interrupts

You can install just the Windows Performance Toolkit from the ADK, without the rest of it:

```powershell
winget install --id Microsoft.WindowsADK --override "/features OptionId.WindowsPerformanceToolkit /quiet"
```

Record a trace over a MousePlotter run. Use `GeneralProfile`, the built-in `CPU` profile has no DPC or interrupt events (check with `wpr -profiledetails`).

```powershell
wpr -start GeneralProfile
# record in MousePlotter for 60 s
wpr -stop "$env:USERPROFILE\Downloads\mouse-dpc.etl" -skipPdbGen
```

A plain `wpr -stop` failed every time for me with `Cannot change thread mode after it is set` (0x80010106), and the session kept recording after that. With `-skipPdbGen` (skips the PDB/NGEN merge, a DPC/ISR summary doesn't need it) the stop works. An unelevated `wpr -status` doesn't see the elevated session, so check from the admin window, and `wpr -cancel` any leftover session before the next measurement or that measurement runs under the trace.

While tracing, MousePlotter loses its kernel timestamps for thousands of rows and falls back to user-space time, so the timing numbers of a traced run don't compare with anything. Measure in an untraced run first and trace in a second one. The merged count only uses report counts, so that one still holds under a trace.

Summarise per driver and per CPU:

```powershell
& "C:\Program Files (x86)\Windows Kits\10\Windows Performance Toolkit\xperf.exe" -i mouse-dpc.etl -o dpcisr.txt -a dpcisr -summary
```

On my machine (628 s trace):

| Module | DPCs | DPC time CPU 0 / CPU 1 | Long DPCs |
|---|---|---|---|
| USBXHCI.SYS (USB controllers) | 432,164 | 4.48 s / 0.76 s | 32 of 128-256 us, 1 of 256-512 us |
| nvlddmkm.sys (NVIDIA driver) | 227,323 | 4.18 s / 0.19 s | 3,827 of 128-256 us, 13 of 256-512 us, 1 of 0.5-1 ms, 1 of 1-2 ms, 16 of 2-4 ms |
| storport.sys (NVMe) | 187,087 | 0.14 s / 0.21 s (spread over all cores) | 12 of 128-256 us, 7 of 256-512 us |

The GPU's interrupts (dxgkrnl.sys ISR, 3.67 s) were on CPU 0 too. So USB and NVIDIA shared CPU 0, and 3,827 NVIDIA DPCs in 628 s took longer than one poll interval. The GPU is busy during a recording cause Windows redraws the cursor for every report.

## Part 4: pin the controller interrupts

valleyofdoom's PC-Tuning guide recommends this for xHCI controllers, move them to a CPU that isn't doing much, check it with an xperf DPC/ISR report and keep each ISR and its DPC on the same CPU[^pctuning-kms]. Microsoft documents the per-device affinity policy under the device's registry key[^ms-irq-affinity], `DevicePolicy` 4 (`IrqPolicySpecifiedProcessors`) plus `AssignmentSetOverride`, a KAFFINITY mask with bit i for logical processor i. Microsoft does recommend the default policy where it works, so keep the revert handy.

To find which controller each USB device is on, walk its PnP parents up to the PCI device (takes about 20 s, `Get-PnpDeviceProperty` is slow). Find the mouse by its `VID_xxxx&PID_xxxx` (the OP1 is `VID_3367&PID_1978`):

```powershell
Get-PnpDevice -PresentOnly | Where-Object { $_.InstanceId -match '^USB\\VID_[0-9A-F]{4}&PID_[0-9A-F]{4}\\' } | ForEach-Object {
  $id = $_.InstanceId
  while ($id -and $id -notlike 'PCI\*') { $id = (Get-PnpDeviceProperty -InstanceId $id -KeyName DEVPKEY_Device_Parent).Data }
  [pscustomobject]@{ Controller = ($id -split '\\')[1] -replace '&SUBSYS.*'; Device = $_.FriendlyName; Id = $_.InstanceId }
} | Sort-Object Controller, Device | Format-Table -AutoSize
```

The mouse should be the only thing on its controller, move other devices to other ports until it is. Mine was alone on `VEN_1022&DEV_15B7` (a CPU-attached controller), with the keyboard and hubs on `DEV_15B8` and the audio interfaces, webcam and Bluetooth on the chipset's `DEV_43F7`. Then pin it:

```powershell
$id  = (Get-PnpDevice -PresentOnly | Where-Object InstanceId -like 'PCI\VEN_1022&DEV_15B7*').InstanceId
$key = "HKLM:\SYSTEM\CurrentControlSet\Enum\$id\Device Parameters\Interrupt Management\Affinity Policy"
$cpu = 6
New-Item -Path $key -Force | Out-Null
New-ItemProperty -Path $key -Name DevicePolicy -PropertyType DWord -Value 4 -Force | Out-Null
New-ItemProperty -Path $key -Name AssignmentSetOverride -PropertyType Binary -Value ([BitConverter]::GetBytes([uint64]1 -shl $cpu)) -Force | Out-Null
pnputil /restart-device $id
```

This assumes the controller uses message-signalled interrupts. Mine did and so did the GPU, `MSISupported` is 1 under `Device Parameters\Interrupt Management\MessageSignaledInterruptProperties` for both, and the only shared line interrupt was IRQ 0 (system timer and HPET).

Restarting the controller was enough, no reboot needed. Pick a logical CPU the GPU driver doesn't use (in my trace that was everything except CPU 0 and CPU 1). To revert, `Remove-ItemProperty -Path $key -Name DevicePolicy, AssignmentSetOverride` and the same restart.

Check it with a second trace. For me USBXHCI.SYS DPCs moved to the pinned CPU (4.37 of 4.39 s) and its ISR went with them, nvlddmkm.sys and dxgkrnl.sys stayed on CPU 0.

## Part 5: reserve the pinned CPU

After the pin some reports still came in 0.25-0.5 ms late (3-6 a minute over 0.4 ms, off-band 112-123 a minute). Reserving the pinned CPU and its SMT sibling got rid of those, ReservedCpuSets stops the scheduler from putting other threads there[^pctuning-kms]. The value is a CPU bitmask, least significant byte first[^reservedcpusets], CPUs 6 and 7 are bits 6 and 7, so `0xC0`:

```powershell
$k = 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\kernel'
$mask = [uint64](1 -shl 6) -bor [uint64](1 -shl 7)
New-ItemProperty -Path $k -Name ReservedCpuSets -PropertyType Binary -Value ([BitConverter]::GetBytes($mask)) -Force | Out-Null
Restart-Computer
```

Reserve the CPU the controller is pinned to plus its SMT sibling (for me CPU 6 and CPU 7, two threads of one core), never CPU 0. It takes effect after a restart. To see which logical CPUs share a core you can ask Windows (`GetLogicalProcessorInformation`[^ms-glpi]):

```powershell
Add-Type -TypeDefinition @'
using System; using System.Runtime.InteropServices;
public static class Topo {
  [DllImport("kernel32.dll")] static extern bool GetLogicalProcessorInformation(IntPtr buf, ref uint len);
  public static string[] Cores() {   // SYSTEM_LOGICAL_PROCESSOR_INFORMATION is 32 bytes on x64
    uint len = 0; GetLogicalProcessorInformation(IntPtr.Zero, ref len);
    IntPtr p = Marshal.AllocHGlobal((int)len); var r = new System.Collections.Generic.List<string>();
    GetLogicalProcessorInformation(p, ref len);
    for (int off = 0; off + 32 <= len; off += 32) {
      long mask = Marshal.ReadInt64(p, off);
      if (Marshal.ReadInt32(p, off + 8) != 0) continue;   // 0 = RelationProcessorCore
      var cpus = new System.Collections.Generic.List<string>();
      for (int i = 0; i < 64; i++) if ((mask >> i & 1) == 1) cpus.Add(i.ToString());
      r.Add("core: CPUs " + string.Join(", ", cpus));
    }
    Marshal.FreeHGlobal(p); return r.ToArray();
  }
}
'@
[Topo]::Cores()
```

On the 7800X3D that gives eight lines, `core: CPUs 0, 1` to `core: CPUs 14, 15`.

To check it took, start one busy loop per logical CPU and read the per-CPU usage while they run (about 30 s):

```powershell
$jobs = 1..[Environment]::ProcessorCount | ForEach-Object { Start-Job { $end = (Get-Date).AddSeconds(20); while ((Get-Date) -lt $end) { } } }
Start-Sleep -Seconds 8
(Get-Counter '\Processor(*)\% Processor Time' -SampleInterval 1 -MaxSamples 5).CounterSamples |
  Group-Object InstanceName | Where-Object Name -ne '_total' | Sort-Object { [int]$_.Name } |
  ForEach-Object { 'CPU {0,-3} {1,5:N0} %' -f $_.Name, ($_.Group | Measure-Object CookedValue -Average).Average }
$jobs | Wait-Job | Remove-Job
```

CPUs 6 and 7 stayed at 1 % while the rest ran at 8-85 % (the loops don't load every CPU evenly, you only need the reserved pair to stay idle). Without the reservation they get loaded like everything else. The ReservedCpuSets README says older Windows 10 builds need a different route (NtSetSystemInformation), 22H2 (build 19045) took the registry value fine. To revert, `Remove-ItemProperty -Path $k -Name ReservedCpuSets` and restart.

The restart that turned the reservation on also had two smaller changes in it (Phone Link removed, HVCI and NetBIOS set to off), I didn't test those on their own. I did test BIOS Global C-state Control both ways afterwards, no difference (table above).

## Verification

| Check | How | Expected |
|---|---|---|
| Filter gone | `UpperFilters` value from Part 2; `DEVPKEY_Device_Stack` of each root hub | no USBPcap |
| Pin set | `Get-ItemProperty $key` | `DevicePolicy 4`, mask with one bit |
| Pin active | xperf dpcisr on a new trace | USBXHCI.SYS DPC time on the pinned CPU |
| Merged reports | Part 1 query on an untraced 60 s run | 0.0 /min |
| CPUs reserved | per-CPU usage under a full load (Part 5) | the reserved pair near 0 % |
| Late reports | Part 1 query | off-band near 30 /min or less, bunched 0-2 /min |

Merged reports were 0.0 a minute in every recording after the pin, 13 of them by 2026-10-26, OP1 and the second mouse, traced and untraced, quiet and with apps open, and the processor-idle test in the gotchas below.

## What is left

There's still one report about 0.25 ms late (one empty poll) on an almost fixed period, 15-22 a minute, every 3.55-3.73 s depending on the run. It's in every OP1 recording including the 2026-10-16 baseline, and nothing in this guide changed it. The second mouse (Pulsar 8K dongle), recorded on the same machine under the same conditions, has no periodic skip and 5 off-band intervals a minute, so the skip comes from the OP1.

My guess from the data is that the mouse builds its reports on its own clock rather than the host's USB microframe clock. Its 8 kHz runs about 35 ppm slow, so every ~3.5 s a poll finds no report ready and the next one carries two polls of motion. That's 2x, under the 2.5x merged threshold, and no motion gets lost. Other owners in the XBAB Tech Discord see the same and say Endgame Gear plans a firmware fix (I haven't seen Endgame Gear confirm that), one says it goes away at 4 kHz, which I haven't measured. Nothing on the PC side can change the mouse's clock. A community fix isn't realistic either, the firmware images in Endgame Gear's updater are encrypted with a block cipher and the updater sends them to the mouse as is, so the key lives in the mouse's bootloader (checked 2026-10-26).

## Gotchas and lessons learned

- Disabling processor idle made it a lot worse. `powercfg /setacvalueindex scheme_current sub_processor IDLEDISABLE 1` (no C-states on any CPU) took gaps over 0.4 ms from 3.4 to 47.9 a minute, worst 4.25 ms, and WSL wouldn't start until I reverted it. I didn't dig into why, my guess is the idle loop spinning on every thread so the pinned CPU's SMT sibling fights it for the core. Don't use it as a latency tweak without measuring. If you want to test C-states, `powercfg -setacvalueindex scheme_current sub_processor IDLESTATEMAX 1` is the narrower setting, Microsoft documents value 1 as idle depths down to C1 only[^ms-idlestatemax] so idle threads still halt instead of spinning. I didn't need it.
- BIOS Global C-state Control made no difference for me. Disabled and Auto gave the same result once the CPU was reserved (off-band 16-23 against 35 a minute, which is about the spread between two runs of the same setup). What Auto means is up to the board, so check it, Windows' `\Processor(*)\% C2 Time` counter showed every CPU idling 94-100 % in ACPI C2 on Auto (C2 is the deep core state, CC6, on AMD[^ms-idlestatemax]), so deep core sleep was on during the clean runs, the USB CPU too. Data-fabric C-states aren't visible from Windows. I'd leave it on Auto unless your own runs say otherwise, it uses less power at idle.
- With the CPU reserved, closing apps stopped mattering for report timing, runs with my usual apps open matched the quiet ones. Give it a minute or two after the apps start though, the first run after relaunching them had a burst of late reports in its first 20 s. WSL is the exception here, its memory reclaim stalled the whole machine for milliseconds.
- Pinning the GPU's interrupts off CPU 0 isn't needed for the mouse once its controller has its own reserved CPU. I tested it for frame times anyway (`DevicePolicy` 4 on the GPU, CPU 2, 3DMark Time Spy with PresentMon, 3 pinned runs between 4 and 3 unpinned ones): graphics test 2 went from 226.6-228.5 to 229.6-230.3 fps, about 1 %, the 99.9th percentile frame time and the CPU test didn't move. My card only allows one MSI message (`MessageNumberLimit` 1), so its interrupts sit on one CPU whatever the policy says. Small enough that I'd only bother if you're CPU-bound at high fps, which Time Spy doesn't test.
- Change one thing per run and write down the conditions. My reboot run changed two things at once (filter gone from the last hub, Windows Sandbox disabled) so I can't say which one helped.
- Use a traced run to diagnose, not to measure, its timing is off and only the merged count holds.
- The Steam friends-list stutter is a separate thing. It's real in games that poll the friends list when you have hundreds of friends, but it doesn't explain count spikes in MousePlotter.
- Keep the mouse alone on its controller, a keyboard on the same controller shares its interrupt path. The controller list in Part 4 shows what's on it.
