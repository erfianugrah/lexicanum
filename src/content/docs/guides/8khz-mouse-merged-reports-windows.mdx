---
title: Fixing merged reports from an 8 kHz mouse on Windows
description: Diagnosing and fixing the count spikes an 8 kHz mouse shows in MousePlotter on Windows 10 - reports that carry 2-4 polls of motion because the host serviced the USB controller late. Count the merged reports from the export, rule out USB filter drivers such as USBPcap, capture a DPC/ISR trace with WPR (and get past its 0x80010106 stop failure), read it with xperf, pin the mouse's xHCI controller interrupts to a CPU the GPU driver does not use, and reserve that CPU with ReservedCpuSets to remove the leftover jitter.
author: "Erfi Anugrah"
category: workstations
---

An 8 kHz mouse sends a report every 125 us. When Windows services the USB controller late, the mouse cannot send on time, so the next report carries the motion of two to four polls. In MousePlotter that shows as isolated dots far outside the counts band, and the counts axis stretches until the normal trace is a solid block. This guide takes one such machine from 66.5 merged reports a minute to zero: it measures the problem from the export, removes a USB filter driver that made it worse, traces where the delay comes from, moves the mouse's controller interrupts off the CPU the GPU driver uses, and then reserves that CPU so nothing else is scheduled there, which removed the remaining timing jitter.

Prerequisites: admin PowerShell on the Windows box, MousePlotter run elevated (it needs ETW for kernel timestamps), and the Windows Performance Toolkit for the trace step. The numbers are from one machine, measured on 2026-10-16, 2026-10-24 and 2026-10-26; the closing sections say what was and was not shown.

### What the export can tell you

Every MousePlotter HTML export embeds the raw CSV: per report, `x`, `y`, `eventTime (ms)` (kernel, from ETW) and `userTime (ms)` (user space). Three numbers separate the failure modes:

| Number | Definition | Healthy 8 kHz |
|---|---|---|
| Merged reports | Moving reports (4+ counts) carrying more than 2.5x the median motion of the 21 reports around them | 0 |
| Bunched deliveries | Intervals under 40 % of the median interval (several reports delivered together) | about 1 a minute |
| Off-band intervals | Intervals outside the median +-20 % | about 30 a minute |

A merged report points the same way as the motion around it and carries 2.5-3.5x the local median. On the bad runs here, 97 % of the outliers matched that shape and sat right after a run of late (0.25-0.5 ms) or bunched deliveries, and both mice showed it, so the delay was on the host.

### Why a late DPC means a merged report

| Constant | Value | Why it matters |
|---|---|---|
| Poll interval at 8 kHz | 125 us | Any delay longer than this misses a poll |
| DPC ordering | DPCs queued on one CPU run one after another | A long DPC from another driver delays the USB completion queued behind it |
| Where a DPC runs | Normally on the CPU that took the interrupt | Moving a device's interrupt moves its DPCs with it |
| Windows 10 raw input | Background raw-input listeners get every report | Windows 11 throttles background listeners to about 125 Hz (KB5028185); Windows 10 22H2 does not[^boosterx-raw] |

### The numbers to expect

OP1, 60 s of fast circles, quiet host (browser, Discord and WSL closed):

| Config | Off-band /min | Bunched /min | Merged /min | Max counts in one report |
|---|---|---|---|---|
| Baseline 2026-10-16 | 31 | 1 | 0 | 15 |
| USBPcap filter installed | 769 | 135 | 66.5 | 75 |
| USBPcap removed from the mouse's hub | 251 | 46 | 16.8 | 50 |
| + reboot (filter gone from every hub), Windows Sandbox off | 126 | 19 | 10.1 | 38 |
| + controller pinned to CPU 4 | 112 | 32 | 0.0 | 31 |
| Controller pinned to CPU 6 | 123 | 13 | 0.0 | 17 |
| + CPUs 6 and 7 reserved, restart (two runs) | 16-23 | 0 | 0.0 | 13-26 |
| Same, BIOS Global C-state Control on Auto instead of Disabled | 35 | 2 | 0.0 | 28 |
| Same, usual apps open (Discord, browser, chat apps; WSL off), two runs | 16-24 | 0-1 | 0.0 | 14-33 |

The pin removes the merged reports; reserving the pinned CPU brings the timing back to the baseline or better. Of the 16-35 off-band intervals left, 15-22 a minute are the mouse's own skipped poll (see [What is left](#what-is-left)).

Text version: the mouse's controller raised its interrupts on CPU 0, where the NVIDIA driver's DPCs and the GPU's interrupts also ran, so a long NVIDIA DPC held the USB completion. After the pin, the controller's interrupts and DPCs run on CPU 6 and the GPU work stays on CPU 0.

## Part 1: measure the merged reports

1. Close what you can: browsers, Discord, Steam, tray apps. On Windows 10 each of them receives every raw mouse report. Shut WSL down if you use it (`wsl --shutdown`); its memory reclaim caused 5 s stalls on this machine earlier.
2. Run MousePlotter elevated, set its DPI field to the mouse's real CPI, record 60 s of continuous fast circles and sweeps, and Export.
3. Pull the CSV out of the export into `run.csv` (it is embedded in the HTML), then count:

```sql
-- duckdb: merged reports, bunched and off-band intervals per minute
create table d as select row_number() over () i, x, y,
  "eventTime (ms)" t,
  "eventTime (ms)" - lag("eventTime (ms)") over () dt,
  sqrt(x*x + y*y) cnt
  from read_csv('run.csv');
create table f as select *, median(cnt) over (order by i rows between 10 preceding and 10 following) loc
  from d where t > 1000 and t < (select max(t) - 1000 from d);
select
  round(count(*) filter (where dt < 0.8*m or dt > 1.2*m) * 60000.0 / any_value(span)) off_band_per_min,
  round(count(*) filter (where dt < 0.4*m) * 60000.0 / any_value(span)) bunched_per_min,
  round(count(*) filter (where cnt >= 4 and cnt > 2.5 * greatest(loc, 4)) * 60000.0 / any_value(span), 1) merged_per_min,
  round(max(cnt)) max_counts
from f, (select median(dt) m, max(t) - min(t) span from f) q;
```

Merged reports above zero, with gaps over 0.4 ms staying rare, come from a host that services the controller late. Large gaps (1-6 ms) arriving on a fixed period are a different problem: a timer stalling the whole system.

## Part 2: remove USB filter drivers

A class filter on the USB host-controller class sits in the stack of every root hub and every USB device. On this machine USBPcap (installed for protocol captures) was the only non-Microsoft one, and removing it cut merged reports from 66.5 to 16.8 a minute.

Check what is registered:

```powershell
(Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Class\{36FC9E60-C465-11CF-8056-444553540000}').UpperFilters
```

To take USBPcap out without uninstalling it, remove it from that value, then restart each root hub that carries it (devices behind the hub drop for about a second):

```powershell
$k = 'HKLM:\SYSTEM\CurrentControlSet\Control\Class\{36FC9E60-C465-11CF-8056-444553540000}'
$rest = @((Get-ItemProperty $k).UpperFilters | Where-Object { $_ -ne 'USBPcap' })
if ($rest) { Set-ItemProperty $k UpperFilters $rest } else { Remove-ItemProperty $k UpperFilters }
Get-PnpDevice -PresentOnly | Where-Object InstanceId -like 'USB\ROOT_HUB*' | ForEach-Object { pnputil /restart-device $_.InstanceId }
```

Windows can refuse a restart while a device behind the hub is in use (an audio interface was, here); that hub keeps the filter until a reboot. The System log names the process that blocked it: Kernel-PnP event 225, here `audiodg.exe` and the audio interface's control panel. Check a hub's stack with `Get-PnpDeviceProperty -InstanceId <hub> DEVPKEY_Device_Stack`. The entries are driver object paths such as `\Driver\USBPcap`, so a script has to match the last path segment: a check that compared whole entries with `USBPcap` never matched, never restarted a hub and still reported the filter gone.

:::caution
Do not disable the USBPcap service while it is still listed in UpperFilters. Windows then cannot load the filter and the USB stack fails to start, which can leave you without keyboard and mouse. Change the registry value, not the service.
:::

## Part 3: trace the DPCs and interrupts

The Windows Performance Toolkit installs alone from the ADK, without the rest of it:

```powershell
winget install --id Microsoft.WindowsADK --override "/features OptionId.WindowsPerformanceToolkit /quiet"
```

Record a trace across a MousePlotter run. Use `GeneralProfile`: the built-in `CPU` profile has no DPC or interrupt events (check with `wpr -profiledetails`).

```powershell
wpr -start GeneralProfile
# record in MousePlotter for 60 s
wpr -stop "$env:USERPROFILE\Downloads\mouse-dpc.etl" -skipPdbGen
```

A plain `wpr -stop` failed every time on this machine with `Cannot change thread mode after it is set` (0x80010106), and the session kept recording afterwards. Adding `-skipPdbGen` (skip the PDB/NGEN merge, which a DPC/ISR summary does not need) made the stop succeed. An unelevated `wpr -status` does not see the elevated session; check from the admin window, and `wpr -cancel` a leftover session before the next measurement, or that measurement runs under the trace.

Tracing costs MousePlotter its kernel timestamps: thousands of rows fall back to user-space time, so the timing columns of a traced run are not comparable. Measure in an untraced run first, trace in a second one. The merged count uses report counts, not timestamps, so it stays valid under a trace.

Summarise per driver and per CPU:

```powershell
& "C:\Program Files (x86)\Windows Kits\10\Windows Performance Toolkit\xperf.exe" -i mouse-dpc.etl -o dpcisr.txt -a dpcisr -summary
```

On this machine (628 s trace):

| Module | DPCs | DPC time CPU 0 / CPU 1 | Long DPCs |
|---|---|---|---|
| USBXHCI.SYS (USB controllers) | 432,164 | 4.48 s / 0.76 s | 32 of 128-256 us, 1 of 256-512 us |
| nvlddmkm.sys (NVIDIA driver) | 227,323 | 4.18 s / 0.19 s | 3,827 of 128-256 us, 13 of 256-512 us, 1 of 0.5-1 ms, 1 of 1-2 ms, 16 of 2-4 ms |
| storport.sys (NVMe) | 187,087 | 0.14 s / 0.21 s (spread over all cores) | 12 of 128-256 us, 7 of 256-512 us |

The GPU's interrupts (dxgkrnl.sys ISR, 3.67 s) ran on CPU 0 as well. USB and NVIDIA shared CPU 0, and 3,827 NVIDIA DPCs in 628 s ran longer than one poll interval. The GPU is busy during a recording because Windows redraws the cursor for every report.

## Part 4: pin the controller interrupts

valleyofdoom's PC-Tuning guide recommends this for xHCI controllers (move them to an underused CPU, check the result with an xperf DPC/ISR report, keep each ISR and its DPC on the same CPU)[^pctuning-kms]. Microsoft documents the per-device affinity policy under the device's registry key[^ms-irq-affinity]: `DevicePolicy` 4 (`IrqPolicySpecifiedProcessors`) plus `AssignmentSetOverride`, a KAFFINITY mask with bit i for logical processor i. Microsoft recommends the default policy where it applies, so keep the revert at hand.

Find the controller the mouse is on (here `PCI\VEN_1022&DEV_15B7`), then:

```powershell
$id  = (Get-PnpDevice -PresentOnly | Where-Object InstanceId -like 'PCI\VEN_1022&DEV_15B7*').InstanceId
$key = "HKLM:\SYSTEM\CurrentControlSet\Enum\$id\Device Parameters\Interrupt Management\Affinity Policy"
$cpu = 6
New-Item -Path $key -Force | Out-Null
New-ItemProperty -Path $key -Name DevicePolicy -PropertyType DWord -Value 4 -Force | Out-Null
New-ItemProperty -Path $key -Name AssignmentSetOverride -PropertyType Binary -Value ([BitConverter]::GetBytes([uint64]1 -shl $cpu)) -Force | Out-Null
pnputil /restart-device $id
```

The pin assumes the controller uses message-signalled interrupts. It did here, as did the GPU: `MSISupported` is 1 under `Device Parameters\Interrupt Management\MessageSignaledInterruptProperties` for each, and the only shared line interrupt was IRQ 0 (system timer and HPET).

The controller restart was enough here; no reboot. Pick a logical CPU the GPU driver does not use (in the trace above that was everything except CPU 0 and CPU 1). Revert with `Remove-ItemProperty -Path $key -Name DevicePolicy, AssignmentSetOverride` and the same restart.

Confirm with a second trace: on this machine USBXHCI.SYS DPCs moved to 4.37 of 4.39 s on the pinned CPU and its ISR moved with them, while nvlddmkm.sys and dxgkrnl.sys stayed on CPU 0.

## Part 5: reserve the pinned CPU

After the pin, scattered reports still arrived 0.25-0.5 ms late (3-6 a minute over 0.4 ms, off-band 112-123 a minute). Reserving the pinned CPU and its SMT sibling removes them: ReservedCpuSets keeps the scheduler from placing other threads there[^pctuning-kms]. The value is a CPU bitmask, least significant byte first[^reservedcpusets]; CPUs 6 and 7 are bits 6 and 7, `0xC0`:

```powershell
$k = 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\kernel'
$mask = [uint64](1 -shl 6) -bor [uint64](1 -shl 7)
New-ItemProperty -Path $k -Name ReservedCpuSets -PropertyType Binary -Value ([BitConverter]::GetBytes($mask)) -Force | Out-Null
Restart-Computer
```

Reserve the CPU the controller is pinned to and its SMT sibling (here CPU 6 and CPU 7, two threads of one core). Never reserve CPU 0. A restart applies it.

Check that it took: put a busy thread on every CPU for about 10 s (CpuStres from Sysinternals, or any load tool) and watch per-CPU usage in Task Manager. Here CPUs 6 and 7 stayed at 0 % while the other 14 ran at 100 %. The ReservedCpuSets README says older Windows 10 builds need another route (NtSetSystemInformation); 22H2 (build 19045) honoured the registry value. Revert with `Remove-ItemProperty -Path $k -Name ReservedCpuSets` and a restart.

The restart that activated the reservation also carried two smaller changes (Phone Link removed, HVCI and NetBIOS explicitly off), which were not tested on their own. BIOS Global C-state Control was tested both ways afterwards and made no difference (table above).

## Verification

| Check | How | Expected |
|---|---|---|
| Filter gone | `UpperFilters` value from Part 2; `DEVPKEY_Device_Stack` of each root hub | no USBPcap |
| Pin set | `Get-ItemProperty $key` | `DevicePolicy 4`, mask with one bit |
| Pin active | xperf dpcisr on a new trace | USBXHCI.SYS DPC time on the pinned CPU |
| Merged reports | Part 1 query on an untraced 60 s run | 0.0 /min |
| CPUs reserved | per-CPU usage under a full load (Part 5) | the reserved pair near 0 % |
| Late reports | Part 1 query | off-band near 30 /min or less, bunched 0-2 /min |

On this machine merged reports were 0.0 a minute in every recording after the pin, 13 of them by 2026-10-26: OP1 and second-mouse runs, traced and untraced, quiet and with apps open, and the processor-idle experiment in the gotchas below.

## What is left

One report about 0.25 ms late (one empty poll) on a near-fixed period: 15-22 a minute, every 3.55-3.73 s across runs, in every OP1 recording, the 2026-10-16 baseline included, and through every change in this guide. The second mouse (Pulsar 8K dongle), recorded on the same machine in the same conditions, has no periodic skip and 5 off-band intervals a minute, so the skip is in the OP1, not the PC.

Mechanism (reasoned from the data): the mouse builds reports on its own clock instead of the host's USB microframe clock. Its 8 kHz runs about 35 ppm slow, so every ~3.5 s one poll finds no report ready and the next report carries two polls of motion. That is 2x, under the 2.5x merged threshold, and no motion is lost. Owners in the XBAB Tech Discord report the same and say Endgame Gear plans a firmware fix (not confirmed by Endgame Gear here); one says it stops at 4 kHz, which was not measured here. No host setting can change the mouse's clock.

## Gotchas and lessons learned

- **Disabling processor idle made it much worse.** `powercfg /setacvalueindex scheme_current sub_processor IDLEDISABLE 1` (no C-states on any CPU) took gaps over 0.4 ms from 3.4 to 47.9 a minute, worst 4.25 ms, and WSL would not start until it was reverted. The cause was not investigated; one candidate is the idle loop spinning on every thread, so the pinned CPU's SMT sibling competes for the core. Do not use it as a latency tweak without measuring. If you want to test C-states, `powercfg -setacvalueindex scheme_current sub_processor IDLESTATEMAX 1` is the narrower setting: Microsoft documents value 1 as allowing idle depths down to C1 only[^ms-idlestatemax], so idle threads still halt instead of spinning. It was not needed here.
- **BIOS Global C-state Control made no difference here.** Disabled and Auto gave the same result once the CPU was reserved (off-band 16-23 against 35 a minute, within the spread between two runs of one setup). Auto is board-defined, so check what it does: Windows' `\Processor(*)\% C2 Time` counter showed every CPU idling 94-100 % in ACPI C2 under Auto here (C2 is the deep core state, CC6, on AMD[^ms-idlestatemax]), so deep core sleep was on during the clean runs, the USB CPU included. Data-fabric C-states are not visible from Windows. Leave it on Auto unless your own runs show otherwise; it lowers idle power.
- **With the CPU reserved, closing apps no longer mattered for report timing.** Runs with the usual apps open matched the quiet runs. Measure a minute or two after apps start, though: the first run after relaunching them had a burst of late reports in its first 20 s. WSL is the exception on this machine: its memory reclaim stalled the host for milliseconds.
- **Change one thing per run, and record the conditions.** The reboot run changed two things at once (filter gone from the last hub, Windows Sandbox disabled) and cannot say which helped.
- **A traced run is a diagnosis run, not a measurement.** Its timing is distorted; only the merged count survives.
- **The Steam friends-list stutter is a different problem.** It is real in games that poll the friends list with hundreds of friends; it does not explain count spikes in MousePlotter.
- **Keep the mouse alone on its controller.** A keyboard on the same controller shares its interrupt path; check with the PnP parent chain of each USB device.
