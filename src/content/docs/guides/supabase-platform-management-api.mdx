The Management API makes projects, keys, config, usage and lifecycle
programmable. The docs cover the endpoints but not the platform layer on top
of them: the provisioning loop, the rate budget, the metering, the OAuth
paths and the pause playbook. This guide covers that layer. Every number in it was measured against the live API on throwaway projects, on
2026-08-17/18 unless the text carries another date (later checks run to
2026-10-10); where something is gated or untested, it says so. To
follow along: a Supabase org on a paid plan, a personal access token with
Management API access, and throwaway projects you will delete when done. The
[placement doc](/reference/supabase-multi-tenant-placement/) decides where a
tenant should live; this guide is the mechanism that puts it there.

## 1. Decide who owns the project

Two integration shapes, differing on who owns the Supabase organization and
the billing relationship:

- **You provision on their behalf** - your org, your PAT, one project per
  tenant, users never see Supabase. White-label, you hold the billing
  relationship. The rest of this guide is this shape.
- **They bring their own backend** - the user's org, connected to your app
  through the Management API OAuth2 flow. You get a scoped token; they keep
  the direct billing relationship. Section 5 has the measured surface.

You can offer both. The project-claim flow is the (gated) bridge from the
first to the second when a tenant outgrows you. On a normal paid org the
claim route answers
`404 {"message":"Cannot POST /v1/oauth/authorize/project-claim"}`: the route
does not exist for the credential class, which is different from being
forbidden. On a `platform`-plan org on 2026-08-24 the claim, `oauth/apps`,
and `projects/{ref}/transfer` routes all answered `404` as well. The
BYO-backend bridge is off by default regardless of plan, so the two shapes
are not separable in practice until the bridge is enabled for the account.
For a time-boxed, network-restricted, role-scoped grant instead of a full
project handover, the JIT database access invite route works on a
`platform`-plan org: `POST /database/jit/invite` (email + role + `expires_at` +
`allowed_networks` CIDRs) -> `200` with an `invite_id`, and
`DELETE /database/jit/invite/{id}` -> `200` (measured 2026-08-24). The identical
invite on a Pro org is rejected with a `500` (A/B measured 2026-08-25, `S15`).
That `500` belongs to the invite route. On a Pro org (Postgres 17, measured
2026-10-10) the grant routes `PUT /jit-access` with `{state}` and
`PUT /database/jit` answered `200` in all five runs (`JA01c`, `JA01d`), so on
Pro use the grant route and do not use the invite route. The grant route needs
SSL enforcement on first, takes the key `roles` and reads `expires_at` as epoch
seconds; the
[JIT database access page](/reference/supabase-jit-database-access/) has the measured surface.

### Scoped personal access tokens

Documented: scoped tokens "start with `sbp_fc`" and carry only the
organisations, projects and permissions chosen at creation; they are created
from the access tokens settings in the Dashboard, with an expiry up to one year
out.[^sb-pat] The GA changelog adds that `supabase whoami` does not work with
project- or organisation-scoped tokens.[^sb-scoped-pat] Both sentences are the reading of a summarising fetch on 2026-10-10, not a verbatim copy.

Measured 2026-10-10 (`SP01`, `SP05`, `SP06`, one run each, a Pro org):

- Creation has no API. The public `/v1` OpenAPI document (115 paths, 170
  operations) has no access-token creation operation; the only token-named
  routes are the OAuth token and revoke routes and the project claim-token
  routes. The route the Dashboard uses, `GET /platform/profile/access-tokens`,
  answers a PAT `401 {"message":"Unsupported access token"}`, while
  `GET /v1/profile/access-tokens` and `GET /v1/access-tokens` answer `404` and
  `GET /v1/organizations` answers `200`. Only GET was sent, so the Dashboard
  route's POST was not tried and no token was minted.
- The lab token has the `sbp_fc` format; which scope it was created with was
  not read. With it, `GET /v1/profile` answers `403 {"message":"This endpoint
  requires a user-scoped access token"}`, and the Supabase CLI 2.120.0 exits 1
  on `supabase whoami` (`unexpected get profile status 403`) while
  `supabase orgs list` and `supabase projects list` exit 0. That agrees with the
  changelog sentence and does not test it, because the token's scope is unknown
  and "token is scoped" is not separated from "token lacks a user-level grant".
- The SQL read-only boundary has a control. `select 1` answers `201` on both
  `/database/query` and `/database/query/read-only`; `create table` through the
  read-only route is refused with `400` and
  `ERROR: 25006: cannot execute CREATE TABLE in a read-only transaction` and the
  table is absent on read-back, while `/database/query` answers `201` and the
  table is present.

Not measured, each with a named prerequisite in the experiment's run log: an
organisation-scoped token on production (does it create projects, see later
projects, and draw on the same request budget as its owner's token), the
per-permission matrix and the body of the `403`, SQL read-only without the
Database read-write permission, the project boundary of a project-scoped
token, whether a token follows its creator's current role (needs a second human
member), revocation latency, and immutability and expiry (Dashboard-only, so
doc-cited and not tested). A run of the organisation-scoped module with the lab
token standing in created a project (`201`, 3383 ms), listed, read and deleted
it; it describes the lab token, not an organisation-scoped one (`SP04`).

## 2. Provision a tenant

One call creates a project; the rest is setup around it.

- `POST /v1/projects` with `organization_slug`, a strong generated `db_pass`,
  and a region. Create -> `ACTIVE_HEALTHY` measured 131-159 s on paid Micro,
  12-13 s on a free org.
- Smart region selection works on a normal paid org:
  `region_selection: {type: "smartGroup", code: "apac"}` was accepted (201)
  and the platform picked `ap-northeast-2`. Defer the city choice instead of
  pinning per tenant.
- Fresh projects refuse their first
  `/auth/v1/admin/users` write after reporting `ACTIVE_HEALTHY`: 5 of 5 with
  `500 unexpected_failure`, accepting the second call one poll later
  (2026-08-04), and 2 of 2 with `500 "Database error checking email"` for
  ~10 s after passing the per-service health poll (2026-08-03). Poll
  `GET /v1/projects/{ref}/health?services=auth&services=rest&services=db`,
  then retry the first write with backoff; do not treat it as a finding.
- Fetch keys with `GET /v1/projects/{ref}/api-keys?reveal=true` and select by
  `name` OR `type` - new projects carry both legacy JWTs and the new
  `sb_publishable_`/`sb_secret_` shapes.
- Configure services with the config endpoints (auth, PostgREST, storage,
  realtime, functions + secrets). The OAuth server flips on with
  `PATCH /v1/projects/{ref}/config/auth`
  `{oauth_server_enabled: true, oauth_server_authorization_path: ...}` -
  measured 200.
- Treat a create that failed as possibly landed (2026-10-10). A
  `POST /v1/projects` whose answer was lost to a 1 s client cap (`LO04`), to a 4 s
  client timeout over an 8 s hold, or replaced by a `500` after upstream created
  the project (`MF02`) left 1 project with that name in each case. An identical
  re-send answers `400 Project with name "<name>" already exists in your
  organization.` (`LO04`, n=1; `MF02`), which reads as "look it up by name". Keep the name stable across retries of one logical
  create. The same-name `400` is the only duplicate protection observed: a retry
  that generates a fresh name per attempt is not covered by it and was not run.
  [Control-plane fault behaviour](#control-plane-fault-behaviour) has the
  per-client retry counts.

## 3. Know the sizing floors

| Org class | Nano | Floor | Pause |
|---|---|---|---|
| Paid (Pro) org | rejected three ways: create `400 Minimum instance size on paid plans is Micro`, addon PATCH `400 addon_variant: Invalid input`, absent from `available_addons` | Micro, always-on | `400 Project is not free-tier` |
| Free org | accepted (201) - and there is NO compute addon catalogue at all | shared/free compute | full lifecycle: pause -> INACTIVE, restore wakes in 162-204 s, data API answers `HTTP 540 Project paused` while parked |
| Legacy free-era project inside a paid org | n/a | keeps its paused state after the upgrade | one-way door: once restored it cannot be re-paused - pause follows the org's current plan, not the project's lineage |

Scale-to-zero economics are part of the Supabase for Platforms
programme[^sfp]. Measured 2026-08-24: an SfP organization is the `platform`
plan, and Nano is the platform plan's create default - the SfP-prescribed
create (no `desired_instance_size`) provisions `infra_compute_size: nano`
(224MB `shared_buffers`) and the project can pause. Nano is not a select or
resize target on any plan. On a normal paid org there is no idle discount,
which is the cost premise the
[tenant placement doc](/reference/supabase-multi-tenant-placement/) is built
on.

## 4. Budget the rate limit

Measured on a normal paid org, on a cheap scoped read:

- Every response carries `x-ratelimit-limit`, `x-ratelimit-remaining`,
  `x-ratelimit-reset`. The limit read 120, decrementing 1:1 per call. Read
  the header; never infer the budget.
- A deliberate burst tripped
  `429 {"message":"ThrottlerException: Too Many Requests"}` at request 118
  with `retry-after: 60` and recovered after the window. The breach on this
  endpoint is the API's own machine-readable JSON - but aggressive polling
  elsewhere has produced a non-JSON interstitial from the edge layer, so
  treat "non-JSON body" and "JSON 429" as the same back-off signal.
- The budget is cumulative across a user's PATs (measured 2026-08-18, `L01b`,
  on one cheap scoped read): alternating two tokens from the same user on that
  route, each token's `x-ratelimit-remaining` drops on the OTHER token's calls -
  one shared counter per user per scope, on that route. PAT sharding does not
  multiply the budget on the route measured.
- `x-ratelimit-remaining` is a per-route counter at limit 120 (measured
  2026-10-10, `SP10`, one token): the same route read 117, 116, 115, 114 on four
  calls, and two alternated routes (`/organizations`, `/projects`) kept separate
  sequences (113 then 112, and 118 then 117). A two-token comparison is valid
  only on one route; across two routes it shows two counters, not two budgets.
  The Management API introduction documents 120 requests per minute, per user,
  per project or organisation, per endpoint[^sb-mgmt-ratelimit]; `SP10` agrees
  with the documented scope. Whether the header separates
  two tokens of one user on a given route was not re-measured in `SP10`, which
  used one token.

At fleet scale, build the client as a queue with a token bucket.

## 5. Let users bring their own backend

The OAuth2 flow for the Management API: register an OAuth app, the user
approves, you hold a scoped access/refresh pair.[^oauth-integration]
Measured surface on a normal paid org:

- Unknown `client_id` at `/v1/oauth/authorize` ->
  `422 {"message":"Unrecognized client_id"}`. Client validation fires
  before session validation, so the no-session redirect is only observable
  with a real client_id.
- The token lifecycle, measured 2026-08-18 after a real consent: refresh
  grants return 24-hour access tokens AND a NEW refresh token every time -
  rotate or lose the grant. The token is org-scoped: it sees exactly the
  org approved at consent (1 org, its 3 projects), not the account's other
  orgs. Revocation answers 204 and the refresh grant fails immediately
  with 404 - zero measurable lag.
- The `jwt-bearer` token grant validates parameters before any gating
  (`422 Required parameter: client_id`).

The project's OWN OAuth 2.1 server (Supabase-as-IdP for third-party apps) is
a separate surface. It is fully headless-automatable and its tokens carry
`client_id`, which RLS can read. Measured 2026-08-18:
`auth.jwt() ->> 'client_id'` in a policy showed a row to the matching
client's token and hid it from a second client of the same user, so a
shared project can hold per-client permissions as well as per-user ones.

## 6. Meter what tenants consume

Metering has three layers, all measured.
[Per-project cost attribution](/guides/supabase-per-project-cost-attribution/)
is the full build, and also covers the non-tenant case of one consolidated
org wanting per-project chargeback.

1. The invoice already itemises usage per project ref (compute, disk,
   egress, storage, PITR, custom domains) with quantity and rate. The plan
   fee, monthly active users (MAU), function invocations, realtime, and discounts are org-level
   aggregates, so splitting them per tenant takes an allocation policy.
2. Between invoices, estimate from the compute SKU in `billing/addons`,
   `pg_database_size()` and the Storage listing (exact to the byte),
   `usage.api-counts` (exact, ~1 min lag). No per-service
   egress bytes exist in the public per-project API.
3. Your own gateway meters in real time: exact for anything transiting it, and
   scoped keys mean no god-mode PAT in scrapers (measured: 200 with 278
   metric families for the allowed key, 403 deny-by-default elsewhere,
   ~1 s audit flush).

## 7. Move tenants when they outgrow the placement

Cross-project trust (third-party JWKS) makes a tenant's tokens verifiable on
their new project, with two measured edges: refresh only works at the
issuing project (`400 refresh_token_not_found` verbatim at the trusting
one), and key rotation needs a maintenance window (the trusting project's
cache does not re-resolve on any observed timeline). The build
recipes:
[shared tier](/guides/supabase-shared-tenancy/),
[promotion](/guides/supabase-tenant-promotion/),
[consolidation](/guides/supabase-tenant-consolidation/); the decision
framework is the
[placement doc](/reference/supabase-multi-tenant-placement/), and what each
operation costs in client-visible downtime is in
[platform operation costs](/reference/supabase-platform-operation-cost/).

## 8. Gotchas and lessons learned

- Deleting a project has a tail: a delete returns ~2 s but the project
  lingers in lists briefly; batch deletes need canary batches.
- A parked project loses its public DNS record. The `HTTP 540 Project
  paused` the data API returns is a transient, measured seconds after the pause
  completed while DNS was still live or cached; at 13 and 50 minutes parked the
  hostname answers NXDOMAIN on independent public resolvers, with
  `db.<ref>` gone too (September 2026). A client has to handle the resolution
  failure; once teardown finishes there is no 540 left to map to a 503.
- Restores are slow: a legacy project exceeded a 20-min wake bound
  before coming healthy; free-org restores measured 162-204 s. Wake ahead
  of the user, not on their click.
- Parking has a duration too, and a settle period follows a wake
  (2026-09-09, `Z01`). On a platform-plan project `POST /pause` reached
  `INACTIVE` in 53-71 s (n=4) and `POST /restore` reached `ACTIVE_HEALTHY` in
  168-222 s (n=3). A pause issued the moment the org listing first reported
  `ACTIVE_HEALTHY` answered `400` and the project stayed healthy; the same
  call succeeded after the settle.
- Three project-scoped reads answer `200` with an empty result on a parked
  project rather than an error (2026-09-09, `Z01`), so a status code cannot
  separate "nothing to report" from "could not look": `GET /api-keys`
  returned `[]`,
  `GET /advisors/performance` returned `{"lints":[]}` and
  `GET /config/database/pooler` returned `[]`. A fleet-wide advisor or key
  sweep scores every parked tenant clean. `/advisors/security` looks like a
  fourth and is not one - a fresh project's lint list is empty awake as well.
- Sixteen endpoints change status when parked (2026-09-09, `Z01`): `544` carrying
  `"Connection terminated due to connection timeout"`, which costs the caller
  the full timeout (`/database/migrations` took 20.0 s), seven answering `500`
  for what is an expected project state, `/health` answering
  `400 "No active services available"` and `/postgrest`
  `404 "Postgres config not found"`.
- There is no API-observable pause timestamp (2026-09-09, `Z01`).
  `GET /projects/{ref}` carries
  `status` and `created_at` only, the org listing adds `inserted_at`, and
  `/actions` is Continuous Integration action runs rather than lifecycle
  events, so a check-back later reads the state as a binary and the moment it
  changed exists only if something was sampling when it happened.
- Two of the 52 parameter-free GETs returned live credential material to a
  PAT holder in full rather than redacted (2026-09-09, `Z01`), so a PAT is
  full project access rather than a read-only analytics credential. The run
  log records the count and the shape of that finding rather than the two
  paths.
- The staging control plane never exercised auto-pause. Twelve nano projects
  on a staging platform-plan org, parked 2026-09-09 and read back 13 days
  later, were all still `ACTIVE_HEALTHY`, while over the same window both
  free-plan projects on a production org went `INACTIVE` on their own -
  including an untouched control. Run the auto-pause arm against production
  free-plan projects. Staging PATs also expire after 24 hours; every `401` in
  that run was expiry rather than revocation.
- Hibernation was not reachable on any account available here (2026-09-09).
  Four ladder rungs up to 2 hours idle on a production free-plan nano
  project returned no `project_hibernating` in `validation_errors`, and the
  first request of each
  rung cost 0.447-0.763 s against 0.047-0.082 s on the follow-ups that came
  after it - a penalty that does not scale with idle length, since 122 minutes
  looked like 32. A wake check therefore needs a threshold over 3 s rather
  than "elevated over baseline"; the four longer rungs (4 h to 48 h) never
  ran.
- Two of the arms above exist as modules that have not run as modules. The
  73-write figure of 2026-09-09 came from throwaway scripts and `Z02` has
  never executed, so nobody has reproduced it; `Z04` refuses to fire until all twelve fleet
  projects are parked and they never park on staging, so nothing has woken an
  automatically paused project - the zero-waker result is the manual-pause
  path only.

### Control-plane fault behaviour

Measured 2026-10-10 on a Pro org in `ap-southeast-1` (`MF01` to `MF05`). Every
fault was injected through a local proxy in front of `api.supabase.com`; no
real 5xx was observed, so how each client reacts to a real 5xx body (an HTML
interstitial, say) is not measured. `error-before` means the proxy answered
without contacting upstream; `error-after` means it forwarded the request,
upstream completed it, and the proxy replaced the answer with the error.
Attempt counts are proxy-log rows. One trial per cell; the development and final
runs gave the same counts wherever both measured a cell.

| Client | Reads (GET) | Writes (POST, PUT, DELETE) | Slow answer |
|---|---|---|---|
| Lab harness `mgmt()` (`MF01`, `MF02`) | 1 attempt on 500, 502, 503 and 504; the status is returned, not thrown | no retry; the caller gets the 500 | throws `TimeoutError` at 30001 ms on its 30 s default; the proxy still forwarded and upstream answered 200 |
| Lab harness `functionPresent()` (`MF01`) | retries 429 only, a fixed 15 s sleep: 3 attempts in 30144 ms for two 429s; a 500 on the read returns `present: false` with `status` 500 after 1 attempt | n/a | n/a |
| supabase CLI 2.120.0 (`MF03`, `MF05`) | 6 attempts on 500, 502, 503 and 504, 3-4 ms apart first to last, exit 1; five 500s then upstream healthy: 6 attempts, exit 0; six 500s: exit 1; 429 is not retried (1 attempt) | PUT (`ssl-enforcement update`) and DELETE (`projects delete`, `domains delete`) on 500: 6 attempts each; POST (`projects create`, `secrets set`) on 500: 1 attempt; POST `secrets set` on 502, 503, 504 and 429: 1 attempt each | 60 s per attempt: a 100 s hold gave attempts at 0, 60, 120, 180, 240 and 300 s and exit 1 after 360220 ms; a held POST is not resent, so `projects create` held 75 s exited 1 after 60448 ms while the project was created |
| OpenTofu 1.13.1, provider `supabase/supabase` 1.11.0 (`MF04`, `MF05`) | project read: 4 attempts on a persistent 503 (plan exit 1 after 6240 ms), 2 attempts on a single 500 or a single 429 (plan exit 0) | POST, PATCH and DELETE on 500: 1 attempt, not retried | a 100 s hold on the project read: 1 attempt, plan exit 0 after 103298 ms; a `create` held 130 s: apply exit 0 after 132978 ms, 1 POST |

- A create answered `500` after upstream created the project leaves the
  provider's state empty and an orphan upstream. The plain re-apply sends 1
  POST and gets `400` (the name exists in the org), leaving the orphan; after
  the orphan was deleted through the API, the re-apply exited 0 in 3468 ms with
  1 resource in state (`MF04`). The provider's own error text in the first lines
  was only "Client Error". The CLI leaves the same orphan: `projects create`
  answered `500` after upstream created it exits 1 with 1 project carrying the
  name (`MF03`). `tofu import` of the orphan was not run.
- Partial applies converge as follows (`MF04`, one trial each). A settings
  write answered `500` before upstream leaves the project in state and the
  settings not: the next plan exits 2. A settings write that landed upstream but
  answered `500` converges: the next plan exits 0 with no pending change. A
  DELETE that landed but answered `500` leaves a state entry that the next
  destroy removes cleanly, because the GET and DELETE both answer `404` and the
  provider accepts that.
- No tool duplicated a POST in any trial (`MF05`); the same-name `400` is the
  only duplicate protection observed (`MF02`).
- Not measured: real 5xx bodies, connection-level faults (reset, refused, TLS or
  DNS failure), PATCH through the CLI, writes answered 502, 503, 504 or 429 in the
  provider, other provider resources, and any documented retry or idempotency
  behaviour of the CLI, the provider or the API (no docs were read for this).

## What to do about it

A practice with no module id is a design choice rather than a
result: canary batch sizes and token-bucket parameters beyond 120 per minute
per user are unmeasured. No Management API operation restarts a parked
project's compute, so there is no wake signal to send. 52 parameter-free project GETs and 73 write operations were run
against a parked project, including `POST /database/query` and `POST /restart`,
and every one left it `INACTIVE`. The endpoints that need the instance fail
instead - `544` carries a connection timeout and costs the caller the full
wait, and `/database/migrations` took 20 seconds to return it. `POST /pause`
and `POST /restore` are excluded, since they change state by definition. The
reason is structural: with no DNS record there is no hostname for traffic to arrive at, and an automatically paused project lands
in the same state as a manually paused one (both NXDOMAIN, including a control
project nothing had touched).

That result covers PAUSED projects. Scale-to-zero is a separate mechanism -
the control plane models it as its own state, `project_hibernating`, distinct
from `INACTIVE` - and none of the above was measured against it. The null
result rests on a state with no DNS record, where traffic has nowhere to
arrive, so do not assume it carries to a state that keeps its hostname. Treat
the two as separate questions.

## Verification

The probes re-run on throwaway projects you create and delete; the calls are
the ones the sections make. Sections 3 and 8 additionally need a free-tier
project for the free-org rows.

- Sizing (3) - create a project and re-take the three Nano rejections
  (create, addon PATCH, `available_addons`); create with
  `region_selection: {type: "smartGroup", code: "apac"}` and read which
  region lands.
- Rate budget (4) - burst a cheap scoped read until the 429, reading the
  budget from the `x-ratelimit-*` headers; alternate two of your PATs on the
  same route to re-check the shared counter, and alternate two routes with one
  token to see the per-route sequences.
- OAuth (5) - authorize with an unknown `client_id`, then run the token
  lifecycle after a real consent: refresh, revoke, re-refresh.
- Metering (6) - insert a known payload and read `pg_database_size()`;
  send a counted batch of REST GETs and watch `usage.api-counts` catch up;
  scrape per-project metrics through your gateway with a scoped key.
- Control-plane faults (2, 8) - point the CLI profile's `api_url`, the
  provider's `endpoint` or your client's base URL at a proxy that answers 500
  before or after forwarding, and count the requests each tool sends.
- Deletions and pauses (8) - delete the project and re-poll the list for
  the tail; pause a free-tier project and read the data API for the
  `HTTP 540 Project paused`.

The measurement harness is public at
[supabase-lab](https://github.com/erfianugrah/supabase-lab) - one
`RUNLOG.md` per experiment under `experiments/` - but its destructive probes
run against the author's orgs and secrets, so a reader re-runs the API calls
above and reads the run logs in the repo.
