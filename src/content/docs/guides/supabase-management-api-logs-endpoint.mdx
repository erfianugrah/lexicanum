The Management API's `analytics/endpoints/logs.all` endpoint was removed
on 2026-09-23, after a changelog entry dated 2026-07-23 announced the
date.[^changelog] Anything that queried project logs programmatically - a
log-tail script, a SIEM pull, an audit check - had to move to the
replacement `analytics/endpoints/logs` endpoint. Dashboard log exploration
was unaffected.

Beyond the path rename, the backend moved from BigQuery to ClickHouse,
per-source tables collapsed into one unified `logs` table, and nested-field
access changed shape. And the official migration guide has
a bug in its own example - it tells you to filter by `source_name`, a
column that does not exist. Everything below was measured against the live
endpoint on 2026-08-22 on a project with real traffic, except where a
section carries a later date; the 2026-10-10 re-checks ran on a fresh
project with no traffic beyond the probes.

## The migration guide's `source_name` example

The changelog's worked example says:

```sql
SELECT timestamp, event_message
FROM logs
WHERE source_name = 'edge_logs'
ORDER BY timestamp DESC
LIMIT 100
```

Run that against the real endpoint and it fails:

```json
{"result": null, "error": "Field \"source_name\" does not exist."}
```

The column is `source`. The OpenAPI description of the endpoint says
`source`;[^api-ref] the changelog example is the outlier. The working
form:

```sql
SELECT timestamp, event_message
FROM logs
WHERE source = 'edge_logs'
ORDER BY timestamp DESC
LIMIT 100
```

If you migrated early by following the guide verbatim and concluded the
endpoint was broken, this is why.

## The full query

The endpoint is GET-only (POST returns a 404), takes the SQL in the `sql`
query parameter, and requires an explicit timestamp window of at most 24
hours. On 2026-08-22 a query without a window defaulted to the last minute;
on 2026-09-02 it answered the generic backend error instead (trap 6). On
2026-10-10 the same endpoint with only the window parameters (no `sql`)
answered 200 with 66557 bytes, a default tail of recent rows (hand read, not
archived):

```bash
REF=<project-ref>
curl -s -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
  "https://api.supabase.com/v1/projects/$REF/analytics/endpoints/logs?sql=$(jq -rn --arg q "SELECT timestamp, event_message FROM logs WHERE source = 'auth_logs' ORDER BY timestamp DESC LIMIT 50" '$q|@uri')&iso_timestamp_start=$(date -u -d '15 minutes ago' +%Y-%m-%dT%H:%M:%SZ)&iso_timestamp_end=$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

Timestamps need a timezone suffix (`...T%H:%M:%SZ`); a bare
`2026-08-22T00:00:00` is rejected with `Invalid ISO datetime`.

For a pull longer than a day, slice the range into windows of at most 24
hours and issue one query per window, ordered by `timestamp` with an
explicit `LIMIT`. The 24-hour cap was observed on 2026-08-22 and is not in
the evidence table. Whether `LIMIT` has a ceiling, and whether any pagination
exists beyond time-slicing, was not measured.

## Converting old queries

Three conversions cover every query that worked on `logs.all`.

**Per-source table to a `source` filter.** There is no `edge_logs` or
`auth_logs` table anymore - every source lives in the one `logs` table,
keyed by the `source` column. Eight sources were observed on live projects by
2026-09-02: `edge_logs`, `postgres_logs`, `pgbouncer_logs`, `auth_logs`,
`storage_logs`, `realtime_logs`, `postgrest_logs`, and `function_logs` (Edge
Function `console.log` lines, measured 2026-09-02). On 2026-10-10 a fresh
project returned eleven (next section). A quick inventory of what a project
emits:

```sql
SELECT source, count() AS n FROM logs GROUP BY source ORDER BY n DESC
```

### Sources on a project

Measured 2026-10-10 (module OB03b, one run, one fresh Pro-organisation
project in `ap-southeast-1`): one source-count query at the end of a run that
issued one request of each kind returned these eleven values of `source`.
Counts are in the private artifact and not quoted. Which source appeared when,
and whether `pgbouncer_logs` rows exist before any connection, was not
measured.

| `source` | What the run read back from it |
|---|---|
| `auth_audit_logs` | the Auth user's email, 1 row |
| `auth_logs` | the Auth user's email, 1 row |
| `edge_logs` | the marked REST requests, and the storage bucket and object name (1 row) |
| `function_edge_logs` | the marked Edge Function invocations, matched by URL |
| `function_logs` | the marked `console.log` line of the function |
| `pgbouncer_logs` | listed; the run made one connection through the shared pooler on 6543 and one on 5432 |
| `postgres_logs` | the literal of a failing pooler statement, 2 rows (one per port) |
| `postgrest_logs` | listed; event messages such as "Schema cache loaded ..." read back with `where source = 'postgrest_logs'` (hand read, not archived) |
| `realtime_logs` | listed; the run made one WebSocket join, and the Realtime topic name appeared in no source |
| `storage_logs` | the storage bucket and object name, 2 rows |
| `supavisor_logs` | listed; no marker of the run was found here |

`postgrest_logs` is a `source` value on the unified table. A query that
filters `where source = 'postgrest_logs'` replaces the per-source table, and
a `timestamp >= toDateTime64('YYYY-MM-DD HH:MM:SS', 6)` predicate worked as a
lower bound (hand read, not archived). The inventory query above counts as one
request against the rate limit in trap 5, so a script that needs the list of
sources spends 1 of the 10 rather than 11.

**`unnest(metadata)` to `log_attributes` map access.** BigQuery-era queries
reached nested fields by unnesting the `metadata` array one level at a time.
Those joins are gone - fields are flat keys on a `log_attributes` map:

```sql
-- before (BigQuery, logs.all)
SELECT timestamp, r.method
FROM edge_logs
CROSS JOIN unnest(metadata) AS m
CROSS JOIN unnest(m.request) AS r

-- after (ClickHouse, logs)
SELECT timestamp, log_attributes['request.method'] AS method
FROM logs
WHERE source = 'edge_logs'
```

For Postgres logs the parsed fields keep their `parsed.` prefix:
`log_attributes['parsed.error_severity']`, `log_attributes['parsed.backend_type']`.

**ClickHouse dialect.** Use `count()` rather than `count(*)`, and
ClickHouse date functions. An old BigQuery query run unchanged against the
new endpoint fails with HTTP 200 and the generic error body (trap 1).

## Traps, each measured

| # | Trap |
|---|---|
| 1 | **Errors return HTTP 200.** A dialect or parse failure is a `{"result": null, "error": "Backend error! Retry your query."}` envelope with status 200. If your script checks the status code only, every query failure looks like a transient blip - and the generic "Backend error" text is the same for a bad dialect, a bad column, and a real transient failure. Parse the `error` field, then tell the cases apart: on `Backend error! Retry your query.`, re-run a known-good sentinel (`SELECT count() FROM logs` with a window; measured returning a count) before retrying the original. If the sentinel succeeds, the failure is in your query and a retry loop never ends; if the sentinel fails too, back off and retry. |
| 2 | **`SELECT *` fails.** The endpoint requires an explicit column list; `SELECT * FROM logs LIMIT 1` returns the generic backend error, and did so again on 2026-10-10 in an exploratory query (not archived), so name the columns. The usable columns include at least `timestamp`, `id`, `event_message`, `source`, `log_attributes`. |
| 3 | **`timestamp` changed type.** `logs.all` returned microsecond integers; the new endpoint returns ISO strings (`"2026-08-22T00:13:07.000000"`). A parser doing `new Date(ts / 1000)` silently produces garbage dates instead of erroring. The string also carries no offset: the window you send is UTC, so parse the result as UTC (append `Z`) rather than letting a parser default to local time. The zone of the returned value was not tested separately from the input window; the 2026-10-10 re-check read it as an ISO string in UTC without a zone suffix, and the skew arithmetic in this trap treated it as UTC. On 2026-10-10 (module W27d, one run) `toInt64OrNull(log_attributes['request.sb.jwt.authorization.payload.issued_at']) - toUnixTimestamp(timestamp)` worked in SQL: 300 for a future-`iat` token and -3900 for an expired one, which separates a future-`iat` `PGRST303` from an expired one; the incident response around that error code is in the [resilience runbook](/guides/supabase-resilience-runbook/). All `log_attributes` values are strings, and a key a row lacks reads as `''`, not null. |
| 4 | History: no deprecation or sunset header. On the 2026-08-22 measurements `logs.all` served BigQuery queries exactly as before, with no `Deprecation`/`Sunset` header announcing the removal, so monitoring for deprecation headers would not have warned you; the changelog was the only signal. Since 2026-09-23 it answers HTTP 410 (measured 2026-10-10, module W27b). That is a status code, where the new endpoint reports query errors as HTTP 200 (trap 1), so a caller that checks status alone sees the removal and misses the query errors. |
| 5 | **Rate limit is 10.** `x-ratelimit-limit: 10` per window on both endpoints, so a polling loop that worked at the old budget needs spacing out - and one query per source spent 8 of the 10 on the eight sources known on 2026-09-02 before any alert query ran; with the eleven sources of 2026-10-10 it is 11 queries against a limit of 10. Poll with one query per window (`GROUP BY source`, or `source IN (...)`) instead of one per source. On 2026-10-10 the unified endpoint answered `x-ratelimit-limit: 10` and `x-ratelimit-reset: 60` (hand read, not archived), which reads as 10 requests per 60 s; the window length was not recorded on 2026-08-22. Exceeding the limit was not tried, and no `x-ratelimit-remaining` header was recorded. A poller at 4 logs queries a minute met no throttling on 2026-10-10 (module OB03, one run). |
| 6 | **The time window is required, and a missing one returns the same generic error.** On 2026-09-02, four queries sent without `iso_timestamp_start` and `iso_timestamp_end`, including the `WHERE source = 'edge_logs'` query above, answered `Backend error! Retry your query.`; the same SQL with a three-hour window returned rows. On 2026-08-22 that SQL ran without a window and defaulted to the last minute. Trap 1 makes this indistinguishable from a dialect mistake, so send the window every time, and treat the requirement as current behaviour rather than a documented contract. A query carrying only one of the two parameters was not tried. |
| 7 | Permission-denied rows carry no length keys. On 2026-10-10 a 42501 row on the unified table had no `transfer_encoding` and no `content_length` key, where the 2026-09-07 read through `logs.all` showed `transfer_encoding` as `chunked`. A detector that finds permission-denied rows by byte count therefore misses them; select on `log_attributes['response.headers.proxy_status']` instead. In module W27c the anon request answered 401, the authenticated request 403, and SQLSTATE 42501 appeared in `proxy_status` for all three requests (one run, unchanged from 2026-09-07). |

The old endpoint rejected ClickHouse SQL (`count()` failed on `logs.all`), so
no single query worked on both, and a migration meant running the two
dialects side by side until the removal.

The migration path was to put the new-endpoint query into whatever scheduled
check or SIEM pull ran at the time, alongside the old one, and compare the
two result sets. `logs.all` carried no `Deprecation` or `Sunset` header
(trap 4), so 2026-09-23 was the day the old query had to be deleted; a
script that still calls it now gets HTTP 410 in place of rows.

## Auth logs still carry full audit detail

For anything built on the auth log stream, the unified table preserves the
structured detail. A failed login, a failed refresh, and a signup against an
existing email were each captured within a minute under
`source = 'auth_logs'`, with the full attribute set flat on the
`log_attributes` map: `error_code`, `grant_type`, `method`, `path`,
`remote_addr`, `referer`, `request_id`, `status`, `duration`. The same JSON
also arrives in `event_message`, so either extraction path works:

```sql
SELECT timestamp, log_attributes['error_code'] AS error_code,
       log_attributes['remote_addr'] AS remote_addr
FROM logs
WHERE source = 'auth_logs'
ORDER BY timestamp DESC
LIMIT 50
```

## Ingestion lag and usage counts

Measured 2026-10-10 (module OB03, one run, one fresh Pro-organisation project
in `ap-southeast-1`): one marked REST request and one marked Edge Function
invocation every minute for 36 minutes (00:48-01:24 UTC), with a poller asking
the logs endpoint for every marker every 15 s. Each marker's lag is the time
of the first poll that returned it.

| `source` | Markers returned | Lag p50 | p90 | p99 | max | Over 240 s |
|---|---|---|---|---|---|---|
| `edge_logs` | 36 of 36 | 15 s | 15.1 s | 30 s | 30 s | 0 |
| `function_edge_logs` | 36 of 36 | 15 s | 15.1 s | 15.1 s | 15.1 s | 0 |
| `function_logs` | 36 of 36 | 15 s | 15.1 s | 15.1 s | 15.1 s | 0 |

The 15 s poll is the resolution: nearly every marker came back on the first
poll after it was sent, so each figure is a ceiling within one poll interval
(maximum 30 s) and says nothing about lag below 15 s. The row's own `timestamp`
minus the send time was 0 to 1 s, and none of the 142 polls returned an
error. The ingestion lag above 4 minutes seen once in lab runs before
2026-10-10 did not recur in this window. No threshold follows from one
36-minute window on one project.

Two more readings the same day, on the same unified endpoint:

- Rows were queryable 13 s after the request in W27b and 13 s in W27c, against
  46 s and 17 s on 2026-09-07 through `logs.all`. One run each, so the
  difference is not a trend.
- One of two S18 runs that day did not find its marked `edge_logs` row within
  264 s (module S18b, no endpoint error recorded). A row for the marked request
  was read about ten minutes later (hand read, not archived), so the row likely
  existed, but when it landed is unknown. S18c in the same run found its row in
  13 s, and the second run found its REST and Storage requests in 13 s each. The cause of the miss is not
  established.

Counts (module OB03c, same run): a burst of 300 marked REST requests, all
answered 200, returned 300 rows. `usage.api-requests-count` returned 341 and
the logs endpoint counted 341 `edge_logs` rows for the project: the 36 canary
requests, the 300 burst requests and 5 further rows that were not itemised.
The 37 function invocations are in `function_edge_logs` and in neither figure.
The organisation-level usage route, `GET /platform/organizations/{org}/usage`,
answered 401 `Unsupported access token` to a personal access token, and the v1
OpenAPI document has no organisation usage path, so the GB-ingested and
GB-queried figures behind the logs usage pricing are not reachable by token.
The rest of the probe design is in [the observability surface
reference](/reference/supabase-observability-surface/).
