Supabase's security boundary is the database. The managed HTTP tier - Data API, Auth, Storage, Realtime, Edge Functions - is a stateless public veneer over Postgres: reachable by design, and defended at the row (RLS), the grant, and the token. It keeps a public endpoint on every plan, so a perimeter control has nothing to attach to. Every "make Supabase private" question - an IAP over the instance, an IP allowlist on the Data API, proxy-only access, private by default - is the same request against that fact, and resolves to one of three options: push the control into the database, lock the database socket, or own the API layer.

Everything marked **measured** was validated on 2026-08-28 on throwaway micro projects in ap-southeast-1, plus a self-hosted PostgREST (official image, v16.2) in Docker against the project's session pooler, and Cloudflare Workers - an Access-gated proxy on the `erfi.dev` zone, and a local `wrangler dev` instance for the rate limiter. Each lever was applied through the Management API, then every HTTP surface re-probed with three credential classes (no key, anon key, service key). Follow-up runs on the same micro shape covered column grants, the Auth switch-on levers and Storage/Realtime reach on 2026-08-31 (S13-S15); the pre-request hook across a restart, FORCE ROW LEVEL SECURITY, the audit trail and bans, Auth enforcement, the x-forwarded-for trust boundary and the no-RLS shape where a backend uses `service_role` and nothing else on 2026-09-03 (S16-S21); and header-keyed checks on `cf-connecting-ip`, their volatility and advisor coverage of extension objects on 2026-09-14 (S22). On 2026-10-10 a project created through `POST /v1/projects` gave the default privileges, pg_graphql, the OpenAPI root and the lockdowns met by the `postgres` role (DD01-DD04), the hosted MCP server gave the confirmation matrix (K07), and S18 was ported to the unified logs endpoint; each is marked where it appears, n = 1 per probe. Claims about platform internals not re-tested are marked **asserted** and linked. The reproducible form is the supabase-lab `iap-lockdown` and `security-lockdown` experiments, under Reproducing.

**TL;DR:**

- **The managed HTTP tier has no network perimeter.** Network restrictions and PrivateLink act on the Postgres socket; nothing acts on the Data API, Auth, Storage or Realtime at the network layer, on any plan.[^sb-netrestrict][^sb-privatelink] An IP allowlist for the REST API does not exist, and the DB-layer workaround for it does not fire on hosted, neither after a config reload nor after a full project restart.
- **With no perimeter to harden, there are three options:**
  - Push the control into the database - grants, RLS, and claims-keyed identity (third-party auth). The boundary is the row.
  - Lock the database socket - PrivateLink plus "restrict all", on the one surface that has a network perimeter.
  - Own the API layer - your own PostgREST with the managed Data API off, behind an edge you control.
- **The managed levers tighten per service; none of them is a gate.** "Data API off" wedges PostgREST only; `verify_jwt` checks key-possession not identity; disabling legacy keys leaves the new publishable keys working; CORS and a custom domain gate nothing server-side.

The socket has a network perimeter - network restrictions and PrivateLink act on it.[^sb-netrestrict][^sb-privatelink] The HTTP tier has none: it answers on a public endpoint, and each lever on it, measured below, closes one service while the rest keep answering. Hardening it means moving the control off the edge.

| Lever | What it closes | What stays open |
|---|---|---|
| Empty exposed schema ("Data API off"), set with `PATCH .../postgrest` | PostgREST REST + GraphQL (`503 PGRST002` on a table path; `/rest/v1/` root with the anon key still answers 401, and answers per key as in [the OpenAPI root and the GraphQL probe](#the-openapi-root-and-the-graphql-probe-per-key)) | Auth, Storage, Realtime, Edge Functions[^sb-securing] |
| `db_schema` drops `graphql_public` | GraphQL only (`406 PGRST106`) | REST |
| `max_rows = 1` | caps rows per response | a bulk-read brake, not authz |
| Realtime `private_only = true` | public-channel joins (refused at join) | the WebSocket still upgrades; anon socket connects[^sb-realtime] |
| `disable_signup = true` | new signups | an existing user's login |
| Leaked-password protection (HIBP) | a breached password at signup (`422 weak_password`, S19, 2026-09-03) | a password *change* via `PUT /auth/v1/user` still sets a breached one (S11, 2026-08-28) |
| Legacy keys disabled | the legacy anon/service pair | the new publishable key generation still reads |
| Bucket set private | the public object URL (`400 NoSuchBucket`) | a service-key signed URL still serves the object |
| Edge Function `verify_jwt = true` | callers with no key (401) | any valid project JWT, incl. the anon key |

CORS and a custom domain gate nothing. CORS reflects an arbitrary `Origin` and a request with no `Origin` still returns data, so a non-browser client ignores it; a custom domain is a branding CNAME, and the origin `<ref>.supabase.co` answers identically before and after.[^sb-customdomain] The only surfaces reachable with no credential at all are a public storage object and a `verify_jwt = false` Edge Function.

### The OpenAPI root and the GraphQL probe, per key

Two reads that look like "the surface is open" answer differently per key and per extension state. Both were measured on 2026-10-10 on one project created that day through `POST /v1/projects` (Pro, Postgres 17.11; data-api-defaults DD02 and DD04), one trial per probe.

`GET /rest/v1/` returns the OpenAPI document of the exposed schema, and the anon key no longer reads it. The announcement gave 2026-03-11 for new projects and 2026-04-08 for existing ones, and the refusal text `Access to schema is forbidden`.[^sb-openapi-anon] Measured, the key sent as `apikey` alone or with `Authorization` gave the same statuses and bodies:

| Key | `GET /rest/v1/` |
|---|---|
| none | `401` `No API key found in request` |
| anon (legacy JWT) | `401` `Invalid API key`, with a hint naming the `service_role` key |
| publishable | `401` `Secret API key required`, with a hint naming secret API keys |
| `service_role` (legacy JWT) | `200`, swagger 2.0 spec, 5 paths |
| `sb_secret_` key | `200`, the same spec |

The anon status matches the announcement; its text was not seen in any body. As a control, a granted table answered `200` to the anon, publishable, `service_role` and `sb_secret_` keys. `GET /v1/projects/{ref}/database/openapi` with a personal access token returned `200` and the same 5 paths; `?schema=graphql_public` returned `200` with 2 paths, and a request with no token `401` `No access token provided`. The spec's title is the `public` schema comment. Not measured: the 2026-03-11 and 2026-04-08 split, since the one project was created after both dates.

`/graphql/v1` is the second read. pg_graphql is disabled by default on new projects, announced 2026-01-26,[^sb-pggraphql-default] and pg_graphql 1.6.0 turns introspection off for projects created from 2026-06-29.[^sb-pggraphql-introspection] On the same project (DD02):

| State | `{ __typename }` | `{ __schema }` or `__type` |
|---|---|---|
| fresh, extension absent (`pg_available_extensions` offers 1.6.2) | HTTP `200`, `errors: pg_graphql extension is not enabled.` | the same answer |
| after `create extension pg_graphql` | `{"__typename":"Query"}` at the first poll | HTTP `200`, `Unknown field "__schema" on type Query` (`__type` likewise) |
| after `comment on schema public is e'@graphql({"introspection": true})'` | `{"__typename":"Query"}` | `__schema` returns `queryType.name` `Query` and `__type` returns data, at the first poll |
| after the same comment with `"introspection": false` | not read | `__schema` refused again at the first poll |

The HTTP status is `200` in every state, so a GraphQL probe sends `{ __typename }` and reads the body. The lab's inventory probe sent `{ __schema }` and read `200` in all three states; it was changed on 2026-10-10, so a `graphql=200` line in an older iap-lockdown RUNLOG for a project created after 2026-06-29 means only that the endpoint answered HTTP 200. Not measured: the corrected probe inside iap-lockdown L01 and L02 themselves, and a project created before 2026-06-29 with pg_graphql on and then upgraded to 1.6.0.

### The Auth levers, switched on

Auth also has levers a customer switches *on*. Each hardens Auth alone and gates no other service.

| Lever | What it does | Measured |
|---|---|---|
| Before-user-created hook[^sb-authhooks] | runs your code on the signup path before the row exists; a domain allowlist or a fraud check rejects the account at the door | present and off by default ([S14](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s14-auth-switch-on.ts)). As a Postgres function (`pg-functions://postgres/public/<fn>`) rejecting `@mailinator.com`: the client received the hook's own message (`400`, `disposable email domains are not allowed`, `error_code` `unknown`), 200 for another domain, active 5s after the PATCH ([S19](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s19-auth-enforcement.ts)) |
| CAPTCHA (hCaptcha or Cloudflare Turnstile)[^sb-captcha] | gates the signup, sign-in and password-reset entry points against scripted abuse | present and off by default, provider defaulting to hCaptcha ([S14](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s14-auth-switch-on.ts)). With Turnstile's documented always-fail test secret, signup and the password grant both returned `400 captcha_failed: captcha protection: request disallowed (no captcha_token found)`; the documented dummy token was refused under that secret and admitted under the always-pass secret (200) ([S19](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s19-auth-enforcement.ts))[^cf-turnstile-test] |
| Auth rate limits[^sb-authratelimit] | token refresh, OTP, email and SMS sends, verify, and anonymous sign-ins each take a lower ceiling than the shared default | the seven `rate_limit_*` fields present, one driven down and back ([S14](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s14-auth-switch-on.ts)). `rate_limit_anonymous_users` set to 3: 15 anonymous sign-ins returned 3 x 200 and then 12 x 429 (`over_request_rate_limit: Request rate limit reached`), the first 429 at request 4 ([S19](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s19-auth-enforcement.ts)) |
| `password_min_length`, MFA TOTP | password policy and second factor | set to 12, a 4-character password on the update path refused with 422 ([S03](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s03-auth-hardening.ts), [S11](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s11-auth-efficacy.ts)). The value 12 is a design choice; the 422 is the measurement |
| `password_hibp_enabled` | leaked-password protection | off by default; did not fire on `PUT /auth/v1/user` ([S11](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s11-auth-efficacy.ts)); at signup it did, `422 weak_password: Password is known to be weak and easy to guess, please choose a different one.` for a breached password, 200 for a strong one, with `mailer_autoconfirm` on so no email was sent ([S19](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s19-auth-enforcement.ts), 2026-09-03) |

S14 read the switch-on fields on a micro project (2026-08-31) and S19 drove them to their refusals (2026-09-03). In S19 the rate-limit count was exact, with no burst above the configured value in that window. In the seconds before the hook was active, signups returned a 400 without the hook's message (observed while writing the probe, not recorded in the artifact), so a verifier waits for the hook's own text.

## What each platform control covers

The controls a security review asks about outside the HTTP tier each have a documented scope. The right-hand column is what stays reachable, readable or uncovered with the control on.

| Control | Covers | Does not cover |
|---|---|---|
| Network Restrictions | Postgres and the database pooler[^sb-netrestrict] | the HTTPS APIs (the docs name PostgREST, Storage and Auth) and supabase-js. Edge Functions lose direct database access while restrictions are on, and the docs point them at supabase-js instead;[^sb-netrestrict] measured as a `CONNECT_TIMEOUT` under [Option 2](#option-2-lock-the-database-socket) |
| SSL enforcement | connections to Postgres, Supavisor and PgBouncer[^sb-ssl] | the HTTP APIs, which enforce SSL on every connection regardless.[^sb-ssl] (Side effect: applying or updating it triggers a fast database reboot.[^sb-ssl]) |
| PrivateLink | Postgres and PgBouncer connections from an AWS VPC in the project's region; Team and Enterprise; Beta[^sb-privatelink-feature] | the Supabase API, Storage, Auth and Realtime, which stay on public endpoints;[^sb-privatelink-feature] and the uptime SLA, which does not cover Beta products.[^sb-sla] Measured in [AWS PrivateLink to Supabase](/reference/supabase-aws-privatelink/) |
| Read-only organization role (Team and Enterprise) | Dashboard access without writes; its SQL runs as `supabase_read_only_user`, a member of `pg_read_all_data`[^sb-access-control] | secrets: the access-control table footnotes that the Read-only role "is able to access secrets".[^sb-access-control] Nor row visibility: `pg_read_all_data` alone does not bypass RLS,[^pg-predefined] but the lab read BYPASSRLS on `supabase_read_only_user` (governed-starter-kit [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/16077ed/experiments/governed-starter-kit/RUNLOG.md) and [ACCESS-CONTROL.md](https://github.com/erfianugrah/supabase-lab/blob/16077ed/experiments/governed-starter-kit/docs/ACCESS-CONTROL.md), 2026-10-07), so a Read-only member's SQL reads every row. A Read-only member's own session was not exercised |
| MCP server `read_only=true` | writes: it executes SQL "as a read-only Postgres user"[^sb-mcp] | row visibility, as far as the docs say: they name no role and do not mention RLS. The server sends `read_only: true` to the Management API's `/v1/projects/{ref}/database/query`,[^mcp-src] and the API documents its sibling `/database/query/read-only` as running as `supabase_read_only_user`.[^sb-mgmt-query] If the flag lands on that role, a read-only MCP session reads every row as the Read-only role does. Which role the MCP path runs as was not measured. What was measured on 2026-10-10 (the hosted MCP server at the `serverInfo` version 0.13.0 recorded in the [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/governed-starter-kit/RUNLOG.md), [K07](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/governed-starter-kit/tests/k07-mcp-elicitation.ts)): with `read_only=true` a `DROP` was not confirmed and not run, and Postgres answered `25006 cannot execute DROP TABLE in a read-only transaction`. The write stop holds; the role and BYPASSRLS question stays open |
| Extension version pinning ignored; Realtime schema lockdown (changelog entries) | `CREATE EXTENSION ... VERSION` installs the default version with a warning;[^sb-extpin] operations on the `realtime` schema fail with `permission denied for schema realtime`[^sb-rtlock] | Measured as `postgres` (`is_superuser` off) on one API-created project, 2026-10-10 ([DD03](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/data-api-defaults/tests/dd03-platform-lockdowns.ts)). `create extension citext version '1.5'` and `'9.9'` both installed the default 1.6 with the warning, shown on a pooler connection and not in the query endpoint's response. Every `ALTER EXTENSION ... UPDATE` form errored `XX000 pgaudit stack is not empty`, where the changelog says the update proceeds; whether that is the no-op path or every update on a pgaudit project was not separated. Of ten Realtime operations six were refused (`42501`, with `must be owner of ...` text for the ALTER and DROP forms) and four were allowed: `INSERT`, `UPDATE` and `DELETE` on `realtime.schema_migrations` and `drop trigger tr_check_filters`, where the changelog lists `INSERT`, `DELETE` and the trigger drop as refused. The project's Realtime version was not read |
| Enterprise uptime SLA | 99.9% of each calendar month, per product, for generally available products[^sb-sla] | Beta and Alpha products, and the listed exclusions, among them third-party vendors and cloud providers, integration partners, force majeure and ISP outages, customer misconfiguration or resource limits, and account suspension.[^sb-sla] Below Enterprise there is no uptime SLA; the remedy and plan split are in [what the SLA does and does not cover](/reference/supabase-dr-tiers/#what-the-sla-does-and-does-not-cover) |

A Read-only seat should be treated as a whole-database read (BYPASSRLS read on `supabase_read_only_user`, 2026-10-07; no member session exercised), and a read-only MCP session as one until a probe shows otherwise. Network Restrictions, SSL enforcement and PrivateLink act on Postgres connections only, so the HTTP tier stays as the lever table under [Why there is no perimeter to harden](#why-there-is-no-perimeter-to-harden) measured it.

### MCP confirmations depend on the client

The hosted MCP server documents confirmations on four tools (`create_project`, `create_branch`, `execute_sql`, `apply_migration`) and takes a `skip_elicitations` parameter to remove the prompt per tool.[^sb-mcp] K07 (2026-10-10, [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/governed-starter-kit/RUNLOG.md), one project per run, n = 1 per cell) sent the same statements from five client shapes. The server speaks a legacy session shape (`initialize`, protocol 2025-11-25) and the 2026-07-28 stateless shape, where there is no `initialize` and every request carries its capabilities in `params._meta`; a confirmation is an answer with `resultType: "input_required"` that the client repeats with `inputResponses` and a `requestState`.

| Client | Capability declared | `drop`, `truncate`, `update` and `delete` without `where`, `apply_migration` with DROP |
|---|---|---|
| L0, legacy | none | ran, no confirmation |
| L1, legacy | `elicitation.form` at `initialize` | ran, no confirmation |
| S0, 2026-07-28 | none | ran, no confirmation |
| SU, 2026-07-28 | URL elicitation only | ran, no confirmation |
| S1, 2026-07-28 | `elicitation.form` in `params._meta` | asked each time |

L0, L1, S0 and SU ran 20 of 20 (four statements and one migration each) with no confirmation and the table changed. S1 was asked for `drop`, `truncate`, `update` and `delete` without `where`, `delete ... where true`, `alter table ... drop column`, a `do` block running `execute 'drop table ...'` and a multi-statement `select 1; drop table ...`; it was not asked for `update ... where true`, an `update` with a `where`, `insert`, `select`, or a string literal containing DROP. Declining or cancelling ran nothing (4 of 4 `execute_sql` statements and the migration, `status: declined` or `cancelled`). A confirmation therefore exists only for a client that declares form elicitation in the 2026-07-28 metadata, and what it covers is decided by statement shape.

- `skip_elicitations` is a per-tool comma list. With `execute_sql,apply_migration` an S1 client that would have declined was not asked and the statements ran; skipping `apply_migration` alone left an `execute_sql` DROP asking. `Execute_SQL`, `all`, an unknown name and the parameter given twice each returned HTTP 400.
- One acceptance covers repeats of that query. The `requestState` carries keys `b`, `exp` and `p` (tool, project and a query hash), with `exp` 119 s ahead. Replayed with the same query it ran the statement again; presented with a different query (a DROP) it was refused. Behaviour past `exp` was not tested.
- Branches: for L0, L1, S0 and SU a project-scoped `create_branch` errored `Cost confirmation ID does not match the expected cost of creating a branch` and made no branch. On an account-scoped connection the helper tools `get_cost` and `confirm_cost` exist, and the script called them with no person between the calls. `reset_branch`, `rebase_branch` and `delete_branch` raised no prompt under S1.
- Claude Code 2.1.287 declares form and URL elicitation. In `claude -p` with an Elicitation hook that answered through `hookSpecificOutput.action`,[^cc-hooks] it declined or accepted (a statement applied or a branch created only on accept); with no hook `-p` cancelled and the DROP did not run. With `skip_elicitations` on both SQL tools no hook event fired and the DROP applied. A hook that nested the answer under `decision` made the model report `cancelled` in all 6 SQL runs and both branch runs. The outcome was read from database state and the hook event count (10 runs, one model); the interactive dialog, other clients and `create_project` were not run.

`read_only=true` is the lever measured to stop the write (`25006`, above); a hook or script that answers for the user turns a confirmation into a pass-through.

## Which option fits the goal

Before picking an option, read the Management API security advisor. In security-lockdown S01 it caught every seeded exposure - `rls_disabled_in_public`, `rls_enabled_no_policy`, `security_definer_view`, `anon_/authenticated_security_definer_function_executable`, `function_search_path_mutable` - so for the database half it answers "are we locked down?" before any lever is pulled, and again after each one.

| Goal | Option | Mechanism | Cost |
|---|---|---|---|
| Close data to anon, keep the managed tier | into the database | grants, RLS, claims-keyed identity | authz logic lives in Postgres |
| A private database path | lock the socket | PrivateLink + "restrict all" | Team/Enterprise; AWS VPC in-region[^sb-privatelink] |
| IP-restricted or rate-limited REST | own the API layer | your own PostgREST, Data API off | you run PostgREST |
| The whole HTTP tier private | own everything | self-host / BYOC | you run the stack |

## Option 1: push the control into the database

The boundary is the row, so the control belongs on the row, set through grants, RLS, and the token.

### Grants

#### The default is changing

On existing projects a table created in `public` receives `SELECT`, `INSERT`, `UPDATE` and `DELETE` for `anon`, `authenticated` and `service_role` by default, and Supabase is changing the platform default to revoke those automatic grants.[^sb-securing] The rollout was announced on 2026-04-28:[^sb-grants-change]

| Date | What changes |
|---|---|
| 2026-04-28 | opt-in at project creation: leave the "Automatically expose new tables" checkbox unchecked |
| 2026-05-30 | the new behaviour becomes the default for new projects |
| 2026-10-30 | enforced on existing projects: a new table in `public` without an explicit `grant` stops being reachable through the Data API |

The change is to default privileges, so it governs tables created afterwards. The announcement's opt-in SQL changes the defaults for future tables and sequences the `postgres` role creates in `public`, and existing objects keep their current grants.[^sb-grants-change]

A project the lab created with OpenTofu on 2026-08-28, after the new-project date, still had the old default. In iap-lockdown L08 a table created with no `GRANT` was readable by anon through the Data API. The first L08 run on that project made that observation before any lab statement had altered a default privilege. Its attempt to alter them was refused (42501), and its teardown then granted `SELECT` on new tables to anon and authenticated. Revoking `postgres`'s default privileges closed the next new table in the second run, after that teardown, so those runs did not read the default ACL itself ([RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/iap-lockdown/RUNLOG.md), [L08](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/iap-lockdown/tests/l08-grant-lockdown.ts)). The cause was not established.

The default ACL was then read directly (measured 2026-10-10, [DD01](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/data-api-defaults/tests/dd01-default-grants.ts), [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/data-api-defaults/RUNLOG.md)). A project created that day through `POST /v1/projects` (Pro, Postgres 17.11) was read before any statement ran. In `public`, for both `postgres` and `supabase_admin`, `anon`, `authenticated` and `service_role` each held `arwdDxtm` on tables, `rwU` on sequences and `X` on functions (DD01a). A table made in SQL was then readable with no `GRANT`: `200` for the anon key after 2 s of schema-cache wait, and `200` for the publishable key (DD01b). The v1 create-project body, read from the published OpenAPI document that day, has no field for the setting, and the announcement describes it on the project creation screen only. So the old default was in force on a project created after the 2026-05-30 row above. Two readings fit: the new default does not reach projects created through the API, or the gradual rollout had not reached this project. One project cannot separate them. The 2026-10-30 row stays as announced; the standing-project re-run on or after that date has not been done, so what enforcement does to a project created before 2026-05-30 is not measured.

`select defaclrole::regrole, defaclnamespace::regnamespace, defaclobjtype, defaclacl from pg_default_acl where defaclobjtype = 'r'` shows what a given project will grant on new tables: an `anon=` entry for `postgres` in `public` means new tables arrive exposed. Whatever it shows, grant each table explicitly and enable RLS on it;[^sb-securing] a migration written that way behaves the same before and after 2026-10-30.

#### One table

For a table that must shut to anon without a policy migration, the grant is the lever. The next table a migration creates is readable again unless the default privileges move with it (iap-lockdown L08).

| Step | Effect through the Data API | Rests on |
|---|---|---|
| `REVOKE SELECT ON <table> FROM anon, authenticated` | anon gets `42501`; `service_role` keeps reading | [L08](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/iap-lockdown/tests/l08-grant-lockdown.ts) |

| `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE SELECT, INSERT, UPDATE, DELETE ON TABLES FROM anon, authenticated, service_role`, the four-privilege form of the announcement's opt-in (the statement as the probe worded it; plus the sequences form), on the 2026-10-10 API-created project | a new SQL table answered `401` to anon and to the publishable key and `403` to `service_role` and to an `sb_secret_` key, all with `42501` `permission denied for table <t>` and the hint `Grant the required privileges to the current role with: GRANT SELECT ON public.<t> TO anon;` (`TO service_role` for the two secret keys). TO anon` re-opened the table at once (`200`, no wait, anon ACL `rDxtm`), with `service_role` still `403` | [DD01c, DD01d](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/data-api-defaults/tests/dd01-default-grants.ts) |

The two revokes differ in the privileges named (SELECT against four), the roles (`anon` and `authenticated` against those two plus `service_role`), the project and the date (2026-08-28 against 2026-10-10), and the two closed tables answered differently: `404 PGRST205` and `401`/`403` `42501`. The runs do not say which difference accounts for it, and no cause is claimed here. A probe after a default-privilege change should read the body as well as the status. Filed upstream: no, for the `404`-against-`42501` difference.

#### The whole schema: the no-RLS shape

The shape a pen test most often finds is no RLS: authorisation in application code, the backend using `service_role`, and every table readable by any holder of the anon key. Grants alone close that (security-lockdown S21, 2026-09-03), but a revoke aimed only at `anon` and `authenticated` leaves the RPC surface open.

| Step | anon table | authenticated table | anon RPC | `service_role` |
|---|---|---|---|---|
| 1. `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated`, the same for sequences and functions, `REVOKE USAGE ON SCHEMA public FROM anon, authenticated`, and the matching `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public` | `401` `42501: permission denied for table` | `403` `42501: permission denied for table` | **`200` - still callable** | table `200`, 2 rows |
| 2. `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA public FROM public` | - | - | `401` `42501: permission denied for function` | RPC `200` |
| A table and a function created after steps 1-2 | table `401` `42501` | - | **function `200` - callable again** | `200` |
| 3. `ALTER DEFAULT PRIVILEGES FOR ROLE postgres REVOKE EXECUTE ON FUNCTIONS FROM public` (global, no `IN SCHEMA`), then another new function | - | - | `401` `42501` | `200` |

- Functions carry EXECUTE for PUBLIC (`proacl {=X/postgres,...}`) and `public` keeps USAGE for PUBLIC, so a revoke aimed at `anon` and `authenticated` never touches them.
- Per-schema default privileges add to the global default and cannot remove PUBLIC's built-in EXECUTE;[^pg-defprivs] only the global form does. The table created after the schema-level revoke stayed closed, because tables have no PUBLIC default.

#### The exposed schema

Moving the API surface to a dedicated exposed schema is the same lockdown at the PostgREST layer, and it is project-wide (S21). With `db_schema` set to `api` alone, `service_role` reading a `public` table got `404 PGRST205: Could not find the table 'api.sec21_pii' in the schema cache` 3s after the PATCH, and read the `api` view with or without an `Accept-Profile: api` header (the first exposed schema is the default). The backend's own calls move with the setting.

### RLS

#### Where RLS still leaks

Three RLS mistakes still fail a pen test after "we added RLS":[^sb-securing]

- **A view over an RLS table leaks every row** unless it is created `with (security_invoker = true)`. In iap-lockdown L08 the plain view returned every row to anon and the invoker-security view 0.
- **An UPDATE policy gates which rows change, never which columns.** A `WITH CHECK` constrains the row's new values, not which of its columns a caller may touch.
- **PERMISSIVE policies OR together**, so an admin-intended policy bleeds onto anon.

#### Column writes are closed by a grant

`REVOKE UPDATE ON <table> FROM anon, authenticated` followed by `GRANT UPDATE (<the writable columns>)` makes a write to any withheld column return `42501` (permission denied for column) while the row policy still decides which rows move.[^pg-grant] Security-lockdown S13 (2026-08-31) measured the pair:

| Setup | anon write to `balance` | anon write to the granted column |
|---|---|---|
| Permissive UPDATE policy + table-level UPDATE grant | `204` - the hole a pen test writes through | `204` |
| Same policy, `REVOKE UPDATE` + `GRANT UPDATE (note)` | `401` carrying SQLSTATE `42501` | `204` |

#### FORCE ROW LEVEL SECURITY binds only a non-BYPASSRLS owner

A team that wants RLS applied to its backend's roles reaches for FORCE next. It applies RLS to the table owner, and only if the owner cannot bypass RLS (security-lockdown S17). On a managed project the owner usually can:

| Role | `BYPASSRLS` | Note |
|---|---|---|
| `postgres` | yes | the default owner; the role the Management query endpoint runs as (S17a; the Dashboard SQL editor is documented to use the same role) |
| `service_role` | yes | the backend key |
| `supabase_admin` | yes | platform |
| `authenticator`, `anon`, `authenticated`, `supabase_auth_admin` | no | |

| Reader, RLS on and no policy | Rows before FORCE | Rows after FORCE |
|---|---|---|
| `postgres` on a postgres-owned table | 2 | 2 |
| a lab role without `BYPASSRLS` on a table it owns | 2 | 0 |
| `service_role` through REST | `200`, 2 rows | `200`, 2 rows |

`ALTER ROLE service_role NOBYPASSRLS` as the project owner returned `42501: "service_role" is a reserved role, only superusers can modify it`. Role choice does apply RLS to a backend:

1. Create a role `NOBYPASSRLS` and grant it to `authenticator`.
2. Mint the backend's HS256 JWT with that role in the `role` claim, signed with the secret `GET /projects/{ref}/postgrest` returns.
3. Call the Data API with it: `200` with 0 rows under no policy, `200` with 1 row once a `tenant = 'a'` policy existed.

### Identity: the token as the key

Register an external issuer as third-party auth (the `jwks_url` shape resolves; an inline key set never does) and key RLS on a claim only the issuer sets.[^sb-jwts] Measured with Cloudflare Access-for-SaaS registered as the issuer (its JWKS resolved on registration) and the admit/deny run with a lab ES256 issuer whose JWKS was served from an Edge Function, since a real Access token needs the interactive login:

| Caller, policy `(auth.jwt() ->> 'iss') = '<issuer>'` | Rows read |
|---|---|
| anon key | 0 |
| GoTrue user token | 0 |
| token minted by the trusted issuer | its rows |

That is "an IAP over the data" done at the authorisation layer, and it is plan-agnostic. The step-by-step is [Put an IAP over the Supabase Data API](/guides/supabase-iap-data-api/); keeping RLS while dropping the Supabase HTTP layer entirely is [RLS without Supabase Auth](/reference/rls-without-supabase-auth/).

### Where this option stops

Four of the five limits below are measured; the pg_headerkit one rests on its published source plus the two measured mistakes it packages.

#### The IP filter that does not fire on hosted

<Aside type="caution">
PostgREST supports `pgrst.db_pre_request`: a function that reads `current_setting('request.headers')` (which carries `x-forwarded-for`) and rejects a request - a DB-layer IP filter.[^pgrst-prereq] On a managed project the role GUC persists after `ALTER ROLE authenticator SET pgrst.db_pre_request`, and neither reload path activates it:

| Step (iap-lockdown L09, 2026-08-28; security-lockdown S16, 2026-09-03) | Result |
|---|---|
| `NOTIFY pgrst, 'reload config'` | no pre-request within 120 seconds (L09), none within 61s (S16) |
| `POST /projects/{ref}/restart` | `200`; REST refused at once |
| First health poll after that | db and rest already `ACTIVE_HEALTHY` |
| REST answering again | 302s after that poll (303s from the restart call) |
| After REST returned | no pre-request in 182s, GUC still on the role |

The mechanism exists in PostgREST, but on the hosted tier it is not activatable via SQL by reload or by restart. It works on your own PostgREST (option 3), where the config is yours.

An RPC returning `request.headers` on the managed PostgREST (S16) saw one address in `x-forwarded-for` with no client header and two with a client-supplied `x-forwarded-for: 203.0.113.9` - the client value first, then the edge's - so the edge appends rather than replaces, and the first element is attacker-controlled. The forwarding-related keys that reach SQL are `cf-connecting-ip`, `cf-ew-via`, `cf-ipcountry`, `x-forwarded-for` and `x-forwarded-proto`; the two that carry an address are `cf-connecting-ip` and `x-forwarded-for`, and `cf-connecting-ip` is the one to read in a header-keyed check on hosted. Its trust was measured on 2026-09-14 (S22a): the same RPC carrying a client-supplied `cf-connecting-ip: 203.0.113.9` returns `403`, so the edge refuses the request outright rather than overwriting the header and the forged value never reaches SQL; with no client header the key is present and equals the sole `x-forwarded-for` element.[^cf-connecting-ip]
</Aside>

#### Key the check on cf-connecting-ip, inside the object

The hook is a connection-level gate and hosted never activates it, so the check has to sit in the object itself: a policy, a view, or an RPC. That form was measured on 2026-09-14 (S22b) with two tables whose policies differ only in the header they read, an allowlist holding one address, and a single request carrying that address in `x-forwarded-for`:

| Policy keyed on | Rows returned to the forged request |
|---|---|
| `cf-connecting-ip` | 0 |
| `split_part(x-forwarded-for, ',', 1)` | 1 |

Both functions were `stable` for that comparison, so the only variable was the header. Written out, the form that held:

```sql
create function app.caller_ip() returns text
  language sql stable                     -- never immutable; see below
  set search_path = ''
  as $fn$
    select coalesce(current_setting('request.headers', true)::json ->> 'cf-connecting-ip', '')
  $fn$;

create policy allowed_ip on app.t for select to anon
  using (exists (select 1 from app.allow_list a where a.ip = app.caller_ip()));
```

Volatility is a planner property, so it decides whether the check runs per request at all, whichever header you read. Marking that function `immutable` gives it constant arguments, and a zero-argument constant expression is evaluated when the statement is planned rather than when it runs (S22c, same body, same qual):

```text
IMMUTABLE                          STABLE
Result                             Result
  One-Time Filter: false             One-Time Filter: (COALESCE(((current_setting(
                                       'request.headers', true))::json ->> 'cf-connecting-ip'), '') <> '')
                                     ->  Seq Scan on public.t
```

The `immutable` plan has no `current_setting` call left in it and no scan: the planner read the header once, folded the answer to a constant, and the policy stopped being a per-request check. Postgres inlines both SQL functions, so neither plan names the function; read the plan for a surviving `current_setting` call.

#### pg_headerkit reads the forgeable element

Both mistakes are packaged together in [pg_headerkit](https://github.com/supabase-community/pg_headerkit), a set of `hdr.*` helpers over `request.headers` reachable from the dbdev registry's launch post as an IP allow/denylist recipe for PostgREST. Its `hdr.ip()` is `split_part(hdr.header('x-forwarded-for') || ',', ',', 1)`, the form that returned 1 row above. Three of its 24 functions are `stable` (`hdr.headers()`, `hdr.header()`, `hdr.ip()`); the other 21 are `immutable`, and that set includes the two you would put in a policy, `hdr.in_allow_list()` and `hdr.in_deny_list()`, which take no arguments and call the `stable` `hdr.ip()`. Postgres does not check a function's declared volatility. It is v1.0.0 on dbdev, last substantive commit 2023-03-03, and predates the edge measured here. Its README lists rate limiting, request logging, and user allow/denylists as unchecked roadmap boxes rather than shipped functions; the published SQL is header accessors, two `inet` tables, membership checks, and user-agent predicates.

#### Storage and Realtime are not on the REST path

Every control above sits on the PostgREST path, and two managed services never traverse it (security-lockdown S15, 2026-08-31):

- **Storage and Realtime keep answering with the Data API off.** With the schema wedged empty (`503 PGRST002` on a table path), `/storage/v1` still served (`200`) and `/realtime/v1` still answered, because each is its own service against the same Postgres. An IP allowlist or an owner-list read from request headers gates the REST layer and nothing else; for Storage and Realtime the same intent lives in each service's own authorisation - RLS on `storage.objects`, Realtime Authorization - or on an edge you own.
- **The public-schema REVOKE does not reach `storage`.** The schema is owned by `supabase_admin`, not the project owner (measured), so its tables keep their own grants and Storage stays governed by RLS on `storage.objects`.
- **Claims read straight from the wire depend on the connection credential.** The claims GUC is unprivileged, so the connection credential becomes the boundary; [RLS without Supabase Auth](/reference/rls-without-supabase-auth/) works it through with a tampered-claim test.

#### Egress from inside Postgres

`net.http_get('https://...')` returned 200 from SQL on a fresh project (security-lockdown S08): a SQL-capable caller can exfiltrate or SSRF from inside Postgres. Restrict EXECUTE on schema `net` to the roles that need it, or leave `pg_net` disabled if nothing uses it.

## Option 2: lock the database socket

The socket is the one surface with a network perimeter. PrivateLink puts the connection on AWS VPC Lattice, and DB network restrictions narrowed to a break-glass block close the public direct and pooler paths while the endpoint keeps serving - the full public-DB lockout, self-service, on Team or Enterprise. The behaviour, the DNS/TLS pattern, and the latency numbers are in [AWS PrivateLink to Supabase](/reference/supabase-aws-privatelink/).[^sb-privatelink] This option does nothing for the HTTP tier: PrivateLink covers Postgres and the pooler only, and the Data API stays public by design.

Through the shared Supavisor pooler, a caller outside the restriction list is refused at once with `FATAL (EADDRNOTALLOWED) address not in tenant` (security-lockdown S10) - the verification text for the socket lock. On the public direct 5432 and dedicated PgBouncer 6543 paths the excluded address is dropped rather than refused, so the client sees its own connect timeout (`timeout expired` at 6.7 s against 2.7-3.3 s for the Supavisor refusal; recovery 3.8-4.3 s on all four paths after the list is reopened; medium-serverless MS03, 2026-09-30). And Supabase-hosted compute is outside the list too: under restrict-all an Edge Function's direct `pg` connect over `SUPABASE_DB_URL` fails with `CONNECT_TIMEOUT db.<ref>.supabase.co:5432` while the same function's `/rest` call with the service key still serves (iap-lockdown L22), which pushes that data onto the public HTTP tier this option was meant to keep it off. Inventory Edge Functions that open direct connections before applying the restriction; under restrict-all they move to the Data API path or break (L22 measured one function). Whether pg_cron jobs or database webhooks are affected was not measured.

## Option 3: own the API layer

When the goal is an IP-restricted, rate-limited, or otherwise network-controlled REST layer, the managed tier has no lever for it, so take the API layer in-house: turn the Data API off and run PostgREST yourself against the same Postgres, behind an edge you control. Turn it off with `PATCH /v1/projects/{ref}/postgrest` and `db_schema: ""`, never the dashboard toggle. The toggle's off-then-on round-trip rewrites `db_schema` to the constant `public` and drops `graphql_public` with any extra schema, while the API round-trips what you give it (http-tier-lockdown run 2).

S04 measured this end to end: managed REST dark (`503 PGRST002`), a PostgREST v16.2 container connected to the project's session pooler serving the same rows, and its `db-pre-request` filter rejecting a spoofed `x-forwarded-for` with `403` while an allowed request served. The filter judges whatever header reaches it, so the deployment decides what that header holds (S20, 2026-09-03). Called direct on the container with `x-forwarded-for: 198.51.100.7`, an RPC returning the header saw that value (200, 1 address); called through an nginx edge that sets `X-Forwarded-For $remote_addr`, it saw one RFC 1918 address and no client value; and the S04 ban on `203.0.113.9` returned `403 PT403` direct and `200` through the edge. The filter is an allowlist only when PostgREST is reachable from nowhere but the edge. The step-by-step build is [Run your own PostgREST against a Supabase project](/guides/supabase-own-postgrest/).

The proxy-only variant of this option - a Worker in front of the managed origin - can be bypassed until the browser-usable keys are revoked. A Worker holding the service key does not gate the origin, because `<ref>.supabase.co` keeps answering anyone with a key; direct origin with the anon key returned 200 with the proxy in place. It becomes the only path once the browser-usable keys are revoked (direct origin then `401 Legacy API keys are disabled`). Once the keys are revoked, supabase-js from the browser is gone and the Worker owns authorisation because `service_role` bypasses RLS - which is a backend in front of a database, the same shape as running your own PostgREST.

Revocation is three separate facts in iap-lockdown L05 and L11: disabling the legacy keys refuses the legacy anon JWT in about 45s (48s on the L11 run), the newer `sb_publishable_` generation is independent and keeps reading until it is revoked as well, and the control plane re-mints a key at will (201), so "revoked" is a posture any PAT holder can undo.

Rate limiting runs on the edge either way: nginx `limit_req` (2 requests/second, burst 2) in front of the container returned 2 served and 13 rejected on a 15-request burst, and a Cloudflare Worker with the Rate Limiting binding (run locally via `wrangler dev`) returned the same 2 and 13; a WAF rule or Upstash does the same job ([S05](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s05-rate-limit.ts) for the nginx limiter, [S12](https://github.com/erfianugrah/supabase-lab/blob/f703393/experiments/security-lockdown/tests/s12-ratelimit-worker.ts) for the Worker variant).[^sb-ratelimit] It counts only the traffic that passes through it, so it limits a closed origin and cannot limit the managed endpoint, which answers any key-holder directly.

The secrets this option creates - the service key the Worker holds, the connection role's password - can live in the database: `supabase_vault` stores them as ciphertext in `vault.secrets` and returns them through `vault.decrypted_secrets` (security-lockdown S07), rather than a plaintext column or an environment variable in a compose file.

#### What the database logs by default

The platform's logging defaults on a fresh project, read with `show` on

|---|---|---|

| `log_min_duration_statement` | `-1` | every duration-based read - disabled |

| `log_min_error_statement` | `error` | nothing at error level, which is the one error-visibility default that is on |

The connection lifecycle is the part the platform lets you raise: a
`PUT /config/database/postgres` carrying `log_connections` answers `200` and
takes, while the same call carrying `log_statement` answers
`400 Unrecognized key: "log_statement"` (A04a, A04d). The [audit trail
reference](/reference/supabase-audit-trail-integrity/) carries that half.

So a lockdown's evidence side cannot rest on Postgres logs alone: a control
that logs DDL proves a table was created and says nothing about what was read
out of it. The row-level story has to come from `edge_logs` and `auth_logs`
(the table above) or from pgaudit.

### Blocking a bad actor

The three ban paths in the spec are `network-bans/retrieve`, `network-bans/retrieve/enriched` and `DELETE network-bans`, and all of them act on the database socket.[^sb-netbans]

| Step | Result |
|---|---|
| `POST network-bans/retrieve` before | 0 banned |
| 10 failed psql authentications through the session pooler (`FATAL: password authentication failed`) | 1 address banned (the lab machine's, by the fact that psql from it succeeded again only after the `DELETE`) |
| `DELETE /network-bans` with that address | 200; 0 banned after |
| correct-password psql through the pooler afterwards | succeeded |

Nothing in the spec bans an address at the HTTP tier; for Data API, Auth and Storage traffic that control lives in the row, the token, or an edge you own.

```dot
  q2 -> q3 [label="no"];
  q3 -> own [label="yes"];
  q3 -> self [label="need the whole HTTP tier private"];
}
```

The same decision, as text. Start from what has to be private:

1. Just the database socket? Yes: Option 2, PrivateLink + restrict-all. No: go to 2.
2. Identity on the Data API, keeping the managed tier? Yes: Option 1, third-party auth + claim-keyed RLS. No: go to 3.
3. IP or rate-limit the REST layer? Yes: Option 3, your own PostgREST with the Data API off. If the whole HTTP tier has to be private: self-host or BYOC (the whole stack private).

The identity half of every option above - which key signs, who verifies it and
how strictly, what a third-party consumer caches, and what running GoTrue
yourself against the managed database does and does not give you - is measured in
one place in [Supabase Auth end to end](/reference/supabase-auth-end-to-end/).

## Reading the numbers

The split between the socket and the HTTP tier holds regardless of plan or region: the socket is lockable, the HTTP tier keeps a public endpoint, and a different tier changes neither which surface a lever touches nor that fact. Every "restrict the REST API by IP" request lands in option 3: it is not a managed capability and the DB-layer workaround does not fire on hosted, so the REST layer has to be one you own. The boundary generalises further than the status codes: controls that sit on the row, the grant, or the token travel with the database; controls that assume a network edge have to be rebuilt on an edge you run. The control plane is the same shape one layer up - `api.supabase.com` is public and PAT-only, so machine and ops access is gated at your own tooling behind an Access service token (the tooling holds the PAT), the pattern in [kubectl behind Cloudflare Access](/guides/kubectl-cf-access/). For the evidence side of a lockdown, pgaudit is available on the project (statement auditing to the Postgres log, read through the Management API logs), and `GET /database/backups` on a fresh project reports `pitr_enabled=false` with `walg_enabled=true` - recovery is daily backups until PITR is enabled (security-lockdown S09).
