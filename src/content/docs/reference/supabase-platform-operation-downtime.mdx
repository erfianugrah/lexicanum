Planning a maintenance window means knowing what an operation costs. The usual
answer is a single duration - "a restart takes about a minute" - and that
number is wrong in a way that matters: the paths do not move together. An
application whose read path is PostgREST may not notice a restart at all, while
one signing users in during the same window fails for over a minute.

This is the matrix behind that claim: four platform operations, five connection
paths, measured rather than asserted.

<Aside type="caution" title="Provenance">
Measured 2026-08-04 on throwaway Micro projects in `ap-southeast-1`, from an
IPv4-only vantage in Singapore, sampling every **500 ms**. Every window here is
**n=1** - one run per operation. These are observations, not a distribution,
and a second run would move the numbers. What generalizes is the shape and the
ordering, not the seconds. Anything below that was read from an API rather than
measured is labelled as such.
</Aside>

## TL;DR

- **REST and Realtime never failed** under any of the four operations. Zero
  failed samples at 500 ms.
- **A resize costs about twice a restart.** Auth 131 s resizing up against 75 s
  restarting; the pooler 207 s against 158 s.
- **The pooler is the slowest path every time**, roughly twice the HTTP tier on
  a restart, and it is alive throughout - what changes is how the backend is
  unavailable.
- **A network restriction never touches the HTTP tier.** It reaches the pooler
  in about a second.
- **The pooler's error text names the operation**, which makes it diagnostic
  rather than merely negative.
- **The upgrade window is not measurable on a throwaway project**, structurally.

## Why the paths differ

The five paths terminate in different places, and that is the whole
explanation. REST, Auth, Storage and Realtime reach Postgres from inside the
project's own network; a client's connection terminates at the service, not at
the database. The pooler and a direct connection put the client's socket much
closer to the thing being restarted.

## The matrix

Client-visible outage per path. A dash means zero failed samples.

| operation | REST | Realtime | Auth | Storage | pooler |
| --- | --- | --- | --- | --- | --- |
| restart | - | - | 75 s | 78 s | 158 s |
| network restriction | - | - | - | - | bites in 1 s |
| resize up (micro -> small) | - | - | 131 s | 127 s | 207 s |
| resize down (small -> micro) | - | - | 99 s | 100 s | 196 s |

Every path that failed did so about 2-3 seconds after the API returned, so
time-to-bite is effectively constant and the interesting variable is recovery.

### Restart

REST and Realtime served continuously. Auth and Storage went down for 75 s and
78 s, and they fail differently from each other - `HTTP 521` and `HTTP 500`. A
client retrying on any 5xx treats those alike; one matching a specific status
does not.

### Resize

Resizing is not a restart with extra steps, it is roughly twice one. Budget a
maintenance window off the restart figure and you will under-budget.

Direction matters, but only on the HTTP tier: growing costs about a third more
than shrinking (Auth 131 s against 99 s), while the pooler is within 5 % either
way (207 s against 196 s). Whatever dominates the pooler's window is something
neither direction escapes.

Compute size is not a resize endpoint - it is an addon mutation, `PATCH` on the
project's billing addons with an `addon_type` of `compute_instance`[^api-spec].
Returning to the smallest size REMOVES the addon rather than setting one, and
the subsequent read reports no compute addon at all.

### Network restriction

Locking the database to a CIDR that excludes you does not lock down REST, Auth,
Storage or Realtime. Four paths, zero failed samples, twice. They reach Postgres
from inside and never traverse the restricted path.

It does reach the pooler, which is the part worth knowing: Supavisor enforces
the database allow-list against the CLIENT address, so the pooled port is
covered by the restriction and not only a direct connection. It takes effect
about a second after the API returns, and the refusal names the rejected
address, so the failure is self-diagnosing.

<Aside type="note">
The outage duration for this operation is an artifact of the test, not a
platform property: the probe holds the restriction for a fixed dwell before
restoring it. The platform facts are the ~1 s to bite and the ~2 s to recover.
</Aside>

## The pooler tells you which operation is underway

Four operations, four distinct error strings:

| operation | pooler error |
| --- | --- |
| restart | `Failed to connect to database: {:error, :timeout}` |
| network restriction | `(EADDRNOTALLOWED) address not in tenant allow_list` |
| resize up | `Failed to connect to database: {:error, :econnrefused}` |
| resize down | `terminating connection due to administrator command` |

Only the last is a Postgres message; the rest are Supavisor's. So the pooler is
alive through all four, and what varies is how the backend is unavailable -
unreachable, refused, deliberately shut down, or the client not permitted. That
makes the error worth logging verbatim: it distinguishes "someone is resizing
this project" from "someone changed the allow-list" without opening a ticket.

Auth and Storage keep their own modes throughout, `HTTP 521` and `HTTP 500`.

## The upgrade window, and why it is missing

The obvious next row is a major upgrade, which is widely described as costing
hours. It is absent here for a structural reason rather than an oversight.

A freshly created project comes up already at the latest app version:
`eligible: false`, current equal to latest, no upgrade targets. And the
conditions cannot be arranged, because the version selectors on project
creation are both deprecated and typed null in the published API
schema[^api-spec] - a created project takes the current default and there is no
way to ask for an older one.

So measuring a real client-visible upgrade window requires a project that has
aged past the current version, which means being willing to upgrade something
real. That is why the figure stays folklore.

What is readable for free is the platform's own estimate. The eligibility
payload carries a `duration_estimate_hours` field, which reported **1 hour**
for a patch-level app upgrade on three aged projects, each with a single target
and no validation errors. Two caveats travel with that number: it is a
published estimate rather than a measured outage, and this page has already
shown those differ per path by up to 2x; and all three returning exactly `1`
reads as a coarse figure rather than a per-project computation.

## Reading the numbers

**n=1.** One run per operation. The ordering held across four operations and
two projects, which is worth more than any individual second.

**500 ms resolution.** An earlier measurement of the same restart sampled every
5 s on a single path and reported one duration; at that resolution a short
outage rounds to nothing and a per-path difference is invisible. Any window
quoted without its sampling interval is not a measurement.

**One vantage.** Singapore, IPv4 only. The direct port is IPv6-only and was
therefore never in this matrix - which also means the pooler column has no
unpooled baseline to be compared against.

**What generalizes:** that the paths differ, that the pooler is slowest, that
the HTTP tier is insulated from database-socket controls, and that the error
text is diagnostic. **What does not:** the specific seconds.

## Evidence

| Claim | How it was checked |
| --- | --- |
| Restart: REST and Realtime zero failed samples; Auth 75 s, Storage 78 s, pooler 158 s | Measured, 500 ms sampling, one Micro project |
| Resize up 131/127/207 s, down 99/100/196 s | Measured, same probe set, same project |
| Restriction does not affect the HTTP tier | Measured twice, zero failed samples on four paths |
| Restriction bites in ~1 s and recovers in ~2 s | Measured; the dwell between them was chosen, not measured |
| Per-operation pooler error strings | Captured verbatim from the failing probe |
| Compute size is an addon mutation, not a resize endpoint | Read from the published OpenAPI document[^api-spec] |
| A fresh project is already at the latest version and cannot be downgraded | Read from the eligibility endpoint and the create schema[^api-spec]; not upgraded |
| `duration_estimate_hours` of 1 for a patch-level upgrade | Read from the eligibility endpoint on three projects; **not** a measured outage |
| Direct port 5432 behaviour | **Not tested** - IPv6-only, unreachable from this vantage |
| Major upgrade window | **Not tested** - not constructible on a throwaway project |

## Reproducing

Sample every connection path continuously while triggering the operation out of
band, and record the failure mode next to the duration. Two details decide
whether the result means anything:

Recovery must require sustained success, not a single passing sample. The
pooler queues before it refuses, so one lucky probe mid-outage will otherwise
be recorded as recovery.

A path that was already failing before the operation voids that row. Without
that check, a bad credential reads as a platform outage.

[^api-spec]: Supabase, "Management API OpenAPI document," api.supabase.com. https://api.supabase.com/api/v1-json
