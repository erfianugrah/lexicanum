A Supabase read replica is a second database billed at the primary's compute size, and it only earns that bill if requests reach it. This page maps which requests can, which never do, what the replica costs line by line, and how to measure its share yourself.

Pricing, prerequisites and the product boundaries here are documented rather than measured: the Supabase docs were read on 2026-10-08 and every such claim carries a footnote. Five groups of runs were measured in the supabase-lab. The prerequisite chain on a Pro org (sfp-platforms S07/S07e, 2026-08-25) and a same-region replica on a Medium primary in ap-southeast-2 (medium-serverless MS06, 2026-09-30) cover creating a replica. RR01 (replica-routing, 2026-10-10) covers routing and lag: Pro org, one project with a Small primary in ap-northeast-1 and a replica in ap-southeast-1, one run. RR02 (2026-10-23, two runs in the same shape) covers a lagging, down or removed replica and the other products through the load balancer. RR03 (2026-10-26, two runs, one project each) moved both databases into one region: a Small primary and a Small replica in ap-southeast-1, with `@supabase/supabase-js` 2.118.0, and covers user tokens and RLS on the replica, key types, function calls by method, `HEAD`, the same-region split and lag under steady writes. RR01 sent `GET`s and `POST`s through the load balancer from a Singapore workstation and from Edge Functions in eight regions, read what the load balancer logged, and held a long query on the replica while the primary ran conflicting commands. Each measured row names its module id and date; the rest is labelled documented or inferred. The page says where RR01 stops: one project, one run, one replica region, one client at a few requests per second.

**TL;DR**

- Over HTTP, only Data API `GET` requests can be served by a replica, and only when they go to the API load balancer endpoint or to the replica's own API endpoint; SQL over the replica's own pooler or connection string also reaches it. Non-`GET` requests through the load balancer go to the primary.[^sb-rr]
- A Postgres function called over `POST /rest/v1/rpc/...` is a non-`GET` request. In supabase-js, `rpc(fn, args, { get: true })` sends it as a `GET`, which the docs name as the way to run a read-only function on a replica.[^sb-rr][^postgrest-js-rpc]
- Auth always runs on the primary, even through the load balancer; Storage and Realtime cannot use a replica either.[^sb-rr] A custom domain bypasses the load balancer.[^sb-rr]
- A replica bills compute at the primary's size by the hour, a disk 1.25x the primary's billed from the first byte, and copies of any provisioned IOPS, throughput and IPv4.[^sb-rr-usage][^sb-disk-usage] Compute credits do not apply to it, and the spend cap does not cover it.[^sb-rr-usage][^sb-compute-usage]
- Read the replica's share from the API logs field `metadata.load_balancer_redirect_identifier`, from API Reports, or from Database Reports with the Source toggle set to the replica.[^sb-rr][^sb-log-fields]
- Measured 2026-10-10 (RR01, Tokyo primary, Singapore replica): 40 of 40 `GET`s to `rpc/rr_whoami` through the load balancer from a Singapore workstation were served by the replica, and a `POST` to the same function and a `POST` insert were served by the primary. From Edge Functions pinned with `x-region`, the replica served ap-southeast-1, ap-southeast-2, ap-south-1 and sa-east-1; the primary served ap-northeast-1, eu-west-1, us-east-1 and us-west-1. The load balancer's log row names the choice, and it followed the request's Cloudflare colo.
- The load balancer did not route around a bad replica (RR02, 2026-10-23, two runs): it kept sending every read to a replica whose replay had stopped (up to 176,772 ms stale), sent none to the primary while the replica was down, and after the only replica was removed answered `400 Load balancer does not seem to be configured properly.` for the rest of a 1,200 s watch. GraphQL through it is refused with `400`.
- With the primary and the replica in the same region (RR03h, 2026-10-26, two runs), the load balancer spread `GET`s over both, roughly half each, from every vantage tried: 111 / 89 and 94 / 106 replica / primary of 200 from a Singapore workstation, and about half from Edge Functions in ap-southeast-1, us-east-1 and eu-west-1. Across the cross-region runs the same workstation got 100 % replica.
- A user's ES256 access token behaved on the replica as on the primary (RR03d, RR03e): the same rows under RLS, the same `auth.uid()`, for every key type, through the load balancer, the replica's host and the primary's host. In supabase-js, the `accessToken` option and a global `Authorization` header work against the replica's host; `auth.setSession()` there fails (`Failed to parse JSON`) and the next read goes out with the anon key and returns 0 rows with no error.
- Function calls route by method, not by volatility (RR03f): `get: true` calls of stable, security-definer and volatile read-only functions reached both nodes, every `POST` reached the primary, and a writing function called by `GET` answered `405` with `25006` on either node, so that error does not say which node answered.
- A long replica query is cancelled when a primary command conflicts with it: `max_standby_streaming_delay` is 30 s and `hot_standby_feedback` is off on both nodes, and all 6 held queries in RR01 were cancelled with `40001` 30 to 32 s after the primary's command. Replay stopped for that time, so a row written afterwards was invisible on the replica for 30 to 32 s.

## Which do I pick

| Situation | Choice | Why |
| --- | --- | --- |
| Primary CPU high, workload under roughly 80% reads | Larger compute | "Read Replicas only serve reads and won't help writes."[^sb-rr] |
| Read-heavy, users far from the primary's region | Replica near the users, clients on the load balancer endpoint | geo-routing sends each `GET` to the closest database[^sb-rr] |
| Read-heavy, users near the primary | Replica in the primary's region, clients on the load balancer endpoint | RR03h: the load balancer split `GET`s roughly half and half between a same-region primary and replica; read-your-writes was not measured; inferred not guaranteed, since the next `GET` can land on either node |
| Analytical queries competing with the app | Replica, the analytics job on the replica's connection string | the replica has its own pooler and database endpoint[^sb-rr] |
| Region outage cover | Warm standby, not a replica | no promotion path is documented; see [the DR tiers](/reference/supabase-dr-tiers/) |
| Data must stay in one jurisdiction | Replica only in an acceptable region | a replica is a full copy in its own region; see [data residency](/reference/supabase-data-residency/) |
| Long analytical query on the replica | Keep it under 30 s, or accept cancellation | RR01: a conflicting primary command cancelled a held query with `40001` after 30.2 to 31.6 s with `hot_standby_feedback` off |
| A read must see the row just written | Read it from the primary | on a replica whose replay is blocked, a new row was invisible for 30.2 to 31.3 s (RR01) |
| Replica exists, its share of reads is near zero | Fix the client path, or delete it | every hour bills at the primary's compute size, outside credits and the spend cap[^sb-rr-usage] |

The same check as a list:

1. Do the API logs or API Reports show `GET` requests served by the replica? If yes, it is serving reads; keep it and watch replication lag.
2. If not, are the clients on the load balancer endpoint or the replica's endpoint? If not, point Data API reads at the load balancer endpoint.
3. Are the reads function calls sent as `POST`? If yes, call read-only functions with `get: true`.
4. Is the Data API behind a custom domain? If yes, send reads to the replica's own endpoint.
5. Are the users closer to the primary than to the replica, with the replica in another region? If yes, move the replica toward the users or delete it.
6. If the replica is in the primary's region, expect roughly half the `GET`s on it (RR03h, two runs) and check `chosen_supabase_region` in the `edge_logs` rows (RR01o); a share far from that is worth a look at the client path.

## The load balancer

Each replica has its own database and API endpoints, and a project with replicas also gets an API load balancer endpoint, listed on the API settings page.[^sb-rr] The docs on routing, quoted:

> The load balancer enables geo-routing for Data API requests to automatically route `GET` requests to the database closest to your user ensuring the lowest latency. You can also send Non-`GET` requests through this endpoint, and they are routed to the Primary database automatically.[^sb-rr]

> Due to the requirements of the Auth service, all Auth requests are handled by the Primary, even when sent over the load balancer endpoint.[^sb-rr]

The routing rule changed on 2025-04-04, from round-robin "among all databases (all read replicas + primary) of your project, regardless of location" to geo-routing that "directs requests to the closest available database (all read replicas + primary)".[^sb-rr] The primary is in that pool. Under geo-routing as documented, a replica takes a `GET` when it is the closest database to the caller (inferred: a replica farther than the primary takes none). The docs' load balancer section does not say how it chooses between a primary and a replica in the same region; the page does say the load balancer "balances requests between your Primary database and Read Replicas" (read 2026-10-26).[^sb-rr] RR01 had no same-region case. The platform does accept a same-region replica: MS06 (2026-09-30) created one and it answered a read over its own pooler string 219 s after setup, and RR03h (2026-10-26) measured the split, [below](#the-split-inside-one-region-rr03h): roughly half the `GET`s to each node, per request.

The load balancer exists only while a replica does. "If you remove all Read Replicas from your project, the load balancer and its endpoint are removed as well."[^sb-rr] A client still pointed at the load balancer endpoint when the last replica goes has nowhere to send requests, so repoint it first: in RR02j the endpoint answered errors for at least 1,185 s after the remove call, `400 Load balancer does not seem to be configured properly.` continuously from 70.7 s (run 2), and kept resolving (checked in run 2).

<Aside type="caution" title="A custom domain bypasses the load balancer">
"If you use a custom domain, requests will not be routed through the load balancer. You should instead use the dedicated endpoints provided in the dashboard."[^sb-rr] A project that serves its Data API through a custom domain therefore sends no Data API reads to a replica unless the client calls the replica's own endpoint for them.
</Aside>

## When the replica is behind, down or removed (RR02)

RR02 (replica-routing, 2026-10-23) repeated RR01's shape twice, one throwaway Pro project per run: Small primary in ap-northeast-1, one Small replica in ap-southeast-1, a Singapore workstation for which the load balancer picks the replica. Each timed read was `GET /rest/v1/rpc/rr_node` with the anon key, a function returning which node ran it and `stale_ms`, the node's clock minus the newest heartbeat row written on the primary every 250 ms. The load balancer, the replica's own host and the primary's own host were read in parallel, one request at a time each with a 5 s client timeout. "Lagging" means `stale_ms` above 2,000 ms, a threshold chosen for the module.

- A replica whose replay has stopped keeps getting every read. A repeatable-read query held on the replica with `pg_sleep(180)` while the primary updated and vacuumed the same table stopped replay. Run 1 (`max_standby_streaming_delay` read `600000ms` on the replica): the replica host was lagging for 174.6 s, and all 586 reads through the load balancer in that span were served by the replica, every one lagging, up to 176,772 ms stale. Run 2 (the replica still read the `30000ms` default): the query was cancelled at 50 s, and all 98 reads in the 28.8 s span went to the replica. None went to the primary, and no read failed: a stale replica answers 200 with old data.
- A replica that is down does not hand its reads to the primary. `POST /projects/{ref}/restart` restarted both nodes, primary first. While the replica was down and the primary up (about 65 to 100 s in run 1, 85 to 120 s in run 2) the load balancer failed every read in that span (21 and 29 failed reads across its failing span), mostly by the 5 s client timeout, with `HTTP 521`, `HTTP 503 upstream connect error or disconnect/reset before headers` and `HTTP 503 PGRST002` among the rest, and sent none of its 334 and 415 reads across the restart phase to the primary. It recovered in the same 5 s bucket as the replica.
- Removing the only replica leaves the load balancer endpoint answering errors. After `POST read-replicas/remove` (`204`) the load balancer's first failure came about 1 s later, then `HTTP 521`, client timeouts and `HTTP 400 Load balancer does not seem to be configured properly.`; run 2 answered that 400 continuously from 70.7 s to the end of a 1,200 s watch, run 1 alternated it with `HTTP 530` to the end of 360 s. It served 0 of 1,034 and 0 of 4,103 reads from the primary while the primary's own host answered all 958 and 3,236 of its reads, and the name kept resolving once a minute throughout run 2.
- Other products through the load balancer (run 1). Auth (`/health`, `/settings`, admin create user, password grant, `GET /user`), Storage (list, create bucket, upload, authenticated download) and a Realtime join with Postgres Changes answered as they do on the primary's host, and the replica's own host refused every one sent to it (`400`; Realtime `ws error at handshake`). The load balancer's log names the primary for the Auth rows and carries no redirect identifier for Storage and Realtime, so where those ran is inferred (the primary's services), not shown. GraphQL through the load balancer was refused `400 Load balancer does not handle POST requests for the path /gr...` (the module cut the text), and the `GET` form likewise, while GraphQL on the primary's host answered 200 to `POST` (its `GET` form answered `404 PGRST202`). An Edge Function call answered 200 through it, with no `edge_logs` row on that host.
- Not separated: a replica down while the primary and the load balancer config are untouched (the Management API has no per-replica restart; `restart` takes down both nodes), lag from write volume (one bulk insert filled the Small disk after 19.7 s without lagging the replica past 2,000 ms), and the load balancer's rule itself. Two runs, one region pair, one vantage.

## User tokens, keys and function calls on a same-region replica (RR03)

RR03 (replica-routing, 2026-10-26) ran twice, one throwaway Pro project per run: a Small primary in ap-southeast-1 with `pitr_7` and one Small replica in the same region. Clients were the Singapore workstation (Cloudflare colo `SIN`) and Edge Functions invoked with `x-region`, on `@supabase/supabase-js` 2.118.0. Replica setup answered `204` on the first attempt, and the first session-pooler connection to the replica came 166 s and 170 s after the call. The load balancer host was `<ref>-all` again. Run 2 changed three things in the module (no `signOut` after sign-in, the order of nodes recorded per request, and a log poll that waits for the row total to stop growing); the rows below say where that matters. Figures are from the [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/aca5612/experiments/replica-routing/RUNLOG.md) and the two [artifacts](https://github.com/erfianugrah/supabase-lab/tree/aca5612/experiments/replica-routing/out/2026-10-26/).

The table `rr3_docs` had RLS on and one policy, `for select to authenticated using (tenant_id = (select auth.uid()))`, with 3 rows for user A, 5 for user B and 2 for a third tenant. Both users were created and signed in on the primary's host; their access tokens were ES256 with a `kid` and an `iss` of the primary's host. Each read returned `pg_is_in_recovery()` to name the node, and `edge_logs` on the load balancer host was a second record of where each request went.

### User JWTs and RLS (RR03d)

Each user read a `security_invoker` view over `rr3_docs` and a stable function through four client patterns on each host: a supabase-js client created with the `accessToken` option, a client with `global.headers.Authorization`, a client on which `auth.setSession()` was called, and raw `fetch` with the legacy anon key as `apikey` and the user's token as Bearer.

| Read | Load balancer | Replica host | Primary host |
| --- | --- | --- | --- |
| user A, `accessToken`, header or raw | 3 rows, uid A, 0 of another tenant | 3 rows, replica, uid A, 0 of another tenant | 3 rows, primary, uid A, 0 of another tenant |
| user B, same | 5 rows, uid B, 0 of another tenant | 5 rows, replica, uid B, 0 of another tenant | 5 rows, primary, uid B, 0 of another tenant |
| anon key only | 0 rows, `auth.uid()` null, role anon | the same, on the replica | the same, on the primary |

RLS and `auth.uid()` behaved the same on the replica as on the primary for an ES256 user token, in both runs; through the load balancer the node changed from read to read and the rows did not.

- `auth.setSession()` on the replica's host failed in both runs with `Failed to parse JSON`, because the replica host's answer to `GET /auth/v1/user` was not JSON (RR02f recorded `400` for its other Auth paths; RR03 did not record the status). The read after it went out with the anon key as Bearer and returned 0 rows with no error. In run 2 the same call succeeded on the load balancer host and the primary host. Run 1's `setSession` failed on the load balancer and primary hosts with `Auth session missing!` (status 400 on the supabase-js error object; `edge_logs` recorded HTTP 403 for the two load balancer attempts) and on the replica host with `Failed to parse JSON` as in run 2, because the module had signed out (`signOut({ scope: "local" })` ends the session on the server); that was a module bug, not a platform finding.
- `signInWithPassword` on a client created on the load balancer host worked in both runs; the token's `iss` was the primary's host, and that token read as user B on the replica's host. On the replica's host it failed with `Failed to parse JSON`.

### Key types (RR03e)

`GET rpc/list_docs_invoker` with each header combination answered 200 on all three hosts in both runs, with the same role on each:

| `apikey` | `Authorization` | Role, rows seen |
| --- | --- | --- |
| legacy anon JWT (HS256) | the same | anon, 0 |
| `sb_publishable_` | none | anon, 0 |
| `sb_publishable_` | `Bearer sb_publishable_...` | anon, 0 |
| `sb_publishable_` or legacy anon JWT | user A's ES256 token | authenticated, uid A, 3 |
| `sb_publishable_` or legacy anon JWT | user A's claims signed HS256 with the legacy JWT secret | authenticated, uid A, 3 |
| legacy service_role JWT | the same | service_role, 10 |
| `sb_secret_` | none | service_role, 10 |

The HS256 token was minted by the module from user A's claims with the legacy secret (`jwt_secret` from `GET /v1/projects/{ref}/postgrest`); an HS256 token issued by Auth itself was not tested, since new projects sign with ES256. supabase-js created with the publishable key sent it as both `apikey` and Bearer with no session, and the user's token as Bearer with the `accessToken` option.

### Function calls by method (RR03f)

supabase-js on the load balancer host, user A by `accessToken`, 5 calls per function with `rpc(fn, {}, { get: true })` (`GET`) and with `rpc(fn)` (`POST`). Counts are replica / primary:

| Function | `GET`, run 1 | `GET`, run 2 | `POST`, both runs |
| --- | --- | --- | --- |
| `rr3_node` (stable) | 1 / 4 | 1 / 4 | 0 / 5 |
| `list_docs_invoker` (stable) | 3 / 2 | 2 / 3 | 0 / 5 |
| `list_docs_definer` (stable, security definer) | 3 / 2 | 2 / 3 | 0 / 5 |
| `list_docs_volatile` (volatile, reads only) | 1 / 4 | 2 / 3 | 0 / 5 |
| `touch` (volatile, inserts a row) | `405` `25006`, 3 / 2 | `405` `25006`, 3 / 2 | 0 / 5, HTTP 200 |

- Routing followed the method; volatility and security definer did not change it: the volatile read-only function was served by `GET` on the replica as well as the primary, and every `POST` went to the primary, where `touch` wrote (`rr3_touch` went from 0 to 6 rows each run, 5 through the load balancer and 1 on the primary's host).
- `touch` by `GET` answered HTTP `405`, SQLSTATE `25006`, `cannot execute INSERT in a read-only transaction`, on the replica (`in_recovery=t` in the error detail) and on the primary (`in_recovery=f`). PostgREST runs a `GET` read-only on either node, so `25006` does not tell a client which node it reached.
- `list_docs_definer` ran as `postgres` on both nodes and saw `n` 3 (filtered by `auth.uid()` inside the function) and `all_rows` 10 (the table owner is not subject to RLS), the same on the replica as on the primary.
- On the replica's own host every `GET` answered as above and every `POST` answered `400 Read replica does not handle POST requests for the path /res...` (the module's 60-character cut of a non-JSON body).

### HEAD and count=exact (RR03g)

Through the load balancer, 10 calls each, replica / primary:

## Reads that arrive as POST

PostgREST runs `GET` and `HEAD` in a `READ ONLY` transaction: "Modifying the database inside READ ONLY transactions is not possible. PostgREST uses this fact to enforce HTTP semantics in GET and HEAD requests."[^postgrest-tx] A function call over `POST` runs read-write when the function is `VOLATILE` and read-only when it is `STABLE` or `IMMUTABLE`, but either way it is a non-`GET` request and the load balancer sends it to the primary.[^postgrest-tx][^sb-rr] The docs' fix is the client option:

> To call a read-only Postgres function on Read Replicas through the REST API, use the `get: true` option.[^sb-rr]

```ts
// POST /rest/v1/rpc/top_products - always the primary
const a = await supabase.rpc("top_products", { lim: 20 });

// GET /rest/v1/rpc/top_products?lim=20 - eligible for a replica
const b = await supabase.rpc("top_products", { lim: 20 }, { get: true });
```

The supabase-js reference shows the option as "Call a read-only Postgres function" and the client's own doc comment says that with `get: true` "the function will be called with read-only access mode".[^sb-js-rpc][^postgrest-js-rpc] In the postgrest-js source, `get: true` sets the method to `GET` and moves each argument into the query string: arrays become `{a,b}` literals and any other value goes through JavaScript string conversion, so an object argument would arrive as `[object Object]` (source read at commit `84e2c5d`, not run).[^postgrest-js-rpc] RR03f called the option itself on supabase-js 2.118.0: `get: true` calls reached the replica on 1 to 3 of 5 calls per function with both nodes in one region, and the plain `rpc()` calls never did. Volatility did not decide routing: a volatile function that only reads was served by the replica under `GET`. Two consequences:

- The function must not write. A function that writes (inserts, updates, or calls `nextval()`) fails under `GET`, because `GET` runs READ ONLY; the PostgREST docs' example, a view calling `nextval()`, answers HTTP 405 with SQLSTATE `25006`, "cannot execute nextval() in a read-only transaction".[^postgrest-tx] RR03f (2026-10-26) measured the same through the load balancer: a volatile function that inserts answered `405` `25006` under `get: true` on the replica and on the primary alike, so the error does not show which node answered.
- Keep `get: true` for scalar and array arguments. PostgREST matches `GET` parameters to function parameters by name, `?a=1&b=2`.[^postgrest-fn]

The Securing your API page states the same split from the rate-limiting side: "`GET` and `HEAD` requests run in read-only mode. They can be served by Read Replicas, which don't support writing to the database."[^sb-securing-api]

## What a replica does not do

- Writes. The replica accepts `select` only.[^sb-rr]
- Auth, Storage and Realtime. "Requests to other Supabase products, such as Auth, Storage, and Realtime, aren't able to use a Read Replica or its API endpoint."[^sb-rr]
- Failover. The read replica docs describe no way to promote a replica or fail over to one (doc-read 2026-10-08); the production checklist recommends replicas "if you require availability resilience to a disk failure event".[^sb-going-prod] For a region outage, the warm standby in [the DR tiers reference](/reference/supabase-dr-tiers/) is the tier that runs somewhere else.
- Survive an upgrade or a restore. "Projects with read-replicas can't be upgraded. You need to delete the replicas and re-create them after upgrade completes."[^sb-upgrading] The getting-started page puts data restorations under the same rule: all replicas come down first, and you re-deploy them once the operation completes.[^sb-rr-start] The [major upgrade guide](/guides/supabase-postgres-major-upgrade-e2e/) carries this as a pre-window checklist item; reads go to the primary only once clients are repointed at the primary's URL (the load balancer endpoint is removed with the last replica), so repoint first and size the primary to carry them.
- Fresh data on demand. Replication is asynchronous,[^sb-rr] and "High replication lag can result in stale data returned for queries executed against the affected read replicas."[^sb-rr-start] The lag measured in RR01 is under [Replication lag and cancellation](#replication-lag-and-cancellation).

## Replication lag and cancellation

RR01 (2026-10-10; Tokyo primary, Singapore replica, one project, one run) read the standby settings and then provoked the recovery conflict that cancels a long replica query.

`pg_settings` on both nodes (RR01l):

| Setting | Value | Source |
| --- | --- | --- |
| `max_standby_streaming_delay` | 30 s | `default` |
| `max_standby_archive_delay` | 30 s | `default` |
| `hot_standby_feedback` | off | `default` |
| `statement_timeout` | 120 s | configuration file |
| `hot_standby` | on for the replica, off for the primary | |

The 30 s matches the Supabase blog's description of `max_standby_streaming_delay` as the time the replica waits before cancelling conflicting queries, "default: 30 seconds", and its note that raising it costs more replication lag during heavy queries (blog dated 2026-01-15; documented, not run).[^sb-blog-rr]

### The trial

On the replica, a repeatable-read transaction counted a 50,000-row table and then ran `select pg_sleep(100)`. Three seconds later the primary ran either `update` plus `vacuum` on that table (RR01m1 to RR01m3) or `lock table ... in access exclusive mode` (RR01n1 to RR01n3). All 6 replica statements were cancelled with SQLSTATE `40001`, `canceling statement due to conflict with recovery`. The DETAIL was `User query might have needed to see row versions that must be removed.` after the vacuum and `User was holding a relation lock for too long.` after the lock.

| Conflicting primary command | Cancelled after | Row written afterwards, visible on the replica after |
| --- | --- | --- |
| `update` + `vacuum` (3 trials) | 31.1, 31.3, 31.6 s | 30.8, 30.5, 31.3 s |
| `ACCESS EXCLUSIVE` lock (3 trials) | 30.2, 30.2, 30.3 s | 30.4, 30.2, 30.4 s |

Times are from the start of the primary command, taken on the client clock when the error arrived; the visibility column polls the replica's endpoint at 0.7 s. Replay lag sampled during a stall stayed flat (822,920 bytes in the first vacuum trial, 352 bytes in the first lock trial), so replay on the replica was stopped, not slow. Why the vacuum trials run about 1 s longer was not separated: the `update` of 50,000 rows replays first and may start the timer later. `pg_stat_database_conflicts` on the replica read `confl_snapshot` 3 and `confl_lock` 2 after the 3 vacuum and 3 lock trials; its reads lag, so the counters are recorded and not used.

### What it bounds

The read-your-writes gap on a replica is bounded by `max_standby_streaming_delay` when a conflicting command is replaying, not by network lag: a row written on the primary after the conflicting command was invisible on the replica for 30.2 to 31.3 s. That is the largest gap RR01 measured. The load balancer was not read during a stall, so whether it keeps sending `GET`s to a stalled replica is not measured. Not run: `hot_standby_feedback` on, another `max_standby_streaming_delay`, a query idle in transaction instead of in `pg_sleep`, and a query through the Data API (which has its own statement timeout).

### Without a conflict

Every write in RR01 went from Singapore to Tokyo, so the client took longer to return than replication took to arrive, and the rows below bound the gap for a client of that shape; they are not a measurement of replication delay.

| Row | n | Result |
| --- | --- | --- |
| RR01i: insert on the primary's endpoint, then `GET` from the replica's endpoint at once | 30 | 0 of 30 first reads missed; time from `POST` response to the first read that saw the row: median 36.6 ms, p95 113.5 ms, maximum 223 ms; `POST` round trip median 122.2 ms |
| RR01j: `POST` through the load balancer, then `GET rr_whoami` through it | 30 | first `GET` served by the replica 30 of 30, row present 30 of 30 |
| RR01k: per-insert delay from the two database clocks (insert on the primary through a session pooler connection, replica polled with `clock_timestamp()`) | 40 | first poll that saw the row: median 41 ms, p95 44.3 ms, maximum 655.5 ms; poll round trip median 7.3 ms; most polls for one insert 83 |

In RR01i the visible time equals the read's own round trip, because the row was already there. The RR01k median is mostly the insert's response travelling to the client before the first poll, so for 38 or more of the 40 inserts it is a ceiling on the delay; the maximum is a real delay of that order for at least one insert, and its cause was not examined. The two clocks are on different hosts, so skew sits inside every RR01k figure.

## Checking whether the replica serves reads

The dashboard and the logs both answer it, from the docs. Items 1, 2 and 4 were not exercised by a lab module; item 3's fields were read in RR01o (2026-10-10), and item 5 was run in RR01:

1. Database Reports, with the Source toggle on the replica, shows its resource use.[^sb-rr] A replica at idle CPU while the primary is busy is the first sign (inferred).
2. API Reports covers "API requests going through either a Read Replica or Load Balancer API endpoint".[^sb-rr]
3. In the API logs, a request through the load balancer records the database that served it: "The upstream database or the one that eventually handles the request can be found under the `Redirect Identifier` field. This is equivalent to `metadata.load_balancer_redirect_identifier` when querying the underlying logs."[^sb-rr] The log field reference lists it on `edge_logs` as `log_attributes['load_balancer_redirect_identifier']`.[^sb-log-fields] RR01o read it on 152 load balancer rows (`<ref>.supabase.co` for the primary, a `-rr-` host for the replica), next to `request.cf.colo` and the `load_balancer_geo_aware_info` choice fields described [above](#what-the-load-balancer-did-in-rr01).
4. Replication lag sits under Replica Information on Database Reports.[^sb-rr-start] For a metrics pipeline, the docs name `physical_replication_lag_physical_replica_lag_seconds`; the Grafana guide's alert uses `physical_replication_lag_physical_replication_lag_seconds` (not reconciled). The [Grafana monitoring guide](/guides/supabase-grafana-monitoring/) covers ingesting that endpoint. RR01 did not read this metric; it sampled replay lag as primary current LSN minus replica replay LSN during the conflicts above.
5. To tell which node answered a request, call a function that returns `pg_is_in_recovery()` and `pg_postmaster_start_time()`. `inet_server_addr()` cannot identify a replica: it returned the loopback address on the primary and on the replica (RR01 exploratory run, artifact not published).

The query below counts Data API requests per serving database and method. It is built from the documented field names and the documented query syntax[^sb-log-fields][^sb-log-sql] and was not run here (RR01o ran its own `edge_logs` queries against the Management API logs endpoint; a query that put `split(...)[1]` in the select list was refused with `Backend error! Retry your query.`, and the cause was not isolated to `split`):

```sql
-- Data API requests by serving database and method, over the Explorer's time range
select
  log_attributes['load_balancer_redirect_identifier'] as served_by,
  log_attributes['request.method'] as method,
  count() as requests
from logs
where source = 'edge_logs'
  and log_attributes['request.path'] like '/rest/v1/%'
group by served_by, method
order by requests desc
limit 50;
```

Rows with an empty `served_by` are requests the field did not describe; the docs define the field only "for API Load Balancer traffic",[^sb-log-fields] so a large empty bucket reads as traffic that never went through the load balancer (inferred). In RR01 the one load balancer `POST` row had the primary's identifier and no geo fields, so a `POST` through the load balancer is not an empty bucket. `POST` rows against `/rest/v1/rpc/` are function calls the replica cannot take until they use `get: true`.

## What to do about it

Rows marked documented rest on the docs, read 2026-10-08; rows with an RR01 id were measured on 2026-10-10 in one project and one run. The Module column says which.
