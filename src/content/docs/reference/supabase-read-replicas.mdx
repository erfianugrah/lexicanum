A Supabase read replica is a second database billed at the primary's compute size, and it only earns that bill if requests reach it. This page maps which requests can, which never do, what the replica costs line by line, and how to measure its share yourself.

Pricing, prerequisites and the product boundaries here are documented rather than measured: the Supabase docs were read on 2026-10-08 and every such claim carries a footnote. Three groups of runs were measured in the supabase-lab. The prerequisite chain on a Pro org (sfp-platforms S07/S07e, 2026-08-25) and a same-region replica on a Medium primary in ap-southeast-2 (medium-serverless MS06, 2026-09-30) cover creating a replica. RR01 (replica-routing, 2026-10-10) covers routing and lag: Pro org, one project with a Small primary in ap-northeast-1 and a replica in ap-southeast-1, one run. RR01 sent `GET`s and `POST`s through the load balancer from a Singapore workstation and from Edge Functions in eight regions, read what the load balancer logged, and held a long query on the replica while the primary ran conflicting commands. Each measured row names its module id and date; the rest is labelled documented or inferred. The page says where RR01 stops: one project, one run, one replica region, one client at a few requests per second.

**TL;DR**

- Over HTTP, only Data API `GET` requests can be served by a replica, and only when they go to the API load balancer endpoint or to the replica's own API endpoint; SQL over the replica's own pooler or connection string also reaches it. Non-`GET` requests through the load balancer go to the primary.[^sb-rr]
- A Postgres function called over `POST /rest/v1/rpc/...` is a non-`GET` request. In supabase-js, `rpc(fn, args, { get: true })` sends it as a `GET`, which the docs name as the way to run a read-only function on a replica.[^sb-rr][^postgrest-js-rpc]
- Auth always runs on the primary, even through the load balancer; Storage and Realtime cannot use a replica either.[^sb-rr] A custom domain bypasses the load balancer.[^sb-rr]
- A replica bills compute at the primary's size by the hour, a disk 1.25x the primary's billed from the first byte, and copies of any provisioned IOPS, throughput and IPv4.[^sb-rr-usage][^sb-disk-usage] Compute credits do not apply to it, and the spend cap does not cover it.[^sb-rr-usage][^sb-compute-usage]
- Read the replica's share from the API logs field `metadata.load_balancer_redirect_identifier`, from API Reports, or from Database Reports with the Source toggle set to the replica.[^sb-rr][^sb-log-fields]
- Measured 2026-10-10 (RR01, Tokyo primary, Singapore replica): 40 of 40 `GET`s to `rpc/rr_whoami` through the load balancer from a Singapore workstation were served by the replica, and a `POST` to the same function and a `POST` insert were served by the primary. From Edge Functions pinned with `x-region`, the replica served ap-southeast-1, ap-southeast-2, ap-south-1 and sa-east-1; the primary served ap-northeast-1, eu-west-1, us-east-1 and us-west-1. The load balancer's log row names the choice, and it followed the request's Cloudflare colo.
- A long replica query is cancelled when a primary command conflicts with it: `max_standby_streaming_delay` is 30 s and `hot_standby_feedback` is off on both nodes, and all 6 held queries in RR01 were cancelled with `40001` 30 to 32 s after the primary's command. Replay stopped for that time, so a row written afterwards was invisible on the replica for 30 to 32 s.

## The load balancer

Each replica has its own database and API endpoints, and a project with replicas also gets an API load balancer endpoint, listed on the API settings page.[^sb-rr] The docs on routing, quoted:

> The load balancer enables geo-routing for Data API requests to automatically route `GET` requests to the database closest to your user ensuring the lowest latency. You can also send Non-`GET` requests through this endpoint, and they are routed to the Primary database automatically.[^sb-rr]

> Due to the requirements of the Auth service, all Auth requests are handled by the Primary, even when sent over the load balancer endpoint.[^sb-rr]

The routing rule changed on 2025-04-04, from round-robin "among all databases (all read replicas + primary) of your project, regardless of location" to geo-routing that "directs requests to the closest available database (all read replicas + primary)".[^sb-rr] The primary is in that pool. Under geo-routing as documented, a replica takes a `GET` when it is the closest database to the caller (inferred: a replica farther than the primary takes none). The docs do not say how the load balancer chooses between a primary and a replica in the same region, and no lab module measured it; RR01 had no same-region case. The platform does accept a same-region replica: MS06 (2026-09-30) created one and it answered a read over its own pooler string 219 s after setup.

The load balancer exists only while a replica does. "If you remove all Read Replicas from your project, the load balancer and its endpoint are removed as well."[^sb-rr] A client still pointed at the load balancer endpoint when the last replica goes has nowhere to send requests, so repoint it first.

<Aside type="caution" title="A custom domain bypasses the load balancer">
"If you use a custom domain, requests will not be routed through the load balancer. You should instead use the dedicated endpoints provided in the dashboard."[^sb-rr] A project that serves its Data API through a custom domain therefore sends no Data API reads to a replica unless the client calls the replica's own endpoint for them.
</Aside>

## What the load balancer did in RR01

Setup: Pro org, one project, primary in ap-northeast-1 on Small compute with `pitr_7`, one replica in ap-southeast-1, run on 2026-10-10 (module RR01, [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/replica-routing/RUNLOG.md)). The probe is `GET /rest/v1/rpc/rr_whoami`, the request `get: true` sends. The function is stable and returns `pg_is_in_recovery()` and `pg_postmaster_start_time()`, which say which node answered.

### Finding the hosts

The Management API returned neither the load balancer's host nor the replica's REST host. `GET /platform/projects/{ref}/load-balancers`, the route the Dashboard calls, answered a personal access token with `401 {"message":"Unsupported access token"}` (RR01e). The replica answered at `<identifier>.supabase.co`, where `identifier` is the field of the `READ_REPLICA` entry in the pooler config. The load balancer answered at `<ref>-all.supabase.co`, which the run found by trying candidate names, so the name is observed and not documented. Read the load balancer endpoint from the API settings page.

## Reads that arrive as POST

PostgREST runs `GET` and `HEAD` in a `READ ONLY` transaction: "Modifying the database inside READ ONLY transactions is not possible. PostgREST uses this fact to enforce HTTP semantics in GET and HEAD requests."[^postgrest-tx] A function call over `POST` runs read-write when the function is `VOLATILE` and read-only when it is `STABLE` or `IMMUTABLE`, but either way it is a non-`GET` request and the load balancer sends it to the primary.[^postgrest-tx][^sb-rr] The docs' fix is the client option:

> To call a read-only Postgres function on Read Replicas through the REST API, use the `get: true` option.[^sb-rr]

```ts
// POST /rest/v1/rpc/top_products - always the primary
const a = await supabase.rpc("top_products", { lim: 20 });

// GET /rest/v1/rpc/top_products?lim=20 - eligible for a replica
const b = await supabase.rpc("top_products", { lim: 20 }, { get: true });
```

The supabase-js reference shows the option as "Call a read-only Postgres function" and the client's own doc comment says that with `get: true` "the function will be called with read-only access mode".[^sb-js-rpc][^postgrest-js-rpc] In the postgrest-js source, `get: true` sets the method to `GET` and moves each argument into the query string: arrays become `{a,b}` literals and any other value goes through JavaScript string conversion, so an object argument would arrive as `[object Object]` (source read at commit `84e2c5d`, not run).[^postgrest-js-rpc] Two consequences:

- The function must not write. A function that writes (inserts, updates, or calls `nextval()`) fails under `GET`, because `GET` runs READ ONLY; the PostgREST docs' example, a view calling `nextval()`, answers HTTP 405 with SQLSTATE `25006`, "cannot execute nextval() in a read-only transaction".[^postgrest-tx]
- Keep `get: true` for scalar and array arguments. PostgREST matches `GET` parameters to function parameters by name, `?a=1&b=2`.[^postgrest-fn]

The Securing your API page states the same split from the rate-limiting side: "`GET` and `HEAD` requests run in read-only mode. They can be served by Read Replicas, which don't support writing to the database."[^sb-securing-api]

## What a replica costs

The usage docs describe a replica as "a dedicated database" whose resources are "mirrored from the primary database".[^sb-rr-usage]

| Resource | What the replica gets | Billing |
| --- | --- | --- |
| Compute | "the same Compute size as the primary database"[^sb-rr-usage] | by the hour; a partial hour bills as a full one[^sb-rr-usage] |
| Disk size | "1.25x the size of the primary disk to account for WAL archives"[^sb-rr-usage] | from the first byte; the plan's included disk does not cover it[^sb-disk-usage][^sb-rr-usage] |
| Provisioned disk IOPS | inherits any additional IOPS[^sb-rr-usage] | as for the primary |
| Provisioned disk throughput | inherits any additional throughput[^sb-rr-usage] | as for the primary |
| IPv4 add-on | one per replica if the primary has one[^sb-rr-usage][^sb-ipv4] | "Each replica adds to the total IPv4 cost."[^sb-ipv4] |

On the invoice, replica compute is its own line, "Replica Compute Hours"; "Disk Size, Disk IOPS, Disk Throughput and IPv4 are not shown separately for Read Replicas and are rolled up into the project."[^sb-rr-usage] Searching the invoice for the replica's disk will not find it.

Two exclusions apply: no credits offset it, and no spend cap limits it. "No, Compute Credits do not apply to Read Replica Compute."[^sb-rr-usage] Paid plans include \$10 a month in compute credits, "enough to cover one Micro instance",[^sb-pricing] and they "apply only to Compute and do not cover other line items, including Read Replica Compute and Branching Compute".[^sb-compute-usage] And "Read Replicas are **not** covered by the Spend Cap": Read Replica Compute sits on the cost-control page's list of usage the cap excludes.[^sb-rr-usage][^sb-cost-control]

Compute per replica, at the monthly prices on the public pricing page (doc-read 2026-10-08). Projects below XL can have up to two replicas, XL and above up to five.[^sb-rr-start]

| Primary compute | Replica compute per month | Replicas allowed |
| --- | --- | --- |
| Small | \$15 | up to 2 |
| Medium | \$60 | up to 2 |
| Large | \$110 | up to 2 |
| XL | \$210 | up to 5 |
| 2XL | \$410 | up to 5 |
| 4XL | \$960 | up to 5 |
| 8XL | \$1,870 | up to 5 |
| 12XL | \$2,800 | up to 5 |
| 16XL | \$3,730 | up to 5 |

Monthly prices from the pricing page;[^sb-pricing] the usage docs' own examples quote Large at \$111 for 730 hours.[^sb-rr-usage] Micro and Nano are absent because a replica needs Small or larger.[^sb-rr-start]

The docs' smallest worked example, quoted line for line: a Pro project on Small with one replica and no add-ons bills Pro Plan \$25, primary compute \$15, primary disk 8 GB \$0, replica compute \$15, replica disk 10 GB \$1.25, subtotal \$56.25, Compute Credits -\$10: \$46.25 a month.[^sb-rr-usage] The credits cannot apply to the replica's compute, so the replica is \$16.25 of that, none of it offset. The same page's second example, two Large replicas with IPv4 and provisioned IOPS and throughput, totals \$427.06.[^sb-rr-usage]

A resize moves the replicas with the primary. When the primary's compute changes, the primary restarts first while the replicas stay available, then "all the Read Replicas are restarted (and resized, if needed) concurrently".[^sb-rr-start] The compute cost of an upsize therefore multiplies by one plus the replica count.

## Prerequisites

The docs list four requirements on top of a Pro, Team or Enterprise plan: the project runs on AWS, on "at least a Small compute add-on", on Postgres 15 or later, and not on legacy logical backups.[^sb-rr-start] General regions (the Americas, Europe and APAC groupings) "aren't yet supported for read replicas"; a project needs a specific region.[^sb-regions]

The lab hit the compute floor and the backup requirement in order on a fresh Pro project (sfp-platforms S07/S07e, 2026-08-25):

| Step | Response from `POST /v1/projects/{ref}/read-replicas/setup` |
| --- | --- |
| Fresh project on the default Micro | `400 "Read replicas require a minimum size of small"` |
| After a `ci_small` upgrade | `406 "Failed to check for latest completed physical backup"` |
| After enabling the `pitr_7` add-on (physical backups) | `204` accepted |

MS06 (2026-09-30) skipped the chain on a Medium primary in ap-southeast-2, with the replica in the primary's own region: it added `pitr_7` first (HTTP 200), then setup answered `204` on the first attempt; the replica's `READ_REPLICA` entry appeared in the pooler config after 216 s, and a connection through the replica's Supavisor string answered `pg_is_in_recovery() = true` after 219 s. Removal answered `204` and the entry was gone on the first poll. The docs say replicas deploy "across multiple regions"[^sb-rr] and do not mention the same-region case.

RR01 (2026-10-10) timed a cross-region replica on a Small primary: ap-northeast-1 primary with `ci_small` and `pitr_7` applied, replica in ap-southeast-1. Setup answered `204` on the first attempt. The `READ_REPLICA` entry appeared in the pooler config and answered `pg_is_in_recovery() = true` on its first connection, both at 271 s (RR01d). Two exploratory runs on the same shape read roughly 150 s from a console log that was not kept, so no artifact backs that figure. Treat 271 s as the published figure, not a distribution, and do not set it against MS06's 216 s: the compute size and the region pair differ, and each is one run. Removal answered `204`, the entry was gone from the pooler config on the first poll (0 s), and the project delete answered `200` (RR01p).

Resetting a project's database password has a cost on the pooler side. In two exploratory RR01 runs, `PATCH /v1/projects/{ref}/database/password` answered `200`, and a connection to the Tokyo session pooler with the new password still failed with `password authentication failed for user "postgres"` after a 60 s wait; one run saw the same on the replica's pooler. A later connection in one run succeeded after minutes, and no propagation time was measured. A fresh project's session pooler accepted its create-time password on the first attempt for both nodes (RR01l, 1 s wait). That fits the refusal following the reset and not the pooler in general, though it compares two different projects. A script that resets the password and then opens a pooler connection should expect to retry. The [platform operation cost reference](/reference/supabase-platform-operation-cost/) measured the same `PATCH` on a Micro project and did not probe the pooler.

PITR was the lab's way to get a completed physical backup on a fresh project; the backups docs say projects on Postgres `15.8.1.079` and newer use physical backups already.[^sb-backups] Whether the `406` clears on its own once the backup that follows a compute change completes was not run; on 2026-09-03 a fresh project already listed a completed physical backup. PITR is its own add-on priced by retention period, so it belongs in the replica's price when the project needs it.[^sb-backups]

## What a replica does not do

- Writes. The replica accepts `select` only.[^sb-rr]
- Auth, Storage and Realtime. "Requests to other Supabase products, such as Auth, Storage, and Realtime, aren't able to use a Read Replica or its API endpoint."[^sb-rr]
- Failover. The read replica docs describe no way to promote a replica or fail over to one (doc-read 2026-10-08); the production checklist recommends replicas "if you require availability resilience to a disk failure event".[^sb-going-prod] For a region outage, the warm standby in [the DR tiers reference](/reference/supabase-dr-tiers/) is the tier that runs somewhere else.
- Survive an upgrade or a restore. "Projects with read-replicas can't be upgraded. You need to delete the replicas and re-create them after upgrade completes."[^sb-upgrading] The getting-started page puts data restorations under the same rule: all replicas come down first, and you re-deploy them once the operation completes.[^sb-rr-start] The [major upgrade guide](/guides/supabase-postgres-major-upgrade-e2e/) carries this as a pre-window checklist item; reads go to the primary only once clients are repointed at the primary's URL (the load balancer endpoint is removed with the last replica), so repoint first and size the primary to carry them.
- Fresh data on demand. Replication is asynchronous,[^sb-rr] and "High replication lag can result in stale data returned for queries executed against the affected read replicas."[^sb-rr-start] The lag measured in RR01 is under [Replication lag and cancellation](#replication-lag-and-cancellation).

## Replication lag and cancellation

RR01 (2026-10-10; Tokyo primary, Singapore replica, one project, one run) read the standby settings and then provoked the recovery conflict that cancels a long replica query.

`pg_settings` on both nodes (RR01l):

| Setting | Value | Source |
| --- | --- | --- |
| `max_standby_streaming_delay` | 30 s | `default` |
| `max_standby_archive_delay` | 30 s | `default` |
| `hot_standby_feedback` | off | `default` |
| `statement_timeout` | 120 s | configuration file |
| `hot_standby` | on for the replica, off for the primary | |

The 30 s matches the Supabase blog's description of `max_standby_streaming_delay` as the time the replica waits before cancelling conflicting queries, "default: 30 seconds", and its note that raising it costs more replication lag during heavy queries (blog dated 2026-01-15; documented, not run).[^sb-blog-rr]

### The trial

On the replica, a repeatable-read transaction counted a 50,000-row table and then ran `select pg_sleep(100)`. Three seconds later the primary ran either `update` plus `vacuum` on that table (RR01m1 to RR01m3) or `lock table ... in access exclusive mode` (RR01n1 to RR01n3). All 6 replica statements were cancelled with SQLSTATE `40001`, `canceling statement due to conflict with recovery`. The DETAIL was `User query might have needed to see row versions that must be removed.` after the vacuum and `User was holding a relation lock for too long.` after the lock.

| Conflicting primary command | Cancelled after | Row written afterwards, visible on the replica after |
| --- | --- | --- |
| `update` + `vacuum` (3 trials) | 31.1, 31.3, 31.6 s | 30.8, 30.5, 31.3 s |
| `ACCESS EXCLUSIVE` lock (3 trials) | 30.2, 30.2, 30.3 s | 30.4, 30.2, 30.4 s |

Times are from the start of the primary command, taken on the client clock when the error arrived; the visibility column polls the replica's endpoint at 0.7 s. Replay lag sampled during a stall stayed flat (822,920 bytes in the first vacuum trial, 352 bytes in the first lock trial), so replay on the replica was stopped, not slow. Why the vacuum trials run about 1 s longer was not separated: the `update` of 50,000 rows replays first and may start the timer later. `pg_stat_database_conflicts` on the replica read `confl_snapshot` 3 and `confl_lock` 2 after the 3 vacuum and 3 lock trials; its reads lag, so the counters are recorded and not used.

### What it bounds

The read-your-writes gap on a replica is bounded by `max_standby_streaming_delay` when a conflicting command is replaying, not by network lag: a row written on the primary after the conflicting command was invisible on the replica for 30.2 to 31.3 s. That is the largest gap RR01 measured. The load balancer was not read during a stall, so whether it keeps sending `GET`s to a stalled replica is not measured. Not run: `hot_standby_feedback` on, another `max_standby_streaming_delay`, a query idle in transaction instead of in `pg_sleep`, and a query through the Data API (which has its own statement timeout).

### Without a conflict

Every write in RR01 went from Singapore to Tokyo, so the client took longer to return than replication took to arrive, and the rows below bound the gap for a client of that shape; they are not a measurement of replication delay.

| Row | n | Result |
| --- | --- | --- |
| RR01i: insert on the primary's endpoint, then `GET` from the replica's endpoint at once | 30 | 0 of 30 first reads missed; time from `POST` response to the first read that saw the row: median 36.6 ms, p95 113.5 ms, maximum 223 ms; `POST` round trip median 122.2 ms |
| RR01j: `POST` through the load balancer, then `GET rr_whoami` through it | 30 | first `GET` served by the replica 30 of 30, row present 30 of 30 |
| RR01k: per-insert delay from the two database clocks (insert on the primary through a session pooler connection, replica polled with `clock_timestamp()`) | 40 | first poll that saw the row: median 41 ms, p95 44.3 ms, maximum 655.5 ms; poll round trip median 7.3 ms; most polls for one insert 83 |

In RR01i the visible time equals the read's own round trip, because the row was already there. The RR01k median is mostly the insert's response travelling to the client before the first poll, so for 38 or more of the 40 inserts it is a ceiling on the delay; the maximum is a real delay of that order for at least one insert, and its cause was not examined. The two clocks are on different hosts, so skew sits inside every RR01k figure.

## Checking whether the replica serves reads

The dashboard and the logs both answer it, from the docs. Items 1, 2 and 4 were not exercised by a lab module; item 3's fields were read in RR01o (2026-10-10), and item 5 was run in RR01:

1. Database Reports, with the Source toggle on the replica, shows its resource use.[^sb-rr] A replica at idle CPU while the primary is busy is the first sign (inferred).
2. API Reports covers "API requests going through either a Read Replica or Load Balancer API endpoint".[^sb-rr]
3. In the API logs, a request through the load balancer records the database that served it: "The upstream database or the one that eventually handles the request can be found under the `Redirect Identifier` field. This is equivalent to `metadata.load_balancer_redirect_identifier` when querying the underlying logs."[^sb-rr] The log field reference lists it on `edge_logs` as `log_attributes['load_balancer_redirect_identifier']`.[^sb-log-fields] RR01o read it on 152 load balancer rows (`<ref>.supabase.co` for the primary, a `-rr-` host for the replica), next to `request.cf.colo` and the `load_balancer_geo_aware_info` choice fields described [above](#what-the-load-balancer-did-in-rr01).
4. Replication lag sits under Replica Information on Database Reports.[^sb-rr-start] For a metrics pipeline, the docs name `physical_replication_lag_physical_replica_lag_seconds`; the Grafana guide's alert uses `physical_replication_lag_physical_replication_lag_seconds` (not reconciled). The [Grafana monitoring guide](/guides/supabase-grafana-monitoring/) covers ingesting that endpoint. RR01 did not read this metric; it sampled replay lag as primary current LSN minus replica replay LSN during the conflicts above.
5. To tell which node answered a request, call a function that returns `pg_is_in_recovery()` and `pg_postmaster_start_time()`. `inet_server_addr()` cannot identify a replica: it returned the loopback address on the primary and on the replica (RR01 exploratory run, artifact not published).

The query below counts Data API requests per serving database and method. It is built from the documented field names and the documented query syntax[^sb-log-fields][^sb-log-sql] and was not run here (RR01o ran its own `edge_logs` queries against the Management API logs endpoint; a query that put `split(...)[1]` in the select list was refused with `Backend error! Retry your query.`, and the cause was not isolated to `split`):

```sql
-- Data API requests by serving database and method, over the Explorer's time range
select
  log_attributes['load_balancer_redirect_identifier'] as served_by,
  log_attributes['request.method'] as method,
  count() as requests
from logs
where source = 'edge_logs'
  and log_attributes['request.path'] like '/rest/v1/%'
group by served_by, method
order by requests desc
limit 50;
```

Rows with an empty `served_by` are requests the field did not describe; the docs define the field only "for API Load Balancer traffic",[^sb-log-fields] so a large empty bucket reads as traffic that never went through the load balancer (inferred). In RR01 the one load balancer `POST` row had the primary's identifier and no geo fields, so a `POST` through the load balancer is not an empty bucket. `POST` rows against `/rest/v1/rpc/` are function calls the replica cannot take until they use `get: true`.

## Which do I pick

| Situation | Choice | Why |
| --- | --- | --- |
| Primary CPU high, workload under roughly 80% reads | Larger compute | "Read Replicas only serve reads and won't help writes."[^sb-rr] |
| Read-heavy, users far from the primary's region | Replica near the users, clients on the load balancer endpoint | geo-routing sends each `GET` to the closest database[^sb-rr] |
| Analytical queries competing with the app | Replica, the analytics job on the replica's connection string | the replica has its own pooler and database endpoint[^sb-rr] |
| Region outage cover | Warm standby, not a replica | no promotion path is documented; see [the DR tiers](/reference/supabase-dr-tiers/) |
| Data must stay in one jurisdiction | Replica only in an acceptable region | a replica is a full copy in its own region; see [data residency](/reference/supabase-data-residency/) |
| Long analytical query on the replica | Keep it under 30 s, or accept cancellation | RR01: a conflicting primary command cancelled a held query with `40001` after 30.2 to 31.6 s with `hot_standby_feedback` off |
| A read must see the row just written | Read it from the primary | on a replica whose replay is blocked, a new row was invisible for 30.2 to 31.3 s (RR01) |
| Replica exists, its share of reads is near zero | Fix the client path, or delete it | every hour bills at the primary's compute size, outside credits and the spend cap[^sb-rr-usage] |

The same check as a list:

1. Do the API logs or API Reports show `GET` requests served by the replica? If yes, it is serving reads; keep it and watch replication lag.
2. If not, are the clients on the load balancer endpoint or the replica's endpoint? If not, point Data API reads at the load balancer endpoint.
3. Are the reads function calls sent as `POST`? If yes, call read-only functions with `get: true`.
4. Is the Data API behind a custom domain? If yes, send reads to the replica's own endpoint.
5. Is the replica in the primary's region, or are the users closer to the primary? If yes, move the replica toward the users or delete it.
6. If not, check `chosen_supabase_region` in the `edge_logs` rows (RR01o); the same-region split between a primary and a replica was not measured.

## What to do about it

Rows marked documented rest on the docs, read 2026-10-08; rows with an RR01 id were measured on 2026-10-10 in one project and one run. The Module column says which. MS06 and S07 resolve in the [medium-serverless RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/1de7be3/experiments/medium-serverless/RUNLOG.md) and the [sfp-platforms RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/16077ed/experiments/sfp-platforms/RUNLOG.md); RR01 resolves in the [replica-routing RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/c621e0d/experiments/replica-routing/RUNLOG.md).

| Practice | Evidence | Module |
| --- | --- | --- |
| Count the replica's share in the API logs before paying for another month. | `metadata.load_balancer_redirect_identifier` names the database that served a load-balanced request; the query above groups by it. RR01o read the field on 152 rows. | documented; RR01o (2026-10-10) read the fields; query above not run |
| Point Data API reads at the load balancer endpoint or a replica endpoint. | Only those two endpoints reach a replica; the load balancer is a separate endpoint on the API settings page. 40 of 40 `GET`s through it from Singapore reached the replica, at 46.5 ms median against 117.5 ms to the primary directly. | RR01f (2026-10-10) |
| Call read-only functions with `rpc(fn, args, { get: true })`. | Non-`GET` requests go to the primary; `get: true` sends a `GET` with arguments in the query string. A function that writes fails under `GET` with `25006`. Through the load balancer, `GET rpc/rr_whoami` reached the replica and `POST rpc/rr_whoami` the primary. | RR01f, RR01g (2026-10-10); the supabase-js option not called; `25006` documented |
| Keep `get: true` to functions whose arguments are scalars or arrays. | The client converts each argument to a string for the query string; an object argument becomes `[object Object]`. | source read at `84e2c5d`; not run |
| Send reads to a replica endpoint when the project uses a custom domain. | Custom-domain requests are not routed through the load balancer. | documented; not measured |
| Place a replica closer to the users than the primary is. | Chosen region followed the Cloudflare colo in 9 groups of rows (SIN, SYD, BOM, GRU to the replica's region; NRT, DUB, IAD, SJC to the primary's); a distance rule and a fixed colo table both fit. | Price each replica as a second database at the primary's compute size. | Compute, 1.25x disk from the first byte, IOPS, throughput and IPv4 are mirrored; credits and the spend cap do not apply. | documented |
| Budget the replicas into every primary upsize. | Replicas are resized with the primary, after it, concurrently. | documented; not measured |
| Wait for, or force, a completed physical backup after the resize to Small. | Setup answered `406 "Failed to check for latest completed physical backup"` on Small; `204` after `pitr_7`. MS06 served 219 s after setup; the cross-region replica on Small served at 271 s. | S07/S07e (2026-08-25), MS06 (2026-09-30), RR01d (2026-10-10) |
| Delete replicas before an upgrade or restore; repoint clients and size the primary. | Upgrades and data restorations require all replicas down first; recreate after. | documented |
| Repoint clients off the load balancer endpoint before removing the last replica. | The load balancer and its endpoint are removed with the last replica. | documented |
| Plan region failover on a standby, not a replica. | The docs describe no promotion path; Auth stays on the primary. | documented (absence) |
| Keep replica queries under 30 s, or raise `max_standby_streaming_delay`. | 30 s default on both nodes with `hot_standby_feedback` off: 6 of 6 held queries cancelled with `40001` after 30.2 to 31.6 s. Raising it is documented to add lag; not run. | RR01l, RR01m, RR01n (2026-10-10) |
| Read a just-written row from the primary when a long replica query may conflict. | While replay was blocked a new row was invisible on the replica for 30.2 to 31.3 s; the load balancer during a stall was not read. | RR01m, RR01n (2026-10-10) |
| Tell the nodes apart with `pg_is_in_recovery()` and `pg_postmaster_start_time()`. | `inet_server_addr()` returned the loopback address on both nodes. | RR01 exploratory run (not published) |
| Take the load balancer host from the API settings page, not the Management API. | The Management API returns neither host; the Dashboard route answered a PAT `401 Unsupported access token`; `<ref>-all.supabase.co` was found by name. | RR01e (2026-10-10) |
| Retry the pooler connection after `PATCH /database/password`. | The Tokyo session pooler refused the new password after 60 s in 2 exploratory runs; a fresh project's pooler accepted its create-time password at once. | RR01 exploratory runs, recorded in the RUNLOG (not published); RR01l |

Not measured anywhere in the lab, and stated as such above: how the load balancer splits `GET`s between a primary and a same-region replica; whether a custom-domain request lands on the primary; that the supabase-js `get: true` option itself reaches a replica (the `GET` it sends was measured in RR01f); the load balancer's rule, which RR01o could not separate between a distance rule and a fixed colo table; whether the load balancer keeps sending `GET`s to a replica whose replay is stalled; replica lines on a real invoice; the conflict window with `hot_standby_feedback` on; replication delay for a write larger than RR01's 50,000-row update; whether the `406` clears on its own once the backup that follows the resize to Small completes.
