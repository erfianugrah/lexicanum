vfctl is a Go CLI that reads and writes NVIDIA GPU voltage-frequency curves directly via NVAPI, replacing MSI Afterburner's curve editor. Built after Afterburner's editor repeatedly produced broken curves - notch artifacts at selection boundaries, temperature-stale baselines, and unexpected whole-curve shifts[^afterburner] - on an RTX 5090 FE.

Curve struct layouts are from the PenguinBurner reverse-engineering effort[^penguinburner], cross-checked against the LACT issue #936 discovery[^lact-936] and verified via ctypes. Telemetry structs are from nvapi-sys[^nvapi-sys] and NVIDIA's official open-source NVAPI reference[^nvapi-docs]. The write path is verified end-to-end on live silicon: a single-point selftest writes +15 MHz, reads it back, and restores. Telemetry (clock, voltage, utilisation, temperature, power) is verified across full gaming sessions. Measured on a single RTX 5090 FE with driver 610.88; the curve interfaces are undocumented and could change between driver releases.

## TL;DR

- Curve write, telemetry, persistence and automated stability search in one static binary, replacing Afterburner for undervolting.
- Writes are read-modify-write via `ClkVfPointsSetControl`, confirmed by selftest on the card.
- Telemetry covers clock, voltage, utilisation, temperature and live power draw, logged as CSV with a voltage histogram summary.
- A logon task runs `vfctl hold`, which applies the curve and re-applies it whenever a driver reset wipes the offsets. It reacts to driver events instead of polling.
- On Blackwell the curve sets the frequency ceiling per voltage, and the DVFS governor picks where the card sits.
- Since v0.4.0 vfctl also writes the fan curves into the motherboard's Nuvoton NCT6799D, which then runs them with no software in the loop. That replaced FanControl, whose once-a-second polling cost an 8 kHz mouse dozens of missed polls a minute; most of that cost was the NVAPI GPU temperature read.

## Architecture

| Package | What it owns | Key detail |
|---------|-------------|------------|
| `internal/vfcurve` | Afterburner blob parse/encode, generation, validation | 12-byte header, 127 points |
| `internal/curve` | Live-curve math: BuildOffsets, VerifyOffsets, ApplyCurve | bounds guard, read-back verify |
| `internal/testloop` | TDR-loop logic: Classify, StepFreq, ParseTDRCount | 100% coverage |
| `internal/profile` | Afterburner .cfg INI read/write | legacy import path |
| `internal/task` | Task Scheduler XML for `persist` | no 72h limit, restart on failure |
| `internal/nvapi` | nvapi64.dll syscall layer | curve writes + telemetry reads |
| `internal/drvevents` | System event log subscription for `hold` | TDR (4101) and driver install (UserPnp 20003) |
| `internal/sio` | Nuvoton NCT6799D access over a two-method port interface | tested against a simulated chip |
| `internal/pawnio` | PawnIO driver binding, embedded signed LpcIO module | shared ISA-bus mutex |
| `internal/fancurve` | FanControl curve import, 4-point chip fit | pure maths |
| `cmd/vfctl` | CLI dispatch | 20 commands |

Built partly by a self-correcting loop on a local Gemma 4 26B model - the `internal/curve` and `internal/testloop` extractions converged in one iteration each against a `go test` sensor, with human review catching a dropped sentinel guard the tests missed.

## The curve write path

Three bugs separated the first attempt from a working write, and each was caught only by a stricter verification step than the last:

1. A 4-byte struct offset. The control struct's points start at 0x44; the 0x48 came from a read-only PoC that never exercised a write.
2. Mixed struct generations. The status read used a 128-point layout while the control write used 255 points - different index spaces, so "point 72" in the read wasn't "point 72" in the write.
3. A fresh buffer instead of read-modify-write. The driver silently ignores writes to points whose `type_` field doesn't match what it returned. A zeroed buffer writes nothing that sticks.

Writes land when GetControl fills the full table (preserving `type_`/`rsvd`), one `freq_offset_kHz` is modified, and SetControl writes the whole table back. vfctl then reads the point back and treats a write that does not read back as an error.

A fourth bug was in the read path. The status struct's `freq_kHz` (+4) is the *nominal* frequency (base + applied offset), not the base. The true base is `vf_tuple_base.freq_kHz` (+12). Using the nominal double-counts offsets on any non-stock card. This is why Afterburner profiles "mutate" after apply - the stored frequencies are a temperature-time snapshot, and only the offsets are real.

## Telemetry, and what it revealed

`watch` samples clock, voltage, utilisation, temperature, and power every interval, logs CSV, and prints a per-voltage histogram on exit. Full-session data from The Finals on an undervolted 5090:

| Metric | Menu | Full load |
|--------|------|-----------|
| Core clock | 2415 MHz | 2433 avg / 2497 max |
| Voltage | 880-885 mV | 930-935 mV (95.7% of time) |
| Utilisation | 13-17% | 72% avg / 99% peaks |
| Temperature | 45C | 57 avg / 61 max |
| Power | 31W | 76W avg / 103W max |

The card sits at 930 mV with the curve targeting 860 because Blackwell's DVFS governor adds voltage margin under sustained load, independent of the curve. Power (103W max of 575W) and temperature (61C) ruled out both limiters. The voltage step happens the instant utilisation crosses ~85%, before power or clock change, so it tracks how long the load has run rather than how much it asks for.

The cost of that margin is ~5W. The heat goal ("stock perf or better, lowest possible") was already met: 2433 MHz avg at 76W average on a 575W card.

## NVAPI interface reference

All accessed via `nvapi_QueryInterface(function_id)` on `nvapi64.dll`. Version field: `(version << 16) | struct_size`.

### Curve (undocumented, verified working)

| ID | Name | Struct | Notes |
|----|------|--------|-------|
| `0x507B4B59` | ClkVfPointsGetInfo | InfoV1, 0x182C | active mask + per-point type/voltage_based |
| `0x21537AD4` | ClkVfPointsGetStatus | StatusV3, 0x15B0C | 255 pts x 348B at 0x68; base at +12, nominal at +4 |
| `0x23F1B133` | ClkVfPointsGetControl | ControlV1, 0x2420 | 255 pts x 36B at 0x44; offset at +20 |
| `0x0733E009` | ClkVfPointsSetControl | ControlV1, 0x2420 | read-modify-write ONLY |

Only points with info-struct `type==0 && voltage_based==1` are editable core points - the 255-point buffer also carries memory/other clock domains, and writing those offsets corrupts them.

### Telemetry (documented public APIs)

| ID | Name | Reads |
|----|------|-------|
| `0xDCB616C3` | GetAllClockFrequencies | current core/memory clocks (kHz) |
| `0x60DED2ED` | GetDynamicPstatesInfoEx | utilization % (domain 0) |
| `0xE3640A56` | GetThermalSettings | temperature - 3-arg call (gpu, sensorIndex, struct) |
| `0xEDCF624E` | ClientPowerTopologyGetStatus | live power draw |
| `0x465F9BCF` | ClientVoltRailsGetStatus | voltage (uV at +0x28) |

`ClientPowerPoliciesGetStatus` (0x70916171) is one name away from `ClientPowerTopologyGetStatus` and returns the power-limit *policy* (frozen ~100%), not live draw. The symptom is a power reading pinned at exactly 100.0 W that never moves.

## The undervolt algorithm

Stock below the ramp start, linear ramp to the target frequency at the target voltage, flat above. Offsets are computed against the live base (`vf_tuple_base`), so the result is temperature-correct at apply time:

```
offset = target_freq - base_freq_at_voltage
```

NVIDIA snaps frequencies to 15 MHz steps. A bounds guard rejects values outside sane envelopes (the catastrophic-typo check: 27970 instead of 2797). Every write is verified by read-back within one step, and `set` self-cleans stale offsets below the ramp region so switching curves never stacks.

## Persistence: offsets do not survive a driver reload

The offsets live in driver memory. A reboot clears them, and so does any driver reload - including a driver reinstall by the NVIDIA installer while the desktop is running. On 2026-10-08 an installer run reinstalled `nvlddmkm` mid-session and the card went back to the stock curve with nothing signalling the process that had set it; the original logon-only `set` task never noticed.

`vfctl hold` closes that gap. It applies the curve, then checks it only when the driver may have reset it: it subscribes to the System event log for a TDR (Event 4101) or a driver install (Event 20003 from UserPnp, which the 2026-10-08 reinstall logged for `nvlddmkm`) and checks 10 s after one fires. A safety check every 15 minutes covers anything the log misses and is skipped while a fullscreen game is in front. The first version polled every 15 s, then every 30 s; seven days of its log showed the poll catching drift once, 30 s after startup, so v0.3.0 moved to events. Each check opens a fresh NVAPI session, compares the offsets with what `hold` last wrote, and re-applies on drift. After 20 failed checks in a row it exits non-zero so Task Scheduler restarts it with a freshly loaded `nvapi64.dll`.

`persist --profile` installs the binary and a machine profile under `%ProgramFiles%` (the task runs elevated, so neither may sit in a user-writable folder) and registers the task without the default 72-hour execution limit. The profile is a JSON file kept in the repo with the undervolt and fan settings, so changing a setting means editing the file and running `persist` again. Verified live: a fake Event 4101 written to the System log produced a check that found the curve intact, and resetting the card to stock followed by another fake 4101 got the curve re-applied (63 points verified).

## Fan curves on the motherboard chip

FanControl reads every enabled sensor through LibreHardwareMonitor once a second and rewrites each fan's duty in manual mode every tick. On this machine (ASUS ROG STRIX X670E-I, whose fan headers hang off a Nuvoton NCT6799D Super I/O) that polling showed up as missed polls on an 8 kHz mouse. The chip can run a fan curve itself in its SmartFan IV mode, which is how the BIOS Q-Fan curves already work, so vfctl writes the curves once and leaves the chip to run them.

How it works:

- Chip access goes through PawnIO[^pawnio], the signed kernel driver FanControl and LibreHardwareMonitor already install, using its signed `LpcIO` module[^pawnio-lpcio] embedded in vfctl. Every transaction holds the shared `Global\Access_ISABUS.HTP.Method` mutex those tools use, and vfctl refuses to touch the chip while FanControl runs.
- Each FanControl curve (10-13 points) is fitted to the chip's 4 points plus a full-speed temperature. The fitter tries every 4-point subset and keeps the one with the smallest worst-case duty error: 2.2, 3.7 and 6.4 percentage points for the three curves here.
- Before the first write vfctl saves the BIOS register values, and `vfctl fan restore` puts them back. Every write is read back. vfctl never puts a fan in manual mode, so if it dies the chip keeps running the last curve.
- `hold` writes the curves at logon and re-reads them on its 15-minute safety check. Between checks it makes no fan-side calls.

Register addresses come from the Linux `nct6775` driver[^nct6775] and the NCT6796D datasheet[^nct6796d] (Nuvoton publishes no NCT6799D datasheet). Several facts only showed up on the hardware:

| Finding | How it was checked |
|---------|-------------------|
| PawnIO's `ioctl_find_bars` returns `0x80070490` (not found) unless the chip is already in extended-function mode, because it reads the chip id first | measured: first run failed; the module source confirms the order[^pawnio-lpcio] |
| The BIOS runs the CPU and chassis channels on source 28, the AMD CPU temperature over SB-TSI (register `0x4F4`), not on the PECI or CPUTIN sources | measured: register dump; rose 50 -> 66 C under a 30 s all-core load |
| Registers `0x073`-`0x07D` show each fan channel's current input temperature, not fixed sensors, so LibreHardwareMonitor's names for them (PECI_0, CPUTIN, SYSTIN, AUXTIN0-2) do not fit this board | measured: `0x073` read 0 when channel 0 moved to an unset source, then the value written into that source |
| SmartFan IV interpolates linearly between the 4 points | measured: three channels within one duty step of the linear value |
| Index `0x03` is the step-up time and `0x04` the step-down time (some sources swap them). The ASUS BIOS leaves both at 0 and the duty-per-step register `0x66` at 0, so writing a non-zero step time freezes the output | measured: with step times written, the chip's computed target (`0x0B`) was right but two outputs never moved; keeping the BIOS 0/0 fixed it. Register meanings from the datasheet[^nct6796d] |
| Source 31 reads the channel's software-writable Virtual1 register, so a program can feed the chip an outside temperature | measured: monitor slot and output followed the written value |
| The ASUS embedded controller does not rewrite the registers | measured: unchanged 7 minutes later and across restarts of `hold` |

## What sensor polling costs an 8 kHz mouse

MousePlotter[^mouseplotter] recordings of an Endgame Gear OP1 8k at 8 kHz showed the missed polls that started this work. Each run below counts gaps over 0.4 ms per minute while the mouse was moving. The runs are 30-65 s each, and two that should match (the "curves on the chip" and "chip read only" rows) differ by 2x, so treat a single row as plus or minus half. The direction held across every run.

| Configuration | Gaps over 0.4 ms per minute |
|---------------|------------------------------|
| FanControl running (Motherboard, CPU and NVAPI sources) | 54 |
| FanControl closed | 11 |
| vfctl curves on the chip, nothing polling | 15 |
| `hold` reading only the fan chip every 5 s | 7 |
| `hold` reading the GPU temperature through NVAPI every 5 s | 49-60 |
| `hold` reading the GPU temperature every 60 s | 36 |

A chip register read through PawnIO (p99 0.53 ms of wall time) cost nothing measurable. The NVAPI GPU temperature read cost most of FanControl's overhead, whether the session stayed open or was opened per read, and the gaps came with the stall signature of a system-wide pause: MousePlotter lost its kernel timestamps for them. That runs against the usual view that on-die GPU temperature reads are cheap, at "a few microseconds" of CPU time[^unwinder]; on this RTX 5090 the CPU time may be small, but the stall it causes is not. Why the driver stalls is not established.

So the chassis fan, which FanControl drove from the higher of the CPU and GPU curves, now follows the CPU curve on the chip. vfctl can still drive a channel from max(CPU, GPU) by writing the GPU temperature into the channel's Virtual1 register at a set interval; the profile leaves that off.

## Stability testing methodology

1. Run the selftest first: write +15 MHz to one point, read back, restore. This proves the write path before anything else depends on it.
2. Test in a game: The Finals (Unreal Engine 5, transient-heavy).
3. On TDR (Windows Event 4101), step down -15 MHz and retest; `vfctl test` automates this loop.
4. Watch the histogram, and judge the undervolt by where the card sits under load rather than by the target you set.

On driver 610.88, the stability cliff for a 5090 FE is exactly one 15 MHz step wide: 2812 @ 900 mV is stable, 2827 (the old-driver stable curve) crashes.

## Known limitations

- Writes require Administrator (error -137, `NVAPI_INVALID_USER_PRIVILEGE`); reads work unelevated
- The curve does not pin the operating voltage; the DVFS governor adds margin under sustained load. Forcing lower needs a declining curve, which is notch territory
- The undocumented curve interfaces may change between driver releases
- Windows only today. The Linux driver ships `libnvidia-api.so.1` with the same `nvapi_QueryInterface` entry point and VF function IDs (LACT's VF curve editor uses them[^lact-957]), so a Linux backend is a port of the call layer, not new reverse engineering
- GPU fan control is out of scope: manual % clamps to 30% minimum and 0 RPM is vBIOS-auto only; the card's own curve stays in charge
- Motherboard fan control covers the Nuvoton NCT6799D only, verified on one ASUS board; other Super I/O chips need their own register map
- Tested on a single card: RTX 5090 FE (Blackwell GB202)
