import { Aside } from "@astrojs/starlight/components";

Whether one application, with no code branch on where it runs, behaves the same on managed Supabase and on the self-hosted Docker stack when it encrypts large objects on the client, keeps the key-encryption key (KEK) outside Supabase, resumes interrupted uploads and reads byte ranges. For anyone designing client-side encryption over Supabase Storage, or carrying one application across both deployment models.

Everything marked measured comes from the [client-keyed-objects](https://github.com/erfianugrah/supabase-lab/tree/5f7ce52/experiments/client-keyed-objects) experiment in [supabase-lab](https://github.com/erfianugrah/supabase-lab), run on 2026-10-12 against four targets: `onprem` (the self-hosted stack with a MinIO backend), `onprem-file` (the same stack on the file backend), `region-a` (a managed Pro-org micro project in `ap-southeast-1`) and `region-b` (the same in `eu-central-1`). The self-hosted stack is supabase/supabase `docker/` at commit `8617532`, the pin the [self-hosted defaults page](/reference/supabase-self-hosted-defaults/) uses, with the Storage image raised to the version managed reported. The vantage is one laptop in Singapore on Docker Desktop for Mac, one run per target (n = 1). The parity table is generated from four published artifacts; the run list, partial rows and the operator's notes are in the [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/5f7ce52/experiments/client-keyed-objects/RUNLOG.md). Statements marked source-read come from the Storage server source or the experiment's own code and were not measured. Statements cited to documentation were not run.

TL;DR:

- The same four migrations left the same catalogue on all four targets (fingerprint `de77a73c2298ee14`: 22 policies, 6 functions, 4 triggers, 6 tables), and a scan of 15 client and migration files found 0 branches on target identity (CK01).
- Resuming an S3 multipart upload with a user's session token re-sent every part until a SELECT policy existed on `storage.s3_multipart_uploads_parts`. On `onprem` without it (first run, three migrations): 0 of 32 parts kept, and the bytes and SHA-256 still matched, so a content check alone passes a resume that did not resume. With it: 13 of 32 kept on `onprem` and `region-a` (CK04).
- TUS resumed from offset 861929472 on `onprem`, `region-a` and `region-b` with no policy change (CK05).
- Ranged reads returned exactly the covering ciphertext chunks on all four read paths, 25 of 25 per path on `onprem` and `region-a`. On `region-a`, reads through fresh signed URLs had a p50 of 30479 ms (`MISS:25`) against 548 ms for `/object/authenticated` (`MISS:1 HIT:24`) and 419 ms for S3 GetObject, each p50 over 25 reads per path of random 1 KiB to 64 MiB ranges, in ms of read time (`info_ms`; metric not verified as total or headers). One vantage, one run (CK06).
- Tamper, ciphertext-only and key-service-down checks passed on all four targets; region isolation held both ways between the two managed projects (CK07-CK10).
- 8 of 22 failing requests had a different error shape on managed and self-hosted. The Data API and S3 differences come from the layer in front of the service (Envoy's own `401`; `text/plain` attributed to the managed edge, inferred), the Storage REST one is configuration or gateway with no Storage version gap, and the Auth one is not separated from the Auth version (CK12, CK13).
- One failed cell: CK04 on `region-b`, where the resume process timed out on the Data API during a stretch of host sleep. It was not re-run, and a platform cause is neither excluded nor shown.

1. The client resolves the tenant's target from a static directory, then signs in to that target's Auth; the hook adds `tenant_ids` to the access token.
2. To upload, it asks the key service to wrap a fresh data-encryption key (DEK), writes the asset row and the wrapped DEK through the Data API, and sends ciphertext to Storage.
3. To read, it fetches the wrapped DEK and the chunk hashes, asks the key service to unwrap, fetches only the covering ciphertext range from Storage, verifies and decrypts.
4. The key service verifies the caller's token against the target's JWKS and checks membership through the Data API with the caller's own token, so RLS decides who may unwrap. Supabase never holds the KEK or an unwrapped DEK.

## The application

The experiment builds the application as a reference implementation and runs the same acceptance suite against every target. The key service is a stand-in for an operator's KMS or HSM, not a recommendation of one.

### Catalogue in Postgres

Schema `app` holds `tenants`, `memberships` (role `owner`, `editor` or `viewer`), `records`, `assets` (wrapped DEK, nonce prefix, sizes, upload state), `asset_chunks` (a SHA-256 per ciphertext chunk) and `access_log`. Members read their tenant's rows, editors write, viewers only read. Storage policies on `storage.objects` key on the tenant id as the first path segment (`<tenant_id>/<asset_id>/data`) in a private bucket, so an object key alone grants nothing without a membership ([migrations](https://github.com/erfianugrah/supabase-lab/tree/5f7ce52/experiments/client-keyed-objects/supabase/migrations), source-read).

A custom access token hook adds `tenant_ids` (sorted UUID strings) to every access token.[^sb-hook] It is the same function on every target, enabled through the Management API auth config on managed and the `GOTRUE_HOOK_CUSTOM_ACCESS_TOKEN_*` variables on self-hosted, and CK01 confirmed it is executable by `supabase_auth_admin` and not by `authenticated`. Every target issued ES256 access tokens with a 300 s lifetime carrying the claim (CK02).

The RLS matrix (CK03) checked 8 cells for each of 4 actors (owner, editor, viewer, non-member) on catalogue rows and on objects over REST and S3 with the user's token, identically on all four targets. A non-member's S3 GET answered `404 NoSuchKey` and a REST GET `400`; a viewer's S3 PUT answered `403 AccessDenied`.

### Key service

One KEK per tenant, two calls: `POST /wrap {tenant_id, dek}` and `POST /unwrap {tenant_id, wrapped}`. Both need the caller's Supabase access token as a bearer. The service verifies it against the JWKS of the tenant's home target, with the issuer pinned per target and audience `authenticated`, then reads the caller's membership through that target's Data API with the caller's token. `wrap` needs `owner` or `editor`; `unwrap` needs any membership. The DEK is wrapped with AES-256-GCM under the tenant KEK with the tenant id in the associated data ([`keysvc/server.ts`](https://github.com/erfianugrah/supabase-lab/blob/5f7ce52/experiments/client-keyed-objects/keysvc/server.ts), source-read). The service ran in Docker on the laptop for every target.

A partner key service could take part of this role (doc-read, not tested). CipherStash's ZeroKMS splits key material between its authority key and a client key the application holds, per its docs,[^cs-key-mgmt] and EQL columns can hold the catalogue's searchable fields and a ciphertext copy of each data key; EQL has no binary domain, so the objects themselves stay with this envelope format. What was measured of EQL on Supabase (grants, PostgREST operands, the data key column, on a local rig and a managed project, without ZeroKMS) is on the [EQL on Supabase page](/reference/supabase-cipherstash-eql/). ZeroKMS in place of this key service was not tested.

### Envelope format

| Element | Value ([`client/src/envelope.ts`](https://github.com/erfianugrah/supabase-lab/blob/5f7ce52/experiments/client-keyed-objects/client/src/envelope.ts), source-read) |
|---|---|
| DEK | random 256-bit key per asset, wrapped by the key service |
| Chunk | 8 MiB of plaintext; ciphertext chunk = plaintext + 16-byte GCM tag |
| Cipher | AES-256-GCM through WebCrypto, the same code in Bun and the browser |
| Nonce | 8 random bytes per asset (`nonce_prefix`) followed by the chunk index as a 32-bit big-endian integer |
| AAD | asset id, then the chunk index, then the chunk count |
| Integrity | ciphertext SHA-256 per chunk in `asset_chunks`; plaintext SHA-256 per asset |

The associated data binds each chunk to its asset, its position and the total count, so a reordered, swapped or truncated chunk fails the tag check even when the catalogue hashes are not consulted. A 2 GiB plaintext (2147483648 bytes) is 256 chunks and 2147487744 bytes of ciphertext (CK04).

### Uploads and reads

| Path | How | Resume |
|---|---|---|
| S3 multipart | 64 MiB parts (32 for 2 GiB), signed with the session-token form of S3 credentials, which applies the user's RLS[^sb-s3-auth] | `ListParts` on the upload id stored in `assets` |
| TUS | 6 MiB transport chunks, the size the resumable upload docs state[^sb-tus]; the ciphertext stream is independent of the transport chunking | `HEAD` for the offset |

A ranged read maps a plaintext range to chunk indices, fetches one ciphertext `Range` GET, checks the chunk hashes against `asset_chunks`, decrypts and slices. It runs over four paths: S3 GetObject, an S3 presigned GET, a Storage signed URL and `/object/authenticated`.

### Region routing

A static directory in config maps tenant -> home region -> target, and the client resolves the target before every call. There are no cross-region reads, and a user exists per region because each project has its own Auth.

## Findings

### A user-token multipart resume needs a policy on the parts table

The first `onprem` run, with three migrations, killed the uploader at 40 % and resumed from a new process: `parts_skipped` 0 of 32. The object's bytes and its plaintext SHA-256 still matched the fixture, because the client re-sent every part. With migration 0004 the same flow kept 13 of 32 parts, and all 13 resumed ETags matched (`resumed_etag_matches` 13, mismatches 0), on `onprem` and on `region-a` (CK04).

The cause, from the Storage source at v1.80.2 and not measured: UploadPart writes the part row as the storage superuser, while `listParts` reads `storage.s3_multipart_uploads_parts` as the caller's role. That table has RLS enabled and a SELECT grant to `authenticated`, and Storage ships no policy on it ([`0021-s3-multipart-uploads.sql`](https://github.com/supabase/storage/blob/v1.80.2/migrations/tenant/0021-s3-multipart-uploads.sql), [`s3-handler.ts`](https://github.com/supabase/storage/blob/v1.80.2/src/storage/protocols/s3/s3-handler.ts) `listParts`). With a user's token, ListParts therefore returns no rows. The policy the experiment adds:

```sql
create policy ck_multipart_parts_read on storage.s3_multipart_uploads_parts for select to authenticated
  using (bucket_id = 'assets' and app.my_role(app.key_tenant(key)) in ('owner', 'editor'));
```

`supabase db push` created it on managed, running as `postgres`. The part ETag was the MD5 of the part on MinIO and on managed: 13 matches and 0 mismatches on both.

<Aside type="caution" title="A content check does not prove a resume">
The run without the policy passed a full-read SHA-256 check while re-uploading 32 of 32 parts. Count the parts the server already held, or assert on transferred bytes, when testing resume.
</Aside>

### Ranged reads per path

Every ranged read on `onprem` and `region-a` returned exactly the ciphertext chunks covering the requested plaintext: 25 of 25 per path, and per-path body bytes equal to the covering-chunk bytes (CK06). The 100 ranges ran from 1 KiB to 64 MiB and asked for 499413339 plaintext bytes in all.

| Path | onprem p50 / p95 (ms) | region-a p50 / p95 (ms) | region-a `cf-cache-status` |
|---|---|---|---|
| S3 GetObject | 181 / 361 | 419 / 1472 | not present |
| S3 presigned GET | 182 / 301 | 385 / 946 | `DYNAMIC:25` |
| Signed URL | 109 / 187 | 30479 / 66340 | `MISS:25` |
| `/object/authenticated` | 116 / 226 | 548 / 1577 | `MISS:1 HIT:24` |

These are info values from one laptop and one run per target: p50 and p95 over 25 reads per path of random 1 KiB to 64 MiB ranges, in ms of read time (`info_ms`; metric not verified as total or headers). On `region-a` the signed URLs were the slowest path, and the authenticated path was served from the CDN after one miss. The likely cause, inferred and not shown: each fresh signed URL carries its own token and so is its own cache key (the [data residency page](/reference/supabase-data-residency/) records the Storage CDN cache key as the object or token), and the ranges were up to 64 MiB. A cold 1 KiB signed-URL range of an object of the same size answered in 272 ms to headers in storage-surface run 4 ([large objects page](/reference/supabase-storage-large-objects/#the-cdn-cache-by-read-path)), so object size alone does not explain 30479 ms.

### Error shapes and where the difference comes from

Of 22 failing requests sent to each target, 14 had the same status, media type, body keys and code on all four (CK12). The differences, with the version gap from CK13 beside each:

| Request | Self-hosted | Managed | Version gap | Attribution |
|---|---|---|---|---|
| Auth `/user` without a bearer | `403` `bad_jwt` | `401` `no_authorization` | Auth v2.196.0 against v2.197.0 | not separated: the Auth version or the gateway in front of it |
| Data API without `apikey` | `401` `text/plain` `Unauthorized` | `401` `application/json` with `hint,message` | PostgREST 14.17 against 14.18 | the gateway answers, not PostgREST: Envoy's own `401` on self-hosted ([self-hosted defaults](/reference/supabase-self-hosted-defaults/), SD02) |
| Storage REST without auth | `400` `NoSuchKey` | `400` `InvalidRequest` | none, Storage 1.80.2 on both | configuration or gateway, not the Storage version |
| S3 `NoSuchKey`, missing bucket, bad signature, range past EOF, RLS-denied PUT (5 requests) | `application/xml` | `text/plain`, same XML elements and codes | none, Storage 1.80.2 on both | the managed edge sets the media type (inferred, as in storage-surface SS03i); body and code match |

A request for a missing bucket over S3 answered `NoSuchKey`, not `NoSuchBucket`, on every target. CK02's refusals (wrong password `invalid_credentials`, disabled user `user_banned`, an expired token `403 bad_jwt` from Auth and `401 PGRST303` from the Data API) were identical on all four. The RUNLOG records no upstream report for any of these differences.

### PostgREST accepts a just-expired token, Auth does not

At `exp` + 5 s, Auth answered `403` and the Data API `200`; at `exp` + 45 s both refused. The same on all four targets (CK02). PostgREST documents a 30-second clock skew allowance on its claim checks,[^pgrst-auth] which covers the 5 s probe. By that allowance, a Data API `200` does not prove the token is unexpired for up to 30 s past `exp`. The [Auth end to end page](/reference/supabase-auth-end-to-end/) covers who verifies a token and with what tolerance.

### Region isolation

A `region-a` token sent to `region-b` got Auth `403 bad_jwt`, Data API `401 PGRST301`, Storage REST `400 AccessDenied` and S3 `403 AccessDenied`; the object key answered `404` there, and the key service refused the other region's token with `401 invalid_token`. The reverse direction gave the same results (CK10).

### Browser

Headless Chromium ran the same library from a page on every target: S3 multipart upload, then ranged reads through a signed URL, S3 and `/object/authenticated`, 3 of 3 each (CK11). Part ETags were readable from the UploadPart response on all targets, so the ListParts fallback was never needed. A ranged signed-URL GET exposed `content-length,content-type` to the page on managed, and `content-range,etag,content-length,content-type` on self-hosted. The managed preflights answered `allow-origin=*` with no expose list; the self-hosted ones echoed the page origin with `expose=*`. storage-surface SS03h recorded the same split, covered on the [large objects page](/reference/supabase-storage-large-objects/).

### Self-hosted only

- Storage verifies an S3 SigV4 signature against the host of `STORAGE_PUBLIC_URL`. In the first `onprem` run the page reached the stack under another host name and CreateMultipartUpload got `SignatureDoesNotMatch`; with the same URL as every other client it worked (CK11). Source: `getHostHeader` in [`signature-v4.ts`](https://github.com/supabase/storage/blob/v1.80.2/src/storage/protocols/s3/signature-v4.ts).
- The upstream file backend (`./volumes/storage` bind mount) failed every upload on Docker Desktop for Mac: REST upload `500` "The file system does not support extended attributes", S3 UploadPart and TUS create `500`. The file backend keeps metadata in extended attributes (`fs-xattr` in the v1.74.0 and v1.80.2 images, source-read). On a named Docker volume every module passed (CK03-CK05).
- PostgREST 14.17 refused a just-issued token with `401 PGRST303 JWT issued at future` once each in CK05 and CK06 of the final `onprem` run, and 0 times on managed. The client now retries once after 2 s and counts it (`iat_future_retries`). The operator notes say the Docker VM clock fell about 260 s behind the host during the sleep period that ended about 13:08Z; the run started at 12:23Z, and whether the drift caused the refusals was not separated.

### Client-side lessons

These are this application's code, not platform behaviour.

- tus-js-client's Node HTTP stack under Bun stalled twice: a Buffer body got a server `408 stream timeout`, and with a Readable body one PATCH to `region-b` hung with no bytes moving. [`tus-fetch.ts`](https://github.com/erfianugrah/supabase-lab/blob/5f7ce52/experiments/client-keyed-objects/client/src/tus-fetch.ts) replaces it with `fetch` and a 120 s per-request timeout.
- A ranged read fetches ciphertext and chunk hashes in parallel, and both calls refreshed the same session. Auth answered the second refresh with `400 refresh_token_already_used`, and later calls carried an expired token. The session refresh is single-flight now. This was on `onprem` during client re-runs, two refreshes in quick succession; edge-resilience W08 on a managed project saw two concurrent refreshes both answer 200 ([incident resilience](/reference/supabase-incident-resilience/)), and the two were not reconciled (different target, different timing, and the Auth reuse interval was not varied).
- Bun's `fetch` reused pooled keep-alive connections the far side had closed (`The socket connection was closed unexpectedly`); Auth grants and the harness HTTP helper retry on that network error.

## Reading the numbers

- The parity rows assert correctness; the timing rows are context from one vantage.
- The signed-URL p50 is one run from one vantage against one project. A cache miss per URL fits it, and the data residency measurements make that plausible, but the run did not isolate the cause; a cold 1 KiB signed-URL range of a 2 GiB object answered in 272 ms to headers in storage-surface run 4, so object size alone does not explain it.
- The `region-b` CK04 failure coincides with host sleep. It is recorded as a fail; the TUS upload of the same size on the same project passed.
- The error-shape differences with no version gap point at configuration or the layer in front of the service. The Auth one could be either, and the run cannot tell.

## Not measured

- CK04 and CK06 on `region-b`: the resume died during host sleep and was not re-run.
- CK04-CK06 on `onprem-file`: the Docker VM disk had no room for two 2 GiB objects.
- CK10 on the self-hosted targets, which have one region per run.
- A scan of managed's object store for plaintext: there is no access to it.
- Any other vantage, region or repeat run. Every target ran once.
- Self-hosted on Linux amd64 or Kubernetes, high availability for the self-hosted stack, and self-hosted backup and restore.
- A real KMS or HSM behind the key service, and fitness for any regulatory or contractual regime.
- A partner key service (CipherStash ZeroKMS) in place of the operator key service, and EQL columns in this catalogue; EQL alone was measured on a local rig and a managed project ([EQL on Supabase](/reference/supabase-cipherstash-eql/)).
- The cause of the slow signed-URL reads on `region-a`.
- Two managed attempts before the final one produced no artifact (one hit a background-job time limit, one was stopped by hand) and are not counted.
