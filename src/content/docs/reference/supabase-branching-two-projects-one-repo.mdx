A monorepo holds two apps, `apps/a/` and `apps/b/`, each with its own
`supabase/` directory and its own Supabase project. Both projects connect to
the same GitHub repository through the Supabase GitHub integration, each with
its own working directory, and both have Automatic branching on. Two
questions follow: which pull requests create a preview branch on which
project, and whether a CI job can wait for one project's preview when both
report checks on the same commit.

Every figure marked measured comes from
[experiments/github-branching](https://github.com/erfianugrah/supabase-lab/tree/f836203/experiments/github-branching)
in the [supabase-lab](https://github.com/erfianugrah/supabase-lab) harness, run
on 2026-09-23 against two Micro projects in `ap-southeast-1` on a Pro
organization and a private throwaway repository, all created and destroyed the
same day, then again from 03:27 UTC on two fresh projects and a fresh
repository for the file-kind, late-change and merge questions. The
second-session modules (GB04-GB06), their artifacts and RUNLOG Runs 5-7 are
at [0c90777](https://github.com/erfianugrah/supabase-lab/tree/0c90777/experiments/github-branching). Project A was connected with Working directory `apps/a`, project B
with `apps/b`. The branching docs the results are compared against were read
the same day.[^sb-gh-integration][^sb-working-branches] Anything not marked
measured is either cited or labelled as a design or as not run.

**TL;DR:**

- Connecting a second project to a repository another project already uses is
  accepted (B's first attempt did not save; it did on reconnect); each
  connection keeps its own working directory.
- With "Supabase changes only" off, each project created a preview for all 5
  pull requests in the run, a root `README.md` change included. With it on, a
  project created a preview only for pull requests that changed files under
  its own `<workdir>/supabase/` (tested with migrations; a `seed.sql`,
  `config.toml`, function or `NOTES.md` change under A's `<workdir>/supabase/`
  also triggered A).
- Every connected project posted check-runs named `Supabase Preview`, from
  the same GitHub App, to every pull request head commit read.
  Every project posts at least one `skipped` run; a project that does not
  branch posts only `skipped` runs, 2 of them.
- The docs' wait-by-check-name workflow, path-filtered to app A, returned
  project B's `skipped` on an A-only pull request, so its migrate job was
  skipped, and B's `success` on a pull request touching both apps.
- Per project, the Management API branch list reports the preview's state:
  `MIGRATIONS_FAILED` for A and `FUNCTIONS_DEPLOYED` for B on the same pull
  request. Its first reading, at 15 s, was `FUNCTIONS_DEPLOYED` on both,
  before `CREATING_PROJECT` appeared at 32 s.
- With the setting on, a migration pushed to a pull request that opened
  without Supabase changes created no preview until the pull request was
  closed and reopened.
- Merging a pull request that changed only app A started a production action
  run on both projects, with "Supabase changes only" on (one merge).

## Which setup to pick

| Goal | Setup | Status |
|---|---|---|
| A pull request that touches only app A creates only A's preview | "Supabase changes only" on, on both projects | measured |
| Every pull request gets a preview on both projects | "Supabase changes only" off | measured; 2 previews per pull request, each billed for its own usage[^sb-branching-usage] |
| A CI job waits for app A's preview before seeding or testing it | poll project A's branch list for the pull request's git branch | measured signal; the wait loop below is a design, not run in CI |
| A CI job waits on the `Supabase Preview` check by name | do not use with two projects connected | measured: it read the other project's run |
| Try to have only one project report on a commit | Automatic branching off on one project; create its branches from CI | not run; whether a connected project with Automatic branching off still posts check-runs is untested |

## Preview creation: the working directory and "Supabase changes only"

The docs define the working directory as "the path from your repository root
to the directory that contains the `supabase/` folder", and the setting as
"only create Supabase branches when Supabase files change".[^sb-gh-integration]
Neither says which files count when two projects share a repository. The run
opened the same five pull requests once with the setting off on both projects
and once with it on.

| Pull request changes | Off: preview on A | Off: preview on B | On: preview on A | On: preview on B |
|---|---|---|---|---|
| `README.md` at the repository root | yes | yes | no | no |
| `apps/a/README.md` | yes | yes | no | no |
| a migration under `apps/a/supabase/` | yes | yes | yes | no |
| a migration under `apps/b/supabase/` | yes | yes | no | yes |
| a migration under each | yes | yes | yes | yes |

- Off, the working directory did not limit which pull requests previewed.
  Each project created 5 previews for 5 pull requests, 10 in all.
- On, each project previewed exactly the pull requests that changed a
  migration under its own `<workdir>/supabase/` (5 shapes, one pull request
  each). `apps/a/README.md` sits inside A's working directory and did not
  trigger A.
  In these two runs the files changed under `supabase/` were migrations
  only; a later run tested `seed.sql`, `config.toml`, a function and a
  non-CLI file, below.
- Closing the pull requests removed every preview within 2 minutes in every
  run; nothing was left for the harness to delete.
- The connection form set Branch limit to 3; GB00 read `limit=3` back on
  both projects. The run raised it to 10 on both first, so the limit could
  not hide a preview.

With the setting on, each of four kinds of file under A's
`<workdir>/supabase/` triggered a preview on A, including one the CLI does not
read. Each pull request below changed one file under `apps/a/supabase/`:

| File changed | Preview on A | Preview on B |
|---|---|---|
| `seed.sql` (a second insert) | yes | no |
| `config.toml` (a comment line appended) | yes | no |
| `functions/probe/index.ts` (a new function) | yes | no |
| `NOTES.md` (a file the CLI does not read) | yes | no |

On the function pull request, A's comment marked Edge Functions with a
warning: "Only Functions declared in config.toml will be automatically
deployed to branches". Whether `probe` deployed to the preview was not
checked.

A pull request opened with only `apps/a/README.md` got no preview on A; a migration pushed to it
afterwards still produced none in 240 s; closing and reopening the pull
request produced one at the first 20 s poll. With the setting on, a pull
request that opens without Supabase changes and gains a migration later
needed that close and reopen (one pull request; late `seed.sql` or
`config.toml` changes were not tried).

A `seed.sql` change pushed to a pull request whose preview already exists
did not re-seed it: 240 s after the push the new row was absent from the
preview database. The docs say the same: "The database is only seeded once,
when the preview branch is created. To rerun seeding, delete the preview
branch and recreate it by closing, and reopening your pull
request."[^sb-working-branches]

## The checks on a shared commit

Each project reports its branching pipeline to GitHub as check-runs. With two
projects connected, all of them land on the same commit.

| On the head commit | Measured |
|---|---|
| Check-run name | `Supabase Preview` on every run, from both projects |
| GitHub App and check suite | `supabase` for every `Supabase Preview` run; one check suite on the setting-off commits (RUNLOG snapshot). Commits with the wait workflow also carried that workflow's own `github-actions` runs |
| Runs from a project that branched | 5, once 6: 1 `skipped`, 1 `success` (or `failure`), and 3 (once 4) still `in_progress` at the end of the observation window (600 s; 480 s for the failure run; setting-off run: snapshot at 01:59:12 UTC, inside the window) |
| Runs from a project that did not branch ("Supabase changes only" on) | 2, both `skipped` |
| Field that identifies the project | `details_url` only (checked: `external_id`, `details_url`, output title, output summary). It links the parent project's dashboard on the early runs and the preview branch's own project on later ones |
| `external_id` | empty on every run |
| Output title | `Supabase Preview` or empty |

GitHub's check-runs endpoint defaults to `filter=latest`, "the most recent
check runs".[^gh-check-runs] In the setting-on scoping run, that view
returned a single `Supabase Preview` run. On 2 of the 5 pull requests (the
A-only and the two-app one) the project it belonged to changed during the
build: on the A-only pull request, sampled every 3 s for the first 150 s, the
name-filtered default view showed two different B `skipped` runs in turn
before A's first `in_progress`, then A's `success`. Pass `filter=all` to see every run.

The integration also comments on each pull request, once per connected
project, from `supabase[bot]`. Each comment starts with a `[supa]:<ref>`
marker line. On a pull request that changed only
`apps/a/supabase/`, B's comment carried B's own ref and read "This pull
request has been ignored for the connected project ... because there are no
changes detected in `apps/b/supabase` directory." A's comment carried the
ref of A's preview branch rather than A's, with its Deployments and Tasks
tables and the line "Tasks are run on every commit but only new migration
files are pushed. Close and reopen this PR if you want to apply changes from
existing seed or migration files." So on a one-app pull request the ignored project's comment can be
recognised from its ref or its "has been ignored" text. A branching
project's comment carries its preview's ref, which ties back to the parent
only through the parent's branch list (`project_ref`); the early check-runs'
`details_url` carries the parent ref directly, as above. Two branching
projects' comments were not compared.

## Waiting for one project's preview in CI

The branching docs show a CI job that waits for the preview with
`fountainhead/action-wait-for-check@v1.2.0` and `checkName: Supabase
Preview`, then gates a migrate job on the result being
`success`.[^sb-working-branches] The action lists check-runs by name with the
endpoint's default filter and returns the conclusion of the first completed
one.[^wait-action-poll] The run added that workflow to the repository with a
path filter of `apps/a/supabase/**`, the migrate job reduced to an echo, and
"Supabase changes only" on for both projects.

| Pull request | Wait step returned | That run belonged to | Migrate job | A's own first `success` (first seen, s after the run started creating the pull requests, 30 s poll) |
|---|---|---|---|---|
| migration under `apps/a` only | `skipped` | project B | skipped | 108 s |
| migration under each app | `success` | project B | ran | 108 s |

On the A-only pull request, the B `skipped` run the wait step read started
at 02:22:13 UTC. A's own `skipped` run, started at 02:22:10 and already completed, was not
the latest; A's `success` run started at 02:22:58 and was first seen
completed by the poll at 108 s. The path filter decides
which pull requests run app A's workflow (no B-only pull request was opened in
this run); it cannot stop B's runs being on A's commits, and with "Supabase
changes only" on, B posts `skipped` runs to every pull request commit it does
not branch for.

The Management API's branch list is per project, so it reports each
project's preview separately. `GET /v1/projects/{ref}/branches` on the parent project, matched on
`git_branch`, was sampled on one pull request that broke A's migration and kept B's
valid:

| First sample showing the value (s after opening, 15 s polling) | A branch `status` | B branch `status` |
|---|---|---|
| 15 | `FUNCTIONS_DEPLOYED` | `FUNCTIONS_DEPLOYED` |
| 32 | `CREATING_PROJECT` | `CREATING_PROJECT` |
| 65 | `RUNNING_MIGRATIONS` | `RUNNING_MIGRATIONS` |
| 81 | `MIGRATIONS_FAILED` | `FUNCTIONS_DEPLOYED` |

Both branch rows read `FUNCTIONS_DEPLOYED` at 15 s, before `CREATING_PROJECT`
appeared at 32 s, so a loop that exits on that value can return before the
preview project is created. The published OpenAPI document marks `status` as
deprecated, with "List action runs to get branch status instead".[^sb-openapi]
The preview project's latest action run
(`GET /v1/projects/{preview_ref}/actions`) showed `migrate` `DEAD`, with
`deploy` and `seed` still `CREATED`, on A at 81 s, and every step `EXITED` on
B.

In the wait-workflow run, the action runs that carried a `check_run_id` and
pointed at that run's commits were 3, one per preview project (1 on the
A-only pull request, 2 on the two-app one). Each pointed at a run left
`in_progress` at the end of the 600 s window while the action run's steps
were all `EXITED`, so it cannot serve as a wait target. The parent projects'
action runs pointed at no run on those commits.

A wait loop built on the branch list, as a design (the calls are the ones the
run made from the harness; the loop was not run in CI):

```bash
# Needs SUPABASE_ACCESS_TOKEN and this app's parent project ref.
seen_busy=0
for i in $(seq 1 60); do
  s=$(curl -s -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
        "https://api.supabase.com/v1/projects/$PROJECT_REF/branches" |
      jq -r --arg b "$GITHUB_HEAD_REF" '.[] | select(.git_branch == $b) | .status')
  case "$s" in
    CREATING_PROJECT|RUNNING_MIGRATIONS|MIGRATIONS_PASSED) seen_busy=1 ;;
    MIGRATIONS_FAILED|FUNCTIONS_FAILED) [ "$seen_busy" = 1 ] && exit 1 ;;
    FUNCTIONS_DEPLOYED) [ "$seen_busy" = 1 ] && exit 0 ;;
  esac
  sleep 10
done
exit 1
```

`MIGRATIONS_PASSED` and `FUNCTIONS_FAILED` come from the OpenAPI enum and
were not observed in the run.[^sb-openapi] Requiring a non-terminal state
first covers the first reading, which was `FUNCTIONS_DEPLOYED` at 15 s on
both rows before `CREATING_PROJECT`. It also means a loop that starts after
the preview has finished never sees one and times out; a job that can start
late could compare the branch's `updated_at` with the head commit's time
instead (`updated_at` was not read in the run; untested).

<Aside type="caution" title="One failure sample">
The failure path rests on one run with one kind of failure, a migration that
errors. Seed, configuration and function-deploy failures were not run, and
neither was a check of whether a `DEAD` step always means a failed one.
</Aside>

## Merging to the production branch

Both projects had Deploy to production on with `main` as the production
branch: the merge module runs only if both default branch rows read
`git_branch` `main`, and it ran (the value is not recorded in the artifact);
the dashboard form writes that field only when the option is enabled. The docs say that on a push or merge to it, new migrations are
applied and the Edge Functions and Storage buckets declared in `config.toml`
are deployed; they do not mention "Supabase changes only" or the working
directory in that section.[^sb-gh-integration] The run merged a pull request
with one migration under `apps/a/supabase/` and watched both projects for
240 s:

| After the merge | Project A | Project B |
|---|---|---|
| New production action runs | 1 | 1 |
| Steps | `clone`, `pull`, `health`, `migrate`, `seed`, `deploy` `EXITED`; `configure` `PAUSED` | the same |
| The merged migration in the project's migrations list | yes | no |
| `supabase` app check-runs on the merge commit, at the end of the watch | 3: `success` + 2 `in_progress` | 3: `success` + 2 `in_progress` |

B's production run took `clone`, `pull`, `health`, `migrate`, `seed` and
`deploy` to `EXITED`, the same as A's, for a merge that changed nothing
under `apps/b/`, with "Supabase changes only" on. One merge was tried. The
merged migration did not appear in B's migrations list. Whether B's run
changed anything else, including whether `deploy` redeployed anything (B
had no functions), was not measured. A `seed` step reached `EXITED` on both
projects; whether it seeded anything was not checked, and the docs say seed
files are ignored on production deploys.[^sb-gh-integration]

## Reading the numbers

- The runs used two pairs of projects, one pair per session, in one
  organization and one region, on one day.
  The counts per commit (5 runs from a project that branched, 2 from one that
  did not; B posted 6 on the two-app pull request in the setting-on scoping
  run, 5 in the wait-workflow and failure runs) could change without notice.
  Two things held on every commit read: every run from the `supabase` app was
  named `Supabase Preview`, and every connected project posted to it.
- Preview first-seen times in the scoping runs are 30 s poll samples;
  creation latency was not measured. The file-kind run's previews were first
  seen at 56 s at a 30 s poll, counted from when the run started creating
  the pull requests.
- The late-change, re-seed and merge results are one pull request each.
- The run with the setting off used an earlier revision of the scoping module
  that read only the default check-runs view. Its check-run figures come from
  a `filter=all` snapshot taken during that run and recorded in the RUNLOG,
  not from its published artifact.
- The wait-by-name result depends on when the action's first poll lands
  relative to the check-runs. The run recorded one pull request per shape on
  GitHub-hosted runners; a different start time can pick a different
  project's run.
- A single project on its own was not tested. In the setting-on scoping
  run's A-only pull request, A's own `skipped` run came 29 s before its next
  run, and in that window the name-filtered view showed only B's `skipped`
  runs; whether a wait step ever reads a lone project's `skipped` was not
  separated.
- The Vercel integration was not part of the run.
