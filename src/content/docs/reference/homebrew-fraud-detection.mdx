How **forminator** and **markov-mail** (private repos) implement multi-layer fraud detection for form submissions on Cloudflare Workers. Two Workers - one handling form submissions with multi-layer detection and 10-component risk scoring, the other running a 48-feature Random Forest classifier on email addresses with automated weekly retraining - connected via RPC service bindings.

This is a reference template for building similar systems. All patterns are derived from production code.

**TL;DR:**

- Two Workers carry the system: the form Worker runs the submission pipeline and the 10-component risk scoring, and the ML Worker runs a 48-feature Random Forest email classifier. They talk over a Worker-to-Worker RPC service binding, which executes on the same thread of the same server.
- Detection runs in layers: a local D1 blacklist fast path skips the Turnstile API call for identifiers already known bad, then the ML email check, the ephemeral-ID signals and the JA4 TLS fingerprint analysis each contribute one score component.
- Component failures fail open - an unavailable ML Worker scores 0 risk for its component and its weight is redistributed to the remaining active signals - while token replay and Turnstile validation stay fail-secure.
- Weights, thresholds and detection parameters live in a mergeable config and are auto-normalised to sum to 1.0 after any override; block/allow comes from deterministic floors and a corroboration bonus on top of the weighted score.
- Decisions are written to a `ScoringDecision` audit trail, and the model behind them is a 20-tree Random Forest serialised as JSON in KV, guarded before deploy on accuracy, KV's 25 MB value limit and feature alignment.
- On Supabase the same layers run in the project's Postgres behind Supabase Auth hooks, and the edge Worker hands the signup hook a signed summary of what only it can see (the Turnstile device ID, JA4). See [On Supabase: the same layers in Postgres](#on-supabase-the-same-layers-in-postgres).

### Layer 0: blacklist fast path

Pre-Turnstile check against a TTL-based blacklist. Matches on email, ephemeral ID, JA4 fingerprint, or IP address (checked in that priority order, most specific first). Returns in single-digit milliseconds and short-circuits the entire pipeline.

```typescript
// Check order: most specific identifier first
async function checkPreValidationBlock(
  ephemeralId: string | null,
  remoteIp: string,
  ja4: string | null,
  email: string | null,
  db: D1Database,
): Promise<PreValidationResult> {
  const identifiers = [
    { type: "email", value: email },
    { type: "ephemeral_id", value: ephemeralId },
    { type: "ja4", value: ja4 },
    { type: "ip_address", value: remoteIp },
  ].filter((id) => id.value != null);

  for (const { type, value } of identifiers) {
    const entry = await db
      .prepare(
        `SELECT * FROM fraud_blacklist
         WHERE identifier_type = ? AND identifier_value = ?
         AND expires_at > ?`,
      )
      .bind(type, value, new Date().toISOString())
      .first();

    if (entry && ["high", "medium"].includes(entry.confidence)) {
      return {
        blocked: true,
        reason: entry.detection_type,
        confidence: entry.confidence,
      };
    }
  }
  return { blocked: false };
}
```

<Aside type="tip" title="The fast path avoids one API call">
  Turnstile validation costs an external API call. If you've already determined
  an identifier is fraudulent, checking a local D1 table first avoids that cost
  entirely. In practice, this can eliminate the API call for the majority of
  repeat offenders.
</Aside>

### Layer 1: email fraud via ML (RPC)

The form Worker calls the ML Worker via a service binding. The RPC call has zero overhead per Cloudflare's documentation - both Workers execute on the same thread of the same server.

```typescript
// Form Worker: call ML Worker via service binding
async function checkEmailFraud(
  email: string,
  env: Env,
  request?: Request,
): Promise<EmailFraudResult | null> {
  try {
    // Pass request headers so ML Worker has access to
    // geo, network, and bot management signals
    const headers: Record<string, string | null> = {};
    if (request?.cf) {
      headers["cf-ipcountry"] = request.headers.get("cf-ipcountry");
      headers["cf-connecting-ip"] = request.headers.get("cf-connecting-ip");
      // ... additional cf headers for fingerprinting
    }

    const result = await env.FRAUD_DETECTOR.validate({
      email,
      consumer: "form-worker",
      flow: "submission",
      headers,
    });

    return {
      riskScore: result.riskScore * 100, // ML returns 0-1, scoring expects 0-100
      decision: result.decision,
      signals: result.signals,
    };
  } catch {
    return null; // Fail-open: ML unavailable = 0 risk
  }
}
```

<Aside type="note" title="Fail-open design">
  Email fraud detection fails open - if the ML Worker is unavailable, the
  submission proceeds with a 0 risk score for that component. Its weight is
  redistributed to the remaining active signals. Token replay and Turnstile
  validation are the only fail-secure checks.
</Aside>

### Layer 2: ephemeral ID behavioral signals

Collects three signals from D1 using Turnstile's ephemeral device ID (Enterprise) to detect volume abuse:

| Signal                   | Query                                             | Detection                           |
| ------------------------ | ------------------------------------------------- | ----------------------------------- |
| **Submission count**     | Count submissions by ephemeral ID in 24h          | Form stuffing from same device      |
| **Validation frequency** | Count Turnstile validations by ephemeral ID in 1h | Rapid-fire CAPTCHA solving          |
| **IP diversity**         | Count distinct IPs per ephemeral ID in 24h        | VPN/proxy rotation from same device |

```typescript
async function collectEphemeralIdSignals(
  ephemeralId: string,
  db: D1Database,
  config: FraudDetectionConfig,
): Promise<EphemeralIdSignals> {
  try {
    const [submissions, validations, ips] = await Promise.all([
      db
        .prepare(
          `SELECT COUNT(*) as count FROM submissions
         WHERE ephemeral_id = ? AND created_at > datetime('now', '-24 hours')`,
        )
        .bind(ephemeralId)
        .first<{ count: number }>(),

      db
        .prepare(
          `SELECT COUNT(*) as count FROM turnstile_validations
         WHERE ephemeral_id = ? AND validated_at > datetime('now', '-1 hour')`,
        )
        .bind(ephemeralId)
        .first<{ count: number }>(),

      db
        .prepare(
          `SELECT COUNT(DISTINCT ip) as count FROM (
           SELECT ip_address as ip FROM submissions
           WHERE ephemeral_id = ? AND created_at > datetime('now', '-24 hours')
           UNION
           SELECT ip_address as ip FROM turnstile_validations
           WHERE ephemeral_id = ? AND validated_at > datetime('now', '-24 hours')
         )`,
        )
        .bind(ephemeralId, ephemeralId)
        .first<{ count: number }>(),
    ]);

    return {
      submissionCount: submissions?.count ?? 1,
      validationCount: validations?.count ?? 1,
      uniqueIPCount: ips?.count ?? 1,
    };
  } catch {
    return { submissionCount: 1, validationCount: 1, uniqueIPCount: 1 }; // Fail-open baseline
  }
}
```

<Aside type="caution" title="Write-before-read">
  The current request's validation record must be inserted into D1 **before**
  collecting signals. Otherwise you have a time-of-check/time-of-use (TOCTOU) race where the first request
  from a device always sees count=0. Insert the pending record first, then
  query.
</Aside>

### Layer 3: JA4 TLS fingerprint analysis

Uses Bot Management's JA4 fingerprint (Enterprise) to detect session hopping - multiple distinct devices sharing the same TLS fingerprint, which indicates automated tooling.

Three sub-layers with increasing scope:

| Sub-layer               | Scope                     | Window | Threshold        | Catches                    |
| ----------------------- | ------------------------- | ------ | ---------------- | -------------------------- |
| **4a: IP Clustering**   | Same JA4 + same IP/subnet | 1 hour | 2+ ephemeral IDs | Bot farm on single network |
| **4b: Rapid Global**    | Same JA4, any IP          | 5 min  | 3+ ephemeral IDs | VPN-hopping automation     |
| **4c: Extended Global** | Same JA4, any IP          | 1 hour | 5+ ephemeral IDs | Slow distributed attacks   |

```typescript
interface ClusteringAnalysis {
  ja4: string;
  ephemeralCount: number;
  submissionCount: number;
  timeSpanMinutes: number;
  avgBotScore: number | null;
}

function calculateCompositeRiskScore(
  analysis: ClusteringAnalysis,
  config: FraudDetectionConfig,
): number {
  let rawScore = 0;

  // Signal 1: Clustering (multiple devices sharing JA4)
  if (analysis.ephemeralCount >= 2) {
    let clusterScore = 80;
    // Household mitigation: halve score if bot score indicates human
    if (analysis.avgBotScore && analysis.avgBotScore >= 50 && !isRapid) {
      clusterScore = Math.round(clusterScore / 2);
    }
    rawScore += clusterScore;
  }

  // Signal 2: Velocity (submissions too close together)
  if (analysis.timeSpanMinutes < config.ja4.velocityThreshold) {
    rawScore += 60;
  }

  // Signal 3a: Global anomaly (high IP distribution + local clustering)
  if (ja4Signals?.ips_quantile_1h > config.ja4.ipsQuantileThreshold) {
    rawScore += 50;
  }

  // Signal 3b: Bot pattern (high request volume + local clustering)
  if (ja4Signals?.reqs_quantile_1h > config.ja4.reqsQuantileThreshold) {
    rawScore += 40;
  }

  // Max raw = 230, normalized to 0-100 by scoring module
  return rawScore;
}
```

<Aside type="tip" title="IPv6 subnet matching">
  For IP clustering, compare IPv6 addresses at the /64 prefix level (first 4
  groups). Privacy extensions (RFC 8981) rotate the interface identifier but
  keep the prefix stable, so /64 matching links requests from the same network
  without relying on a stable full address.
</Aside>

<Aside type="note" title="Clustering includes blocked requests">
  JA4 clustering queries both `submissions` and `turnstile_validations` tables
  via `UNION ALL`. This ensures attackers who are repeatedly blocked by the
  blacklist fast path (and therefore never create submissions) still escalate
  the clustering score for their JA4 fingerprint.
</Aside>

## Risk scoring

All signals feed into a 10-component weighted score. The architecture ensures every decision is auditable - the full breakdown is stored alongside each submission.

### Score components and weights

| Component            | Weight | Source              | What it measures                                  |
| -------------------- | ------ | ------------------- | ------------------------------------------------- |
| Token Replay         | 0.28   | Turnstile           | Reused CAPTCHA token (binary: 0 or 100)           |
| Email Fraud          | 0.14   | ML Worker RPC       | ML-classified email fraud probability             |
| Ephemeral ID         | 0.15   | D1 query            | Submission volume from same device                |
| Validation Frequency | 0.10   | D1 query            | CAPTCHA solve rate from same device               |
| IP Diversity         | 0.07   | D1 query            | IP rotation from same device                      |
| JA4 Session Hopping  | 0.06   | D1 query + Bot Mgmt | TLS fingerprint clustering                        |
| IP Rate Limit        | 0.07   | D1 query            | Browser-switching OR email diversity from same IP |
| Header Fingerprint   | 0.07   | Request headers     | Header pattern reuse across ephemeral IDs         |
| TLS Anomaly          | 0.04   | D1 + Bot Mgmt       | Fingerprint baseline deviation                    |
| Latency Mismatch     | 0.02   | Request timing      | Geo vs network latency inconsistency              |

Weights must sum to 1.0. The system auto-normalises after config overrides.

The IP Rate Limit component is a composite of two sub-signals - submission frequency per IP and email diversity per IP - combined via `Math.max()`. The email diversity signal detects form spam with unique emails from the same address:

```typescript
async function collectEmailDiversitySignal(
  remoteIp: string,
  db: D1Database,
  config: FraudDetectionConfig,
): Promise<{ distinctEmails: number; riskScore: number }> {
  const result = await db
    .prepare(
      `SELECT COUNT(DISTINCT email) as count FROM submissions
       WHERE remote_ip = ? AND created_at > datetime('now', '-1 hour')`,
    )
    .bind(remoteIp)
    .first<{ count: number }>();

  const distinctEmails = (result?.count ?? 0) + 1; // +1 for current submission

  let riskScore: number;
  if (distinctEmails <= 1) riskScore = 0;
  else if (distinctEmails === 2)
    riskScore = 20; // Could be household
  else if (distinctEmails === 3)
    riskScore = 60; // Suspicious
  else riskScore = 100; // Definite form spam

  return { distinctEmails, riskScore };
}
```

<Aside type="note" title="IP rate limit is never a standalone block trigger">
  The IP Rate Limit component contributes to the weighted risk score but never
  independently triggers a block. This prevents false positives from shared IPs
  (offices, universities, NAT). Blocks only occur when the combined risk from
  all signals exceeds the threshold.
</Aside>

### Weight redistribution

When signals are inactive (at baseline), their weight is redistributed proportionally to active signals. This prevents the score from being suppressed when some detection layers aren't available (e.g., no Enterprise features, ML Worker down).

```typescript
// Identify inactive signals (at baseline values)
const inactiveWeight = components
  .filter((c) => c.score === 0 || c.score === baselineForComponent(c))
  .reduce((sum, c) => sum + c.weight, 0);

// Redistribute to active signals
const normalizationFactor = 1.0 / (1.0 - inactiveWeight);

for (const component of activeComponents) {
  component.contribution =
    component.score * component.weight * normalizationFactor;
}
```

### Corroboration bonus

When 3+ independent signals score above a threshold (default: 30), a bonus (default: +15 points) is added. This rewards convergent evidence from different detection methods. All three parameters are configurable via `risk.corroboration` in the config:

```typescript
corroboration: {
  threshold: 30,   // Minimum component score to count as "corroborating"
  minSignals: 3,   // Number of corroborating signals required
  bonus: 15,       // Flat bonus added to the score when triggered
},
```

### Deterministic block floors

Certain triggers immediately floor the score at the block threshold, regardless of the weighted calculation. Each has qualification requirements to prevent false positives:

| Trigger                | Qualification                                                       |
| ---------------------- | ------------------------------------------------------------------- |
| `token_replay`         | Always qualifies (fail-secure)                                      |
| `turnstile_failed`     | Always qualifies (fail-secure)                                      |
| `email_fraud`          | Self-sufficient (ML confidence)                                     |
| `ephemeral_id_fraud`   | Requires elevated ephemeral ID score AND validation frequency      |
| `ja4_session_hopping`  | Requires raw score at least 140 AND IP rate limit score at least 25 |
| `validation_frequency` | Requires ephemeral ID score above threshold                         |

### Dual scoring modes

| Mode        | Behavior                                           | Use case            |
| ----------- | -------------------------------------------------- | ------------------- |
| `defensive` | Deterministic triggers can override weighted score | Production default  |
| `additive`  | Purely weighted, no overrides                      | A/B testing, tuning |

### Decision audit trail

Every score adjustment is recorded:

```typescript
  };

```

### Block trigger priority

When the final score exceeds the block threshold, a `blockTrigger` is assigned based on which signal was the primary cause. The evaluation order matters - it determines the detection type recorded for forensic analysis and the user-facing error message.

| Priority | Condition                                                   | blockTrigger           | detectionType           |
| -------- | ----------------------------------------------------------- | ---------------------- | ----------------------- |
| 1        | ML email decision = block                                   | `email_fraud`          | `email_fraud_detection` |
| 2        | Ephemeral submission count exceeds threshold                | `ephemeral_id_fraud`   | `ephemeral_id_tracking` |
| 3        | Validation count exceeds frequency threshold                | `validation_frequency` | `ephemeral_id_tracking` |
| 4        | Validation burst (5+ validations, fewer than 2 submissions) | `validation_frequency` | `ephemeral_id_tracking` |
| 5        | Unique IP count exceeds IP diversity threshold              | `ip_diversity`         | `ephemeral_id_tracking` |
| 6        | JA4 clustering detected                                     | `ja4_session_hopping`  | `ja4_fingerprinting`    |
| 7        | Fingerprint anomaly triggered                               | per-signal             | `fingerprint_anomaly`   |

IP rate limit is intentionally excluded as a block trigger (see note above).

### Duplicate email handling

Duplicate email submissions use a tiered approach that distinguishes user error from automated probing:

| Attempt | Response                               | Blacklist                                      | Rationale                 |
| ------- | -------------------------------------- | ---------------------------------------------- | ------------------------- |
| 1st-2nd | `409 Conflict` with friendly message   | Low-confidence tracking entry (24h)            | Likely user re-submission |
| 3rd+    | `429 Too Many Requests` with wait time | High-confidence entry with progressive timeout | Automated probing pattern |

The escalation happens because the blacklist tracks duplicate attempts per email+IP combination. On the 3rd attempt, the system calculates a progressive timeout and adds a high-confidence blacklist entry that triggers the Layer 0 fast path for subsequent requests.

## Input validation and sanitisation
<a id="input-validation-and-sanitization"></a>

All form inputs pass through Zod schema validation and HTML sanitisation before entering the fraud detection pipeline.

**Schema validation** (Zod):

- Names: 1-50 chars, Unicode-aware pattern (`\p{L}\s'-`)
- Email: max 100 chars, standard format
- Phone: optional, normalised to E.164 format (strip non-digits, add `+1` prefix), validated against `^\+[1-9]\d{1,14}$`
- Address: optional, country required if any address field present
- Date of birth: optional, `YYYY-MM-DD`, must be 18-120 years old

**HTML sanitisation** applied to all text inputs:

```typescript
function sanitizeString(input: string): string {
  return input
    .replace(/<[^>]*>?/g, "") // Strip HTML tags
    .replace(/&#?\w+;/g, "") // Strip HTML entities
    .replace(/javascript\s*:/gi, "") // Strip javascript: URIs
    .replace(/data\s*:/gi, "") // Strip data: URIs
    .replace(/on\w+\s*=/gi, "") // Strip inline event handlers
    .trim();
}
```

<Aside type="tip" title="Sanitise before fraud detection">
  Run sanitisation before the fraud pipeline so detection signals operate on
  clean input. The Turnstile token is explicitly excluded from sanitisation.
</Aside>

### Detectors

The 48 features are produced by specialised detector modules. Each operates independently and returns structured results.

#### Sequential pattern detection

Identifies `user123`, `test001`, `account42` style emails. Two patterns: trailing numbers (`/^(.+?)(\d+)$/`) and middle numbers with separators (`/^(.+?)[._-](\d+)[._-](.+)$/`).

Confidence factors: sequence length (+0.25 to +0.7), leading zeros (+0.3), digit ratio (+0.1 to +0.2), common bot bases (+0.25). Threshold: `confidence >= 0.4` marks as sequential.

**Exemptions** (reduce false positives):

- **Birth years** (1940-present, ages 13-100): `john1990@` is not sequential
- **Small memorable numbers** (3 or fewer digits, base 4+ chars, no leading zeros, no common base): `mike42@` is not sequential

Common bot bases: `test`, `user`, `account`, `email`, `temp`, `demo`, `admin`, `guest`, `trial`, `sample`, `hello`, `service`, `team`, `info`, `support`, `member`.

#### Dated pattern detection

Identifies date components in email local parts. Five format patterns checked in priority order (most specific first): full date (`20241031`), month+year (`oct2024`), four-digit year (`2024`), leading year (`2024.username`), two-digit year (`24`).

Age-aware classification is the key insight - birth years get low risk, recent years get high risk:

| Category               | Year Age                  | Risk | Example     |
| ---------------------- | ------------------------- | ---- | ----------- |
| `future`               | negative (year > current) | 0.95 | `user2027@` |
| `recent_timestamp`     | 0-2                       | 0.90 | `user2025@` |
| `underage`             | 3-12                      | 0.70 | `user2015@` |
| `plausible_birth_year` | 13-65                     | 0.20 | `john1990@` |
| `elderly_birth_year`   | 66-100                    | 0.40 | `user1940@` |
| `ancient`              | >100                      | 0.80 | `user1900@` |

#### Linguistic feature extraction

Three feature groups measuring how "natural" an email local part looks:

- **Linguistic**: Pronounceability (composite: vowel ratio, consonant cluster penalties, impossible cluster detection), vowel/consonant ratios, max cluster lengths, syllable estimate. Context-dependent `y`/`w` classification (e.g., `y` is a vowel when not adjacent to vowels).
- **Structure**: Word boundary detection (`.`, `_`, `-`), segment count and length statistics, segments-without-vowels ratio.
- **Statistical**: Shannon entropy, bigram entropy (character pair transition randomness - higher = more suspicious), digit ratio, unique character ratio.

18 allowed consonant clusters (e.g., `sch`, `str`, `thr`, `ght`, `tch`, `nch`). Clusters of 3+ consonants not containing an allowed pattern are counted as "impossible."

#### N-gram naturalness

Bigram and trigram frequency analysis across 8 language groups (English, Spanish, French, German, Italian, Portuguese, Romanised, and a universal/mixed set). Input is NFD-normalised (Unicode Normalization Form D) to strip diacritics while preserving base characters, reducing false positives on international names. Scores how likely a character sequence is to appear in natural text for each language, taking the best match. Language detection uses suffix-based heuristics (e.g., `-ez` for Spanish, `-stein` for German, `-ovich` for Russian). Higher naturalness = lower fraud risk.

#### Benford's Law analysis

Checks whether the first-digit distribution of numbers in an email batch follows Benford's Law (`P(d) = log10(1 + 1/d)`). Natural registrations follow this distribution; sequential/automated generation produces uniform distribution.

Method: chi-square goodness-of-fit test (df=8) with critical value at 0.05 significance (15.507). Requires minimum 30 digit samples for statistical validity. Used primarily in batch analysis rather than individual scoring.

#### MX resolution

Resolves the email domain's MX records to classify the provider and detect suspicious hosting:

- **Resolution**: Cloudflare DNS-over-HTTPS (`cloudflare-dns.com/dns-query`) with 500ms fetch timeout via `AbortController` (wrapped in a 1500ms middleware timeout with background retry)
- **Caching**: In-memory with 15-minute TTL. Concurrent requests for the same domain are deduplicated via an inflight map.
- **Provider classification**: Google, Microsoft, iCloud, Yahoo, Zoho, Proton, self-hosted (MX points to own domain), other. Provider is determined by the MX exchange hostname patterns.
- **Features produced**: `mx_has_records`, `mx_record_count`, and one-hot encoded `mx_provider_*` flags (8 providers: Google, Microsoft, iCloud, Yahoo, Zoho, Proton, self-hosted, other). Cache bounded to 10k entries with LRU eviction.

<Aside type="note" title="Well-known provider fast path">
  Common domains (gmail.com, outlook.com, yahoo.com, etc.) skip DNS entirely and
  return cached provider classifications. This avoids the DoH call for the vast
  majority of legitimate email addresses.
</Aside>

### Production model configuration

The ML Worker's behavior is controlled by a config loaded from KV:

```json
{
  "riskThresholds": { "block": 0.88, "warn": 0.56 },
  "actionOverride": null,
  "adjustments": {
    "professionalEmailFactor": 0.5,
    "professionalDomainFactor": 0.5,
    "professionalAbnormalityFactor": 0.6
  },
  "ood": { "maxRisk": 0.85, "warnZoneMin": 0.6 }

```

- **`actionOverride`**: Set to `"allow"` for monitoring mode - runs all detection and logs decisions but never blocks. Required for a safe rollout of a new model or config change.
- **`adjustments`**: Professional email patterns (name-based addresses at reputable domains) get their risk score multiplied by these factors, reducing false positives on legitimate business emails.
- **`ood` (out-of-distribution)**: When the model encounters feature vectors outside its training distribution, risk is capped at `maxRisk` (0.85) and flagged if above `warnZoneMin` (0.6). Prevents overconfident predictions on novel patterns.

### Risk heuristics override

A post-model safety net that can override ML decisions based on simple threshold rules. Loaded from KV (`risk-heuristics.json`) with 60-second cache TTL, falling back to hardcoded defaults.

| Heuristic             | Block Threshold | Warn Threshold | Score Offset |
| --------------------- | --------------- | -------------- | ------------ |
| TLD risk              | 0.9+            | 0.8+           | +0.10        |
| Domain reputation     | 0.95+           | 0.85+          | +0.08        |
| Sequential confidence | 0.98+           | 0.9+           | +0.05        |
| Digit ratio           | 0.9+            | 0.8+           | +0.05        |
| Plus-addressing abuse | 0.8+            | -             | +0.03        |

Each rule has a `threshold`, `decision` (`warn` or `block`), `direction` (`gte` or `lte`), and `minScoreOffset`. Rules are applied after model scoring - they can elevate a score but never reduce it. The KV-based config means you can add or adjust heuristics without redeploying.

```typescript
interface HeuristicRule {
  threshold: number;
  decision: "warn" | "block";
  reason: string;
  direction?: "gte" | "lte"; // Default: gte
  minScoreOffset?: number;
}
```

### Random Forest inference at the edge

The model (20 decision trees of the classification-and-regression (CART) kind, trained both offline via scikit-learn and online via a container-based TypeScript implementation) is serialised as JSON and stored in KV. The Worker evaluates it using iterative tree traversal (not recursive, to avoid stack limits on the edge runtime).

```typescript
type CompactTreeNode =
  | { t: "l"; v: number } // Leaf: fraud probability
  | { t: "n"; f: string; v: number; l: CompactTreeNode; r: CompactTreeNode }; // Split node

function predictForestScore(
  model: ForestModel,
  features: Record<string, number>,
): number {
  const maxDepth = Math.min(model.meta.config?.max_depth ?? 20, 50);
  let total = 0;

  for (const tree of model.forest) {
    let node = tree;
    let depth = 0;

    // Iterative traversal (no recursion)
    while (node.t === "n" && depth < maxDepth) {
      const featureValue = features[node.f] ?? 0;
      node = featureValue <= node.v ? node.l : node.r; // scikit-learn convention
      depth++;
    }

    total += node.t === "l" ? node.v : 0.5; // Fallback if depth exceeded
  }

  return total / model.forest.length; // Average probability across trees
}
```

<Aside type="tip" title="Hot-swappable models">
  Storing the model in KV means you can deploy a new model without redeploying
  the Worker. The config loader caches the model with a TTL (default 60 seconds
  per KV's caching behavior). Upload a new model JSON to KV and it propagates
  globally within the eventual consistency window.
</Aside>

### Platt calibration

Raw forest outputs are calibrated using Platt scaling (sigmoid fit on out-of-bag predictions from training). This converts raw vote averages into well-calibrated probabilities:

```
calibrated = 1 / (1 + exp(-(intercept + coef * raw_score)))
```

Calibration parameters (`intercept`, `coef`) are stored in the model's metadata and applied automatically during inference. The production model's calibration was fitted on 50,000 out-of-bag (OOB) samples.

### Model fallback

The middleware uses Random Forest as primary and Decision Tree as fallback. If both models are unavailable (KV failure), the system applies a degraded "warn floor" score and fires an ops alert. This ensures the detection pipeline never silently passes traffic unscored.

### Global fraud detection middleware

Instead of wiring fraud detection per-route, a Hono middleware runs on every POST request that contains an `email` field:

```typescript
async function fraudDetectionMiddleware(c: Context, next: Next) {
  if (c.req.method !== "POST" || c.get("skipFraudDetection")) {
    return next();
  }

  const body = await c.req.raw
    .clone()
    .json()
    .catch(() => null);
  const email = body?.email;
  if (!email) return next();

  // Load model from KV, extract features, score, decide
  const features = buildFeatureVector(email, c.req);
  const score = predictForestScore(model, features);
  const calibrated = applyPlattCalibration(score, model.meta.calibration);
  const decision =
    calibrated >= threshold
      ? "block"
      : calibrated >= warnThreshold
        ? "warn"
        : "allow";

  c.set("fraudDetection", { score: calibrated, decision, signals });
  return next();
}

// Register globally
app.use("/*", fraudDetectionMiddleware);
```

Routes that need to opt out (e.g., dashboard auth) set a context flag:

```typescript

  c.set("skipFraudDetection", true);
  // ... handle auth
});
```

```typescript
class FraudDetectionService extends WorkerEntrypoint<Env> {

    email: string;
    consumer?: string;
    flow?: string;
```

## Progressive timeout and blacklisting

When a submission is blocked, the offending identifiers are blacklisted with escalating TTLs:

| Offense | Timeout  | Cumulative |
| ------- | -------- | ---------- |
| 1st     | 1 hour   | 1h         |
| 2nd     | 4 hours  | 5h         |
| 3rd     | 8 hours  | 13h        |
| 4th     | 12 hours | 25h        |
| 5th+    | 24 hours | 49h+       |

```typescript
function calculateProgressiveTimeout(
  offenseCount: number,
  config: FraudDetectionConfig,
): number {
  const schedule = config.timeouts.schedule; // [3600, 14400, 28800, 43200, 86400]
  const index = Math.min(offenseCount, schedule.length - 1);
  return schedule[index];
}
```

Blacklist entries store multiple identifiers (email, ephemeral ID, JA4, IP) and are checked on the fast path before any Turnstile API call. Each subsequent hit updates `last_seen_at` and increments `offense_count`.

## Scheduled tasks

The ML Worker uses two cron triggers to run three background tasks:

| Cron Expression  | Schedule           | Task                                                                                              |
| ---------------- | ------------------ | ------------------------------------------------------------------------------------------------- |
| `0 */6 * * *`    | Every 6 hours      | Refresh disposable domain list from external GitHub sources (71k+ domains stored in KV)           |
| `0 */6 * * *`    | Every 6 hours      | Prune validation records older than 30 days from D1 (GDPR compliance)                             |
| `0 3 * * SUN`    | Sundays 3AM UTC    | Automated model retraining via `TrainerContainer` Durable Object (see training pipeline below)    |

```typescript
export default {
  async scheduled(
    controller: ScheduledController,
    env: Env,
    ctx: ExecutionContext,
  ) {
    // Domain refresh + data pruning run on every cron trigger
    ctx.waitUntil(updateDisposableDomains(env));
    ctx.waitUntil(pruneOldValidations(env.DB, 30));

    // Weekly retraining runs only on the Sunday schedule
    if (controller.cron === "0 3 * * SUN") {
      ctx.waitUntil(triggerContainerRetraining(env));
    }
  },
};
```

The weekly retraining task sends training parameters (`nTrees: 20, maxDepth: 6, minSamplesLeaf: 20, conflictWeight: 20`) to the `TrainerContainer` Durable Object, which runs a full pipeline: fetch live training data from D1, train a new Random Forest, run guardrails, and upload the validated model to KV. After success, training samples older than 14 days are pruned.

## Model training pipeline

The Random Forest is trained through two complementary pipelines: an **automated container-based pipeline** that retrains weekly on live production data, and an **offline CLI pipeline** for initial training and major model revisions.

### Container-based retraining (production)

A weekly cron (Sundays 3AM UTC) triggers the `TrainerContainer` Durable Object, which runs a Bun-based Docker container. The container:

1. Fetches the current training dataset from the Worker's D1 database (auto-collected feature vectors from every `/validate` call)
2. Trains a new Random Forest using a TypeScript CART implementation with Gini impurity, random feature subsampling, and conflict-zone weighting
3. Applies Platt calibration via Newton-Raphson optimisation on OOB predictions
4. Runs guardrails (`recall >= 95%`, `FPR <= 5%`, `FNR <= 5%`)
5. Uploads the validated model to KV (propagates globally within 60 seconds)
6. Prunes training samples older than 14 days

If guardrails fail, the existing model remains active and a training failure event is logged.

### Offline CLI pipeline (development)

For initial training and major model changes, an offline Python/CLI toolchain produces the model artifact.

Key training parameters:

- **Conflict-zone weighting**: Samples with `bigram_entropy > 3.0` AND `domain_reputation_score >= 0.6` get 20x weight. These are the overlap-region cases where legitimate and fraudulent emails look similar - forcing the forest to learn deeper patterns in this zone.

- **Platt calibration**: Fits `LogisticRegression` on OOB predictions to produce well-calibrated probabilities. Outputs `intercept` and `coef` stored in model metadata.

## A/B testing framework

The ML Worker includes a fully implemented A/B testing framework for comparing model variants. Experiments are configured in KV and use consistent hash-based traffic splitting.

### Experiment configuration

```typescript
interface ABTestConfig {
  experimentId: string;
  description: string;
  variants: {
    control: { weight: number; config?: Partial<FraudDetectionConfig> };
    treatment: { weight: number; config?: Partial<FraudDetectionConfig> };
  };
  startDate: string; // ISO 8601
  endDate: string;
  enabled: boolean;
  metadata?: {
    hypothesis: string;
    expectedImpact: string;
    successMetrics: string[];
  };
}
```

### Traffic assignment

Variant assignment uses the first 8 hex characters of the request fingerprint hash, converted to a bucket (0-99). Buckets below the treatment weight go to treatment, the rest to control. This ensures the same device consistently sees the same variant.

```typescript
function getVariant(
  fingerprintHash: string,
  config: ABTestConfig,
): "control" | "treatment" {
  const bucket = parseInt(fingerprintHash.substring(0, 8), 16) % 100;
  return bucket < config.variants.treatment.weight ? "treatment" : "control";
}
```

Variant-specific config overrides are deep-merged with the base config, so experiments can change thresholds, weights, or feature flags independently. Weights must sum to 100.

### CLI management

```bash
npm run cli ab:create   # Create and upload experiment config to KV
npm run cli ab:status   # Check active experiment status
npm run cli ab:analyze  # Compare variant performance from D1 metrics
npm run cli ab:stop     # End experiment and remove from KV
```

## Design principles

| Principle                       | Implementation                                                                                            |
| ------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Fail-open by default**        | Signal collection, ML scoring, blacklist writes - all return safe baselines on error                     |
| **Fail-secure for definitives** | Token replay and Turnstile validation block on error (assume reused/invalid)                              |
| **Weight redistribution**       | Inactive signals don't suppress the score - their weight shifts to active ones                           |
| **Transparent decisions**       | Every score stores a full `ScoringDecision` audit trail with each adjustment step                         |
| **Per-request tracing**         | A unique request ID generated at entry threads through all DB writes for forensic correlation             |
| **Config-driven thresholds**    | All magic numbers live in a mergeable config with auto-normalisation for weights                          |
| **Progressive mitigation**      | Escalating timeouts instead of permanent bans - reduces false positive impact                            |
| **Single code path**            | RPC entrypoint constructs a synthetic HTTP request through the same Hono handler as direct API calls      |
| **Monitoring mode**             | Action override flag runs all detection and logs decisions without blocking - safe rollout for new rules |

## From scoring to operations

A multi-layer scorer rates how risky one submission is. Abuse operations also asks
about actors, campaigns, and what happens after a block. Each row below is a generic
pattern; the middle column shows where a scoring-first system like this one typically
sits.

<Aside type="note" title="Per-event vs per-actor">
A scorer judges each submission in isolation; its only cross-submission memory tends
to be a blacklist. Abuse operations treats the campaign - one actor or kit seen across
many submissions - as the unit of work, and most of the rows below follow from that.
</Aside>

### Event-scoring vs actor-centric operations

| Dimension | What a scoring-only system misses | Pattern that closes it |
| --- | --- | --- |
| **Campaign / actor footprints** | It can't see that today's submission is yesterday's actor with one signal changed. | A *footprint* - a set of individually weak indicators identifying a campaign - matched N-of-M: a full match auto-actions, a partial match flags a likely pivot (same actor, changed tactic) for review. |
| **Intent classification** | A 0-100 score captures *how bad*, never *what kind* (monetisation, weaponisation, disruption, reputation-gaming, victimisation). | Tag each detection with an intent aspect so the output can be routed and explained by kind as well as by magnitude. |
| **A review tier** | One block/allow threshold forces every ambiguous case into either a false positive or a miss. | A third review band routes mid-confidence cases to a human queue - "is it good, or just not-bad-yet?" |
| **Return tracking** | If banned-actor records are deleted when a timeout lapses, a returning actor looks brand-new and any escalation resets. | Operations reduce but never fully delete return-detection data, so repeat offenders keep accumulating history across windows. |
| **Non-repetition** | Learning a new pattern only protects against *future* instances. | A retroactive sweep re-runs a newly learned footprint over recent history to catch stragglers - which means retaining enough raw signal to re-evaluate after the fact. |
| **Outbound = inbound** | Blocking protects the platform; it does nothing for the victim downstream. | Report or reset harvested credentials and notify other providers in a distributed kit; a blocked payload is still live elsewhere. |
| **External signal** | A self-generated blacklist only learns from abuse that already reached you. | Ingest external feeds (disposable-email lists, known-bad IPs/JA4) to act on abuse "seen elsewhere first". |

forminator itself ships the footprint matcher as `src/lib/footprint.ts` (N-of-M
bands, pivot and splash detection, update suggestions; added 2026-06-19), but the
submission route does not call it, so on Workers it is a library rather than a
running layer. The Supabase port below runs it as a scheduled sweep with
retroactive matching and a review queue.

### What scoring-first already gets right

A scorer built like this one already covers two principles.

- **Reversibility** - a non-zero false-positive rate is unavoidable, so remediations should
  be undoable: escalating timeouts and soft state instead of permanent deletes. Here that
  is the progressive (self-reversing) timeouts.
- **Codifiability** - every decision carries an audit trail and rules live in
  configuration, never in manual database edits. Here that is the per-decision
  `ScoringDecision` audit trail and hot-reloadable config and heuristics.

<Aside type="tip" title="Where to start">
The cheapest capabilities to add are the ones that only log or label - return
tracking, intent tags, a review tier. They change a stored record and leave the request
path alone. The analyst queue around them takes far more effort to build and run than the detection that
fills it, so ship the log-only signal first and add the operator UI once the signal is
producing useful labels.
</Aside>

## On Supabase: the same layers in Postgres

The Workers system protects a form it owns. Signups on Supabase go to Supabase
Auth, and two facts stop the Workers system from simply sitting in front of it:

- The project's own Auth endpoint (`https://<ref>.supabase.co/auth/v1/signup`)
  keeps answering after a custom domain is set up[^sb-custom-domains], so a bot can
  skip any proxy on the app's domain. [Locking down Supabase](/reference/supabase-data-surface-lockdown/)
  measured this.
- Supabase's hosted CAPTCHA verifies Turnstile but keeps only `success`,
  `error-codes` and `hostname` from the response
  ([`captcha.go` L18-L22](https://github.com/supabase/auth/blob/88725864802773ad4533e0cad28f7a2740c89a7e/internal/security/captcha.go#L18-L22)),
  so the ephemeral device ID[^cf-ephemeral-id] - the signal that sees through
  residential proxy rotation - never reaches the project.

The port, a private kit called **abuse-kit**, moves the layers into the project's
Postgres and enforces them where no request can bypass them: in Auth hooks. The
edge Worker does what only it can do and signs the result.

```dot
digraph {
  rankdir=LR; bgcolor="transparent"; nodesep=0.3; ranksep=0.7;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];

  Browser [label="Browser"];
  Worker  [label="Edge Worker\nTurnstile + JA4"];
  Auth    [label="Supabase Auth"];
  Hook    [label="before-user-created\nPostgres function", shape=hexagon];
  PG      [label="abuse schema\nevents, blocklist, tiers", shape=cylinder];
  Cron    [label="pg_cron\nscore, footprints"];
  RLS     [label="RLS on app tables\nmy_tier()"];

  Browser -> Worker  [label="Turnstile token"];
  Worker  -> Browser [label="signed verdict"];
  Browser -> Auth    [label="signUp(data)"];
  Auth    -> Hook    [label="verify, record"];
  Hook    -> PG;
  Cron    -> PG      [label="decisions, tiers"];
  PG      -> RLS     [style=dashed];
}
```

1. The browser solves Turnstile and sends the token to the edge Worker.
2. The Worker verifies the token itself (so it gets the ephemeral ID), reads JA4 and bot score, and returns a short-lived HMAC-signed verdict bound to the signup email.
3. The browser signs up with the verdict in `options.data`, which reaches the before-user-created hook[^sb-before-user-created] as `user_metadata`.
4. The hook verifies the verdict (signature, expiry, email, single-use nonce), checks the blocklist, records the event with capped velocity counts, and denies only on a blocklist hit or a missing verdict when verdicts are required.
5. pg_cron scores each signup and sweeps campaign footprints; the resulting tier is read live by RLS policies on the app's own tables.

With verdicts required, a signup posted straight to the Auth endpoint has none and
is refused before any `auth.users` row exists. OAuth and SSO signups cannot carry
`options.data` and are exempt.

The kit's reference Worker can also post the signup itself, with the project's
secret key and `Sb-Forwarded-For` set to the client's IP, so the verdict never
reaches the browser and, by Auth's code, its per-IP limits count the end
user, not the Worker (the rate-limit key was not measured). Supabase's docs say the header is honoured only with a secret key and
only once IP address forwarding is enabled for the project[^sb-rate-limits].
Auth's own code applies it whenever the setting is on, and does not check the
key ([`sbff.go`](https://github.com/supabase/auth/blob/88725864802773ad4533e0cad28f7a2740c89a7e/internal/sbff/sbff.go)).
On two fresh hosted projects the docs' rule held anyway (2026-11-12)[^lab-hgs],
so something in front of Auth, or a deployed Auth version other than the one
read, enforces it (not measured). With forwarding on, the before-user-created
hook saw `Sb-Forwarded-For` only from the secret key; publishable, legacy anon
and legacy service_role requests got the same address as a signup sent with no
header, which the second run matched to the client's own. A publishable-key
request's `X-Forwarded-For` was ignored as well; the other keys were not tried
with it. With forwarding off, the hook's `ip_address` was the
leftmost `X-Forwarded-For` entry the caller sent, with the publishable and with
the secret key, so any direct caller chooses the address every IP rule in the
kit's signup hook reads. Turn forwarding on. If Turnstile cannot be verified, the Worker
refuses the signup rather than forwarding it unverified.

With Auth's own CAPTCHA on, secret-key and legacy service_role signups passed
with no token and publishable or legacy anon ones got `captcha_failed`
(same runs), so a project can keep Auth's CAPTCHA for direct callers while the
Worker's forwards pass on the secret key.

| Workers system | On Supabase | Notes |
| --- | --- | --- |

### What the port does not decide

Without the signed verdict a signup carries only an IP and an email. Two of the
ten components are then live - email (0.14) and IP rate limit (0.07) - and the
redistribution cap of 2.0x keeps the highest score without a trigger at
(14 + 7) x 2 = 42, under the block threshold of 70 (arithmetic from the weights,
not a measurement). Only an email classifier `block` crosses it, through the
email-fraud floor. That is forminator's rule held as written: IP-derived signals
never block alone.

The kit adds a second score for what the hook can count. It looks at bursts of
signups from one network (a /24 or /64), on one email domain outside the big
free-mail providers, or from one address. Each burst scores from a threshold
upwards. Bursts from one network count once and can reach watch on their own,
never quarantine; two bursts that agree reach quarantine. The scorer decides on
the higher of this score and forminator's.

The thresholds were fitted on replayed traffic. Each starts one above the largest
value a legit signup reached on three training seeds and is full at twice its
start: carrier NAT reached 40 signups per hour from one /24, and a team of up to
20 onboarding together reached 23 on its domain. They were re-fitted on
2026-11-13 with the network counts' cap at 200. The results below are from three
other seeds: 600 bot
signups an hour against about 1,200 legit ones (70% single users, 15% behind
four carrier NAT ranges, and the rest households, offices and teams), 3% of
them retrying once:

| Campaign | Bots at watch or above % | Bots at quarantine % | Legit flagged % |
| --- | --- | --- | --- |
| Residential proxies, anonymous | 0.0 | 0.0 | 0.0 |
| Three datacenter /24s, anonymous | 67.5 | 0.0 | 0.0 |
| Two throwaway domains, residential IPs | 86.7 | 0.0 | 0.0 |
| 40 addresses retried after failed or denied signups | 80.0 | 0.0 | 0.0 |
| Three datacenter /24s and two throwaway domains | 86.7 | 71.0 | 0.0 |

The first fit ran with every count capped at 50 an hour. With twice as many
users per carrier prefix, legit traffic alone filled that cap, the fit turned
the network score off and the datacenter pool went uncaught. With the network
counts capped at 200 the same model's pool reaches watch at 41.0% and pool plus
domains reaches quarantine at 50.0%. The cap of 50 also cut the network ramp
short, so in the four-range model above the pool scored higher then: 77.0% at
watch, 77.5% at quarantine with the domains. The higher cap added 0.016-0.055 ms
to the hook's p50 (difference of medians at 0, 10,000 and 100,000 prior events;
at 0 the run ranges overlap) for an anonymous sign-in from a /24 already past
the cap (local benchmark, 2026-11-13, 5 runs per cell). These thresholds fit a stated
model, not real traffic; re-fit them in monitor mode on the project's own
signups.

### Reading the numbers

Measured 2026-11-12 on a Supabase CLI 3.1.0 local stack (Postgres 17) on a
10-core laptop, load average 2.0-2.6. These are local numbers, not hosted ones.

The replay sent 600 synthetic bot signups and about 1,200 legit ones per run through
the hook, the scorer and the footprint sweep, 5 seeds per cell, 135 runs. Every
event got a decision, none errored, and every verdict verified. Every bot holds a
solved Turnstile token, so CAPTCHA catches none of them by construction, not by
measurement. Bots are anonymous sign-ins from a fresh residential IP each; legit
traffic is 85% one signup per device, 10% households (two accounts on one device)
and 5% behind shared office IPs, signing in anonymously unless the row says email.

| Bot farm devices | Kit | Bots flagged % | Legit flagged % |
| --- | --- | --- | --- |
| 5 / 50 / 600 | hook only, no verdict | 0.0 / 0.0 / 0.0 | 0.0 |
| 5 / 50 / 600 | verdict, device threshold 2 | 99.2 / 91.7 / 37.0 | 10.2 (8.8-10.7) |
| 5 / 50 / 600 | verdict, device threshold 3 | 98.3 / 83.3 / 10.5 | 0.0 |

- Without the verdict the hook cannot see this campaign at all.
- With it, the device layer flags every signup after a device's first, so recall
  is the share of bot signups landing on a device already used. Its false
  positives are the households' second accounts.
- A footprint catches the rest only when the campaign has a tell the legit traffic
  lacks. `{anonymous, ja4}` on a copied Chrome JA4 flags every anonymous Chrome
  user; when legit users sign up with an email the same footprint adds no false
  positives, and the 9.4% left is households.
- What the replay cannot supply is how often a real solver farm reuses device
  IDs. That number decides real-world recall.

<Aside type="caution" title="Gotchas">
- Deny by returning the error object, never by raising: a raise rolls back the hook's event row with it.
- Set `lock_timeout` on the hook function and catch `query_canceled` as well as `others`. GoTrue's own timeout does not apply to this hook, and `when others` does not catch a cancelled statement.
- Anything passed in `options.data` is stored in `auth.users` and returned in the user's JWT unless something removes it.
- Turn IP address forwarding on. With it off, a direct caller's `X-Forwarded-For` sets the `ip_address` the before-user-created hook reads (measured with the publishable and the secret key).
- An HTTP hook must reject with a 200 and an error body. GoTrue turns a 400 reply into a 500 and drops the message ([`hookshttp.go` L186-L251](https://github.com/supabase/auth/blob/88725864802773ad4533e0cad28f7a2740c89a7e/internal/hooks/hookshttp/hookshttp.go#L186-L251)); the documented HTTP example returns 400. Not filed upstream.
- The second signup from one device triggers at forminator's default threshold of 2, which catches households. Read `proposed_tier` in monitor mode before enforcing.
- RLS covers the Data API, Storage and Realtime; Edge Functions and anything on the secret key bypass it and must check the tier themselves.
- On the local stack (CLI 3.1.0), phone login stays off when no SMS provider is enabled, even with a send-SMS hook configured. A placeholder provider turns it on, and GoTrue still sends every SMS through the hook.
- With postgres.js, `${JSON.stringify(event)}::jsonb` reaches Postgres as a JSON string, not an object, so every key lookup is null. Pass `sql.json(event)`.
</Aside>
