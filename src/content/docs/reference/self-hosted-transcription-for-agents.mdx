title: "A self-hosted transcription service for coding agents"
description: "A self-hosted transcription stack on a shared GPU, exposed to a coding agent through compact tools: models and translation policy, speaker diarization with voice-print auto-naming, cached bundles for instant re-analysis, and conversation metrics computed from word-level speaker timing - what each can and cannot tell you about a recorded conversation."
author: Erfi Anugrah
category: workstations
---

A transcription stack runs on one GPU shared with an LLM engine, and a coding agent reaches it through tools that never return a raw transcript. The agent gets a summary and a bundle path, and the analysis tools compute from the cached bundle. A recorded conversation becomes a reviewable document without diarized text filling the agent's context.

Every number, model name and default below is read from the whisper-transcribe service source, the agent-side `video-review-core.ts` library and the whisper skill, as of 2026-10-20. Figures that are defaults in code are labelled as defaults; the timings in the pipeline section are observed, not benchmarked. The overlap and metrics tools are arithmetic over diarized transcripts, and their accuracy is bounded by the heuristics described below.

This is the transcription half of a larger workstation setup. [Scheduling one GPU between LLM, image and training work](/reference/llmc-single-gpu-stack/) covers GPU scheduling and the cost of a model swap. [Which model runs which agent work](/reference/agent-model-routing/) covers the vision-fallback path that also uses the whisper stack.

**TL;DR:**

- Two Python services in a Compose stack: `whisper` (transcription, diarization, frame description and OCR on port 7860) and `whisper-live` (live transcription over a WebSocket).
- The default model is `turbo`, with five other sizes. Translation defaults to `"auto"`: a 30-second language-ID pre-pass, then translation to English for non-English audio.
- A 60-minute recording takes 2-3 minutes without diarization and 8-10 minutes with it, on a consumer GPU (observed).
- Voice prints store a 256-dimensional speaker embedding and auto-name that speaker in every later transcript from the same service.
- `video_extract` returns speaker shares, duration, a mic-routing warning, a format-tag suggestion and a bundle path. The bundle is cached on disk, so re-analysis is instant.
- `video_overlap`, `video_metrics` and `video_doc` read the cached bundle.
- Question-flow classification is form-based and about 70% accurate. Overlap counts cannot tell a steering question from an information-seeking one.
- A transcription job evicts the LLM engine. The next agent turn pays a cold-context prefill of 40-90 seconds to first token at about 200k tokens of history.

1. The harness calls six tools (`video_extract`, `video_overlap`, `video_metrics`, `video_doc`, `video_enroll`, `video_name`) that use the whisper service's HTTP API on port 7860. On pi they are extension tools. On Claude Code a toolkit MCP server wraps the same core library.

## Which tool for which need

| You need | Use | Returns | Notes |
|---|---|---|---|
| A transcript plus a cached bundle for re-analysis | `video_extract` | Summary + bundle path | Takes minutes for a long recording. The raw transcript stays on disk. |
| Who talked over whom | `video_overlap` | Per-speaker overlap stats, event list, pair-cluster matrix | Instant from cache. Minimum collision 0.3 s (default). |
| Rate, fillers, turn-gap percentiles, question flow | `video_metrics` | Per-speaker metrics, per-pair gap matrix, question outcomes, block analysis | Instant from cache. Heuristic, about 70% accurate on classifications. |
| A markdown evidence bundle to write a review from | `video_doc` | Transcript + visual timeline + overlap summary + speaker table | Instant from cache. The agent writes the document. |
| Auto-naming across future transcripts | `video_enroll` | Enrolment confirmation | Stores a 256-d voice print server-side. |
| Correct labels in one cached bundle | `video_name` | Updated bundle | Client-side only; enrols nothing. |

Only `video_extract` runs the GPU pipeline. The other tools finish in under a second.

## The transcription pipeline

```dot
digraph {
  rankdir=TB; bgcolor="transparent"; nodesep=0.3; ranksep=0.5;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];

  job [label="POST /api/jobs\n(model, language,\ntranslate, diarize)"];
  poll [label="poll every 4 s\n(timeout 1800 s)"];
  desc [label="POST /api/describe\n(frames: true only)", style=dashed];
  bundle [label="bundle on disk\nXDG_DATA_HOME/\nvideo-review/"];
  tools [label="video_overlap\nvideo_metrics\nvideo_doc"];

  job -> poll [label="202 + job_id"];
  poll -> desc [label="done"];
  poll -> bundle [label="done"];
  desc -> bundle;
  bundle -> tools;
}
```

`video_extract` runs three steps, the last two optional or cheap:

1. Transcription and diarization. `POST /api/jobs` enqueues on the valkey FIFO with the model, language hint, translation policy and diarization flag. The tool polls `GET /api/jobs/<id>` every 4 seconds until the job reaches `done`, `failed` or the timeout (default 1800 seconds). The result is word-level segments with speaker labels and, with diarization on, one 256-dimensional WeSpeaker embedding per speaker.
2. Frame description, when `frames: true`. `POST /api/describe` extracts frames at an interval (default 10 seconds, capped at 60 frames) and sends each to a VLM for a one-sentence description. It is the visual track for recordings with screen shares, slides or a whiteboard.
3. Bundling. Segments, frames, speaker list, embeddings and parameters are written as a JSON bundle under `XDG_DATA_HOME/video-review/<hash>.json`. The key is a truncated SHA-256 of the server-side file path and the extract parameters, so the same recording extracted with and without diarization gives two bundles. An `index.json` beside the bundles supports lookups across bundles.

The extract summary is compact:

- File name and recording duration.
- Active speech share: clocked speaking time as a percentage of wall time.
- Per-speaker speaking shares, longest first.
- A warning when the enrolled owner is near-silent (possible mic-routing failure).
- A format-tag suggestion when the bundle is untagged (table below).
- The bundle path.

| Call shape | Suggested tag |
|---|---|
| 2 speakers, both named | `1:1` |
| One speaker holds at least 60% of speech and at least one speaker is unnamed | `customer` (presentation format) |
| 3 or more speakers, at least half named | `review` (team call) |

The tag is a free-form label stored on the bundle. `video_metrics` builds per-format longitudinal baselines from it.

### Job handling and timing

`/api/jobs` returns `202 Accepted` with a `job_id` at once. The poll loop runs inside the tool call, so the agent's 30-second bash timeout does not apply and the model is not re-prompted while the job runs.

A 60-minute call on `turbo` takes 8-10 minutes with diarization and 2-3 minutes without, on an RTX 5090 (observed, not a benchmark). That is 3-4 times as long with diarization, which runs a separate neural model over the audio. Skip it when only a transcript is needed.

### Translation policy

The `translate` parameter defaults to `"auto"`. The service runs a 30-second language-ID pre-pass, and if the detected language is not English it transcribes with `task=translate`. English audio is not translated. `translate: true` forces translation and `translate: false` keeps the source language. The default exists because the downstream summarisation LLM reads English best.

Whisper's per-segment decoder sometimes ignores the translate task token on deliberately multilingual audio, where each short segment is in a different language. The per-chunk language detection wins and those segments stay untranslated. The downstream LLM reads them natively and still produces a coherent English summary, so summarisation works end to end. A verbatim all-English transcript would need a post-processing LLM translation step, which the service lists as deferred until someone needs it.

### Diarization

Diarization assigns each word to a speaker (`SPEAKER_00`, `SPEAKER_01`, ...). Overlap detection, per-speaker metrics, question-flow attribution and block analysis all need word-level speaker timing. A bundle extracted without diarization has segments only, no speaker labels and no word timing, and the analysis tools return an error on it.

### Voice prints

A voice print is a 256-dimensional speaker embedding stored server-side under a name. Once enrolled, the speaker is auto-named in every later transcript the service produces, whether it comes through the agent tools, the web UI, the Discord bot or curl.

Enrolment uses an existing diarized bundle. `video_enroll` takes `action: "add"`, the bundle path and the diarized label to pull the embedding from (`M-SPEAKER_01`, not a display name). The server already returned the embedding with the transcription job, so no audio is re-run. Enrolling the same name twice adds a second reference vector and improves matching.

Names reach a bundle by two paths:

1. Server-side matching. When a job finishes, the server compares each diarized speaker's embedding with all enrolled voice prints. Matches above a cosine-similarity threshold fill `speaker_names` in the job result, and the cached bundle stores them under `bundle.names`.
2. Client-side relabelling. `video_name` takes a `{label: name}` map and rewrites segment speakers, word speakers and the speaker list. The map can be manual or inferred from address cues in the transcript ("Hi, Alice" -> the next different speaker is probably Alice). The extension's `suggestNames()` extracts these cues with high, medium or low confidence. A greeting pile-in where several speakers greet at once cannot be attributed to a responder, so it is emitted at low confidence.

A bundle keeps the original diarized labels as stable ids and a `names` record mapping them to display names. Embedding keys are not renamed, so `video_enroll` can always pull a vector by the diarized label. Renaming a label that already has a name updates the existing entry.

## Conversation analysis from word-level timing

The analysis tools use per-word speaker labels with start and end timestamps. Segment boundaries are rounded to utterance edges, so two speakers can overlap inside what a segment-level view shows as sequential turns. Word timing catches the overlap.

### Utterance merging

Words are grouped by speaker, then merged into utterances: consecutive same-speaker words no more than 0.6 seconds apart become one utterance. The merge runs per speaker. A merge over one globally time-sorted stream would interleave two overlapping speakers' words and split both into short alternating utterances, inventing overlaps that never happened. Per-speaker merging keeps each speaker's spans whole, and overlap becomes an interval intersection between different speakers.

### Speech overlaps

`computeOverlap()` scans time-sorted utterances for a later utterance that starts inside an earlier one from a different speaker. Each collision records:

- `interrupter` and `interruptee`.
- The collision duration.
- `yielded`: who stopped first. The interruptee stopping is a talk-over. The interrupter stopping is a false start or a short backchannel.

`min_overlap_sec` defaults to 0.30 seconds, which filters alignment jitter and short acknowledgements ("yeah", "mm"). The output has per-speaker counts (times this speaker started over someone, times someone started over them), an event list sorted by time, and a pair-cluster matrix with, for each speaker pair, how often the first came in over the second and the total collision seconds.

A steering question that interrupts and an information-seeking question that overlaps a closing sentence look the same acoustically. The numbers describe what happened physically; the reviewer decides what it means.

### Speaking-style metrics

`computeMetrics()` builds on the overlap analysis:

| Metric | Definition |
|---|---|
| Words per minute | Words over clocked speaking time |
| Words per turn | Words over utterance count |
| Filler rate | Fillers per 100 words, matched against a lexicon: `um`, `uh`, `you know`, `sort of`, `kind of`, `basically`, `actually`, `I mean`, `to some extent`, `effectively` |
| Turn-gap p25, median, p75 | Gap between the previous different speaker's utterance end and this speaker's start, in seconds. A negative gap means the speaker entered before the previous one finished. |
| Per-pair gap matrix | Median gap and sample count for each ordered pair ("B after A"). A pair needs at least 3 samples to appear. |

The p25 shows the fast-response tail that the median hides.

### Question-flow classification

`analyzeQuestionFlow()` works at sentence level inside utterances. Each question-marked sentence gets a dialogue act first (DAMSL-lite, Stolcke et al. 2000):

| Act | Form | Example |
|---|---|---|
| `question` | Interrogative lead (`what`, `why`, `how`, `is`, `do`, `can`) | "Did you try the new endpoint?" |
| `check` | Statement-form confirmation | "So I use the admin SDK?" |
| `tag` | Declarative stem with a short question tail | "That's the second endpoint, right?" |
| `backchannel` | Phatic continuer in question form | "Really?", "Is that right?" |

Tags and backchannels are left out of the outcome analysis. For each `question` or `check`, the analyser scans forward up to a window (default 10 seconds) and assigns an outcome:

| Outcome | Condition |
|---|---|
| `elaboration` | A different speaker gives a substantive response with new information |
| `assent` | A different speaker's response matches the acknowledgement lexicon ("yeah", "that makes sense", "sounds good", "fair enough"; 41 entries, multi-word phrases matched greedily) |
| `self-answered` | Others give only backchannels, then the asker speaks next |
| `unanswered` | Nothing within the window. The answer may come later, so the label is low-confidence. |

The classification is form-based and about 70% accurate against human-labelled dialogue-act corpora. The output says so, and the tool's prompt guidelines tell the agent to check flagged instances against the transcript before asserting them.

Two limits follow from classifying by form:

- A steering question and an information-seeking question with the same surface form get the same label. "Did you try X?" followed by "yeah" is probably steering, but the tool reports only the assent.
- `check` versus `question` depends on the interrogative-lead lexicon. "You tried the new endpoint?" is a `check` and "Did you try the new endpoint?" is a `question`, though in conversation they are the same act. The counts are reported but should not be over-read.

### Multi-unit turn blocks

Diarization splits a held floor into many short turns because it inserts boundaries at acoustic pauses. `computeBlocks()` merges consecutive same-speaker utterances separated by no more than 3 seconds into blocks. The output is a per-speaker block count, duration percentiles and the share of words spoken inside blocks of 30 seconds or longer.

Long blocks are not a defect in themselves, since expert answers and stacked questions run long. The five longest blocks are returned as evidence to read before judging. Verbatim phrase repetitions inside a block (4 or more tokens, 2 or more content words) are flagged separately as a composing-aloud signature.

### Longitudinal baselines

`video_metrics` appends a row per (speaker, bundle) to a JSON-lines file in the cache directory. When the same speaker appears in a later call with the same format tag, the tool prints the change in fillers per 100 words, gap median and long-block share against the prior results. A failed write does not block the metrics call. Re-running metrics on a bundle replaces that bundle's rows.

## Vision reuse

`/api/describe`, used for video frames, is one of two vision endpoints. The other is `/api/image`, which takes raw image bytes as a multipart upload and returns a description plus OCR text. Both use the same VLM, reported in `/api/status` with the GPU device and compute type.

`vision-fallback.ts` uses `/api/image`. When the default cloud model is text-only, the extension replaces each image block in the outgoing request with a text description. The first-choice backend is the LLM engine, if its loaded model has vision. `/api/image` is the fallback because it needs no server-side file path. Descriptions are cached by image hash, so each image is described once.

## What carries over

The model names, the port numbers and the tool count belong to this setup. These design points do not:

- Return a summary and a bundle path. A diarized transcript is thousands of tokens, and the agent can drill in with tools that read from disk.
- Cache the expensive step. Transcription and diarization are GPU-bound and slow, and the analysis over the same data is instant.
- Keep voice prints on the server. Every consumer of the service gets named speakers, and display names sit in a layer above the stable diarized labels.
- Use a queue and a job-id endpoint for long jobs. Transcribing a long recording outlasts any reasonable HTTP timeout.

```dot
  r_frames [label="frames:true", shape=box, style=rounded];

  q_dia -> r_txt [label="transcript only"];
  r_dia -> q_vis;
  r_txt -> q_vis;
  q_vis -> q_name [label="no"];
  q_vis -> r_frames [label="yes"];
  r_frames -> q_name;

```

1. Per-speaker analysis (overlap, metrics, blocks) needs `diarize: true`: 8-10 minutes for a 60-minute recording. A transcript alone takes 2-3 minutes with `diarize: false`.
2. Screen shares or slides need `frames: true`.
3. A speaker who is not enrolled gets named with `video_enroll` from the cached bundle, or relabelled with `video_name`.
4. `video_overlap` gives who talked over whom and who yielded.
5. `video_metrics` gives rate, fillers, turn-gap percentiles and question flow. Check the top events against the transcript.
6. `video_doc` assembles the evidence bundle the agent writes the review from.
