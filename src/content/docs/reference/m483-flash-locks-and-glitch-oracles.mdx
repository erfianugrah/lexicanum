Non-destructive readout of a locked microcontroller by voltage-fault injection is an instrumentation problem before it is a timing problem. This reference documents the Flash Memory Controller (`FMC`) protection model on the Nuvoton `M480`/`M483` family (`M483SIDAE`)[^m480trm][^m480ds] and the methodological post-mortem of an `8,651`-attempt `trigger=none` (`10,157` total attempts including `1,506` reset-rising trials) fault-injection investigation on a locked Cortex-M4-based peripheral - where the lock held, no key or plaintext `APROM` was extracted over SWD, and a post-run review of the journals showed that the sweep had been firing against a repeatable failure signature rather than a qualified memory-read oracle.

For the physical wiring, single-rail-owner power sequencing that prevents Faultier RP2040 back-powering (`Windows error code 10`), and the patched OpenOCD driver used during these tests, see the companion guide [Read-only SWD and voltage-glitch harness on a locked Nuvoton M483](/guides/swd-and-voltage-glitch-harness-m483/). For the broader workflow combining static binary decompilation with black-box protocol captures prior to hardware probing, see [Agent-assisted reverse engineering](/reference/agent-assisted-reverse-engineering/).

## TL;DR

- **`0xFF` in `CONFIG2` means locked, not unlocked.** On the `M480`/`M483` family, `CONFIG2[15:8]` (`SBLOCK`) and `CONFIG2[7:0]` (`ALOCK`) use `0x5A` as their explicit unlock token[^m480trm]. Any other byte value - including an erased or default `0xFF` - activates the lock.
- **`M483SIDAE` has no hardware AES accelerator or `XOM`, but `SBLOCK` still blocks ICE reads.** The `M483xIDAE` sub-family omits the cryptographic accelerator and Execute-Only Memory present on `GCAE`/`E8AE` parts[^m480ds]. When `SBLOCK != 0x5A`, Note 6 of the TRM ICE Lock Effect Table (`Table 6.5-7`) marks every ICE-initiated `FMC` operation except `MassErase` invalid and sets the ISP Fail Flag (`ISPFF`)[^m480trm][^fmcreg].
- **A repeated `DPIDR` word (`0x2ba01477`) at memory addresses is a failure signature, not a memory read.** Reading `CPUID` (`0xe000ed00`), `CONFIG0`..`CONFIG3` (`0x00300000`), `APROM` (`0x00000000`), and peripheral registers (`0x50080100`, `0x50080110`) over raw Nu-Link HLA commands returned `0x2ba01477` at every word. Treating that repeatable response as a working readback oracle left the sweep unable to distinguish chip-level lock enforcement from adapter-level stale buffer echoes. Follow-up inspection of the HLA open sequence confirmed that skipping `CMD_MCU_RESET` to suppress target resets had also skipped `CONNECT_NORMAL`, leaving the `AHB-AP` unpowered so every memory read echoed `DPIDR`; switching to connect-only mode (`reset type 5` with `CONNECT_NORMAL`) restored live `SYS_PDID` (`0x00d48310`) and `SRAM` (`0x20001c60`) reads while `APROM`, `LDROM`, and `SPROM` still read `0xffffffff`.
- **The AHB-AP write gate is per-subsystem, and it closes every debugger-driven readout route.** A live per-region write map (2026-11-17) shows that under `SBLOCK` the core debug registers (`DCRSR`/`DCRDR`), the clock controller (`CLK_AHBCLK`) and `SPIM` accept debugger writes, while `SRAM` (8/16/32-bit), the `FMC` `ISPCTL` enable and the `PDMA` channel registers silently no-op - the lock gates the subsystems that could move flash contents, and leaves benign clock/debug registers open. CPU-issued flash reads also collapse when the core is halted under debug (`PC=0xFFFFFFFE` HardFault; the same device is healthy free-running), so any flash readout must be driven by the *running* CPU, not the debug bus. Under the current model the flash itself stores plaintext: with no `XOM`, no hardware crypto, and no plaintext code in the sampled `SRAM`, the application must execute plaintext directly from flash, and the update-mode read path encrypts on egress (arch B). [Recover a firmware key with power side-channel analysis on Cortex-M](/guides/sca-firmware-key-cortex-m/) covers the deduction and the read-capture experiment that confirms it.
- **Three other evidence promotions compounded the blind oracle.** Running `8,651` `trigger=none` pulses with no synchronization to a target reset or boot event (and multi-second OpenOCD startup latency after a `35`-`37 us` reset response), treating an update-mode application ciphertext backup (`65` pages, `66,560` bytes) as proof of full-chip recoverability, and treating a microsecond ADC rail dip (`0.388 -> 0.0235`) as proof that nanosecond (`4`-`128 ns`) pulses reached the core latch all masked missing prerequisites.

## Early diagnostic table: what each observation actually proves

When probing a locked microcontroller, most early milestones prove less than they appear to. Use this table to separate what a measurement confirms from the stronger claim it is often promoted to support.

| Bench observation | What it genuinely proves | What it does **not** prove | Minimum gate to advance |
|---|---|---|---|
| SWD returns `DPIDR = 0x2ba01477` | Physical SWD clock/data continuity to the Cortex-M4 Debug Port (`DP`) | That `AHB-AP` memory reads work, or which `M483` sub-variant is fitted | Read an address-dependent register (`CPUID`, `SYS_PDID`) and verify distinct values |
| Raw SWD read returns `0xFFFFFFFF` or `0x2ba01477` at `0x00300000` (`CONFIG0`) | The read path did not return valid plaintext configuration words | That `CONFIG0` or `CONFIG2` actually contains `0xFFFFFFFF` in flash | Qualify the read path against an unlocked `M480`/`M483` control board |
| `10 us` crowbar pulse drops Faultier ADC min from `0.388` to `0.0235` | The MOSFET pulls the probed rail down at `10 us` (`~26` ADC samples at `2.604 MS/s`) | That `4`-`128 ns` pulses cross the core `LDO` or `FMC` sense threshold | Measure nanosecond waveforms on an oscilloscope (`>= 100 MHz`) |
| `40 us` `VDD` pulse drives `nRESET` low `35`-`37 us` after `VDD` fall | External reset assertion occurs above `35`-`40 us` of `VDD` droop on this harness | Whether shorter pulses trigger internal `POR`/`BOD`/`LVR`, or when `CONFIG` latches | Synchronise readback to `nRESET` release with sub-millisecond latency |
| USB update-mode backup saves `65` pages (`66,560` B app + `1,024` B configuration) | The bootloader exports encrypted application pages and configuration data | That the file matches the currently wired PCB, or restores `LDROM`/`OTP` | Bind backup manifest to a hardware `board_id` and verify round-trip restore |
| Connect-only `AHB-AP` reads `SYS_PDID = 0x00d48310` and `SRAM` (`0x20001c60`) while `APROM`/`LDROM` read `0xffffffff` | The `AHB-AP` transport is live and address-sensitive, and flash is genuinely read-locked | That the debugger can write to `SRAM`, or whether `APROM` stores ciphertext versus plaintext at rest | Test `SRAM` write readback and observe a CPU-initiated flash read via `DWT` |
| `PPB` debug writes (`0xe000xxxx`) succeed while a Nu-Link `SRAM` write (`0x20000400`) reads back `0x00000000` | Core halt, examination, and `DWT`/`FPB` comparators work; the Nu-Link SRAM write path no-ops | Whether Nu-Link firmware filters the write, or whether `DWT` events will fire without separate verification | Direct Faultier writes also no-op at two addresses in both `LOCKUP` and clean vector-catch halt; qualify `DWT` separately |

## The Nuvoton M480/M483 flash-lock model

### What `M483SIDAE` includes and omits

The Nuvoton `M480` family spans parts with full cryptographic secure boot (`M487`, `M483GCAE`, `M483E8AE`) and general-purpose high-speed USB parts (`M483SIDAE` in the `M483xIDAE` selection group)[^m480ds]. According to the Datasheet Rev. 3.09 selection table, `M483SIDAE` has:

- **No hardware cryptography peripheral** (no AES, DES, SHA, or ECC engine, and no `KEYPRT` hardware key-protection registers).
- **No `XOM` (Execute-Only Memory) region support.**
- **Standard `FMC` readout-protection and boot locks** stored in the User Configuration block starting at `0x00300000` (`CONFIG0` through `CONFIG3`, with extended configuration words up to `CONFIG10`).

Eliminating hardware AES and `XOM` narrows the problem: any protection on `M483SIDAE` comes from the standard `FMC` configuration gates and mask-ROM / `LDROM` boot flow rather than a dedicated cryptographic coprocessor.

### `CONFIG0` and `CONFIG2`: why `0xFF` means locked

A common trap when reading Nuvoton documentation quickly is assuming that erased flash (`0xFF`) leaves every protection field open. While single-bit flags in `CONFIG0` use `1` for their inactive/default state, the byte-wide lock tokens in `CONFIG2` invert that intuition by requiring an explicit `0x5A` magic byte to unlock[^m480trm]:

| Register bits | Field name | Erased / default value | Unlocked value | Documented behaviour in M480 TRM Rev. 3.07 |
|---|---|---|---|---|
| `CONFIG0[1]` | `LOCK` | `1` | `1` (`0` = locked) | Flash content is unlocked **only if** `LOCK == 1`, `ALOCK == 0x5A`, and `SBLOCK == 0x5A`[^m480trm] |
| `CONFIG0[5]` | `MBS` | `1` | `1` (`APROM`/`LDROM`) | Master Boot Selection; `0` or `SBLOCK != 0x5A` routes boot through the mask-ROM Boot Loader[^m480trm] |
| `CONFIG0[7:6]` | `CBS` | `11` | Application-defined | Chip Boot Selection between `APROM` and `LDROM` when `MBS == 1` |
| `CONFIG0[11]` | `ICELOCK` | `1` | `1` (`0` = ICE disabled) | Controls whether the Cortex-M4 debug interface (`ICE`) is enabled |
| `CONFIG2[15:8]` | `SBLOCK` | `0xFF` | `0x5A` | Secure Boot Lock; any value other than `0x5A` locks flash and restricts `ICE` to `Chip Erase`[^m480trm] |
| `CONFIG2[7:0]` | `ALOCK` | `0xFF` | `0x5A` | Advance Security Lock; any value other than `0x5A` enables security lock even when `LOCK == 1`[^m480trm] |

Two structural consequences follow from this layout:

1. **Both `SBLOCK` and `ALOCK` live in the same 32-bit word (`CONFIG2` at `0x00300008`).** For the `FMC` to treat flash as unlocked over SWD, both comparators must evaluate to `0x5A` (`CONFIG2[15:0] == 0x5A5A`) while `CONFIG0[1]` (`LOCK`) is `1` and `CONFIG0[11]` (`ICELOCK`) is `1`. Flipping a single bit in `CONFIG0` cannot unlock a chip whose `SBLOCK` or `ALOCK` byte is `0xFF`.
2. **An `all-0xFF` SWD read of `0x00300000` is not a reading of `CONFIG0`..`CONFIG3`.** Early in the investigation (2026-11-01), an `all-0xFF` SWD read of the `CONFIG` block was interpreted literally as "the chip's `CONFIG` words are `0xFFFFFFFF`, so `SBLOCK = 0xFF` and `ALOCK = 0xFF`". While `SBLOCK != 0x5A` is consistent with the official NuMicro ICP tool reporting `Target flash is in security lock mode`, a locked chip returning `0xFFFFFFFF` (or `0x2ba01477`) at every address is returning a bus-level lock mask, not the stored flash bytes. You cannot know the exact programmed `CONFIG` bits of a locked board from a blocked SWD read.

## CPU versus ICE access asymmetry and the `ISPFF` gate

The M480 TRM splits flash access permissions into two separate tables: **Table 6.5-6** (operations initiated by the CPU via `FMC` In-System Programming registers) and **Table 6.5-7** (operations initiated by an external `ICE`/`ICP`/Writer tool)[^m480trm].

| Memory region / operation | Address window | CPU master (`Table 6.5-6`, `SBLOCK` active) | ICE / SWD master (`Table 6.5-7` + Note 6, `SBLOCK != 0x5A`) |
|---|---|---|---|
| `APROM` (512 KB application flash) | `0x00000000`-`0x0007FFFF` | `R W` (CPU can read and write `APROM`) | **Blocked** (Note 6 overrides column; sets `ISPFF = 1`) |
| `LDROM` (4 KB loader flash) | `0x00100000`-`0x00100FFF` | Blocked or restricted by `LOCK`/`SBLOCK` | **Blocked** (Note 6: only `MassErase` valid) |
| User Configuration (`CONFIG0`..`3`) | `0x00300000`-`0x0030000F` | Readable by CPU / boot path | Table column says `R W`, but Note 6 + live SWD block reads |
| `OTP` / Secure Boot Key (`SBK`) | `0x00300500`-`0x003005FF` | Direct reads return masked `0xA5` (`0xA5A5A5A5`) | **Blocked** (no read/compare oracle before unlock) |
| Mask-ROM Boot Loader (32 KB) | `0x00800000`-`0x00807FFF` | `R -` (readable in all protection columns) | **Blocked** by ICE lock gate |

### Why ICE-initiated `FMC` register writes fail (`Note 6` and `ISPFF`)

At first glance, `Table 6.5-6` suggests an ISP workaround: since the CPU is allowed to read `APROM` under `SBLOCK`, use SWD to write an ISP read command (`FMC_ISPCMD = 0x00`, target address in `FMC_ISPADR`, trigger `ISPGO` in `FMC_ISPTRG`, poll `FMC_ISPSTS` for `ISPBUSY == 0`, and read `FMC_ISPDAT` at `0x4000C008`).

**Note 6 of Table 6.5-7** closes that ICE-initiated ISP route: *"All operations (except for MassErase) are invalid for ICE when SBLOCK is not 0x5A."*[^m480trm] It does not by itself establish how a generic AHB-AP SRAM write behaves; that is the separate probe question below. When `SBLOCK != 0x5A`:

- Any `ICE`-initiated `FMC` operation sets the ISP Fail Flag (`ISPFF`, bit 6 / `0x40` in `FMC_ISPSTS` and `FMC_ISPCTL`)[^fmcreg]. The TRM's `ISPFF` condition list explicitly includes *"Invalid operations with ICE connection if SBLOCK is not 0x5A"* (TRM Rev. 3.07, pages 711 and 721)[^m480trm].
- OpenNuvoton's own `numicro.c` flash driver in OpenOCD[^numicro] does not attempt ISP reads on a locked chip; its unlock path writes the `CHEAT` register and triggers a whole-chip mass erase.
- As for the Secure Boot Key (`SBK`) region in `OTP` (`0x00300500`-`0x003005FF`) and the adjacent configuration page around `0x00300800`, static analysis of the vendor boot path showed that direct reads return a constant `0xA5` (`0xA5A5A5A5`) mask unless preceded by a matching unlock write. There is no partial-match or timing oracle on that region from outside the chip.

### The write gate mapped per-region (2026-11-17)

Once the `AHB-AP` transport is properly connected via `CONNECT_NORMAL` in connect-only mode, the debugger can halt the Cortex-M4 core, read `SYS_PDID` (`0x40000000` = `0x00d48310`), and read live `SRAM` (`0x20000000`). That raises the classic CPU-mediated readout question: since `Table 6.5-6` allows the CPU to read `APROM` while `ICE` reads of `APROM` return `0xffffffff`, can the debugger write a small readout stub into `SRAM`, point the program counter at it, and let the CPU copy `APROM` into `SRAM`?

Probing the write surface region by region (direct Faultier SWD, one SWD master, verified restoration after every write) produced a precise gate map:

| Target | Operation | Result |
|---|---|---|
| Core register `r0` via `DCRSR`/`DCRDR` | write `0xdeadbeef`, read back, restore | **Landed** |
| `CLK_AHBCLK` (`0x40000204`, `PDMACKEN`\|`ISPCKEN`) | write, read back | **Landed** |
| `SPIM_CTL1` (`0x40007004`) | write | **Landed** |
| `SRAM` `0x20001000`, 32-bit | write `0xdeadbeef`, read back | **Blocked** (no-op) |
| `SRAM`, 8-bit and 16-bit | write, read back | **Blocked** (no-op) |
| `FMC` `ISPCTL.ISPEN` (`0x4000c000`) | write, read back | **Blocked** (reads back `0`, even with `ISPCKEN` set) |
| `PDMA` `DSCT0_CTL`/`SA`/`DA`/`CHCTL` (`0x40008000`) | write, read back | **Blocked** (reads back `0`, even with `PDMACKEN` set) |
| `SRAM` via bit-band alias (`0x22020000`) | write bit 0, read target | **Blocked** (target unchanged) |
| `FMC`/`PDMA` via peripheral bit-band aliases | write, read register | **Blocked** (register unchanged) |

Earlier runs had already shown Nu-Link `CMD_WRITE_RAM` (`0xb9`) writes to `SRAM` no-op while Private Peripheral Bus writes (`0xe000xxxx`, including `FPB` and `DWT` comparators) land, and that direct 32-bit `SRAM` writes no-op in both `LOCKUP` and a clean vector-catch halt. The per-region map extends that to 8/16/32-bit widths, to the running-halted update-mode state, and to the two flash-moving subsystems (`FMC` and `PDMA`): a scoped lock that closes exactly the paths a debugger would use to stage or move flash contents while leaving benign clock and debug registers writable. This matches Nuvoton's documented anti-readout measure for security-locked devices[^m480trm].

Three qualifications keep the map honest:

1. **The bit-band rows have no same-alias positive control.** No write to a known-writable register *through its bit-band alias* was attempted in the same run, so under the control rule below those rows are `probe_unqualified`: they show the aliases did not change the target, not that the alias path itself works.
2. **CPU-issued flash reads collapse when the core is halted under debug.** A clean `SYSRESETREQ` plus halt still yields a degenerate stack pointer and `PC=0xFFFFFFFE` (HardFault) on any flash-touching path, while the same board enumerates and works normally when free-running. Halted-CPU flash readout is gated separately from the bus write gate.
3. **Post-glitch states are untested.** The map describes the lock in its normal states; whether a successful glitch opens any of these gates is unknown.

The remaining readout route is therefore the running CPU itself: core-register access and execution control work, and `Table 6.5-6` permits CPU-issued `APROM` reads and `FMC` ISP operations under `SBLOCK`[^m480trm].

### Proving whether flash stores ciphertext or plaintext: CPU-bus observation via `DWT`

When a device's USB updater writes an encrypted firmware image and its update-mode read command exports those exact same high-entropy bytes, while direct SWD reads of `APROM` (`0x00000000`), `LDROM` (`0x00100000`), and `SPROM` (`0x00200000`) return `0xffffffff`, it is easy to assume that `APROM` stores ciphertext at rest. Epistemically, those external observations are equally consistent with two different architectures:

1. Ciphertext at rest, where the bootloader writes the encrypted update stream to `APROM` and the update-mode read command exports the stored `APROM` bytes directly.
2. Plaintext at rest with an encrypting export path, where the bootloader decrypts the update payload in `SRAM` before programming plaintext Cortex-M4 instructions into `APROM` and the update-mode read path encrypts `APROM` pages on the way out.

Neither the USB read-back channel nor a blocked SWD `AHB-AP` read (`0xffffffff`) can tell those two designs apart. Because `CONFIG0[11]` (`ICELOCK`) remains inactive (`1`) and Private Peripheral Bus debug writes (`0xe000xxxx`) still land on the locked part, you can settle that question with a read-only test that needs neither `SRAM` writes nor voltage glitches: let the bootloader's own CPU execute a legitimate flash read (which `Table 6.5-6` allows) while observing the bus transaction through the Cortex-M4 Data Watchpoint and Trace (`DWT`) unit. Arming a `DWT` comparator (`DWT_COMP0`/`DWT_MASK0`/`DWT_FUNCTION0` at `0xe0001020`..`0xe0001028`, with `DEMCR.TRCENA` set at `0xe000edfc`) on the flash-controller trigger register (`FMC_ISPTRG` at `0x4000c010`) or on the target `APROM` application base address halts the core when the bootloader services a normal read request; reading the core registers and `FMC_ISPADDR`/`FMC_ISPDAT` (`0x4000c004`/`0x4000c008`) at that halt reveals the actual 32-bit word the CPU bus fetched from flash. On the test target, `DEMCR.VC_CORERESET` now produces a clean halt, but resuming the locked updater currently fails with PC `0xfffffffe` and a caught instruction-fetch fault. Raw memory reads still work; the remaining DWT problem is updater resume.

**2026-11-17 update: three measured facts now point to arch B as the working model, and they move the deciding measurement.** Three established facts force arch B as the model: the `M483SIDAE` has no `XOM`, it has no hardware cryptography engine, and no plaintext code appears in the `135 KB` of sampled `SRAM` - yet the application demonstrably runs. It cannot run from `XOM` it does not have, or from a `RAM` copy that is not there, so it must execute plaintext directly from `APROM`, and the ciphertext seen on the update-mode read channel is produced by an encrypt-on-egress read path. That deduction rests on three measured facts and reframes the discriminator: instead of a `DWT` halt on the CPU bus (which the halted-core flash gate above now fights), observe the *power rail* during a plain firmware read - cipher activity during reads confirms arch B, its absence points back to arch A and a boot/update decryption target. The measurement and the CPA attack it feeds are in [Recover a firmware key with power side-channel analysis on Cortex-M](/guides/sca-firmware-key-cortex-m/).

## The oracle problem: how a failure signature masquerades as a memory read

In fault-injection testing, an **oracle** is the measurement that tells the runner whether a single glitch pulse changed the target's security state. To be valid for a flash-readout sweep, a readback oracle must satisfy three properties:

1. **Address sensitivity.** Querying two different addresses that contain different values must return two different words.
2. **Failure-mode separation.** The classifier must distinguish a transport error or adapter buffer echo from a valid bus read.
3. **Positive-control verification.** Before attacking the locked target, the exact readback command must be proven to return expected, address-dependent words on an unlocked control target (or an unlocked address range on the same bus).

### What actually happened on the locked `M483SIDAE`

Once the physical `SWCLK` contact fault on pin 34 was repaired on 2026-11-14 and the safe-connect OpenOCD driver connected at `200 kHz` (`2980 mV` sense voltage, `supply=0`), the probe returned the exact Cortex-M4 `DPIDR` (`0x2ba01477`) across three consecutive runs. The next step was reading memory:

1. **Standard OpenOCD `mdw` failed at target examination.** Before running `mdw 0x00300000 1`, OpenOCD's Cortex-M target layer reads the architectural `CPUID` register at `0xe000ed00`. The trace log showed that reading `0xe000ed00` returned `0x2ba01477` - the exact `DPIDR` value. OpenOCD extracted bits `[15:4]` as `PARTNO = 0x147` (unrecognised Cortex-M part), left the target unexamined, and rejected `mdw` with `Target not examined yet`.
2. **Bypassing `CPUID` examination via `raw_mdw` returned `0x2ba01477` everywhere.** Adding a custom HLA command (`raw_mdw <address>`) that called the Nu-Link memory-read API directly bypassed OpenOCD's `CPUID` gate. Querying the locked chip then produced:
   - `CONFIG0`..`CONFIG3` (`0x00300000`..`0x0030000C`): `0x2ba01477` at every word.
   - First 16 words of `APROM` (`0x00000000`..`0x0000003C`): `0x2ba01477` at every word.
   - Peripheral register addresses (`0x50080100`, `0x50080110`): `0x2ba01477` at every word.

### Why `locked-response` was not a qualified oracle

The runner code classified any 16-word `APROM` read consisting entirely of `0xFFFFFFFF` as `all-ff` and any read consisting of repeated `0x2ba01477` as `locked-response`. For a sample to be promoted to `plaintext`, the classifier required a plausible Cortex-M SRAM initial stack pointer (`0x2000xxxx`) in word 0 and a Thumb reset vector in `APROM`/`LDROM` in word 1, confirmed by a second identical read.

That classifier properly rejected `0x2ba01477` as plaintext, **but the preflight gate accepted `locked-response` as proof that the readback oracle worked.** That was a category error:

- Returning `0x2ba01477` at `0xe000ed00`, `0x00300000`, `0x00000000`, and `0x50080100` has **zero address sensitivity**.
- Because two similarly locked target boards both returned `0x2ba01477` (and earlier `0xFFFFFFFF`), the bench had no unlocked `M483` positive control showing that `raw_mdw` over the Nu-Link HLA transport would return real flash words *even if a glitch briefly cleared the `FMC` lock latch*.
- Worse, a repeated `DPIDR` value on an HLA adapter is indistinguishable from the adapter's USB firmware returning its last valid SWD buffer word when an `AHB-AP` read stalls or faults (just as disconnected `IDCODE` reads echoed the `0x0b9f` ADC voltage word twice as `0x0b9f0b9f`).

### Resolving the transport trap: connect-only AP power-up and the three-tier oracle check

Inspecting the OpenNuvoton USB JTAG/SWD driver source (`src/jtag/drivers/`)[^openocdnuvoton] resolved why `raw_mdw` had returned `0x2ba01477` at every address across all `10,157` attempts. During normal adapter open, the stock driver sends `CMD_MCU_RESET` bundling a hardware or system reset (`RESET_HW` or `RESET_SYSRESETREQ`) with `CONNECT_NORMAL`. When the first version of the safe-connect patch skipped that reset call to protect the live target, it also omitted `CONNECT_NORMAL` - the command that instructs the Nu-Link firmware to power up and connect the Cortex-M4 `AHB-AP`. Without `CONNECT_NORMAL`, the SWD Debug Port (`DP`) answered `IDCODE` reads with `0x2ba01477`, but the `AHB-AP` never connected to the internal bus, so every HLA memory read echoed the stale `DPIDR` word from the adapter buffer.

Replacing the skipped call with a connect-only handshake (`CMD_MCU_RESET` using connect-only `reset type 5` and `CONNECT_NORMAL`, keeping `supply=0` and suppressing all resets) powered the `AHB-AP` non-destructively. That enabled a three-tier read-only qualification ladder on the locked board in a single session:

1. Tier A (non-lock-gated peripheral positive control): the M480 TRM protection matrix marks the Part Device ID register (`SYS_PDID` at `0x40000000`) readable under all lock states[^m480trm]. With connect-only `CONNECT_NORMAL` active, `0x40000000` returned `0x00d48310` reproducibly (the real `M483SIDAE` part ID) instead of `0x2ba01477`, and OpenOCD examined `Cortex-M4 r0p1` (`CPUID` at `0xe000ed00` no longer echoed `DPIDR`).
2. Tier B (`SRAM` positive control): reading internal `SRAM` at `0x20000000` returned live, address-distinct data, including a valid Cortex-M4 stack pointer (`0x20001c60`).
3. Tier C (locked flash negative control): with both positive controls passing on the same connection, reading `APROM` (`0x00000000` and `0x00004000`), `LDROM` (`0x00100000`), and `SPROM` (`0x00200000`) returned `0xffffffff`. Because a running MCU cannot execute from an erased vector table at `0x00000000`, `0xffffffff` alongside live `SYS_PDID` and `SRAM` reads proved that the flash was genuinely read-locked by `SBLOCK`, while the earlier `10,157`-attempt `locked-response` corpus was a dead-transport artifact.

## Three more ways evidence promotion derailed the sweep

A post-run review of the session history and run journals on 2026-11-15 identified three additional places where a scoped observation was promoted into a stronger assumption that the data did not support.

### 1. Timing sweeps without a qualified target event (`trigger=none` and readback latency)

Where in the boot cycle does the `M483` sample `CONFIG0`/`CONFIG2`? The M480 TRM (printed page 652, *Flash Initialization Controller*) states: *"When chip is powered on or active from reset, Flash Initialization Controller checks the flash stability first, and then reloads User Configuration to flash control registers"* (with reset-source exceptions for `BL`/`BS` documented on pages 711-712)[^m480trm].

After an initial `1,506`-attempt reset-rising sweep (`0`-`250 us` delay, `4`-`128 ns` width on `LDO_CAP` with the decoupling capacitor installed) returned no change, a working note hypothesised that `SBLOCK` is latched **only at cold Power-On Reset (`POR`)** and never on `nRESET`. Later summaries repeated that `POR`-only hypothesis as an established fact, even though the TRM explicitly lists *"powered on or active from reset"* and the actual latch window had never been measured.

Acting on that unverified premise, two larger sweeps were launched on 2026-11-15 with `trigger=none` and power-cycling disabled (`OUT_NONE`):

| Run identifier | Trigger mode | Requested attempts | Completed rows | Recorded outcome classes | Final state |
|---|---|---:|---:|---|---|
| Initial `LDO_CAP` grid (2026-11-14) | `nRESET` rising edge | `1,506` | `1,506` | `1,506` `all-ff` / `locked-response` | Exhausted, `disarmed=true` |
| Baseline `VDD` grid (2026-11-15) | `trigger=none` (`OUT_NONE`) | `1,506` | `1,506` | `1,506` `locked-response` | Exhausted, `disarmed=true` |
| Wide `VDD` grid (2026-11-15) | `trigger=none` (`OUT_NONE`) | `10,000` | `7,145` | `7,142` `locked-response`, `3` `readback_error` | Stopped on 3rd error, `disarmed=true` |

Look at what the two `trigger=none` runs (`8,651` attempts combined) actually did in hardware:

- **No synchronisation to any target event.** With `trigger=none` and `OUT_NONE`, the target MCU was already booted and idling in USB application/update mode. Varying Faultier's `delay` parameter only changed how many microseconds the RP2040 waited *after receiving the host USB command* before pulsing the MOSFET. Every delay value was firing into the same steady-state idle loop, never intersecting a `POR` or reset-release `CONFIG`-reload window.
- **Five-order-of-magnitude readback latency mismatch.** As the logic-analyzer pulse ladder in the [companion harness guide](/guides/swd-and-voltage-glitch-harness-m483/) showed, a `VDD` crowbar pulse of `40 us` or longer causes `nRESET` to assert `35`-`37 us` after the `VDD` falling edge. Even if a pulse triggered a reset and transiently corrupted a volatile configuration latch, the runner checked the result by spawning a fresh `openocd` OS process after the pulse - a step that takes **seconds** on Windows, missing a microsecond boot window by five orders of magnitude.

### 2. Intact update-mode backups promoted to full-chip recovery proof

Before running hardware fault trials on a live device, a sound safety rule is to capture a verified backup so any corrupted flash page can be restored. Using the target's USB update-mode HID protocol, a read-only backup tool dumped all `65` application pages (`66,560` bytes total, starting with the expected `96` bytes of header padding across page ranges `0x00`-`0x33`, `0x34`-`0x74` application ciphertext, and `0x75`-`0x7F`) alongside a `1,024`-byte configuration block.

When hashed across three physical locked boards, the captures showed:

| Capture source | Application image size | App SHA-256 prefix | Configuration image size | Configuration SHA-256 prefix |
|---|---:|---|---:|---|
| Board A pre-update backup | `66,560 B` (`65` pages) | `33b06cf0` | `1,024 B` | `71809669` |
| Board B in-boot backup (2026-11-14) | `66,560 B` (`65` pages) | `5194d938` | `1,024 B` | `71809669` |
| Board C bring-up backup (2026-11-15) | `66,560 B` (`65` pages) | `33b06cf0` | `1,024 B` | `c1917858` |

The runner checked that the recovery files existed on disk and matched their recorded SHA-256 hashes before arming the crowbar. Promoting that hash check into "full recovery is proven" hid three gaps:

1. **Application ciphertext is not a full-chip dump.** The update-mode reader exports the encrypted application partition and its configuration block. It does not back up the `4 KB` `LDROM` bootloader (`0x00100000`), the `FMC` `CONFIG0`..`CONFIG3` words (`0x00300000`), or `OTP` (`0x00300500`). If a voltage glitch during flash initialisation corrupts `LDROM` or `CONFIG`, an application-partition backup cannot unbrick the board.
2. **Equal hashes do not prove board identity or fresh capture.** Board A and Board C shared the exact same `33b06cf0` application hash, while Board B differed (`5194d938`), and Board A and Board B shared the `71809669` configuration hash. A hash proves file integrity on disk, not which physical PCB is currently under the needles.
3. **Readback is not write-restoration.** Proving that `65` pages can be read in update mode does not prove that a standalone script can write them back and exit update mode without the vendor's official updater binary.

### 3. Undersampled ADC dips promoted to sweep qualification

Faultier's onboard `ADC_CROWBAR` (`250 MHz / 96 = 2.604 MS/s`, `~384 ns` per sample) recorded a normalised baseline of `~0.388` on `LDO_CAP` (pin 50, `1.26 V`) and `~0.919`-`0.933` on `VDD` (pin 51, `3.3 V`). When a `10 us` test pulse dropped the `LDO_CAP` minimum to `0.0235` and the `VDD` minimum to `0.0627`, that confirmed DC continuity and microsecond MOSFET conduction.

Promoted into "the crowbar path is qualified for a nanosecond sweep", it masked the sampling physics:

- At `384 ns` per sample, any pulse between `4 ns` and `128 ns` falls inside a single ADC conversion window.
- With the factory `2.2 uF` decoupling capacitor still soldered to `LDO_CAP` (pin 50), nanosecond crowbar pulses are absorbed by the capacitor's charge reservoir; with the crowbar on `VDD` (pin 51), the onboard `LDO` regulator and bulk decoupling sit between the crowbar drain and the `1.26 V` internal core domain (`LDO_CAP`) where the `FMC` sense amplifiers run[^stm32glitch].
- Without an oscilloscope trace on the core rail, there is no evidence that a sub-microsecond pulse on `VDD` reaches the internal `FMC` comparators before triggering a whole-chip brown-out reset.

(On the test target, USB HID ISP was absent on power-up; `UART1` remains a separate read-only check.)
2. **Qualify an address-sensitive positive control.** Never start a sweep whose preflight accepts `locked-response` (`0x2ba01477`) or `all-ff` as proof that memory reads work. Verify the readback transport (such as persistent vendor-interface SWD over Faultier interface 1 or OpenOCD `raw_mdw`) against an unlocked `M480`/`M483` board first, and on the locked board itself require connect-only `AHB-AP` reads of non-lock-gated `SYS_PDID` (`0x40000000` = `0x00d48310`) and live `SRAM` (`0x20000000`) to pass alongside the `0xffffffff` negative control on `APROM` (`0x00000000`).
3. **Couple the trigger and readback to a measured target event.** Never run a delay grid with `trigger=none`. Tie the glitch timer to a physical `POR` ramp or `nRESET` edge, and use an in-process SWD readback rather than spawning a multi-second OS process per trial.
4. **Measure pulse shape at the timescale under test.** Treat Faultier's `2.604 MS/s` ADC and a `1`-`2 MHz` logic analyzer as tools for microsecond (`>= 1 us`) delivery and reset-threshold checks; require an oscilloscope before sweeping nanosecond (`4`-`128 ns`) widths.
5. **Bind recovery artifacts to the physical board and scope.** Record the target's `board_id` in the backup manifest, verify round-trip restoration, and treat `LDROM`/`CONFIG` corruption as an explicit unbacked risk.

## Driving OpenOCD against a locked M483: Tcl RPC and adapter-state discipline

Three operational rules for scripting OpenOCD against an M480/M483 target over the Nu-Link HLA transport. Each was discovered when a Tcl-based OpenOCD wrapper hit an undocumented interaction between the Nu-Link firmware's cached state and the Cortex-M4 core's real debug state.

**Run-control through adapter commands, not raw DHCSR writes.** The Nu-Link firmware gate-keeps its `CMD_MCU_STOP_RUN` / `CMD_MCU_START_RUN` USB commands (which `halt` and `resume` proxy) against an internal cached copy of the core's run state. Writing `C_HALT` or `C_DEBUGEN` to `DHCSR` (`0xE000EDF0`) through the memory-write path changes the real `DHCSR` but leaves the firmware's cache stale. The firmware may refuse to resume a core it believes is already running, or skip halting one it believes is already halted. The next memory transaction hangs OpenOCD's event loop indefinitely. The fix: use only `halt`, `resume`, `poll`, and `get_reg` through the Tcl RPC - these route through the firmware's native run-control commands.

**Drive OpenOCD over its Tcl RPC port, not stdin, and wrap reads in `capture { ... }`.** OpenOCD ignores Tcl on stdin except in `gdb_port pipe` mode. Connect to the Tcl RPC port (configured with `tcl_port`) over TCP, send commands terminated with `0x1A` framing, and wrap memory reads in `capture { mdw <addr> 1 }` so the result line is returned as the RPC result rather than emitted to the log stream. Without `capture`, a `mdw` command returns empty.

**Call `poll` before `resume` after the HLA examine.** After the HLA adapter initialises and examines the target, OpenOCD leaves `target->state` at `TARGET_UNKNOWN`. The `adapter_resume` command checks `target->state`, not the real `DHCSR`, and refuses to resume from `TARGET_UNKNOWN` even when `DHCSR.S_HALT` is set. The `poll` command reads the real `DHCSR` through the adapter and updates `target->state` to `TARGET_HALTED`; `resume` then works.

## The connect-lockup: attaching to a running locked M480/M483 core

The safe-connect OpenOCD layout described in the [companion harness guide](/guides/swd-and-voltage-glitch-harness-m483/) sends the Nu-Link firmware a `CMD_MCU_RESET` command with `RESET_NONE` (no hardware or system reset) and `CONNECT_NORMAL`. `CONNECT_NORMAL` tells the closed-source Nu-Link firmware to halt the running core as part of establishing debug connectivity - it is the same connect mode the upstream driver pairs with hardware resets. On a flash-locked M480/M483 whose core is actively executing from the locked `APROM` region, that debug-halt triggers a fault chain that escalates to permanent LOCKUP.

### Fault register evidence

After the connect-lockup, reading the Cortex-M4 fault-status registers over the `AHB-AP` (which remains functional - the debug connection itself is not lost) reveals the exact fault chain:

| Register | Address | Observed value | Meaning |
|---|---|---|---|
| `PC` | (via `get_reg pc`) | `0xFFFFFFFE` | LOCKUP state address |
| `xPSR` exception number | (via `get_reg xPSR`) | `3` | Exception escalated to HardFault |
| `HFSR` | `0xE000ED2C` | `0x40000000` | `VECTTBL` bit set: vector table read fault occurred |
| `DFSR` | `0xE000ED30` | `0x00000001` | `HALTED` bit set: a halt request was received |
| `VTOR` | `0xE000ED08` | application value | Vector table offset register was configured (not at default `0x00000000`) |
| FMC `VECMAP` | `0x4000C02C` | `0x00000000` | `APROM` mapped at `0x00000000` |
| `SP` | (via `get_reg sp`) | valid | Stack pointer was valid at time of fault |
| `LR` | (via `get_reg lr`) | `EXC_RETURN` | Core was in exception context when halted (bootloader interrupt handler active) |

The `HFSR.VECTTBL` bit (`0x40000000`) is the load-bearing finding. It confirms that the core attempted to vector to the HardFault handler at `0x0000000C`, the vector-table read fetched from locked `APROM` and returned `0xFFFFFFFF` (consistent with all debug-AP reads of locked flash returning `0xFFFFFFFF`), and the core branched to `0xFFFFFFFE` (the `0xFFFFFFFF` value with the Thumb bit cleared). ARMv7-M then escalated the HardFault to LOCKUP because the branch target is an invalid address.

The `DFSR.HALTED` bit confirms the trigger: a debug halt request was received. The `LR = EXC_RETURN` value shows the core was running in an exception context (an interrupt handler) when the halt arrived, which is consistent with the bootloader's normal execution loop.

### Mechanism

The exact sequence inside the closed Nu-Link firmware is not observable, but the ARM architecture and the fault-register evidence support this chain:

1. As part of `CONNECT_NORMAL`, the Nu-Link firmware writes `DHCSR` to set `C_DEBUGEN` and `C_HALT`. This is the standard ARM debug halt sequence.

2. On the M483 with `SBLOCK` active and the core running from locked `APROM`, the debug-enable transition triggers a fault. The mechanism could be a debug-related bus fault when the `AHB-AP` is powered while the core is mid-instruction, a silicon-specific interaction between the flash controller's security state and debug enable, or the Nu-Link firmware writing additional debug registers as part of its connect sequence that trigger a fault on a locked part.

3. The core vectors to the fault handler at `0x0000000C`. At this point, with the debugger connected and the core transitioning to exception state, the vector table read through the I-bus returns `0xFFFFFFFF` - the locked-flash read value observed through the debug AP. This sets `HFSR.VECTTBL`.

4. The core attempts to fetch from `0xFFFFFFFE` (`0xFFFFFFFF` with Thumb bit cleared). This is an invalid address.

5. ARMv7-M escalates this to LOCKUP: `PC` permanently set to `0xFFFFFFFE`, no further instructions executed. Only a reset (pin reset, `SYSRESETREQ`, or power cycle) can escape LOCKUP.

The upstream Nuvoton OpenOCD driver never hits this code path because `nulink_usb_open()` always runs `RESET_HW` before `CONNECT_NORMAL` - the core is in reset, stopped, when the connect runs. The safe-connect layout deliberately suppresses the reset (`RESET_NONE`) but still sends `CONNECT_NORMAL` to power the `AHB-AP`, creating the untested combination: connect-with-halt on a running core.

The `cortex_m_poll()` function in OpenOCD's Cortex-M target layer can recover debug access to a locked-up core by writing `C_HALT` to `DHCSR` (clearing the LOCKUP state), which restores register reads through the debug AP. The core remains dead until a physical reset.

### A gentler connect mode: CONNECT_DISCONNECT investigation

The Nu-Link protocol defines `CONNECT_DISCONNECT` (enum value `4`) as a non-perturbing connect mode. It is used by the upstream Nuvoton OpenOCD driver in its close handler for clean disconnection, explicitly paired with `RESET_NONE`, and documented as supporting the no-reset case. The hypothesis: replacing `CONNECT_NORMAL` with `CONNECT_DISCONNECT` in the safe-connect path would tell the Nu-Link firmware to power the `AHB-AP` without halting the core.

Three outcomes are possible:

1. **`AHB-AP` powered, core running.** Memory reads work, the core keeps executing, and the USB peripheral remains alive. This is the non-perturbing observe mode needed for DWT-based CPU-bus observation without voltage glitching.
2. **`AHB-AP` not powered, reads echo `DPIDR`.** The `CONNECT_DISCONNECT` mode releases the debug connection without powering the `AHB-AP`. Every memory read echoes the stale `DPIDR` value `0x2ba01477` - the same failure mode as the early safe-connect patch that skipped `CMD_MCU_RESET` entirely. A separate AP power-up command would be needed.
3. **Same lockup.** `CONNECT_DISCONNECT` also halts the core, or the M483 silicon always faults on debug connection regardless of connect mode.

Resolved on the bench (2026-11-16): `CONNECT_DISCONNECT` does NOT power the `AHB-AP`. Reads returned a garbage `IDCODE` (`0x0bbc0bc7`, not `0x2ba01477`) and `SRST` was rejected - the same dead-transport failure mode as the early safe-connect patch that skipped `CMD_MCU_RESET` entirely. So outcome 2 is the measured one: the Nu-Link powers the AP only inside `CONNECT_NORMAL`, bundled with the halt, and offers no power-without-halt path. No debug-attach sequence against a locked M480/M483 through the Nu-Link is side-effect-free; a raw-SWD probe that powers the AP directly (no bundled halt) is the remaining alternative. Reads through the raw memory-access path still work on the locked-up core, which is what the fault-injection read-back relies on.

## Open surfaces after the 2026-11-17 review

Seven claims need separate wording because the available measurements do not collapse them into one lock model:

1. **Mask ROM and LDROM are different read targets.** The M483 map places the factory Boot Loader in mask ROM at `0x00800000` and the 4 KB ISP Loader in LDROM at `0x00100000`. The lock tables mark mask ROM unreadable through ICE even when unlocked, while LDROM becomes ICE-readable in the unlocked state[^m480trm]. On the test target, LDROM is a candidate location for vendor loader/decryptor code; its population and any key presence remain unproven.
2. **A per-operation failure flag does not prove a per-read configuration reload.** `FMC_ISPSTS.ISPFF` records a failed operation and `FMC_ISPDAT` has a documented `0xffffffff` failure value[^fmcreg]. A gate can set that flag on each denied operation while consulting lock state latched at reset. The reviewed material does not establish that every AP DRW read freshly reloads `CONFIG2`.
3. **A read-time pulse needs transaction-level synchronization.** A custom Faultier firmware path starts the glitcher on PIO0 around an SWD read on PIO1 and exposes an EXT1 timing marker, avoiding host USB scheduling between arm and read[^faultierfw]. The reset-capable firmware is flashed and direct reads are live-qualified; the synchronized GLITCH_READ command is live-qualified with `OUT_NONE` (its reads matched and the run disarmed cleanly) but has never fired a real crowbar pulse. There is no live read-time bypass result.
4. **The write surface is mapped, with one unqualified row.** The per-region gate map above supersedes the earlier two-address `SRAM` result: `SRAM`, `FMC` and `PDMA` writes are blocked at 8/16/32-bit widths in clean halt, LOCKUP and running-halted update mode, while core registers, `CLK_AHBCLK` and `SPIM` accept writes. The bit-band alias rows remain `probe_unqualified` (no same-alias positive control), and post-glitch states are untested.
5. **HID overread is a proven RAM window, and its earlier negatives were a mode artifact.** A 60,042-byte contiguous match maps overread byte 0 to SRAM `0x200009e4`, but the window's base moves between sessions and the `A0`/`A1` selectors and length do not steer it. The 2026-11-17 re-run also voided a class of earlier negatives: the pre-review overread and `SetFeature` probes ran in update mode (PID `1977`) rather than application mode (PID `1978`); in application mode a 4,096-byte overread returns a real, repeatable, address-distinct RAM window. Its content is a structured descriptor/table region, not the decrypt buffer, and no key material has been found in it.
6. **Vector catch and post-session recovery work.** `DEMCR.VC_CORERESET` avoids `LOCKUP`; powering down the DP before reset restores normal USB. These are separate results from the write block and from updater resume.
7. **The update-mode read command is a full-flash ciphertext primitive, and native restoration is proven.** `cmdRead` returns a 1,024-byte flash page by index (`address = index * 0x400`); sweeping the full map (`0x00`-`0xc8`) returns ciphertext at every index, with the recurring pages verified byte-identical to the vendor image's own filler and trailer pages, so they are real flash content; out-of-range indices return a cached default page. Restoration is also now measured, not assumed: all `65` application pages were rewritten and verified page-by-page from the board's own backup, and the vendor updater then returned the device to application mode. `LDROM`/`CONFIG`/`OTP` remain outside both the backup and the restore, so full-chip recovery still does not exist.

## What to do about it

| Practice | Evidence |
|---|---|
| Require a same-primitive, same-state, same-run positive **and** negative control before believing any negative | Three separate "locked" results on this target were tooling bugs (unpowered `AHB-AP`, a missing `ISPCKEN` clock, a wrong clock-controller address); each unqualified negative closed an avenue that was actually open. |
| Require an address-sensitive positive control before any glitch sweep | `raw_mdw` returned `0x2ba01477` at `0xe000ed00`, `0x00300000`, `0x00000000`, and `0x50080100`; accepting `locked-response` in preflight hid a zero-sensitivity oracle across `8,651` `trigger=none` rows. |
| Qualify `AHB-AP` reads with `SYS_PDID` and `SRAM` before trusting a lock read | Skipping `CMD_MCU_RESET` left the `AHB-AP` unpowered so every address echoed `0x2ba01477`; connect-only `CONNECT_NORMAL` read `SYS_PDID = 0x00d48310` and `SRAM` while locked `APROM` read `0xffffffff`. |
| Verify debugger `SRAM` write readback through more than one probe before designing a RAM-stub dumper | Under `SBLOCK`, `PPB` debug writes (`0xe000xxxx`) succeed so target examination works, but `SRAM`, `FMC` and `PDMA` writes no-op at every tested width and state; only post-glitch states and bit-band positive controls remain open. |
| Test ciphertext-at-rest claims with the cheapest discriminator available | An encrypted USB read-back matches both ciphertext in `APROM` and plaintext encrypted on export; on a part with no `XOM` and no hardware crypto, the deduction already favours encrypt-on-egress, and a power trace of a plain read (cipher activity or none) settles it without a `DWT` halt the locked core fights. |
| Reject `trigger=none` in automated timing-grid configurations | Without a hardware `POR` or `nRESET` trigger edge, varying `delay` only shifts when the MOSFET fires relative to the host USB command, testing `0` points of the boot-time `CONFIG` latch window. |
| Couple readback to the trigger over a persistent SWD session | `nRESET` asserts `35`-`37 us` after a `>= 40 us` `VDD` droop, whereas spawning a fresh `openocd` process per trial takes seconds and misses any transient unlock state. |
| Treat changed words on a locked target as an anomaly first, never plaintext | A single non-`0xFF`, non-`DPIDR` read can come from SWD framing corruption; require a repeatable re-read and an address-dependent match across multiple offsets before claiming an unlock. |
| Bind backup manifests to a hardware `board_id` and state unbacked regions | Two boards shared a `1,024 B` configuration SHA-256 (`71809669`) with different `66,560 B` app images (`33b06cf0` vs `5194d938`), and update-mode backups omit `LDROM` (`0x00100000`) and `CONFIG` (`0x00300000`). |
