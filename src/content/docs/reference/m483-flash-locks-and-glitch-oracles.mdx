Non-destructive readout of a locked microcontroller by voltage-fault injection is an instrumentation problem before it is a timing problem. This reference is two things: a documented Flash Memory Controller (`FMC`) protection model for the Nuvoton `M480`/`M483` family (`M483SIDAE`)[^m480trm][^m480ds], and a chronological evidence ledger from a locked Cortex-M4-based peripheral. The lock held: `10,157` fault-injection attempts (`1,506` reset-rising plus `8,651` `trigger=none`) produced no key, no plaintext `APROM`, and no measured lock-state change. The first `8,651` of those attempts were firing into an unconnected debug transport whose echo was misread as a locked-chip memory response - a dead-transport artifact that took four rounds of tooling fixes to root out.

For the physical wiring, single-rail-owner power sequencing, and the patched OpenOCD driver, see the companion guide [Read-only SWD and voltage-glitch harness on a locked Nuvoton M483](/guides/swd-and-voltage-glitch-harness-m483/). For the passive side-channel companion, see [Test a firmware cipher with power side-channel analysis on Cortex-M](/guides/sca-firmware-key-cortex-m/). For the WCH RISC-V debug attach triage on a separate target, see [CH32V305 WCH-LinkE read-only debug triage](/guides/ch32v305-wch-linke-read-only-triage/).

<Aside type="note" title="Provenance: measured versus documented">
Hardware measurements were recorded between 2026-11-01 and 2026-11-17 across three locked target boards (`Nuvoton M483SIDAE`, `LQFP-64`), a Nu-Link Pro debug adapter (`0416:511c`, FW `8062`) driven by a patched xPack OpenOCD build (`7bb05570f40dae2c742e6e581db4129468fed689`)[^xpack] at `200 kHz`, a direct RP2040-based SWD master (the glitcher's raw debug interface, `pyusb` backend), an RP2040 MOSFET crowbar (`ADC_CROWBAR` at `2.604 MS/s`) on `LDO_CAP` (pin 50, `~1.26 V`) and `VDD` (pin 51, `3.3 V`), and an `fx2lafw` logic analyzer sampling `nRESET` and `VDD` at `1 MHz` and `2 MHz`. Register definitions, lock-effect tables and reset reload rules come from the Nuvoton M480 Series Technical Reference Manual Rev. 3.07[^m480trm] and Datasheet Rev. 3.09[^m480ds]. No chip erase, mass erase, or `OTP` write was executed; the flash lock was not bypassed.

## Evidence timeline (chronological, with corrections inline)

### 2026-11-01 through 2026-11-13: initial bring-up, two adapter faults

**2026-11-01**: First SWD contact. Physical SWCLK (pin 34) found open; `DPIDR` was a voltage-channel echo (`0x0b9f0b9f`, the `~2963 mV` ADC sense reading echoed twice). Multiple probes confirmed the SWCLK leg needed a fresh spring-loaded microprobe. Once seated, `DPIDR` returned `0x2ba01477` - the valid Cortex-M4 Debug Port ID.

**2026-11-05**: Early HID overread sweeps captured repeatable windows, but their USB mode and memory-base mapping were not yet qualified. The later application/update-mode correction changed their interpretation; these early captures were not valid app-mode RAM evidence.

**2026-11-13**: A safe-connect OpenOCD patch was written to skip `CMD_MCU_RESET` so the target would not be reset during adapter open. This patch omitted `CONNECT_NORMAL` - the command that powers up the Cortex-M4 `AHB-AP`. The `DP` (Debug Port) answered `IDCODE` reads with `0x2ba01477`, but every HLA memory read echoed the stale `DPIDR` word from the adapter buffer. This dead-transport state persisted across the next two days and produced the entire `10,157`-attempt `locked-response` corpus that the late-campaign review would later identify as worthless.

### 2026-11-14: readback oracle failure surfaces

With the safe-connect patch running (still missing `CONNECT_NORMAL`), raw HLA memory reads returned `0x2ba01477` at `CPUID` (`0xe000ed00`), `CONFIG0`..`CONFIG3` (`0x00300000`), `APROM` (`0x00000000`), and peripheral registers. The runner classified this uniform response as `locked-response` - a stable lock signature. OpenOCD rejected normal `mdw` commands with `Target not examined yet` because `CPUID` returned `DPIDR` rather than a valid Cortex-M part number.

Decision note (wrong): "The `locked-response` classifier is a working readback oracle. We have two locked boards that both return it; any glitch that changes the response is a positive hit. Proceed with the crowbar grid."

**2026-11-14: first fault-injection grid.** `1,506` reset-rising trials (`0`-`250 us` delay, `4`-`128 ns` width on `LDO_CAP` with the decoupling capacitor installed) returned no change - every trial classified `locked-response` or `all-ff`. At the time this was read as "the crowbar didn't hit the latch window", but every trial had the dead-transport echo as its readback. No failure could be distinguished from no effect.

**2026-11-14: update-mode backup captured.** The USB bootloader exported `65` application pages (`66,560` bytes) and a `1,024`-byte configuration block over HID. The backup was treated as "full recovery is proven", but it covered only the application partition and its configuration. `LDROM` (`0x00100000`, 4 KB bootloader), `CONFIG0`..`CONFIG3` (`0x00300000`), and `OTP` (`0x00300500`) were not backed up. Two boards shared the same application SHA-256 prefix with different configuration hashes; two boards shared the same configuration prefix with different applications. The backup hashes could not identify which physical PCB was currently wired.

### 2026-11-15: two more blind grids and the `trigger=none` premise

A working note hypothesised that `SBLOCK` latches only at cold Power-On Reset (`POR`) and never on `nRESET`. Later summaries repeated that `POR`-only hypothesis as an established fact, even though the TRM explicitly states *"when chip is powered on or active from reset"*. Acting on this unverified premise:

| Run | Trigger | Attempts | Outcome |
|---|---:|---|
| Baseline `VDD` grid | `trigger=none` (`OUT_NONE`) | `1,506` | `1,506` `locked-response` |
| Wide `VDD` grid | `trigger=none` (`OUT_NONE`) | `7,145` (stopped on 3rd `readback_error`) | `7,142` `locked-response`, `3` `readback_error` |

With `trigger=none` and `OUT_NONE`, the target was already booted and idling. Every `delay` value fired into the same steady-state idle loop, never intersecting a `POR` or reset-release `CONFIG`-reload window. After each pulse the runner spawned a fresh `openocd` OS process to check the result - a step taking seconds, while `nRESET` asserts `35`-`37 us` after a `>= 40 us` `VDD` droop. The readback was five orders of magnitude too slow to catch a transient unlock even if one had occurred.

**Pulse-ladder measured on the harness.** An `fx2lafw` logic-analyzer capture at `1`-`2 MHz` with `D0` on `nRESET` and `D1` on `VDD` produced the ladder in the companion harness guide. `VDD` pulses of `1`-`35 us` droop the rail without asserting `nRESET`; `>= 40 us` triggers external reset assertion `35`-`37 us` after the `VDD` falling edge. The glitcher's onboard ADC at `2.604 MS/s` (`~384 ns/sample`) resolved microsecond-level droop but cannot resolve nanosecond (`4`-`128 ns`) pulse shape, so the ADC traces were promoted into "pulses qualified" when they were undersampled by a factor of `24x` to `96x`.

### 2026-11-15 (evening): the transport trap is found

Inspecting the OpenNuvoton USB JTAG/SWD driver source[^openocdnuvoton] showed that the safe-connect patch's skip of `CMD_MCU_RESET` had also skipped `CONNECT_NORMAL` - the AP power-up command. Replacing the skipped call with a connect-only handshake (`CMD_MCU_RESET` using `reset type 5` and `CONNECT_NORMAL`, `supply=0`, all resets suppressed) powered the `AHB-AP` non-destructively:

| Address | Connect-only result |
|---|---|
| `SYS_PDID` (`0x40000000`) | `0x00d48310` (genuine M483SIDAE part ID) |
| `SRAM` (`0x20000000`) | Live, address-distinct data; stack pointer `0x20001c60` |
| `CPUID` (`0xe000ed00`) | `Cortex-M4 r0p1` examined cleanly |
| `APROM` (`0x00000000`) | `0xffffffff` |
| `LDROM` (`0x00100000`) | `0xffffffff` |
| `SPROM` (`0x00200000`) | `0xffffffff` |

The `AHB-AP` is live, `SRAM` is readable, flash is genuinely locked - but the earlier `10,157`-attempt `locked-response` corpus was a dead-transport artifact. The three-tier qualification (`SYS_PDID` positive control, `SRAM` positive control, `APROM` negative control) became the standard oracle check.

### 2026-11-16: SRAM writes, Nu-Link attach, and the connect-lockup

**Direct SWD write probes via the glitcher's raw interface.**[^faultierfw] With the glitcher as the sole SWD master, 32-bit writes to `SRAM` at `0x20000400` and `0x20004000` no-oped in both `LOCKUP` and clean vector-catch halt states. Private Peripheral Bus debug writes (`0xe000xxxx`) landed, confirming selective gating, not a global SWD-write bug. A full general-SRAM dump (`128 KB` at `0x20000000`-`0x2001ffff`) qualified: no plaintext firmware code, no key material, no exact 32-byte-or-longer match against the corpus of related binaries.

**Connect-lockup on a running core.** With `CONNECT_NORMAL` (which bundles AP power-up and core halt), the recorded core state faults into LOCKUP with `PC = 0xFFFFFFFE`. Fault registers include `HFSR.VECTTBL` (`0x40000000`), `DFSR.HALTED` (`0x00000001`), and `LR = EXC_RETURN`. A vector-fetch/lock interaction is one hypothesis; the register snapshot alone does not establish the exact fetch path. `CONNECT_DISCONNECT` (enum value `4`) was tested as a non-halting alternative: it does not power the `AHB-AP`, so memory reads die - the Nu-Link bundles AP power-up with the halt and offers no power-without-halt path.

**Vector catch avoids lockup.** `DEMCR.VC_CORERESET` plus `C_HALT` produces a clean halt on reset release, avoiding the fault escalation. DP power-down before the close reset restores normal USB enumeration. These are separate from the write gate and from updater resume.

**Resume is blocked.** Resuming from the reset-caught state fails: `PC = 0xFFFFFFFE`, `HFSR = 0x40000000`, `CFSR = 0x00001001`. This blocks DWT-based CPU-bus observation and single-step readout - the two capture designs that depended on resume.

**Bank-2 SRAM qualified.** The earlier "SPIM clock/CCMEN writes blocked" result was a transposed clock address (`0x40002004` instead of `0x40000204`). With the corrected address, a full `32 KB` bank-2 dump (`0x20020000`-`0x20027fff`) qualified in both reset-state and running-halted conditions; the two dumps are byte-identical. The contents are high-entropy with no plaintext vector candidate and no firmware match. Bank 2 is in SPIM cache mode (`CCMEN=0`); it was not tested as general SRAM.

### 2026-11-17: per-region write-gate map, full page read sweep, and the campaign verdict

**Per-region write-gate map.** A single-session live SWD probe via the glitcher mapped the AHB-AP write surface region by region, with core-register and `CLK_AHBCLK` positive controls in the same run:

| Target | Operation | Result |
|---|---|---|
| Core register `r0` via `DCRSR`/`DCRDR` | write, read back, restore | Landed |
| `CLK_AHBCLK` (`0x40000204`, `PDMACKEN`\|`ISPCKEN`) | write, read back | Landed |
| `SPIM_CTL1` (`0x40007004`) | write | Landed |
| `SRAM` `0x20001000`, 32-bit | write, read back | Blocked (no-op) |
| `SRAM`, 8-bit and 16-bit | write, read back | Blocked (no-op) |
| `FMC` `ISPCTL.ISPEN` (`0x4000c000`) | write, read back | Blocked (reads back `0`) |
| `PDMA` `DSCT0_CTL`/`SA`/`DA`/`CHCTL` | write, read back | Blocked (reads back `0`) |
| `SRAM` via bit-band alias (`0x22020000`) | write bit 0, read target | Unqualified: target unchanged |
| `FMC`/`PDMA` via peripheral bit-band aliases | write, read register | Unqualified: register unchanged |

The bit-band rows have no same-alias positive control (no write to a known-writable register through its bit-band alias was attempted in the same run), so they are `probe_unqualified`. The direct-write rows stand. The gate is selective: core debug registers, the clock controller and `SPIM` accept writes; `SRAM`, `FMC` and `PDMA` are blocked - exactly the subsystems that could read or move flash contents.

**Recorded halted states do not provide CPU execution.** A clean `SYSRESETREQ` plus halt yields a degenerate stack pointer and `PC=0xFFFFFFFE` (HardFault), while the same board enumerates as a working HID device when free-running. These fault states block the tested single-step and DWT capture paths. They do not prove a global rule that the lock gates every halted-CPU flash read.

**Full page read sweep (`0x00`-`0xC8`).** The update-mode HID `page read` command returns a 1,024-byte flash page by index (`addr = index * 0x400`). A full sweep returned ciphertext at every index (entropy `~7.8` bits/byte). The recurring filler and trailer pages are the vendor image's own repeated pages (verified byte-identical against the vendor image and all board backups) - this is a real flash ciphertext primitive, not a 64-page RAM buffer. Out-of-range indices return a cached default page. The sweep covered the full map, including indices below the application boot that the debug AHB-AP returned `0xFF` for.

**App-mode overread is a real RAM window.** An update-mode overread returns zeros at every length; in application mode, a 4,096-byte overread returns a real, repeatable, address-distinct RAM window - a structured descriptor/table region. Its base moves between sessions, and the `A0`/`A1` selectors and report length do not steer it. No key material has been found in it. The earlier update-mode overread-negative was a mode artifact, now voided.

**`SetFeature` write/overflow probes.** Valid application-mode `SetFeature A0` writes of 2, 15, 16, 32, and 64 bytes at page and flash boundaries did not advance page state past the measured 2-byte staging behaviour or expose an overread-window overflow. That is a scoped negative at the tested lengths and boundaries. Update-mode large writes exposed heap/pool state rather than providing the same control. No RAM-write primitive has been demonstrated over the HID path.

**Recovery scope is app+config only.** All `65` application pages were rewritten and verified page-by-page from the board's own backup (SHA-256 verified), and the official vendor updater then returned the device to application mode. `LDROM`, `CONFIG0`..`CONFIG3`, and `OTP` are outside both the backup and the restore. Full-chip recovery does not exist.

### 2026-11-17: whole-campaign verdict (multi-model review)

Two independent model families reviewed the entire campaign. The lead verdict: the campaign investigated reasonable targets in the wrong order, repeated the unqualified-negative pattern it had diagnosed, and never ran the decisive free experiments before buying instrumentation.

1. **Blind crowbar FI was the biggest misallocation.** `~8,651` attempts with `trigger=none`, scope off, no target-event model, and an initially-broken readback consumed sessions of unattended runs producing zero trustworthy evidence.
2. **The capture pipeline was built before its crux.** The DWT/harvest design depends on resume-from-halt, which locks up. The design's own "must-qualify-first" section named resume but did not gate implementation.
3. **False-negative pattern: unqualified negatives.** Three separate "locked" results were tooling bugs (unpowered `AHB-AP`, a missing `ISPCKEN` clock, a wrong clock-controller address). Each unqualified negative closed an avenue that was actually open.
4. **Arch A vs arch B was never the central experiment.** The campaign oscillated between the two instead of deciding it - it changes what "win" means and which SCA round to attack.
5. **SCA was invisible in every prior open-avenue list** until the missed-vector review - the highest-ROI passive key-recovery path, overlooked for weeks.

### 2026-11-18: review-fixed controls, the command sweep, and the liveness audit

A multi-model review of the 2026-11-17 gadget evidence found tooling and evidence-qualification defects: narrow AP_DRW writes lacked byte-lane packing, `C_STEP` survived close/reset, and several conclusions were drawn from contaminated or unqualified sessions. The fixes were re-reviewed and rerun in a clean control matrix.

**Clean narrow-width and bit-band controls.** With `CLK_AHBCLK` at `0x0000C404`, 8-bit and 16-bit writes landed and restored; the same-width SRAM writes stayed blocked and restored. The peripheral bit-band alias `0x420040B8` landed and restored `CLK_AHBCLK[14]`; the SRAM alias `0x22020000` stayed unchanged. The earlier 8-bit anomaly was a DRW byte-lane tooling bug; the lock did not cause it.

**In-SRAM LDR execution.** An in-session-validated `ldr r2,[r1]` gadget at `0x20002277` executed with the destination changing and PC advancing; APROM address 0 returned `0xFFFFFFFF` through the same qualified path. A current `str r2,[r3]` gadget landed on `CLK_AHBCLK` and restored, but did not land on SRAM. CPU-issued FMC reached the engine but CID returned `fmc-fail`; no APROM READ ran. RW1C/CLK/core restoration passed.

**App-mode command sweep.** The bounded app-mode HID sweep found no hidden raw-image or RAM-read command. Command `0x15` is a config-writing power command; with a zero payload it changed 55 config bytes and was restored byte-exact. Command `0x01` returned status 1 on the wrong report ID and did not change config. The sweep tool now requires a matching response report ID before marking a command accepted.

**step-ram-diff control-only retry.** The corrected engine again rejected the initial state: `PC=0xFFFFFFFE`, zero frames, zero collection steps. No exhaustive series ran. The earlier claim that SWD cannot observe live firmware was retracted; the evidence audit shows that no live series was demonstrated and leaves the universal limit unproven.

**Liveness fixture.** A QEMU MPS2-AN386 counter fixture now tests whether repeated reads track a running program: during a deliberate hold, heartbeats advance while the sampled counter stays fixed. The physical observer qualification on an unlocked board remains open. The dated research corpus is indexed in `<source file>`.

## The FMC lock model (document-level facts that held)

Every fact in this section comes from the Nuvoton M480 series Technical Reference Manual Rev. 3.07[^m480trm] and Datasheet Rev. 3.09[^m480ds]. None depends on the fault-injection campaign.

### Why `0xFF` means locked

`CONFIG2[15:8]` (`SBLOCK`) and `CONFIG2[7:0]` (`ALOCK`) use `0x5A` as their explicit unlock token. Any other byte value - including an erased or default `0xFF` - activates the lock[^m480trm].

| Register bits | Field | Erased/default | Unlocked value | Behaviour |
|---|---|---|---|---|
| `CONFIG0[1]` | `LOCK` | `1` | `1` (`0` = locked) | Flash is unlocked only if `LOCK == 1`, `ALOCK == 0x5A`, and `SBLOCK == 0x5A`[^m480trm] |
| `CONFIG0[11]` | `ICELOCK` | `1` | `1` (`0` = ICE disabled) | Debug interface enable |
| `CONFIG2[15:8]` | `SBLOCK` | `0xFF` | `0x5A` | Secure Boot Lock; any other value restricts ICE to `MassErase`[^m480trm] |
| `CONFIG2[7:0]` | `ALOCK` | `0xFF` | `0x5A` | Advance Security Lock; any other value enables lock even when `LOCK == 1`[^m480trm] |

An `all-0xFF` SWD read of `0x00300000` is not a reading of `CONFIG0`..`CONFIG3`. A locked chip returning `0xFFFFFFFF` (or `0x2ba01477`) at every address returns a bus-level lock mask, not the stored flash bytes. The exact programmed `CONFIG` bits of a locked board are not known from a blocked SWD read.

### CPU versus ICE access (Tables 6.5-6 and 6.5-7)

| Memory region | Address | CPU master (`Table 6.5-6`, `SBLOCK` active) | ICE / SWD master (`Table 6.5-7` + Note 6) |
|---|---|---|---|
| `APROM` (512 KB) | `0x00000000`-`0x0007FFFF` | `R W` | Blocked (Note 6 overrides; sets `ISPFF = 1`) |
| `LDROM` (4 KB) | `0x00100000`-`0x00100FFF` | Restricted | Blocked |
| `CONFIG0`..`3` | `0x00300000`-`0x0030000F` | Readable by CPU | Table says `R W`, but Note 6 + live SWD block reads |
| Mask-ROM Boot Loader | `0x00800000`-`0x00807FFF` | `R -` in all columns | Blocked by ICE lock gate |

**Note 6 of Table 6.5-7**: *"All operations (except for MassErase) are invalid for ICE when SBLOCK is not 0x5A."*[^m480trm] Any ICE-initiated `FMC` operation sets the ISP Fail Flag (`ISPFF`, bit 6 in `FMC_ISPSTS`)[^fmcreg]. This closes the ICE-initiated ISP read route: a debugger cannot write `FMC` ISP registers to trigger a CPU-side flash read.

### What `M483SIDAE` includes and omits

The `M483xIDAE` sub-family has no hardware cryptography peripheral (no AES, DES, SHA, or ECC engine), no Execute-Only Memory (`XOM`) region support, and no `KEYPRT` hardware key-protection registers[^m480ds]. All protection comes from the standard `FMC` configuration gates and mask-ROM / `LDROM` boot flow.

### The Flash Initialization Controller reload rule

The TRM states: *"When chip is powered on or active from reset, Flash Initialization Controller checks the flash stability first, and then reloads User Configuration to flash control registers"*[^m480trm] (with reset-source exceptions for `BL`/`BS`). This means `CONFIG` is reloaded at `POR` and on certain resets - the `POR`-only hypothesis that motivated the `trigger=none` grids was wrong.

## Architecture: where the plaintext lives

With the `M483SIDAE` confirmed to have no `XOM`, no hardware crypto engine, and no plaintext firmware in the sampled SRAM snapshots, **arch B** is the favoured model: the CPU executes plaintext directly from flash and `page read` encrypts on egress. The working application and absent executable decode paths support that model.

This is a strong prior, not a forced deduction. Arch A (ciphertext at rest, returned verbatim, decrypted somewhere executable) remains possible through a transient plaintext buffer or another unobserved execution path. No physical power-side-channel capture has been run; neither architecture has been confirmed or excluded by a direct measurement.

The lowest-cost planned discriminator is differential SPA of the core rail (`LDO_CAP`, pin 50) during repeated `page read` operations and non-crypto reference commands. Repeatable cipher-like activity during reads supports arch B; its absence would redirect attention to boot/update decryption under arch A. Copying, checksums, USB, and flash activity prevent any single trace from settling the model alone.

### Prioritized open avenues

1. **SPA-on-read.** Capture `LDO_CAP` during repeated `page read` and reference commands. Differential cipher-like activity supports arch B and identifies whether ordinary reads exercise the candidate key operation. It requires a qualified analog front-end and fresh scope triggers.
2. **Clean running-halt with a valid `PC` + real resume.** Halt while the updater is demonstrably running rather than from reset, capture `PC`/`xPSR`/`SP`/`LR`/fault regs, resume and verify USB. If it works, the DWT capture and single-step designs reopen.
3. **Physical live-observer qualification.** Run the counter fixture on an unlocked board with an independent heartbeat; the QEMU version passes, but the physical SWD path is unqualified.
4. **Unlocked `M483SIDAE` reference board.** Provides halt/write/DWT/`FMC`/`PDMA`/bit-band/FI controls on identical silicon. Does not contain the per-model key; generic `M483` equivalence must be proven.
5. **CPA key recovery.** SPA-first to confirm AES (or identify the primitive) and the correct operation (read vs update). Then capture N traces with known ciphertext. The current `cpa_aes.py` self-test validates synthetic AES only; if the primitive is not AES, it provides no key-recovery guarantee. No LNA purchase before unamplified SNR measurement.
6. **Scope-qualified fault injection.** Last resort - only after mechanism, event, pulse shape, and broad-oracle qualification. The `8,651`-attempt blind campaign already showed that glitching without a qualified trigger, timing model and live oracle is an instrumentation problem first.

### RAM question: what was tried and what was not

- **Full static SRAM dumps**: 128 KB general (`0x20000000`) + 32 KB bank 2 (`0x20020000`), in reset-state and running-halted conditions. No plaintext application code or identified key/decrypt buffer found in either.
- **HID overread snapshots**: the moving-base RAM window (currently mapping to `~0x200009e4`) was sampled in app mode; app-mode overread content is a structured descriptor/table region, not a decrypt buffer. The 1 s and 3 s update-phase captures did not expose a decrypted page.
- **Single-step RAM diff**: attempted separately and faulted (`PC=0xFFFFFFFE`). The exact sequence "halt -> dump the RAM region of interest -> single-step one instruction -> dump the same region -> diff -> repeat" has NOT been run. No per-instruction RAM timeline exists.
- **Transient plaintext between snapshots is not excluded** by the sampled dumps. The experiment remains technically valid once clean stepping is qualified. The real blocker is a valid `PC` and successful single-step, not dump speed. Slow full dumps are acceptable; narrowing the region only reduces capture time.
- **Tooling status**: the step-ram-diff command implements the bounded experiment with a mandatory known store-to-RAM/PC control, per-frame diffs, and fault preservation. A control-only live probe rejected the initial state (`PC=0xFFFFFFFE`, zero frames). No physical collection series has run. A QEMU counter fixture now provides a control for observer qualification; the physical version is pending.

## What to do about it (methodological)

| Practice | Evidence from this campaign |
|---|---|
| Require a same-primitive, same-state, same-run positive AND negative control before believing a negative | Three "locked" results on this target were tooling bugs (unpowered `AHB-AP`, missing `ISPCKEN`, wrong clock address); each unqualified negative closed an avenue that was actually open |
| Require an address-sensitive positive control before any glitch sweep | `raw_mdw` returned `0x2ba01477` at every address; accepting `locked-response` in preflight hid a zero-sensitivity oracle across `8,651` `trigger=none` rows |
| Qualify `AHB-AP` reads with `SYS_PDID` and `SRAM` before trusting a lock read | Connect-only `CONNECT_NORMAL` reads `SYS_PDID = 0x00d48310` and live `SRAM` while locked `APROM` reads `0xffffffff` - a three-tier qualification that catches dead-transport echoes |
| Reject `trigger=none` in automated timing-grid configurations | Without a hardware `POR` or `nRESET` trigger edge, varying `delay` only shifts when the MOSFET fires relative to the host USB command, testing 0 points of the boot-time `CONFIG` latch window |
| Couple readback to the trigger over a persistent SWD session | Spawning a fresh `openocd` process per trial takes seconds; `nRESET` asserts `35`-`37 us` after a `>= 40 us` `VDD` droop |
| Measure nanosecond pulse shape with an oscilloscope | ADC at `2.604 MS/s` (`~384 ns/sample`) cannot resolve `4`-`128 ns` pulses; a microsecond ADC dip does not prove the pulse crossed the core LDO or FMC sense threshold |
| Bind backup manifests to a hardware `board_id` and state unbacked regions | Two boards shared identical application/configuration hashes; `LDROM`, `CONFIG`, and `OTP` were outside every backup |
| Treat changed words on a locked target as an anomaly first, never plaintext | A single non-`0xFF`, non-`DPIDR` read can come from SWD framing corruption; require a repeatable re-read and an address-dependent match across multiple offsets |
| Decide architecture A vs B with the cheapest discriminator available | The campaign oscillated between the two without a central experiment; differential SPA during `page read` tests the favoured model, and the answer changes what "win" means |
| Run low-cost deciders before large blind campaigns | The `8,651`-attempt blind campaign ran while app-mode overread and the full `page read` sweep were untried; SPA-on-read still needs qualified physical capture |
