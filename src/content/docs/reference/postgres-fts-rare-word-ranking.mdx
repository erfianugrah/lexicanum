A Postgres full-text query of the form `a OR b OR c` matches every row that
holds any one of the words, and `ts_rank` then reads the `tsvector` of every
one of those rows before `ORDER BY rank LIMIT 10` keeps ten. This page measures
that cost on a real table and describes a ranking change that cut the slow tail
from seconds to under a second without losing results.

Everything here was measured on 2026-11-05 on the live
[agent memory store](/reference/agent-memory-store/): one Postgres 18 database
(the `pgvector/pgvector:0.8.7-pg18` image) on a home server, a `messages`
table of 1,651,545 rows with a generated `tsvector` column and a GIN index,
queried through PostgREST. The heap is 2787 MB and the TOAST table 5279 MB.
The queries are 25 real searches agents ran through the `session_search` tool,
taken from the session-fts measurement of the same day (see
[resuming agent sessions](/reference/resume-agent-sessions/)). Quality is
scored against a second engine: for each query, how many of the ten sessions
that a local SQLite FTS5 index ranks first also appear in the Postgres top 10
(101 such sessions over 24 queries; one query had none). The measurement
scripts and output live in the private memledger repository
(`docs/research/lab/2026-11-05-search-rank/`), so the tables below are pasted
from that output, not linked. The
[follow-up of 2026-11-07](#follow-up-toast-reads-and-the-buffer-pool) has its
own lab (`docs/research/lab/2026-11-07-search-cold-cache/`).

## TL;DR

- One broad query, `git OR credential OR forgejo OR lfs OR pre OR push`,
  matched 183,494 of the table's `pi` rows. The old function ranked all of
  them: 4686 ms in `EXPLAIN ANALYZE`, a top-N heapsort on top of a bitmap heap
  scan over 125,538 heap blocks.
- Postgres's ranking functions use no corpus-wide statistics[^pg-rank], so a
  common word counts as much as a rare one. The rare words carry the meaning
  of a query anyway.
- The fix reads the planner's own list of common lexemes,
  `pg_stats.most_common_elems`[^pg-stats], which held 1000 lexemes on this
  column, each in at least 1.6% of rows. OR operands with a lexeme outside
  that list pick the candidate rows; the full query ranks them; a short result
  is topped up from the newest matches.
- Over the 25 queries the slow tail fell from p90 5557 ms and a 16965 ms
  maximum to p90 576 ms and a 1318 ms maximum, with 40 of 101 reference
  sessions found against 39 before. Through the live HTTP API: p50 78 ms,
  p90 409 ms.
- Two cheaper ideas failed: four parallel workers did not make the old query
  faster (5937 ms against 5407 ms with two), and ranking only the newest 2000
  matches was fast but found 31 of 101.
- Follow-up, 2026-11-07: an `OFFSET 0` fence added with the fix had become
  pure overhead and was removed (lab p90 1192 -> 759 ms). The remaining cost
  was TOAST: for a 23,467-match query, `ts_rank` added about 98,000 TOAST page
  reads to 26,337 heap blocks. Ranking only the newest 8000 matches of the
  rare operands kept recall (38 of 101, unchanged; 4000 gave 33) and cut p90
  from 873 to 346 ms. `shared_buffers` went from 512 MB to 1536 MB after
  pg-analyser showed a 23.17% cache hit ratio.

## Where the time goes

```dot
digraph {
  rankdir=LR; bgcolor="transparent"; nodesep=0.3; ranksep=0.7;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];
  q [label="a OR b OR c\n(websearch_to_tsquery)"];
  gin [label="GIN bitmap\n254,171 rows"];
  src [label="source btree bitmap\n1,102,881 rows"];
  and [label="BitmapAnd\n183,494 rows"];
  heap [label="heap + TOAST\nread every tsvector"];
  rank [label="ts_rank x 183,494"];
  top [label="top-N heapsort\nkeep 10"];
  q -> gin; gin -> and; src -> and; and -> heap; heap -> rank; rank -> top;
}
```

The plan for the broad query, read top to bottom:

1. The GIN index returns 254,171 candidate rows for the six OR'd lexemes.
2. The planner ANDs that bitmap with a scan of the `(source, ts)` btree for
   `source = 'pi'`, which returns 1,102,881 rows. The intersection is 183,494:
   the source filter removed only the other clients' rows, and it cost a scan
   of a bitmap six times the size of the result.
3. The bitmap heap scan visits 125,538 heap blocks and fetches each row's
   `tsvector`, which for any message of more than a few lines lives in TOAST.
4. `ts_rank` runs once per row. The sort is a top-N heapsort using 33 kB, so
   the sort itself is cheap; reading and scoring 183,494 vectors is the work.

The Postgres documentation says this outright: ranking "requires consulting
the tsvector of each matching document, which can be I/O bound and therefore
slow", and is "almost impossible to avoid since practical queries often result
in large numbers of matches"[^pg-rank]. `ts_headline` was not the problem: it
runs only on the ten rows the `LIMIT` keeps.

The OR query is the common case here. The agent tools join the words of a
multi-word query with `OR` (always in one tool, as a retry after a zero-hit
search in the others, see
[two retrieval modes](/reference/agent-memory-store/#two-retrieval-modes-one-database)),
so every common word in a query adds tens of thousands of matches.

## What did not work

| Attempt | Result | Why |
|---|---|---|
| More parallel workers (`max_parallel_workers_per_gather` 2 -> 4) | 5407 ms -> 5937 ms on the broad query, same run | The per-row work splits across workers, but every worker still reads its share of 5.3 GB of TOAST; on this host the extra workers bought nothing |
| Rank only the newest 2000 matches per source | p90 725 ms, but 31 of 101 reference sessions (39 before) | A date cut keeps whatever is recent, so a rare-word hit in an older session falls outside it |
| Filter source after the GIN scan instead of the BitmapAnd | Kept in the first version (an `OFFSET 0` fence), removed two days later | It saved the btree scan then; on Postgres 18 the planner stopped building the BitmapAnd, and the fence only forced every candidate row to be materialised (see the follow-up) |

The recency cap is the instructive failure. It is the obvious fix and its
latency was fine, but it lost results on exactly the OR lists that mix one
rare word with common ones: `agent OR driven OR KiCad` went from 2 reference
sessions to 0, `Lamzu OR key` from 1 to 0, `sks8300 OR autorebase OR patch OR
id` from 2 to 0.

## Rank what the rare words match

`ts_rank` gives no weight to rarity, so for an OR query the rows that matter
are the ones holding the uncommon words. Postgres already keeps a list of the
common ones: `ANALYZE` stores the most frequent elements of a `tsvector` column
in `pg_stats.most_common_elems`, with their frequencies in
`most_common_elem_freqs`[^pg-stats]. On this table the list held 1000 lexemes,
the rarest at a frequency of 0.016, about 26,000 rows. `autovacuum` keeps it
current, and it costs no new index or table.

The new `search_messages` (migration 037 in the memledger repository) does
this:

1. Parse the query with `websearch_to_tsquery`. If it is not a plain OR list
   (it has `&`, `!`, a prefix match or parentheses), rank every match exactly
   as before.
2. Split the OR list into operands. An operand is selective if at least one of
   its lexemes is missing from `most_common_elems`; a quoted phrase counts as
   one operand.
3. Fetch the rows matching only the selective operands, rank them with the
   full query, and keep the top `lim`.
4. If that gave fewer than `lim` rows, or no operand was selective, add the
   best of the newest 2000 rows per source that match the full query and were
   not already returned.

With no statistics on the column, as on a freshly loaded database, every
operand is selective and the function behaves like the old one.

```sql
-- step 2: an operand is selective when a lexeme is missing from the stats
SELECT s.most_common_elems::text::text[] INTO mce
  FROM pg_catalog.pg_stats s
 WHERE s.schemaname = 'public' AND s.tablename = 'messages' AND s.attname = 'fts';
FOREACH op IN ARRAY string_to_array(tq::text, ' | ') LOOP
  IF EXISTS (SELECT 1 FROM regexp_matches(op, $re$'((?:[^']|'')+)'$re$, 'g') AS m(x)
              WHERE NOT (replace(m.x[1], $q$''$q$, $q$'$q$) = ANY (mce))) THEN
    sel := sel || op;
  END IF;
END LOOP;
```

For the broad query, `forgejo`, `lfs` and `credenti` are selective and `git`,
`pre` and `push` are in the list, so only the rows holding one of the three
rare lexemes are ranked, and they are ranked with all six words.

### Prior art: Hindsight

The idea is not new. Hindsight, an MIT-licensed agent memory system from Vectorize[^hindsight-readme], hit
the same failure and reached for the same statistic: its tsvector backend
OR-joins a long recall query, `ts_rank_cd` runs for every matched row, and
queries that matched thousands of memories timed out (its source names a
60-second hang). Its fix reads `most_common_elems` to estimate each token's
document frequency and keeps only the N tokens with the lowest one; on any
failure to read the statistics it falls back to the first N
tokens[^hindsight]. This page's version was written before finding
Hindsight's, and the two differ in what happens to the common words:

| | Hindsight | This page |
|---|---|---|
| Common words in the query | Dropped before the search | Kept |
| Which rows get ranked | Rows matching the kept rare tokens | Rows matching the selective OR operands |
| What ranks them | The reduced query | The full query, common words included |
| Rare words match fewer rows than the limit | Fewer results | Topped up from the newest rows matching the full query |
| Query of only common words | The N least common of them | Newest 2000 matches per source, ranked |
| Statistics unavailable | First N tokens | Every operand selective: rank every match, as before |

On the broad query, Hindsight with N = 3 would search
`forgejo OR lfs OR credenti` and rank with those three words only. Here the
same three words pick the rows, and a message holding `forgejo` and `git
push` ranks above one holding `forgejo` alone. Neither approach was compared
against the other on this corpus.

## Reading the numbers

Over the 25 queries, run inside Postgres, one run per variant per query:

| Variant | p50 | p90 | Max | Reference sessions found |
|---|---|---|---|---|
| old: rank every match | 442 ms | 5557 ms | 16965 ms | 39 / 101 |
| cap: newest 2000 per source | 308 ms | 725 ms | 1191 ms | 31 / 101 |
| live: rare operands pick candidates | 81 ms | 576 ms | 1318 ms | 40 / 101 |

Through the live PostgREST endpoint over HTTPS from a workstation, median of
three runs per query: p50 78 ms, p90 409 ms, maximum 1279 ms, 40 of 101.

Selected rows, same run:

| Query | Old | Live |
|---|---|---|
| `"can't type" OR "cannot type" OR ...` (5 phrases and words) | 16965 ms | 24 ms |
| `git OR credential OR forgejo OR lfs OR pre OR push` | 6706 ms | 525 ms |
| `gridlock OR name OR 5x12 OR repo` | 6247 ms | 96 ms |
| `Lamzu OR key` | 3400 ms | 54 ms |
| `lockstep OR rebuffer OR BBR OR buffering` | 352 ms | 1318 ms |
| `wise` | 8 ms | 69 ms |

Three cautions on these numbers:

- For each query the variants ran in the order live, cap, old, so the old
  function always ran on the warmest cache. The comparison favours the old
  function.
- Single queries vary between runs: the broad query took 9.4 s in an earlier
  `EXPLAIN ANALYZE` the same day and 4686 ms in the one quoted above. The
  distribution is the result; one row is not.
- The new function is slower on some queries whose words are all uncommon
  but not rare: it is PL/pgSQL with a `pg_stats` lookup, it ran first on a
  colder cache, and a selective operand can still match many rows. The p50
  across all 25 queries still fell from 442 ms to 81 ms.

Forty of 101 reference sessions sounds low, and the old function scored the
same: the two engines rank differently (FTS5 uses BM25 with IDF, Postgres
`ts_rank` does not). In the session-fts lab, reading the Postgres results 200
rows deep together with a plain-text scan of the files found 95 of the 101.
The metric here only checks that the change lost nothing, and it did not.

## Follow-up: TOAST reads and the buffer pool

Two days later the same queries were slow again during a review: 7 to 15
seconds on a first run, 2 to 8 seconds on a second. Three findings, all
measured read-only on the live store (1.70 million rows by then, heap 2787 MB,
TOAST 5856 MB):

1. The fence had turned into overhead. `EXPLAIN ANALYZE` showed no BitmapAnd
   any more, even with a parameterised statement: the planner applied the
   source filter inside the bitmap heap scan. The `OFFSET 0` subquery now only
   forced a materialisation of every candidate before the top-N sort.
   Removing it moved the lab p90 from 1192 ms to 759 ms and the maximum from
   1519 ms to 901 ms.
2. The 7-15 s first runs coincided with a large backfill writing to the
   same database. On a quiet store, six broad queries never run before took
   0.31 to 2.60 s. What remained was page reads, and most of them were TOAST:

   | Same 23,467-match query | Buffers | Execution time |
   |---|---|---|
   | Heap only (`max(ts)` over the matches) | 26,399 | 269.716 ms |
   | With `ts_rank` (detoasts every matched `tsvector`) | 124,706 | 797.460 ms |

   A slimmer side table with only keys and the `tsvector` would not help: the
   heap scan is the cheap part, and the `tsvector` is what lives in TOAST
   (1633 bytes on average, 19,941 at the 99th percentile in a 2% sample).
3. The buffer pool was too small for this workload. pg-analyser in no-PAT
   mode reported a 23.17% cache hit ratio, a 22.7% heap hit ratio on
   `messages`, and client backends that had evicted 1,335,908,345 buffers and
   written 22,938,725 dirty ones themselves since the statistics reset. With
   `shared_buffers` at 512 MB (65,536 buffers), one broad search touching
   about 125,000 buffers cycled the whole pool, and a read query paid for
   writes.

The fix ranks fewer rows after the rare-word filter: collect only keys and
timestamps for the selective matches (heap pages, no TOAST), keep the newest
8000, join them back by primary key and rank those. This is a recency cap,
which failed in the first round, but it is applied to a different set: the
first attempt kept the newest 2000 of all matches, common words included, so
older rare-word hits fell out; this one keeps the newest 8000 of the rare
operands' matches only.

| Variant, 25 real queries + 4 broad ones | Reference sessions | p50 | p90 | Max |
|---|---|---|---|---|
| live (fence removed) | 38 / 101 | 73 ms | 873 ms | 1212 ms |
| rank pool 8000 | 38 / 101 | 166 ms | 346 ms | 814 ms |
| rank pool 4000 | 33 / 101 | 207 ms | 410 ms | 474 ms |

Each query ran the variants in the order 4000, 8000, live, so the live
function got the warmest cache. The 8000 pool returned the same top-10 rows as
live on 24 of the 25 real queries; only queries with more than 8000 selective
matches rank differently, within the newest 8000. The rare-word queries got
slower at the median (the CTE and the join cost a little when there is
nothing to cap), the tail got faster.

`shared_buffers` went to 1536 MB and `effective_cache_size` to 8 GB (the
host's ZFS ARC can hold 16 GiB, the container limit is 4 GB, and the
container's memory peak was 1.8 GB). Right after the restart, with an empty
buffer pool, six broad queries took 0.22 to 1.92 s on their first run and
about 0.22 s on the second.

## Testing it

A small test database defeats the check. With only a few thousand rows and
few distinct words, `ANALYZE` puts every lexeme into `most_common_elems`, the
"rare" word included, and the function takes the all-common path. The
end-to-end test therefore seeds 3000 rows sharing one common word plus about
3000 distinct filler words, adds one old row holding the rare word and one new
row repeating the common word 50 times, and asserts the statistics first:

| Check | Expected |
|---|---|
| `commonword` in `most_common_elems`, `rareword` not | `t` and `f`, else the test fails before querying |
| `rareword OR commonword`, `lim=5` | the rare-word row first, then four common rows, no duplicates |
| `commonword` alone | three rows, all from the newest 2000 |
| An AND query no row satisfies | no rows |
| `src=claude` and an empty query | no rows |
| 8001 weak recent matches and one strong old match, an AND query | the old row is not returned (it is outside the newest 8000); a small match set still ranks the strong row first |

Before migration 037 the second check failed: the row repeating the common
word 50 times outranked the single rare-word row, which is `ts_rank` without
IDF doing what it is documented to do.

## Decision guide

```dot
digraph {
  rankdir=TB; bgcolor="transparent"; nodesep=0.3; ranksep=0.5;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];
  slow [label="FTS query slow?"];
  plan [label="EXPLAIN ANALYZE:\nrows into ts_rank?"];
  few [label="a few thousand:\nlook elsewhere\n(index, headline, I/O)"];
  orq [label="query is an OR list\nwith common words?"];
  sel [label="rank what the\nselective operands match"];
  other [label="AND or phrase query:\nrank all, or order\nnewest first above\na match-count threshold"];
  slow -> plan;
  plan -> few [label="small"];
  plan -> orq [label="10^5 and up"];
  orq -> sel [label="yes"];
  orq -> other [label="no"];
}
```

1. Run `EXPLAIN ANALYZE` and read the row count entering the sort. A few
   thousand rows is not this problem.
2. Hundreds of thousands of rows from an OR query with common words: let the
   operands holding a lexeme outside `most_common_elems` pick the candidates,
   rank them with the full query, top up from a recency window.
3. An AND or phrase query that still matches that many rows has no rare
   operand to lean on: rank everything, or order newest first above a
   match-count threshold.
4. Still slow after that: compare `EXPLAIN (ANALYZE, BUFFERS)` with and
   without `ts_rank`. If ranking adds several times the heap pages, the
   `tsvector`s live in TOAST: cap the rank pool after the selective filter
   (collect keys and timestamps first), and size `shared_buffers` so one
   query does not cycle the pool.
