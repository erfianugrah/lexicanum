A knowledge graph over a personal document archive, built on local hardware. The pipeline walks a mounted archive, extracts text, mines entities and relations with a local LLM under constrained JSON output, stores the graph in Postgres, and exposes it to a coding agent through read-only MCP tools. No document content goes to a hosted model.

This page describes the system as of 2026-10-20, read from its source. The pipeline was measured on a local GPU (RTX 5090, 32 GB VRAM, one model at a time). The chat-history lane (structured ingest, no LLM) is described near the end.

The [agent session-memory store](/reference/agent-memory-store/) and the [Vikunja kanban board](/reference/kanban-board-for-coding-agents/) run as separate Postgres clusters on the same storage host, not as databases inside the graph's cluster. **TL;DR:**

- The archive is an SMB share with ~470k files, of which ~12.6k are documents.
- Ingest is gated by a 17-extension allowlist and a sensitive-filename exclusion regex.
- Text extraction is per file type and sha256-cached, so each file is read once.
- Extraction runs on the local llmc engine at `reasoning_effort: none` and `temperature: 0`. llama-server presets get a `json_schema` response format, NInfer presets get none.
- The graph is one Postgres database. Entities are keyed by `(type, canonical_key)`, so "Jane Doe" across forty documents is one node.
- An MCP server exposes 10 read-only tools.
- The extraction model was picked for continuity on 2026-10-04, ran 719 documents by 2026-10-14 and had never been compared with an alternative. The [bake-off](#the-extraction-model-was-not-evaluated) closed that gap.

4. The local LLM extracts entities and relations per chunk, 2 requests in flight, at temperature 0 with thinking disabled.
5. Postgres holds the document ledger (stage, timestamps, errors) and the graph. The cluster is on a separate machine, and extraction writes to it across the tailnet.
6. The MCP server gives the agent read-only entity search, dossier, cross-document entities, level-set neighbourhoods, timeline and chat-message search.

## Decisions

| Decision | Choice | Reason |
|---|---|---|
| Scan scope | Extension allowlist | Photos, app bundles and code are most of the 470k files and would dominate a denylist. 17 extensions cover ~12.6k documents. |
| Extraction model location | Local only | Medical, tax and identity documents are in scope. A cloud model is an opt-in per folder. |
| Text caching | sha256-keyed file cache | A 9p mount is slow. Re-running a stage on unchanged files does no work, and a NAS outage blocks only new files. |
| Chunking | Characters, paragraph-boundary preference | Semantic chunking matters for retrieval, not for per-chunk entity extraction. |
| Entity identity | `(type, canonical_key)` | Normalised for case and whitespace. The type keeps "Apple" the org apart from "Apple" the topic. |
| Output format | `json_schema` on llama-server, none on NInfer | NInfer presets return empty extractions with any response format. |
| Graph traversal | Level-set `UNION` | The archive owner is in every document, a mega-hub. See Storage for the measurement. |
| Concurrency | 2 workers, one DB connection | One GPU, so 2 in flight keeps the queue shallow. No DB call spans an await, so psycopg is safe. |
| Agent access | MCP over stdio, read-only | `default_transaction_read_only=on` per session, connection opened per call. |

## The archive and the scan stage

The source is a personal document archive on a network share, mounted read-only on the dev box. A scan walks every file, hashes it with sha256 and compares the hash with the document ledger. New and changed files enter the pipeline and unchanged files skip every later stage.

The `ALLOWED_EXTENSIONS` allowlist selects 17 document types:

| Group | Extensions |
|---|---|
| Documents | pdf, docx, doc, odt, rtf, epub |
| Presentations and sheets | pptx, ppt, xlsx, xls, xlsm, csv |
| Text and mail | txt, md, html, htm, eml |

Everything else is skipped: photos, application bundles, code repositories, database files.

An exclusion list covers files that match a document extension but must never be ingested:

- KeePass databases
- PKCS#12 certificate bundles
- private keys
- BitLocker recovery keys
- filenames matching a sensitive-name regex (`password`, `credential`, `secret`, `api key`, `private key`)

The exclusions are a security boundary, and over-exclusion is the safe direction. The walker streams through `os.walk` instead of `sorted(rglob())`, which would build all 470k paths before yielding the first.

## Text extraction

One extractor per file type, dispatched by extension through a registry. Each writes to a text cache on local NVMe, keyed by sha256. After the first full scan, a re-scan of unchanged files hits the cache at every stage.

- An extractor that fails raises `ExtractionError`, and the CLI marks the file `failed` in the ledger and moves on.
- A scanned PDF (under 270 characters of extracted text per page) raises `ScannedPDFError` and goes to an `ocr_pending` lane for a later tesseract pass.
- Legacy Office formats (.doc, .ppt, .xls) go through headless LibreOffice with a 120-second timeout. They take ~1-2 seconds per file and an occasional file hangs the process.

A junk gate runs before the LLM sees a document. A document above 10,000 characters whose lines are more than 90% delimiter-dense (three or more commas, tabs, semicolons or pipes) is marked `skipped`. These are marketing recipient spreadsheets and lead-list CSVs, which would otherwise cost hundreds of LLM calls for no knowledge. The 10,000-character floor keeps small real tables (grade sheets, address books) in, since below it a document costs at most two chunks.

## Entity and relation extraction

Each document's cached text is split into 6,000-character chunks with a 400-character overlap, at paragraph boundaries where possible. Each chunk goes to the local LLM at temperature 0 with thinking disabled (`reasoning_effort: none`, `chat_template_kwargs: {enable_thinking: false}`). Strict-JSON extraction gains nothing from chain-of-thought, and thinking traces cost 5-10x latency on the default preset.

The prompt:

- asks for five entity types (Person, Org, Place, Topic, Date) and relations as `{subject, predicate, object}` triples
- requires subject and object to appear in the chunk's entity list
- asks for canonical names for the same entity across chunks
- asks for an empty extraction when a chunk has nothing extractable

The type vocabulary stays small because exotic types become resolution debt later.

### Output contract

llama-server presets get a `json_schema` response format derived from the pydantic model, with `additionalProperties: false` and both `entities` and `relations` required, so the grammar cannot let the model answer `{}`. NInfer presets return empty extractions with any response format when `reasoning_effort: none` is also set, confirmed by live probe on 2026-10-16. On those presets the `response_format` field is omitted and per-item validation in the client is the only schema guard.

### Validation and failure handling

The client finds the outermost `{...}` in the response, since models sometimes wrap JSON in prose or Markdown fences, then validates each entity and relation on its own. A malformed item is dropped and the rest of the chunk is kept. At temperature 0 a retry would return the same malformed item, so one bad relation cannot sink a chunk. A chunk with no valid items is not an error, which is normal for prose with no named entities.

## Storage

The graph, the document ledger and the chat history are separate tables in one Postgres database.

The document ledger (`documents`) has one row per scanned file:

- relative path, extension, size in bytes, sha256, modification time in nanoseconds
- the pipeline stage: `new`, `extracted`, `graphed`, `failed`, `skipped` or `ocr_pending`
- an error column

Each stage writes its outcome back to the same row, so the drain is resumable.

| Table | Columns | Notes |
|---|---|---|
| `entities` | `(id, type, key, name)` | Unique on `(type, key)`, where `key = canonical_key(name)` (case and whitespace normalised). A re-mention upserts the name and returns the existing id. |
| `mentions` | `(document, entity_id, role)` | Unique on `(document, entity_id)`. Links an entity to a document, with an optional role. |
| `relations` | `(subject_id, predicate, object_id, source)` | Person-to-Person only at 2026-10-20. The LLM's free-text predicates are not yet canonicalised, so other entity types wait for that pass. |

The owner entity is seeded once and linked from chat identities across sources. Every other entity comes from document extraction. The graph is reset whenever the extraction model changes, because mixing models in one graph gives inconsistent relations. The 719 documents graphed under the previous model were reset to `extracted` before the current model ran.

### Hub-safe traversal

Traversal uses level-set recursive CTEs with `UNION` deduplication on `(id, depth)`, never `UNION ALL`. The owner entity appears in every document, so it is a hub of degree N for N documents, and any depth-2 neighbourhood from it reaches every other entity. Path enumeration there explodes: 65,721 ms on a degree-917 hub in the earlier demo corpus, against 155-159 ms for the level-set form. Both figures were measured in that demo and recorded in the source notes.

## Agent access: MCP server

A read-only MCP server over stdio exposes the graph to the coding agent. It connects per call with `default_transaction_read_only=on`, so the server has no write path. Schema application lives in the main pipeline, which this server never calls. Connecting per call means a Postgres connection flap fails one tool call and does not wedge the MCP session.

| Tool | Returns |
|---|---|
| Status | Pipeline stage counts, entity, mention and relation totals |
| Search entities | Entities matching a name substring, with type filter and mention counts |
| Dossier | One entity's type, dated mentions across documents, relations in and out |
| Cross-document entities | Entities appearing in N or more documents, with the corpus bridging rate |
| Related entities | One-hop edges or a two-hop level-set neighbourhood |
| Timeline | One entity's mentions ordered by document modification time |
| Document | One ledger row: stage, size, modification time, error, extracted entities |
| Search messages | Full-text search over chat history |
| Conversation | One conversation by id or title substring, oldest first |
| Person history | Chat identities matching a name across all sources |

The server is registered in the agent's configuration with deferred exposure, so its tools appear only when the agent searches for them and the per-turn prompt stays smaller. The database connection string is injected through a `sops -d --extract` substitution at process start, so no secret sits in a tracked configuration file.

## Chat history lane

A separate ingestion path, structured only, with no LLM extraction. Chat-history exports are parsed into a source-neutral model and written to the same database:

| Table | Holds |
|---|---|
| `identities` | One row per handle per source |
| `conversations` | One per chat |
| `participants` | Join table |
| `messages` | Message text, with a generated `search_tsv` column and a GIN index for `websearch_to_tsquery` |

Ingestion is idempotent. Re-running a source deduplicates on a hash of the raw source values, or on per-message ids where the source has them. The owner's identity across sources links to the same Person entity in the document graph, so a person who appears in both chat history and documents resolves through one entity id.

## Privacy: no hosted endpoint

At 2026-10-20 every stage ran on the dev box. The LLM endpoint was the local llmc proxy at `127.0.0.1:11434`, an OpenAI-compatible HTTP API over the llama-server engine on the local GPU. The extraction model was Qwen3.8 27B dense, loaded as a preset on that proxy.

No hosted LLM endpoint (OpenRouter, Anthropic or any cloud API) receives document content by default. The configuration points at the local proxy, and a cloud endpoint is a documented opt-in per folder set, not a config switch. Agent work that touches document content runs in local-model background workers, never in a cloud-model parent session. The parent sees aggregates only: pipeline status, counts, and error classes with the model's output stripped.

The text cache and the Postgres database both live on the local network. The database port is tailnet-only, and the archive is read-only over its mount.

## Throughput and the drain

The pipeline was measured on a local RTX 5090 (32 GB VRAM) with two requests in flight. The extraction model was `qwen38-swift-ninfer` (Qwen3.8 27B dense, NVFP4 on NInfer), picked on 2026-10-16 in a three-model bake-off (next section). The bake-off measured documents per hour under the production chunking and junk gate: 485 for `qwen38-swift-ninfer`, 409 for `summarizer`, 107 for `gemma4`. These are end-to-end, including extraction, chunking and graph writes.

The August 2026 partial drain ran ~45 docs/hr with one request in flight. The graph stage was single-request then because its semaphore never admitted a second request, leaving the preset's second slot idle. The current pipeline runs two. The model changed as well as the concurrency, so 45 -> 485 is not a clean before/after.

The archive holds ~12.6k documents, so a full drain at 485 docs/hr is roughly 26 hours. `drain.sh` was resumable: it ran scan and extract, then a `while` loop on the graph stage under an llmc preset lock, renewed every 5 minutes and released on exit. A crash or Ctrl-C re-ran from where it stopped, and scan and extract were cache hits after the first run.

- The extraction preset must stay locked during the drain. Another llmc client can otherwise evict it mid-run, which wipes the prompt cache and forces a full re-prefill on the next request. The script locked the preset with an owner tag.
- An LLM outage is recoverable. The 1-token probe described above decides between aborting the run and marking one document `failed`, and the `until` loop in the script retried the graph stage on any non-zero exit.

## The extraction model was not evaluated

The first extraction model, `summarizer` (Gemma 4 26B-A4B Q4_K_M), was chosen on 2026-10-04 as a continuity pick. It ran 719 documents by 2026-10-14 without a quality test. Nothing in the session history, the plan documents or the agent memory records compared it with any alternative.

On 2026-10-16 a three-model bake-off ran 29 stratified documents through each model at production settings. A Qwen judge and a Gemma judge both scored the output.

| | `summarizer` (old) | `qwen38-swift-ninfer` | `gemma4` |
|---|---|---|---|
| Entities per document | 38.4 | 25.6 | 36.7 |
| Relations per document | 20.4 | 14.8 | 18.5 |
| Entity names grounded in text (fraction) | 0.87 | 0.75 | 0.86 |
| Relation correctness, Qwen judge / Gemma judge (fraction) | 0.27 / 0.24 | 0.51 / 0.44 | 0.30 / 0.28 |
| Relations with reversed direction, Qwen judge / Gemma judge (fraction) | 0.25 / 0.25 | 0.00 / 0.00 | 0.17 / 0.08 |
| Documents per hour | 409 | 485 | 107 |

Both judges agreed that the Qwen model had the most correct relations and no reversals, while `summarizer` reversed a quarter of its relations. `summarizer` had better entity coverage and grounding (0.87 against 0.75), and the Qwen model produced four empty extractions out of 29 documents. The user chose on relation correctness and replaced the old model, resetting the 719 graphed documents to `extracted` so the graph comes from one model.

The sequence was: pick for continuity, drain ~720 documents without evaluation, then measure and find a quarter of the relations reversed. A config value, a commit and a plan document all record a choice, and none of them shows it was compared. The [agent guard extensions page](/reference/agent-guard-extensions/) covers the epistemic guard rule that follows from this ("a recorded choice is not an evaluated one"), and the [agent model routing page](/reference/agent-model-routing/) covers the effort rule for high-stakes work.

## What carries over

The archive size, the model and the GPU belong to this setup. These choices do not:

- An extension allowlist beats a denylist on a personal archive that is mostly non-documents.
- A sha256-keyed cache means a restart or a model change re-runs only what changed.
- Identity by `(type, canonical_key)` handles case and whitespace variation and keeps types apart.
- Per-item validation keeps the good items from a chunk that also holds a malformed one.
- Evaluate the extraction model on a sample, with a judge from another model family, before draining the corpus.

1. Sensitive documents (medical, insurance, identity) in scope: extraction runs on the local model. A hosted endpoint is an explicit, documented opt-in per folder set, never a config default.
2. No sensitive documents: either endpoint works, and local stays the default.
3. Agent work that reads document content (failure triage, extraction spot checks, judge passes) runs in local-model workers. A cloud session sees aggregates only: status, counts and error classes with the model's output stripped, because a stored error can quote document text.
