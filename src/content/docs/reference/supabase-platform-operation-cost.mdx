import { Aside } from "@astrojs/starlight/components";

A restart, a compute resize, a network restriction, provisioning a fresh
project, and moving one between organizations each interrupt a client
differently: on a different connection path, for a different duration, by a
different failure mode. A plan that assumes "a restart takes about a minute"
can be checked here, per path, against what happened.

<Aside type="caution" title="What this is and is not">
The restart, resize and network-restriction figures below were measured
2026-08-04 against my own organization, on throwaway Micro projects in
`ap-southeast-1` created and destroyed for the purpose, from an IPv4-only
vantage in Singapore, sampling every 500 ms. That resolution does not hold
for every path - see [Sampling resolution is not uniform
either](#sampling-resolution-is-not-uniform-either).

Each operation is n=1 except the network restriction, which ran twice with
the same result, and the restart, which was re-checked n=5 on 2026-10-10 on
another Micro project (see [the matrix](#what-breaks-and-for-how-long)). These
are observations from one account, not a distribution, and not a claim about what anyone else would see. A second run would move the
seconds.

The provisioning and project-transfer figures further down come from other
days, runs and projects; each of those sections carries its own date, method
and n.

Rows read from an API rather than measured are labelled; rows that were not
tested are named as untested.
</Aside>

**TL;DR:**

- REST and Realtime never failed under restart, either resize direction, or the
  network restriction. Auth, Storage and the pooler did, for different
  durations and by different failure modes.
- A resize costs more than a restart, but not by a constant factor: Auth 131 s
  against 75 s is 1.75x; the pooler 207 s against 158 s is 1.31x. Those are
  Micro to Small. A Medium to Large resize on another project took Auth 35 s,
  Storage 34 s and the pooler 30 s, with REST and Realtime untouched again
  (medium-serverless MS07, 2026-09-30).
- A network restriction reaches the pooler in ~1 s and never touches the HTTP
  tier. The reported 62 s window is mostly a chosen 60 s test dwell, not a
  platform duration.
- A restart re-checked on 2026-10-10 (n=5, one Micro project) had REST never
  failing, Auth 54 s, Storage 58 s, pooler 54 s and direct 50 s at p50, so the
  n=1 D01 figures of 75, 78 and 158 s are one observation of a window that was
  about 30 s in two of five re-check runs and 50 to 60 s in the other three.
- The restart-pooler window (158 s) fails by a 5 s timeout (`TIMEOUT_MS = 5000`
  in `probes.ts`), so it carries multi-second resolution despite the rest of
  the matrix sampling at 500 ms.
- pg_cron jobs resume across a restart on schedule, with no catch-up
  doubling - a 1/min heartbeat job had 2 rows before the restart and 5
  after, measured separately
  ([supabase-lab](https://github.com/erfianugrah/supabase-lab)
  edge-resilience W23, 2026-08-16).
- Provisioning a fresh project to `ACTIVE_HEALTHY` took 131-159 s (n=5);
  moving a project into a Free organization cost 75.2 s continuous, because
  the instance resizes to Nano on arrival.

## Method

One probe per connection path - PostgREST, Auth, Storage, Realtime, and the
pooler on 6543 - each sampled independently every 500 ms while the operation
was triggered out of band.

What counts as answering differs per path.

| Path | Counts as answering |
|---|---|
| PostgREST, Auth, Storage | any HTTP status other than a 5xx |
| Realtime | the WebSocket handshake completes |
| pooler (6543) | a connection opens and `select 1` returns |

The HTTP rule is loose on purpose: anon receives a 401 from `/rest/v1/` and a
400 from Storage without a bearer, so a probe demanding 200 would report a
permanent outage on two paths. The pooler's rule is stricter.
`EADDRNOTALLOWED` under a network restriction is a reply - the pooler is
reachable and refusing - but it is scored as a failure, because the probe asks
whether a query reached Postgres.

Recovery required five seconds of sustained success rather than one passing
sample. The reported recovery time is the first sample of that sustained run;
the settle period confirms recovery and is not counted into the outage.

A path already failing before the operation voided that row.

The direct port 5432 was not tested: it is IPv6-only and unreachable from
this vantage, so there is no unpooled baseline here.

## What breaks, and for how long

REST and Realtime never failed under any of the four operations sampled here,
so whatever insulates the read path from a restart insulates it from a resize
as well; the paths do not move together, and a single duration for
"a restart" or "a resize" throws away which path failed, for how long, and by
what failure mode.

| operation | REST | Realtime | Auth | Storage | pooler |
| --- | --- | --- | --- | --- | --- |
| restart | - | - | 75 s | 78 s | 158 s |
| restart, re-check 2026-10-10 (LO05, p50 of 5) | - | not sampled | 54 s | 58 s | 54 s |
| network restriction | - | - | - | - | see below |
| resize up (micro -> small) | - | - | 131 s | 127 s | 207 s |
| resize down (small -> micro) | - | - | 99 s | 100 s | 196 s |
| resize up (medium -> large) | - | - | 35 s | 34 s | 30 s |
| resize down (large -> medium) | - | - | 42 s | 44 s | 39 s |

A dash is zero failed samples. The Medium rows come from a different project
and day (medium-serverless MS07, ap-southeast-2, 2026-09-30, n=1 each
way); their pooler column is Supavisor 6543, and the same run watched four
more paths (up / down): shared 5432 36 s / 39 s, dedicated PgBouncer 6543 34 s / 55 s,
direct 5432 35 s / 41 s, and REST and Realtime with zero failed samples
both ways. The dedicated pooler was the last path back on the way down,
answering `server login has been failing, cached error: connect failed
(server_login_retry)` for about 14 s after Postgres was up. The restriction row has no duration because its
window is a test parameter; the
[network restriction section](#the-network-restriction-only-reaches-the-pooler)
has the dwell and what was measured around it.

The restart row above is n=1 (D01, 2026-08-04). The re-check row is a separate
run on 2026-10-10 (LO05): one Micro project in `ap-southeast-1`, restarted five
times in sequence, each after a readiness check, from one macOS orchestrator
with IPv6, with REST, Auth, Storage, the pooler on 6543 and the direct port
5432 sampled every 0.5 s. Realtime was not sampled, hence its cell. The figures
are the p50 of the five windows; the direct path, which D01 could not reach, had
a p50 of 50 s.

| path | runs with a failure | window p50 | window max |
| --- | --- | --- | --- |
| REST | 0 of 5 | - | - |
| Auth | 5 of 5 | 54 s | 60 s |
| Storage | 5 of 5 | 58 s | 59 s |
| pooler (6543) | 5 of 5 | 54 s | 151 s |
| direct (5432) | 5 of 5 | 50 s | 56 s |

- The first failed sample came 2-3 s after the `POST /restart` on every path
  that failed (direct: p50 3 s, max 3 s), which matches the 2 s bite time of
  D01. `POST /restart` answered 200 in about a tenth of a second each time.
- The control plane read `ACTIVE_HEALTHY` again at 40, 41, 61, 61 and 71 s on a
  10 s poll, ahead of the data plane in at least one run: in run 2 the status
  read `ACTIVE_HEALTHY` at 41 s while the pooler window ran to 151 s. A script
  that waits for `ACTIVE_HEALTHY` can hand traffic to a pooler that has not
  recovered.
- The windows split into two groups. Runs 1 and 2 were about 30 s on every path
  except the pooler's 151 s in run 2; runs 3 to 5 were 50 to 60 s on every path
  (Auth 32, 31, 54, 59, 60 s by run; pooler 31, 151, 52, 54, 59 s). Five
  sequential restarts of one project cannot separate drift across back-to-back
  restarts from platform load or chance.
- The 2026-08-04 pooler figure of 158 s is close to this run's single 151 s and
  not to its other four. Different day, different project, and Realtime
  dropped: not a controlled comparison, and the re-check does not replace the
  D01 row.
- A second `POST /restart` sent while the status read `RESTARTING` returned 200
  with an empty body, as the first had (LO05c). Whether it queued a second
  restart or was absorbed into the first was not sampled.

How these windows read from a client, and the workarounds, is in [the incident
resilience reference](/reference/supabase-incident-resilience/); provisioning
and fleet operations through the same API are in [the platform Management API
guide](/guides/supabase-platform-management-api/).

On the same restart that left Auth unavailable for 75 s, both REST and Realtime
served continuously at 500 ms resolution. Auth and Storage also fail
differently from each other, `HTTP 521` against `HTTP 500`.

### Time to bite is not one number either

Bite time is measured from when sampling started, not from when the
operation's own API call returned: `sampleDuring` in `sampler.ts` sets `t0`
before the probe loops begin, and the operation runs inside that same sampled
window, so the reported time already includes however long that call itself
took to complete. It also differs by operation.

| operation | bite time, HTTP tier | bite time, pooler |
| --- | --- | --- |
| restart | 2 s | 2 s |
| network restriction | - | 1 s |
| resize up | 2 s | 3 s |
| resize down | 2 s | 3 s |

None of it is a flat 2-3 s range, and none of it is measured against the
API's response.

### The explanation this suggests, which was not tested

The obvious reading is that the four HTTP services reach Postgres from inside
the project and a client's connection terminates at the service, while a
pooled client's socket sits much closer to what is being restarted or resized.

That is an inference from the result, not something measured here. It is
drawn because it predicts the ordering, not because the topology was
inspected.

## Resize costs more than a restart, unevenly

Auth was down 75 s restarting and 131 s resizing up, 1.75x. The pooler was
down 158 s restarting and 207 s resizing up, 1.31x. The two ratios are far
enough apart that neither stands in for the other.

Direction matters unevenly too. On the HTTP tier, growing costs about a third
more than shrinking: Auth 131 s up against 99 s down. On the pooler the two
directions are closer, 207 s up against 196 s down, which is +5.6% and just
outside 5%.

Compute size is set by an addon mutation rather than a resize endpoint: `PATCH` on the project's billing addons with an `addon_type` of
`compute_instance`[^api-spec]. Returning to the smallest size REMOVES the
addon rather than setting one, and the subsequent read reports no compute
addon.

## The network restriction only reaches the pooler

Locking the database to a CIDR that excluded this vantage left REST, Auth,
Storage and Realtime serving - four paths, zero failed samples, across two
runs. The restriction controls database sockets and leaves the HTTP tier
alone.

It did reach the pooler, biting 1 s after sampling started, with a refusal
that named the rejected address. The restriction covers the pooled port as
well as a direct connection.

<Aside type="note">
The outage DURATION here is an artifact of the test rather than a property of
the platform: the probe holds the restriction for a fixed 60 s dwell
(`DWELL_MS` in `d02-restriction-flip.ts`) before restoring it, so the measured
window is that dwell plus the ~2 s to recover - about 62 s total. What was
measured about the platform is the ~1 s to bite and the ~2 s to recover; the
60 s in the middle was chosen, not observed.
</Aside>

## The pooler answers differently for each operation

| operation | pooler error |
| --- | --- |
| restart | `Failed to connect to database: {:error, :timeout}` |
| network restriction | `(EADDRNOTALLOWED) address not in tenant allow_list` |
| resize up | `Failed to connect to database: {:error, :econnrefused}` |
| resize down | `terminating connection due to administrator command` |

Only the last is a Postgres message; the others come from Supavisor. In all
four operations the pooler itself answered, reporting the backend unavailable
a different way each time: unreachable, refused, deliberately shut down, or the
client not permitted.

## Sampling resolution is not uniform either

The probe timeout is 5 s (`TIMEOUT_MS = 5000` in `probes.ts`), and each
path's sampler loop is serial: `await probe.run(); await sleep(intervalMs)`.
A sample that fails BY TIMEOUT can take up to that full 5 s to return, before
the 500 ms sleep between samples even starts.

Bite time is recorded against when a sample STARTS, not when it returns (see
[Time to bite is not one number
either](#time-to-bite-is-not-one-number-either)), so a slow-to-return timeout
does not push the reported bite time later. It does delay every sample after
the first failure: on a path that keeps timing out, the next attempt
cannot start until the previous one has waited out the full timeout. The
loop's period becomes the 5 s timeout plus the 500 ms sleep, so a path stuck
in timeout mode is resampled about every 5.5 s, and the recovery boundary is
only located to within that interval.

The restart's pooler mode is `{:error, :timeout}` - a timeout, not a fast
refusal. Its bite (2 s) was recorded on a sample that started while the
previous sample had still returned fast, but for the rest of the 158 s window
the pooler was resampled at roughly 5.5 s intervals rather than 500 ms. The
158 s therefore carries several seconds of slack at the recovery end.

Fast-failing modes are unaffected: `econnrefused`, `EADDRNOTALLOWED`,
`HTTP 521` and `HTTP 500` all return immediately rather than waiting out the
timeout, so those windows keep 500 ms resolution throughout.

The ~2x difference between the pooler and the HTTP tier on restart survives
this: 158 s and 75-78 s are tens of seconds apart whichever side of the gap
carries more slack. It does mean the numbers on this page do not share one
sampling resolution.

The 2026-08-04 gap is one run. In the 2026-10-10 restart re-check (LO05, n=5)
the pooler's p50 window was 54 s against 54 s for Auth and 58 s for Storage, and
its window was longer than Auth's in 1 of the 5 runs (run 2: 151 s against 31 s,
derived from the per-run windows). A pooler that is reliably about twice the
HTTP tier is therefore not a figure to carry from one restart.

Every published figure is also rounded to a whole second: `flatten()` divides
each millisecond count by 1000 and rounds before it is reported, so a window
described as "158 s" was some value between 157.5 and 158.5 seconds in the
raw sample data.

## What this rig could not measure

A freshly created project comes up already at the latest app version:
`eligible: false`, current equal to latest, no upgrade targets. The version
selectors on project creation are deprecated and typed null in the published
schema[^api-spec], and the project this rig created took the current default,
so the version fields give no way to create one that has already aged past its
version.

A field typed null is not necessarily ignored. Measured 2026-10-10 on one Small
project per engine in `ap-southeast-1` (OR01a, OR01b), `postgres_engine` is
typed deprecated null on the create body in the published OpenAPI
document[^api-spec], yet `POST /v1/projects` with `postgres_engine: "17-oriole"`
was accepted and applied. The project read back `17-oriole`, PostgreSQL 17.6,
aarch64, `OrioleDB public beta 14`, while the heap control, created without the
field, read 17.11 on x86_64. `release_channel` is typed the same way on that
body; whether a non-default value of it is honoured was not tested. The engine
field selects a different build line rather than an older copy of the default
one, and the upgrade eligibility of the Oriole project was not read, so the
aged-project limitation below still holds.

Measuring a client-visible upgrade window therefore needs a project that has
aged past the current version, which this rig's throwaway-project method
cannot produce. That limits the rig and says nothing about how long an
upgrade takes a client.

Without upgrading anything, the eligibility payload carries
`duration_estimate_hours`, which returned 1 on each of three aged projects
in this organization, all offering a single patch-level target with no
validation errors. That is a value the API returned, not an observed outage -
and this page has already shown paths differing by more than 2x on the same
operation. Three projects returning exactly `1` also reads like a coarse,
published estimate rather than a per-project computation.

## What a fresh project costs before its first write

Measured 2026-08-04 against a live organization, n=5, in [the multitenant
reference](/reference/supabase-multi-tenant-placement/) - a separate run from
the restart/resize/restriction matrix above, on the same day but a different
project set.

| Operation | Measured | Method |
| --- | --- | --- |
| Create project -> `ACTIVE_HEALTHY` | 131-159 s (n=5, median 131 s) | poll `GET /v1/projects/{ref}` |
| `ACTIVE_HEALTHY` -> first write succeeds | +1 poll tick (5 of 5 refused the first write) | poll, then retry the write |
| Delete project (API call) | ~2 s | `DELETE /v1/projects/{ref}` |

`ACTIVE_HEALTHY` was not writable on any of those five projects: each refused
its first `POST /auth/v1/admin/users` with `500 unexpected_failure` and
accepted the next attempt, one poll tick later. A script that provisions a
project and immediately creates a user has to retry.

Two lifecycle runs on 2026-10-10 (LO03, LO05a; one Micro-requested project per
create in `ap-southeast-1`, one Pro organization, a different day and project
set from the table above) read differently, and the two sets are unreconciled:

| Operation | Measured 2026-10-10 | Method |
| --- | --- | --- |
| Create -> `ACTIVE_HEALTHY` (LO03, n=3) | at the first 10 s poll twice (2 s after the POST), at 145 s once (`COMING_UP` at 3 s) | 10 s poll from before the POST |
| Project that read healthy at the first poll (LO05a) | REST, Auth, Storage, pooler and direct all answered 5 s after that poll | one probe of each path |
| Create call (LO03) | 2358, 1499 and 1656 ms | time of the `POST /v1/projects` call |

The earlier table has 131-159 s in 5 of 5 creates and a refused first write
in 5 of 5; this run has an immediate `ACTIVE_HEALTHY` in 2 of 3 and, in the one
immediate case that was probed, every path answering. The lifecycle run records
probe answers, not a write, so the two do not test the same thing on the
write side, and n=3 says both a 2 s and a 145 s create happen rather than how
often. The size actually applied was not read back, and no cause for the
difference was found.

A restart sent right after a create was refused in one observation (LO05f) and
accepted in another:

- About 70 s after the creating `POST`, on a project handed over from the
  duplicate-create check below, `POST /v1/projects/{ref}/restart` answered
  `400` with `Project restarts are only allowed ten minutes after the creation
  process has completed.` followed by text the artifact cut off. The 70 s is
  read off the timestamps of two modules, not timed by one.
- 300 s after the first `ACTIVE_HEALTHY` read, on a different project, a restart
  was accepted (200, empty body) and restarted the project. The runs that
  followed, from 696 s after that read, were accepted with no refusals.

The message says ten minutes and a restart at 300 s went through, so either
the stated window is not what is enforced or the clock it runs from ("the
creation process has completed") is not the first `ACTIVE_HEALTHY` read. The
boundary between about 70 s and 300 s is unresolved, and the two observations
are on two projects.

Create bodies that are invalid fail fast and create nothing (LO03a, one
request each, 55-194 ms):

| Request | Answer |
| --- | --- |
| unknown region code | `400` `region_selection.code: Need to use one of available regions.` |
| unknown organization slug | `404` `Not Found` |
| missing `name` | `400` `name: Invalid input: expected string, received undefined` |
| unknown instance size | `400` `desired_instance_size: Need to use one of available instance sizes.` |

The organization listing held no project with the run's name tag afterwards.
A create whose response the caller abandoned does create the project (LO04,
n=1): with the client wait capped at 1 s, the `POST` timed out client-side,
and the listing then held one project with that name. The identical request
re-sent 1 s later answered `400` in 0.17 s with `Project with name "<name>"
already exists in your organization.`, and 60 s later there was still one
project with that name, `ACTIVE_HEALTHY`. A client that retries after a lost
response therefore has to read that 400 as "probably created, look it up by
name". A retry wrapper that adds a random suffix per attempt would create a
second project; that consequence is reasoned from the 400, not run. Not
measured: whether the name match is case-sensitive, whether a name freed by
`DELETE` is reusable at once, and two concurrent identical requests.

## What moving a project between organizations costs

Measured 2026-08-03 against live projects moved between a Team-plan, a
Pro-plan and a Free-plan organization, polling `/auth/v1/health` every 250 ms
across each move, in [the org-consolidation
guide](/guides/supabase-org-consolidation/) - a separate run from both tables
above.

| Direction | Measured |
| --- | --- |
| Paid to paid | 2.3 s, no outage above the probing host's noise floor |
| Paid to Free | 75.2 s continuous |

A Free organization only offers Nano compute[^sb-pricing], so the instance is
resized on
arrival; during that window the edge returns `HTTP 521` and `HTTP 525` rather
than a clean `503`. The 75.2 s is the arrival resize, charged to the transfer;
a paid-to-paid move produces no data-plane interruption distinguishable from
measurement noise.

## What a restore costs

Measured 2026-10-10 on throwaway projects in `ap-southeast-1`, driven over the
Management API and the shared pooler from one IPv4-only workstation (RP01 to
RP03). In the PITR runs REST, Auth and Realtime were probed every 1 s, the
pooler by a login every 5 s, and the project status every 10 s; the Free runs
polled status every 5 s for pause and every 10 s for unpause. A separate run
(RP01) read which restore routes a Pro project exposes and timed nothing, so it
has no row in any table above. The tiers, what a restore does not bring back, and the cost of
each are in [the DR tiers reference](/reference/supabase-dr-tiers/); this
section adds the per-path outage of the two restores a lab organization could
drive.

### Point-in-time restore on Small

PITR needs at least Small compute[^sb-backups]. The subject was a Pro project
on Small with the `pitr_7` add-on, a 2 GB gp3 disk, a seed row, a bucket and
an object (RP02, five runs). Each run chose a target instant, rotated the
database password 15 s later, inserted a second row and called
`restore-pitr`; a control then rotated again, chose a target after that
rotation and restored again. That is 9 clean restores: 4 with a target before
a rotation and 5 controls.

| Restore | Back to `ACTIVE_HEALTHY` (10 s polling) | n |
| --- | --- | --- |
| target before a rotation, 10 MB database | 30 s | 3 |
| target before a rotation, 574 MB database | 81 s | 1 |
| control, target after a rotation | 40, 30, 41, 40, 30 s (median 40 s, 30-41 s) | 5 |

Two of the five controls ran on larger databases (715 MB at 41 s, 574 MB at
40 s), so the 81 s at 574 MB is a single point.

| Path | Failed samples across the 9 clean restores |
| --- | --- |
| REST, Auth, Realtime (1 s probes) | none |
| Storage | a 12 s failure window in 8 of 9 restores, 24 s in one; `The operation timed out`, never an HTTP 5xx |
| pooler (5 s login poll) | 5-13 s on the 10 MB runs and on a 715 MB control; 41 s and 23 s on the 574 MB runs |

REST, Auth and Realtime recorded one simultaneous timeout on all three, 338 s
after the first restore request of the 574 MB run, with no recovery recorded
and no explanation. The pooler errors were `the database system is not
accepting connections`, `is starting up`, `is shutting down`, `econnrefused` and
`terminating connection due to administrator command`. The 41 s pooler window
sat on the 574 MB database and the 5-13 s one on a 715 MB database, so the
database size does not order them.

- The first `restore-pitr` call was refused in 8 of the 9 clean restores with
  `400` `Recovery time target must be within range: <earliest> <= t <=
  <latest>`; where the target was recorded it sat 19-96 s past the quoted upper
  bound. A retry 60 s later (or 121 s later) was accepted. Retries ran in 60 s
  steps, so the lag is bounded and not resolved.
- With `pitr_7` just applied, the first backups read already had
  `pitr_enabled=true` and a window of 359 or 360 s in 5 of 5 runs.
- After every clean restore the current password logged in through the pooler
  and the replaced one was refused. The current password was refused for one 5 s
  poll between "the database answers" and "the password works" in 6 of 7
  restores observed at that resolution: a short stale window of
  unmeasured length. The changelog says current credentials are reapplied after every
  physical restore[^sb-restore-creds], and the stored verifier differed from
  both the pre-rotation and post-rotation value each time, which is what that
  predicts (an inference from fingerprints).
- Storage listed, downloaded (bytes equal) and accepted an upload with `200`
  after every restore. A restore to before an object's upload made its download
  `404` and the listing omit it, and writing the same path again answered `200`.
- Every target was minutes old. A target hours or days old, a database over
  1 GB and direct 5432 were not run. Seeding a 1500 MB database on the 2 GB
  disk filled it at 715 MB, and the first restore request after that was
  refused as `Database appears to be unreachable` and accepted at 301 s; what
  filled the disk was not separated.
- A poller that tried a known-wrong password every 4 s plus a 1 s probe opened
  the pooler's circuit breaker within about a minute, and every login, the
  correct password included, then answered `(ECIRCUITBREAKER) too many
  authentication failures, new connections are temporarily blocked` before the
  password was checked. The poller moved to once a minute for the replaced
  password, and the breaker reappeared only in the state left by the full disk
  above.

### Free pause and unpause

A Pro organization has no pause (`POST /pause` answers `400 Project is not
free-tier`, entitlement `project_pausing` false on the Pro organization, RP01),
so the only pause and unpause a lab organization could run was a Free project
(RP03, 3 runs of 2 cycles = 6 cycles, one project per run).

| Measurement | 5 of 6 cycles | The outlier cycle |
| --- | --- | --- |
| `POST /pause` -> `INACTIVE` (5 s polling) | 62, 62, 62, 63, 62 s | 276 s |
| unpause -> `ACTIVE_HEALTHY` (10 s polling) | 183-212 s | 444 s |

## What a password change and a config change cost

Measured 2026-10-01 on one Micro project in ap-southeast-1
(platform-downtime D05), a separate run from the tables above: one
`PATCH /v1/projects/{ref}/database/password` to a throwaway value, then
PostgREST, Auth, Storage and Realtime sampled every 500 ms for a 420 s
window, with the password restored afterwards. `pg_postmaster_start_time()`
read `2026-10-01T06:38:25.763Z` before and after the window, and none of the
four paths recorded a failed sample. On that project the password change did
not restart Postgres within the 420 s window. The pooler was not probed: its
probe authenticates with the password being changed, so a failure there could
not be told apart from a stale credential. n=1, on a project provisioned with
OpenTofu through the Management API; a project whose database credentials an
integration syncs was not tested.

A Postgres config change through the CLI is documented rather than measured
here. The custom-config docs say CLI v2 "checks the parameter's context and
requests the correct action (reload or restart)": a reloadable setting
(`pg_settings.context = 'sighup'`) is applied with a reload, and parameters
marked "Restart: Yes" restart the database and any read replicas[^sb-pg-config].
`--no-restart` defers that restart; the docs warn that leaving a changed
parameter pending can break a read replica if the primary or the replica
later restarts on its own. `max_wal_size` and `work_mem` are listed
"Restart: No". Whether a "Restart: No" change ever restarts the database was
not measured.

Whether a platform restart keeps Postgres's cumulative statistics
(`pg_stat_checkpointer`, `pg_stat_statements`) was not measured here.
Locally, how a stop ended and the Postgres major version decided it for
`pg_stat_checkpointer` (`pg_stat_statements` was not measured); those
measurements are in
[the Grafana monitoring guide](/guides/supabase-grafana-monitoring/).

## Reading the numbers

**n=1 per operation, except the restriction and the restart re-check.** One run
each for restart (D01) and both resize directions, two runs for the network
restriction, all on projects in a single organization; the 2026-10-10 restart
re-check (LO05) is five restarts of one other project. The ordering repeated
across every operation and project in the 2026-08-04 matrix, and REST staying
up repeated in the re-check (5 of 5); the pooler being the slowest path did
not (1 of 5 runs). The individual seconds are not worth much confidence either:
the same restart read 75 s on Auth in D01 and 54 s at p50 in LO05.

**500 ms resolution, except where the pooler times out.** The HTTP tier and
the non-timeout pooler modes were sampled every 500 ms. The restart-pooler
window fails by a 5 s timeout and was resampled at that timeout's cadence for
most of its duration, not at 500 ms - see [Sampling resolution is not uniform
either](#sampling-resolution-is-not-uniform-either).

**One vantage, IPv4, one account.** The direct port was never in the matrix,
so the pooler column has nothing unpooled to compare against, and every
restart/resize/restriction figure here is from a single organization in
`ap-southeast-1` observed from Singapore.

**Provisioning and transfer are separate sessions.** The 131-159 s
provisioning window and the 75.2 s paid-to-Free transfer window were measured
on different days, by different runs, against different projects than the
restart/resize/restriction matrix above - each section carries its own date
and method.

The result supports that these paths, on these operations, did not move
together on this account, in this region, on these dates. It does not support
any figure for a different region, plan, project size, or point in time.

## The rate budget your polling runs against

Every method in this doc polls the Management API to watch an operation, so
the API's own throttle is part of the rig's envelope. Measured 2026-08-17 on
a normal paid organization:

- every response carries `x-ratelimit-limit`, `x-ratelimit-remaining`, and
  `x-ratelimit-reset`, so the budget is readable off the wire. The limit read 120 and the remaining count decremented 1:1 per
  call on a scoped single-project read. The budget is cumulative across a
  user's PATs: alternating two tokens from the same user, each token's
  remaining count drops on the other token's calls - one shared counter
  per user per scope, so PAT sharding does not multiply it (measured
  2026-08-18).
- a deliberate burst on that cheap scoped read tripped
  `429 {"message":"ThrottlerException: Too Many Requests"}` at request
  118, with `retry-after: 60` and a clean 200 after the window. On this
  endpoint the 429 body is the API's own JSON. Other endpoints and burst
  shapes have produced an HTML page from the edge layer instead, so a client
  still treats "non-JSON body" and "JSON 429" as the same back-off signal.

At 500 ms sampling the rig spends 120 requests per minute per poller -
exactly the limit the response headers report - which is why the pollers here read
`x-ratelimit-remaining` rather than assuming the ceiling, and why a
platform polling a fleet has to budget per-scope, not per-process.

## Reproducing

Sample every path continuously while triggering the operation out of band,
and record the failure mode beside the duration.

Recovery has to require sustained success rather than one passing sample, and
the reported recovery time is the first sample of that sustained run, not the
end of it. The pooler queues before it refuses, so a single lucky probe
mid-outage otherwise registers as recovery.

A path already failing before the operation has to void that row, or a bad
credential reads as a platform outage.

A probe timeout that is comparable to the sampling interval coarsens
the resolution for whichever failure mode times out rather than fails fast -
know which modes do which before quoting a duration as sub-second.
