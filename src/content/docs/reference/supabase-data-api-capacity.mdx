How many database connections the Data API holds on a Supabase project, what a client gets back when every one of them is busy, what changing the pool costs, and which numbers the platform exposes about it. It is for whoever sizes a project for Data API traffic, sets `db_pool` or the statement timeouts, or alerts on the pool metrics, and wants the measured behaviour next to the documented one.

All measured rows come from the lab's [data-api-capacity experiment](https://github.com/erfianugrah/supabase-lab/tree/993cfae/experiments/data-api-capacity/), run 2026-10-22/23 against throwaway projects on a Pro-plan organization, each created through `POST /v1/projects` and deleted at the end of its run. Modules DC01-DC03 ran four times in `ap-southeast-1` on a project created Small and resized to Large; run 4 is the reference and its figures are quoted unless another run is named (runs 1 and 2 are published for their repeats, run 3 died in DC02 and wrote no artifact). DC04 ran once in `ap-northeast-2` on a Small project resized to 4XL, DC05-DC07 once in `ap-northeast-2` on Small, and DC08 once in `ap-northeast-2` on a Small project resized to 4XL. The project region came from an environment variable and is recorded in the RUNLOG (and in DC08a's artifact as the requested region); the artifacts' region field is the harness default and was not read from the project. Every request in DC01-DC07 came from one Mac in Singapore over the public internet, so those client times include the round trip (p50 141 to 150 ms to Seoul at low load); DC08's clients ran in the project's region ([below](#4xl-with-in-region-clients-and-a-mixed-load-dc08)). PostgREST 14.18 and Postgres 17.11 were read in DC04a's and DC08a's artifacts; for DC01-DC03 they come from console output, and DC05-DC07's artifact records neither. Most cells are n = 1 or n = 2; a row says when it is more. The figures are quoted from the [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/993cfae/experiments/data-api-capacity/RUNLOG.md) and the redacted run artifacts listed in [Modules](#modules). Rows marked documented come from the pages cited at the claim and were not run; rows marked source-read come from the PostgREST v14.18 source, and that the hosted build matches the tag was not checked.

**TL;DR:**

- With `db_pool` unset the Data API pool was 30 connections on Small, 50 on Large and 70 on 4XL (4XL from `pgrst_db_pool_max` and an open-backend count, no burst), against `max_connections` 90, 160 and 480. `GET /postgrest` reads `db_pool` null; I found no published table of these figures.
- A request behind a full pool answered 504 PGRST003 after 61364 and 61972 ms at the default 10 s acquisition timeout, and each left 6 PostgREST access-log lines. The reading is that a layer in front resent it five times; the public `supabase/postgres` Envoy config retries gateway errors 5 times, and whether hosted projects run it was not checked.
- Every accepted `PATCH /v1/projects/{ref}/postgrest` restarted PostgREST (9 start lines for 9 PATCHes), a no-change PATCH included, and so did one that answered 500. With 60 s requests in flight the restart line came 55.3 s after, about when they finished (a reading, twice), and new requests got no answer for about 50 s.
- Statement timeouts through the Data API: anon 3 s, authenticated 8 s, service_role 8 s inherited from `authenticator`. A function's own `set statement_timeout` wins for every key, and `alter role` reaches the Data API only after `notify pgrst, 'reload config'`. All as documented.
- One indexed point read from one Mac, anon key: Small stopped at 853 to 1,020 req/s from 256 concurrent clients on; 4XL reached 3,158 req/s at 512, then the client (os error 51) and 403s from an unidentified layer stopped the measurement. `db_pool` 15, 30 and 60 on Small gave 853, 902 and 909 req/s at 256, a difference not separated from the spread between repeats.
- In-region Edge Function clients with a mixed load (point, range, RPC, insert, `count=exact`) took 4XL to 6,148 req/s at c=3072, a step that added 5 % for about 25 % more requests in flight (derived; one run, one step, nothing above it run), with at most 7 of 71 `authenticator` backends active in that step (14 at most in the ramp). `db_pool` 150 and 250 did not raise throughput or lower p50 there, and p95 and p99 were higher (one step each). The generator under-delivered its requested concurrency.
- `pgrst_db_pool_waiting` counts a request from its pool request until its session ends, so it includes requests holding a connection and PostgREST's own pool sessions (schema cache, config reads), and `pgrst_db_pool_available` is open connections minus those in use (source-read; the snapshots agree). The series are a snapshot: no refresh landed in a 36 s window, and the pool max showed a PATCHed value after 1.4 s once and 28.9 s once. One 4XL snapshot read 1,078 waiting with 58 of 70 connections available at some moment in the first 33 s of the c=3072 step, and still read so 25 s after the load ended (n = 1).
- 60 statement-timeout cancellations caused by a 12.6 s table lock left no aborted pooled connection: 9920 requests answered 200 afterwards, 0 answered 25P02 (one run per arm, anon reads, 20 workers on a pool of 30, so nothing was queued for the pool).

## The pool with db_pool unset

The Management API documents `db_pool` as "If `null`, the value is automatically configured based on compute size" and `db_pool_acquisition_timeout` as "If `null`, the value is automatically configured to 10".[^sb-api-v1] Upstream PostgREST defaults `db-pool` to 10 and `db-pool-acquisition-timeout` to 10 seconds.[^pgrst-db-pool] The Supabase compute page lists Postgres max connections and pooler clients per size, not the Data API pool;[^sb-compute] I found no published table of the pool per size in that page, the connection management guide[^sb-conn-mgmt] or the Management API spec, read 2026-10-23.

The lab counted the pool as the number of `authenticator` backends (the Data API's login role[^sb-conn-mgmt]) sleeping in `PgSleep` in the middle of a burst of long RPCs larger than the pool.

| Size | `max_connections` | Pool, `db_pool` unset | How counted | Runs |
|---|---|---|---|---|
| Small | 90 | 30 | two bursts of 100: 30 / 30 sleeping, 31 `authenticator` backends in total; `pgrst_db_pool_max` 30 (DC04a) | runs 1, 2 and 4 (DC01a), DC04a |
| Large | 160 | 50 | two bursts of 140: 50 / 50 sleeping, 51 in total | runs 1 and 4 (DC01d) |
| 4XL | 480 | 70 | `pgrst_db_pool_max` after the resize (DC04c, DC08a); 71 `authenticator` backends open under load from c=512 (DC08b); no `PgSleep` burst count | two runs (DC04c, DC08) |

`GET /postgrest` read `db_pool` null and `db_pool_acquisition_timeout` 10 (a number, not null) on Small and on Large, and `db_pool` null on 4XL. The `max_connections` figures match the compute page.[^sb-compute] The one `authenticator` backend outside the pool count is unidentified (see [the metric section](#reading-the-pgrst_db_pool-series)).

A burst that drains within about six acquisition timeouts came back as 200s: 100 concurrent 12 s requests on Small's 30 (four waves, the last waiting about 36 s against a 10 s acquisition timeout) all answered 200, as did 140 on Large's 50. That fits the resends below; PostgREST log lines were not counted for bursts. 220 concurrent 15 s requests on a pool of 50 did not: 150 answered 200 and 70 answered 504 PGRST003 (DC02c).

## What a client sees when the pool is full

PostgREST documents that a request waits for a pooled connection for at most `db-pool-acquisition-timeout` seconds and that the timeout answers 504 PGRST003, "The request timed out waiting for a pool connection to be available."[^pgrst-db-pool][^pgrst-errors]

DC01b and DC02b held every pooled connection with long sleeps, then sent single `POST /rest/v1/rpc` requests with the service_role key, each with its own User-Agent, and counted the PostgREST access-log lines carrying that User-Agent. The client was a plain `fetch` with no retry logic and a fresh connection per request.

| Acquisition timeout | Pool held | Client's time to the answer | Answer | PostgREST log lines per request |
|---|---|---|---|---|
| 10 s (default), run 4 | 30 of 30 sleeping | 61364 ms, 61972 ms | 504 PGRST003, both | 6 (504:6), both |
| 10 s, run 1 | 30 | 61343 ms, 61493 ms | 504 PGRST003 | 6 each |
| 10 s, run 2 | 30 | 61972 ms, 61795 ms | 504 PGRST003 | 6 each |
| 2 s | 90 of 90 sleeping | 13767 ms, 13752 ms | 504 PGRST003, both | 6 (504:6), both |
| 4 s | 90 of 90 sleeping | 25007 ms | 504 PGRST003 | 6 (504:6) |
| 4 s, second request | 90 of 90 sleeping | no answer by the client's 105001 ms timeout | status 0 | 0, not explained |

With no separate probe, one client request produced six PostgREST access-log lines, all 504, and the client's wait was six acquisition timeouts plus the round trip (60 s against 61364 ms, 12 s against 13767 ms, 24 s against 25007 ms). The reading is that something between the client and PostgREST sent the request again after each PGRST003, six attempts in total. The competing reading, that PostgREST logs one request several times, was not separated, since no request id was traced through PostgREST. The 4 s figure rests on one request.

A public candidate for that layer is the Envoy configuration in the `supabase/postgres` image repository. Its virtual host carries a retry policy of `num_retries: 5` with `retry_on: gateway-error` and sets `include_attempt_count_in_response: true`, and the `/rest/v1/` routes carry no retry policy of their own;[^sb-envoy-lds] Envoy's `gateway-error` policy retries on 502, 503 and 504, and `include_attempt_count_in_response` returns the attempt count to the client in `x-envoy-attempt-count`.[^envoy-router] Five retries on a 504 is six attempts, and a 500 is outside the policy, which fits DC03d below. That hosted projects run this configuration was not checked, and the attempt-count header was not read in these runs.

Under load the wait was shorter. In DC02c's 220-request control at a pool of 50, the 70 PGRST003 answers came after 10923 to 20903 ms (median 20855), one or two acquisition timeouts. Attempts were not counted inside the burst, so how the resends behave under load is not separated. One candidate in the same repository is the `retry_budget` on Envoy's `postgrest` cluster (`budget_percent` 100, `min_retry_concurrency` 100),[^sb-envoy-cds] which caps concurrent retries at the sum of active and pending requests and never below 100;[^envoy-cb] whether it, or something else, shortened the waits is not established.

A 500 was not sent again. DC03d made an RPC with a side effect (a `nextval`) run past the 8 s authenticated timeout: 500 57014 after 8058 and 8296 ms, one execution per request by the sequence, and one PostgREST log line each (500:1). The resend covered the PGRST003 probes and not this 500. A client that retries a 504 itself adds its attempts on top of the six (inference from the counts above; client retries were not run).

### The bounds the API accepts

The Management API spec gives `db_pool` a range of 0 to 1000 and `db_pool_acquisition_timeout` 0 to 60 on the update body.[^sb-api-v1] Values sent outside them (DC02c):

| Sent | Answer |
|---|---|
| `db_pool` 1001 | 400 `db_pool: Too big: expected number to be <=1000` |
| `db_pool` -1 | 400 `db_pool: Too small: expected number to be >=0` |
| `db_pool_acquisition_timeout` 61 | 400 `db_pool_acquisition_timeout: Too big: expected number to be <=60` |

A 0 for either was not sent. For 70 and 90 on Large, the PATCHed value is what Postgres saw: both read back and a burst then held 70 and 90 `authenticator` backends in `PgSleep` (DC02a).

### A db_pool above what Postgres can give

DC02c PATCHed `db_pool` 1000 on Large (`max_connections` 160); the PATCH answered 200 and read back 1000. The same burst of 220 concurrent 15 s requests as the control then gave:

| `db_pool` | Answers | Error body |
|---|---|---|
| 50 (control, PATCHed back just before) | 150 x 200, 70 x 504 PGRST003 | PGRST003 |
| 1000 | 154 x 200, 66 x 503 PGRST002 | `"Could not query the database for the schema cache. Retrying."` |

PostgREST documents PGRST002 as "Could not connect with the database when building the Schema Cache due to the PostgreSQL service not running."[^pgrst-errors] The reading: PostgREST tried to open more connections than Postgres accepted and the refused connection surfaced as PGRST002 instead of a wait. It is one burst per arm, and no connection count near 160 was observed: the mid-burst read through the Management API query endpoint returned no row (its status and error were not recorded). After the burst, 5 consecutive good pings took 6 s against the check's floor of about 4 s, so no outage after the burst was measured.

The same 503 PGRST002 appears when another client fills `max_connections` first. In the lab's hyperdrive-direct H03 ([RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/864a18e/experiments/hyperdrive-direct/RUNLOG.md#2026-10-23---idle-origin-connections-over-30-minutes-pgrst002-by-arm-h03); 9 arm-runs on Small across three runs), Hyperdrive origin connections held the slots: as many RPCs answered 200 as PostgREST had pool connections plus free slots, every other one answered 503 PGRST002 in 719 to 2718 ms, and PostgREST initialised a new pool and reloaded its schema cache 7.6 to 8.4 s after the burst. How to budget connections when Hyperdrive and the Data API share a project is in [Cloudflare Workers + Supabase](/reference/cloudflare-supabase-architecture/#connection-budget-with-the-data-api).

## Every config PATCH restarts PostgREST

DC02e counted 9 "Starting PostgREST" lines in the project's PostgREST logs (`postgrest_logs`) for 9 accepted PATCHes to `/v1/projects/{ref}/postgrest`, one of them a PATCH that changed nothing. The sibling `data-api-reenable` experiment recorded the same for a no-change PATCH ([DA02 in its RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/c186f34/experiments/data-api-reenable/RUNLOG.md#what-switching-on-does-da02)), and turning the Data API back on is another PATCH that restarts it ([Locking down Supabase](/reference/supabase-data-surface-lockdown/)). PostgREST marks `db-pool` and `db-pool-acquisition-timeout` "Reloadable N", so a new value needs a process start to apply.[^pgrst-db-pool] DC04d adds a case: the PATCH of `db_pool` 250 on 4XL answered 500, and a restart line still followed 1.1 s later. DC08c's three PATCHes (150, 250, 70) each answered 200 and each was followed by a restart line, after 1.8, 1 and 1.4 s; its PATCH to 250 answered 200.

| PATCH | Restart line after the PATCH | Data API requests during the restart |
|---|---|---|
| `db_pool` 70, then 90 (DC02a) | 0.7 s, 0.7 s | 0 of 357 and 0 of 358 pings failed, one every 250 ms for 90 s |
| acquisition timeout 2, then 4 (DC02b) | 0.9 s, 0.7 s | not sampled |
| `db_pool` 50, 1000, 50 (DC02c) | 0.8 s, 0.7 s, 0.5 s | `db_pool` 1000: 0 failed |
| `db_pool` 20, 30 (DC05c) | 1.2 s, 1 s | not sampled |
| `db_pool` 15, 30, 60 (DC07) | 1.1 s, 1.5 s, 1.3 s | not sampled |
| no-change `db_pool` with 20 requests sleeping 60 s in flight, twice (DC02d) | 55.3 s, 55.3 s | 20 of 20 in flight answered 200, both times; 5 of 267 and 5 of 265 pings failed (status 0 at the client's 10 s timeout), first at 1.3 s and 0.8 s, back to back for about 50 s |

With nothing long in flight the restart came within about 1.5 s and no sampled request failed. With 60 s requests in flight (sent 5 s before the PATCH) the restart line came 55.3 s after the PATCH, about when they finished; all of them completed, and new requests got no answer for about 50 s, ending before the logged restart. That fits a restart that drains in-flight requests before stopping and holds new requests behind it; no separate probe was run.

Run 1 sent its PATCHes without waiting for the restart line, and three of its rows look like restart overlaps (a burst where 218 of 220 requests ended on a closed socket at the client, among them). From run 2 on, DC02 waits for the restart line after every PATCH before measuring.

## Statement timeouts the Data API honours

Documented: anon 3 s, authenticated 8 s, service_role "none (defaults to the `authenticator` role's 8s timeout if unset)", and a role change needs `NOTIFY pgrst, 'reload config'` to reach the Data API.[^sb-timeouts] DC03 checked each of those through the Data API with RPCs that sleep.

| Role, how the request was made | `rolconfig` | Sleep | Answer |
|---|---|---|---|
| anon (anon key) | `{statement_timeout=3s}` | 5 s | 500 57014 after 3062 and 3057 ms |
| authenticated (anon key plus a user token) | `{statement_timeout=8s}` | 10 s | 500 57014 after 8065 and 8048 ms |
| service_role (service_role key) | null | 10 s | 500 57014 after 8056 and 8048 ms |
| `authenticator` (PostgREST's login role) | `{"session_preload_libraries=supautils, safeupdate",statement_timeout=8s,lock_timeout=8s}` | - | - |

The error body was `{"code":"57014","details":null,"hint":null,"message":"canceling statement due to statement timeout"}`.

| Change | Answer |
|---|---|
| A function declared `set statement_timeout = '30s'`, 12 s sleep, each of the three keys twice | 200 in every case, 12067 to 12105 ms |
| `alter role authenticated set statement_timeout = '15s'`, user token, 10 s sleep, right after the ALTER | 500 57014 after 8078 and 8064 ms |
| the same after `notify pgrst, 'reload config'` | 200 after 10076 and 10103 ms |
| the same after `notify pgrst, 'reload schema'` as well | 200 after 10098 and 10080 ms |
| back to 8 s plus a config reload | 500 57014 after 8074 ms |

service_role carries no timeout of its own, so a Data API request under it runs with the 8 s that `authenticator` logs in with. A function's own setting applied to the call for every key, anon's 3 s included. An `alter role` reached the Data API only at the next config reload. Every row agrees with the timeouts guide.

## Request rate against the pool

DC01-DC03 used requests that hold a connection for seconds. DC04 and DC07 used request rate instead: `oha` (1.16.0, from console output) in a closed loop, 40 s per step, one `GET /rest/v1/dc_items?id=eq.4242&select=id,payload` (an indexed point read on a 100,000-row table) with the legacy anon key, the pool series scraped every 3 s, node CPU from `node_cpu_seconds_total` and the `authenticator` states read once mid-step. Success is 200s over all attempts, client-side errors included. DC08 moved the clients into the region and used a mixed load ([below](#4xl-with-in-region-clients-and-a-mixed-load-dc08)). The compute page lists Small as shared CPU and 4XL as 16 dedicated vCPUs.[^sb-compute]

From 256 on, throughput stayed at about 920 to 1,020 req/s while latency doubled per step, which is what a closed loop does against a fixed ceiling. In the 256 step one snapshot read 139 waiting with 11 of 30 connections available (the step's median was 7 waiting). Since `waiting` includes requests holding a connection ([below](#reading-the-pgrst_db_pool-series)), and at most 30 minus 11 connections were in use, at least 120 of those 139 had no connection while 11 open ones sat idle, if the payload was internally consistent. The 512 step showed the same 139 and 11 on every scrape, so it is one snapshot across two steps; node CPU comes from the same endpoint and is a snapshot too, which is the condition on the 73.9 % figure. Node CPU covers both Postgres and PostgREST if they share the node, as the project image suggests (it installs PostgREST as a service beside Postgres;[^sb-setup-postgrest] hosted placement not checked), so it does not say which process used the CPU; no per-process figure was read. The 1024 row reads nothing waiting while 12.8 % of requests failed on the client.

### 4XL with in-region clients and a mixed load (DC08)

DC08 moved the clients into the project's region and replaced the single point read with a mix. The lab had no machine of its own in the region that day, so the clients were Supabase Edge Function invocations of a generator deployed to the project under test and pinned to `ap-northeast-2` with the `x-region` header; this lab's Mac fired each round's invocations after one warm-up call per client. Every invocation that reported its region reported `ap-northeast-2`, and every sampled (1 in 50) Data API response carried a `cf-ray` from Cloudflare's ICN (Seoul) colo. One invocation is one closed-loop client of 8 workers for an 8 s round; a step is 6 rounds (48 s), and the concurrency label is clients x 8. Every request used the legacy anon key against the 100,000-row table, mixed by weight: a point read 50, a 50-row range read 15, an RPC returning one indexed row as JSON 15, an insert with `Prefer: return=minimal` 10, and a `Prefer: count=exact` read that counts 10,000 rows and returns 20, 10.

The generator under-delivered. Invocations failed with 546 `WORKER_RESOURCE_LIMIT`, 503 `BOOT_ERROR` and 429 `RATE_LIMIT_EXCEEDED`, a failed invocation was retried while 2 s of its round remained, and observed starts were up to 16.2 s late, so each step's concurrency label overstates the load. "Clients answered" is the invocations that returned a result, per round. Requests in flight (req/s x p50, derived, client-side and including edge and gateway time) are the closest the run has to the delivered load. The generator in this run took its target host from the request; after the run it was changed to target only the project it is deployed in, and that version has not been run.

| Concurrency (clients x 8) | Clients answered per round | req/s | p50 / p95 / p99 ms | `authenticator` active / idle / idle in transaction (range in load, from the RUNLOG; the artifact holds all-sample min/median) | Pool snapshots waiting/available/max | Postgres exec ms/s |
|---|---|---|---|---|---|---|
| 64 (8) | 3.8 | 989 | 18.6 / 30.7 / 47.2 | 0-1 / 9-13 / 0-4 | 0/2/70 | 258 |

The issue gives a pool large enough that nobody waits as the workaround and points to a fix proposed in `hasql-pool` PR #58. Those are the issue's own measurements under its conditions; the lab did not reproduce them. The issue's 2- and 4-core rows with Postgres on 2 cores show CPU per request near its no-wait figure (293 and 324 microseconds against 333); its 4-core pool contrast with Postgres on 1 core shows pool 20 at 2,768 req/s against 6,875 at 200. Which regime a Small project is in was not established: how many cores PostgREST gets there is not documented, and whether DC07's 30 and 60 arms queued at all was not observed. The issue measured the `hasql-pool` copy vendored on PostgREST `main`; v14.18 takes `hasql-pool` from Hackage at `>= 1.0.1 && < 1.1`,[^pgrst-cabal] and whether that version has the same acquisition code was not checked. DC08c on 4XL, flat throughput with most connections idle at pools of 70, 150 and 250, fits a limit in PostgREST that a pool below the requests in flight does not lift. The issue's workaround was not tested there: 250 is below the 1,360 to 1,700 requests in flight in those arms (derived), and the run does not separate a limit in front of PostgREST.

## Reading the pgrst_db_pool series

The project metrics endpoint, `/customer/v1/privileged/metrics` (scrape set-up in [Monitor Supabase with Grafana](/guides/supabase-grafana-monitoring/)), served 9 `pgrst_*` series in DC04a: `pgrst_db_pool_available`, `pgrst_db_pool_max`, `pgrst_db_pool_timeouts_total`, `pgrst_db_pool_waiting`, three JWT cache series and two schema cache series. PostgREST's help text calls `pgrst_db_pool_available` "Available connections in the pool" and `pgrst_db_pool_waiting` "Requests waiting to acquire a pool connection".[^pgrst-metrics]

The v14.18 source counts differently from that help text. `usePool` raises the waiting gauge before it asks the pool for a connection and lowers it after the session using that connection returns,[^pgrst-src-usepool] so `waiting` counts requests from their pool request until their session ends: requests queued for a connection plus requests holding one. PostgREST's own pool sessions go through the same function (the connection check when the listener is off, the schema cache load, the in-database config and role-settings reads), so they count too.[^pgrst-src-callers] `available` is computed as open pool connections minus connections in use.[^pgrst-src-metrics] This is source-read; the Supabase build is assumed to match the tag, which was not checked. DC05 read the series against `pg_stat_activity` for `usename = 'authenticator'`, read through the Management API query endpoint, and the snapshots agree with the source.

### How often they change (DC05a)

1 s scrapes for 100 s while held requests stepped 0, 5, 15, 25 and 0 every 20 s; `pg_stat_activity` about every 2.5 s.

| Measured | Value |
|---|---|
| scrapes | 100, 0 failed |
| distinct waiting/available/max readings | 2: `0/1/30` from 0 s to 60 s, `25/0/30` from 62 s to 99 s |
| changes | 1 |
| response headers, first scrape | `cf-cache-status=DYNAMIC`, `date` current |
| `authenticator` total / in `PgSleep` / idle | 2/0/2 to 20 s; 6/5/1 from 22 s; 16/15/1 from 41 s; 16/0/16 at 58 s; 26/25/1 from 61 s; 26/0/26 from 81 s |

The series moved once in 100 s while the backends moved five times. No refresh landed between 22 s and 58 s, a 36 s window in which the 5- and 15-held states existed and never appeared, and none between 81 s and 99 s, after the holds ended. A periodic refresh would therefore be at least about 40 s apart (the change at 62 s, the previous refresh no later than 22 s); no upper bound was measured. The endpoint answered `DYNAMIC` with a current `date`, so the staleness sits behind the edge.

### What they count (DC05b)

10 then 40 requests held for 30 s on a pool of 30; five scrapes 1.5 s apart from 12 s into the hold, `pg_stat_activity` at the third.

| Held | Scrapes (waiting/available/max) | `authenticator` total / in `PgSleep` / idle | `available` if it meant open idle / max minus checked out | Holds |
|---|---|---|---|---|
| 10 | `25/0/30` x4, then `10/15/30` | 26 / 10 / 16 | 16 / 20 | 200:10 |
| 40 | `10/15/30` x5 | 31 / 30 / 1 | 1 / 0 | 200:40 |

Three snapshots line up with a known state:

- `available` read 15 with 10 held against 16 idle `authenticator` backends, 1 at rest (DC05a, 0 s) against 2 idle, and 0 with 25 held (DC05a, 62 s) against 1 idle. That matches open connections minus those in use. In those three, one idle backend was not counted, which fits one connection outside the pool (PostgREST's listener; not identified). "Max minus checked out" would have read 20, 30 and 5.
- `waiting` read 25 with 25 held and 10 with 10 held, on a pool of 30 where nothing queued: the requests holding a connection, as the source predicts. DC07 shows the queued part too: with `db_pool` 15 at 128 concurrent, one snapshot read 31 waiting against a pool max of 15.
- The 40-held row is the 10-held snapshot still being served. The queued state, 30 in `PgSleep` and 10 waiting for a connection, was never scraped.

Under load on 4XL (DC08b) one tuple showed requests queued while connections sat free. The tuple first scraped 33 s into the c=3072 step (the 25 s scrape read `0/70/70`) read 1,078 waiting with 58 of 70 available. Holding is at most 70 - 58 = 12, so at least 1,066 requests were queued for a pool connection inside PostgREST at some moment between load start and 33 s while 58 open connections were idle; given the lags DC05 measured, the tuple does not say when. The `authenticator` samples in that step read 0 to 7 active and 58 to 64 idle. The tuple still read 1,078 at 73 s, 25 s after the load ended, when the samples read 0 active and 71 idle, and the 14 scrapes that show it are one tuple (n = 1). At c=2048 and in the last pool-70 arm the node CPU counters moved, so the payload refreshed at least once, and the pool tuple still read `0/70/70`; when those refreshes landed relative to the load is not recorded, so whether the queue was there at earlier steps is not settled.

### Pool max after a PATCH (DC05c)

| PATCH | Status | Restart line after | `pgrst_db_pool_max` read the new value after |
|---|---|---|---|
| `db_pool` 20 (from unset, 30) | 200 | 1.2 s | 1.4 s, first scrape |
| `db_pool` 30 | 200 | 1 s | 28.9 s, 22 scrapes |

PostgREST restarted within about 1 s both times; the metric followed after 1.4 s once and 28.9 s the other time. The 28.9 s case fits the slow refresh above. The 1.4 s case puts the refresh within a fraction of a second of the logged restart (client and log clocks, skew not measured), so the competing reading, that a restart resets or refreshes the payload, is open; the two were not separated. Either way it fits DC04d, where each arm read the previous arm's pool.

For an alert or a capacity decision, count the pool where it lives before acting on these series. The lab's own reading was a `pg_stat_activity` query of this shape, run through the SQL editor or the Management API query endpoint:

```sql
select count(*) filter (where usename = 'authenticator') as total,
       count(*) filter (where usename = 'authenticator' and state = 'idle') as idle,
       count(*) filter (where usename = 'authenticator' and state = 'active') as active
from pg_stat_activity;
```

## Statement timeouts from a lock, then the pool

DC06 asked whether requests cancelled by a statement timeout leave pooled connections in a broken state. 20 workers looped anon GETs on `dc_items` while a Management API query ran `begin; lock table public.dc_items in access exclusive mode; select pg_sleep(N); commit;`, with 75 s observed after the lock and `authenticator` states read about every 5.7 s. Anon's 3 s timeout is the DC03a figure, from a different run and project. The 2 s control ran first; each arm ran once.

| Lock asked / held | Before | During (to 4 s after the lock) | After (4 s to 75 s) | 25P02 after | Most `idle in transaction (aborted)` seen | Requests |
|---|---|---|---|---|---|---|
| 2 s / 2.7 s | 200:2034 | 200:664 | 200:9857 | 0 | 0 | 12555 |
| 12 s / 12.6 s | 200:2050 | 200:643, 500 57014:60 | 200:9920 | 0 | 0 | 12673 |

During the 12 s lock the states read `active:20 idle:1` twice, then `idle:21` from 1.4 s after it, with at most 2 `idle in transaction` (not aborted) in any later sample. 60 requests were cancelled by anon's statement timeout while waiting on the lock, and none of the pooled connections they used was left aborted: every request after the lock answered 200 and no sample showed an aborted backend. With 20 workers on a pool of 30 no request waited for a pool connection, so a cancellation while queued was not exercised. A stall where Postgres stops as a whole, with cancellations landing at a different protocol step, was not made: the lab has no way to stop Postgres as a whole on a managed project.

## Decision guide

```dot
digraph {
  rankdir=LR; bgcolor="transparent"; nodesep=0.3; ranksep=0.7;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];

  s [label="Data API requests\nfail or slow down"];
  p3 [label="504 PGRST003\n-> pool full; check pg_stat_activity,\nshorten requests, lower the wait"];
  p2 [label="503 PGRST002 persisting after the restart\nfollowing a db_pool raise\n-> db_pool past max_connections"];
  h [label="503 PGRST002 in about 2.7 s while\nanother client (Hyperdrive) holds the slots\n-> origin connection limits that fit"];
  t [label="500 57014 at 3 s / 8 s\n-> role timeout; function setting\nor alter role + reload config"];
  r [label="no answer just after a config PATCH\n-> PostgREST restart"];
  c [label="flat req/s, rising latency\n-> Small: compute size before db_pool\n-> 4XL, backends idle: db_pool 150 and 250\ndid not help (one step each)"];

  s -> p3; s -> p2; s -> h; s -> t; s -> r; s -> c;
}
```

Text version:

1. 504 PGRST003: every pooled connection is busy. Count `authenticator` backends in `pg_stat_activity`, shorten the requests holding them, or lower `db_pool_acquisition_timeout` to fail sooner.
2. 503 PGRST002 that persists after the restart line following a `db_pool` raise: the pool is past what `max_connections` gives; bring it back down.
3. 503 PGRST002 within about 2.7 s while another client such as Hyperdrive holds the connection slots: Postgres refused PostgREST a new connection, and PostgREST rebuilt its pool about 8 s later (hyperdrive-direct H03). Give the other client an origin connection limit that leaves room; see [the connection budget](/reference/cloudflare-supabase-architecture/#connection-budget-with-the-data-api).
4. 500 57014 at about 3 s or 8 s: the role's statement timeout. Set it on the function, or `alter role` and reload the config.
5. No answer just after a PostgREST config PATCH: the restart; with long requests in flight it came when they finished (DC02d, twice).
6. Flat req/s while latency rises with concurrency on Small: try a larger compute size before a larger `db_pool`. On 4XL at 6,148 req/s with most `authenticator` backends idle, `db_pool` 150 and 250 did not help (DC08c, one step each).

## Not measured

- Compute sizes other than Small, Large and 4XL; regions other than `ap-southeast-1` and `ap-northeast-2`; Team or Enterprise organizations.
- `db_pool` 0 and `db_pool_acquisition_timeout` 0.
- Which component resends after PGRST003, its policy under load, attempt counts inside a burst, and the `x-envoy-attempt-count` header on a PGRST003 answer.
- The 60 s ceiling the timeouts guide gives for client queries.[^sb-timeouts]
- The pool metric refresh interval measured directly (only a lower bound if periodic), whether a restart refreshes the payload, and a `waiting` snapshot taken while requests were known to queue.
- Whether the hosted PostgREST matches the v14.18 source read here.
- A per-process CPU split between PostgREST, the API gateway and Postgres, the latency each layer between the client and PostgREST adds, and node CPU in DC07.
- DC07 repeated per cell (DC08c ran 70, 150 and 250 on 4XL with a different generator, not DC07's 15 to 60), on a size with more vCPU, or with requests that hold a connection longer than a point read, where waiting for a connection is certain.
- Load above c=3072 on 4XL; a load generator whose delivered concurrency matches the requested one; clients outside the Edge Functions runtime (machines in the region) to compare against.
- The pool series at a known refresh during DC08's c=512 to c=2048 steps, and a pool reading during the 150 and 250 arms.
- Issue #5336's workaround on 4XL, a `db_pool` at least as large as the requests in flight (about 1,360 to 1,700 in DC08c, derived, req/s x p50).
- Postgres rates over exactly the 48 s of DC08 load, and why calls and transactions per request fell at the top steps.
- Requests with authenticated-user JWTs (every request used the anon key), larger payloads, writes with indexes or triggers, a mix without `count=exact`, and a high `max_rows`.
- A whole-instance stall for DC06, a cancellation while queued for a pool connection, the authenticated role's 8 s timeout under a lock, RPC or write requests under cancellation.
- Requests through Supavisor or a direct Postgres connection; this page covers the Data API path only.
- Client-side error text for the status-0 rows in run 4 and the 394 in DC08c's pool-150 arm.
- Repeats of any DC04-DC08 row beyond DC07's pool-30 arm, which re-ran DC04b's step on another project, and DC08c's second pool-70 step; XL, 2XL and 8XL under load.

## Reproducing

The experiment provisions and deletes its own project; it needs a Pro-plan organization slug in `PVLAB_ORG_PRO` and a personal access token in `SUPABASE_ACCESS_TOKEN`.

```bash
make run                         # DC01-DC03 then DC99, about 45 minutes
make run ONLY=DC04,DC99          # opt-in, needs oha; PVLAB_DC_REGION / PVLAB_DC_SIZE pick the project
make run ONLY=DC05,DC06,DC07,DC99
make run ONLY=DC08,DC99          # opt-in; PVLAB_DC_REGION, PVLAB_DC08_* pick size, steps, pools, workers, rounds
make clean                       # list leftover pvlab-dc-* projects; DELETE=1 deletes
make publish-evidence RUN=evidence/<ts>/run-<stamp>.json
```

Project time was about 40 minutes for run 4, 18 minutes for DC04, 21 minutes for DC05-DC07 and 22 minutes for DC08, each on a Small project except DC01d-DC03 on Large and the DC04c-DC04d tail and DC08 after its resize on 4XL. DC08 deploys its generator as an Edge Function on the project under test; the version that ran took its target host from the request, and the version in the lab now targets only its own project and has not been run.
