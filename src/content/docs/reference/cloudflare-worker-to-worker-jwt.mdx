Authenticating Workers calling other Workers across Cloudflare accounts without a shared secret, a per-request API charge, or an external control plane. The receiver holds the public keys and assigns identity - the sender cannot self-assert who it is.

Provenance: the design-property claims in this doc - the 520 on orange-clouded mTLS, the 13-step verifier, the JTI Durable Object consistency - are cross-checked against the implementation in `worker-mtls-jose` but not against a multi-colo measurement run. The comparison-table properties for AWS IAM, SPIFFE and Istio are documented architecture, not a measurement from this rig.

**TL;DR:**

- Cloudflare mTLS certificate bindings return `520` when the destination Worker sits behind an orange-clouded (proxied) zone, leaving no built-in mechanism for authenticated Worker-to-Worker calls[^cf-mtls-bindings]
- Access service tokens work but couple you to the Zero Trust control plane
- ES256 JWTs with a receiver-owned key registry give you authenticated calls without vendor lock-in, access charges or a shared secret
- The `CF-Worker` header Cloudflare adds to Worker subrequests is a useful signal but spoofable - identity comes from the JWT signature, not the header[^cf-subrequest-headers]
- Durable Object-backed JTI storage gives strongly consistent replay protection with no eventual-consistency gap

## The mTLS gap

Cloudflare offers [mTLS certificate bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/mtls/) (`mtls_certificate`) for Workers to present a client certificate to an origin. When the target is an orange-clouded (proxied) zone, the connection returns `520`, the catch-all origin-unreachable status[^cf-mtls-bindings]. The bindings work for grey-clouded (DNS-only) origins but that gives up the CDN - caching, DDoS protection and the Workers runtime are all behind the proxy.

Access service tokens (Cloudflare Zero Trust) authenticate Workers but introduce a dependency on the Access control plane and a per-token management model. For a small number of well-known Worker pairs, a shared HMAC secret works. For any scale beyond that, neither pattern fits.

ES256 JWTs fill this gap: asymmetric keys held by the sender, public keys held by the receiver, identity assigned by the receiver through its key registry.

<Aside type="note">
  Reference implementation: the `worker-mtls-jose` library exports `signRequest()` and `verifyRequest()` functions that handle JWT signing and the 13-step verification pipeline. It is not an npm package - copy `lib/` into your own project and depend on the `jose` library directly.
</Aside>

| Step | What happens | Where |
|------|-------------|-------|
| 1 | Sender signs an ES256 JWT with claims: `method`, `path`, `bodyHash`, `iss`, `aud`, `exp`, `jti`, `iat`, plus optional `srcZone`/`dstZone` | Sender Worker |
| 2 | Sender attaches the JWT as `Authorization: Bearer <jwt>` and calls the receiver | Sender Worker |
| 3 | Cloudflare edge adds `CF-Worker: <zone>` to the subrequest | Cloudflare edge |
| 4 | Receiver decodes the JWT header, extracts `kid`, and looks up the key in its registry | Receiver Worker |
| 5 | Receiver verifies the ES256 signature against the registered public key | `jose.jwtVerify()` |
| 6 | Receiver checks `iss`, `aud`, `exp`, `maxTokenAge` | `jose.jwtVerify()` options |
| 7 | Receiver runs JTI replay check against the Durable Object store | `JTI DO` |
| 8 | Receiver resolves identity from the key registry entry (not from the JWT claims) | `RegisteredKey.identity` |
| 9 | Receiver checks the `CF-Worker` header matches the registered identity zone | Runtime check |
| 10 | Receiver checks the destination zone (from `request.url.hostname`) matches `dstZone` claim | Runtime check |
| 11 | Receiver checks the request method matches the JWT `method` claim | Runtime check |
| 12 | Receiver checks the request path matches the JWT `path` claim | Runtime check |
| 13 | Receiver hashes the request body (SHA-256, base64url) and checks it matches `bodyHash` if present | `crypto.subtle.digest()` |

## Three identity layers

The receiver builds identity from three independent signals. Only one - the key registry - is load-bearing.

| Layer | Source | Trust level | Spoofable |
|-------|--------|-------------|-----------|
| Key registry (`kid` -> identity) | Receiver's `KEY_REGISTRY` env var | Receiver-controlled - highest | No (needs private key) |
| `CF-Worker` header | Cloudflare edge, added to Worker subrequests | Cloudflare-attested | Yes, by non-Worker clients |
| Destination hostname | `request.url.hostname` at runtime | Runtime-derived | Needs DNS/routing attack |

**Key registry**: the receiver holds a list of `{ kid, publicKeyPem, identity: { zone, account?, worker? } }` entries. When it sees a JWT with `kid: "sender-a"`, it finds that entry, verifies the signature against the stored public key, and reads the identity from the entry. The sender's `srcZone`/`srcAccount` claims in the JWT are ignored. Identity is receiver-assigned, not self-asserted.

Unlike a shared-secret HMAC, the receiver here can revoke a sender by removing its registry entry, and the sender cannot assert a zone it does not own.

**`CF-Worker` header**: Cloudflare adds `CF-Worker: <zone>` to all Worker subrequests[^cf-subrequest-headers]. It is set by the edge, not by user code. However, Cloudflare does not document stripping it from non-Worker requests - a direct client could set this header and it would pass through. The equivalent trustworthy field (`cf.worker.upstream_zone`) exists only in the WAF/Rules Engine, not the Workers runtime API[^cf-waf-fields].

In this system, `CF-Worker` is a defence-in-depth signal. The JWT signature + key registry is the real proof. A `CF-Worker` mismatch is rejected; an absent header is logged as "skip" rather than failure.

**Destination hostname**: the receiver derives its own zone from `request.url.hostname` at runtime, so a misconfigured `receiverZone` env var does not silently accept tokens meant for another hostname.

## JTI replay prevention

Each JWT carries a `jti` (JWT ID) claim - a unique token identifier[^rfc7519]. The receiver stores seen JTIs and rejects any that appear a second time.

The library provides two backends:

| Store | Consistency | Storage | When to use |
|-------|-------------|---------|-------------|
| Durable Object (`createDoJtiStore()`) | Strong - single writer per DO instance, no replication lag | DO storage, automatically expires entries after token TTL | Production. No replay can slip through during a write propagation window. |
| KV (`createKvJtiStore()`) | Eventual - KV writes are globally consistent within 60 seconds but reads can be stale | KV namespace, TTL-based expiry | Non-critical or budget-constrained paths where a short replay window is acceptable. |

The DO store is the recommended default. A DO instance is a single-threaded actor: every JTI check+store is serialised, so two requests with the same JTI arriving at the same DO instance are linearised and only one succeeds.

## Trust model comparison

AWS, GCP and Kubernetes platforms cryptographically attest a caller's identity at the infrastructure layer because they control the runtime. Cloudflare's Workers runtime does not expose an account ID or Worker-level identity certificate, so the application must supply its own.

| System | Identity attested by | Self-assertion | Consistency |
|--------|---------------------|----------------|-------------|
| This system (ES256 JWT + registry) | Private key + receiver key registry + `CF-Worker` header | No (registry mode) | Strong (DO) |
| AWS IAM (STS) | AWS platform | No | Strong |
| GCP Workload Identity | External IdP + GCP STS | No | Strong |
| SPIFFE/SPIRE | Platform attestation (kernel, kubelet) | No | Strong |
| Istio mTLS | Kubernetes service account + CA | No | Strong |
| OAuth client_credentials | Auth server + client secret | No | Strong |

Systems that do platform attestation have a structural advantage - the platform can prove who the caller is without the application holding a secret. On Cloudflare, the application must carry a secret (the private key), so key hygiene matters: short-lived tokens (60 s default), per-JWT request binding (method + path + body hash), and receiver-side revocation (remove the registry entry).

### Attack vectors

| Attack | Impact | Mitigated by |
|--------|--------|-------------|
| Private key compromise | Full impersonation | Short-lived tokens (60 s), receiver-side revocation (remove key entry) |
| `CF-Worker` spoofing | None - JWT signature must pass first | Signature verification runs before `CF-Worker` check |
| Token replay | None | JTI stored in DO with TTL, strong consistency |
| Token reuse on different endpoint | None | Method + path + body hash bound in JWT |
| Receiver misconfiguration | Reduced - destination derived from hostname | `request.url.hostname` used at runtime |

## Key resolution strategies

The receiver supports three strategies for resolving which key to verify against:

| Strategy | How it works | When to use |
|----------|-------------|-------------|
| Key registry (`keys`) | `kid` in JWT header -> registry entry -> public key + identity | Recommended. Identity is receiver-controlled. |
| Single key (`publicKeyPem`) | One public key without `kid`. Identity from JWT claims, filtered by `allowedSourceZones`. | Legacy single-sender. Sender self-asserts identity. |
| JWKS URL (`jwksUrl`) | Fetches keys from an OIDC provider (Authentik, Keycloak). Identity from the OIDC token's claims. | Delegate identity to an external IdP. |

The key registry is the recommended mode. It supports key rotation via `publicKeyPemOld` on each entry: the receiver tries both current and old keys during rotation, with zero downtime.

| Scenario | Approach | Effort |
|----------|----------|--------|
| Same account, no auth policy needed | Service bindings | None |
| Cross-account, DNS-only (grey-clouded) | mTLS cert bindings | Low |
| Cross-account, 2-3 static senders | Shared HMAC secret | Low |
| Cross-account, many senders or key rotation | ES256 JWT + key registry (this system) | Medium |
| Cross-account, external identity provider | ES256 JWT + JWKS from IdP | Medium-high |
