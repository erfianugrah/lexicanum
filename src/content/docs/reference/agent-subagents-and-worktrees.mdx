The pi harness runs parallel work through four worker kinds (`task`, `bg_task`, `bg_bash`, `bg_loop`) plus `/btw` side questions. They share one lifecycle: progress streams into a panel under the editor and no worker runs mutating git. `task` workers also resume after transient provider errors. File-level `/undo` is covered at the end of the page.

The loop agents spawned through this surface are covered in [Loop or graph: a sensor-gated coding-agent loop](/reference/self-correcting-agent-loop/). The gates that block workers from running git are covered in [The guard extensions that police agent tool calls](/reference/agent-guard-extensions/).

Every mechanism below is read from the harness source. Incidents come from session history and carry their dates.

**TL;DR:**

- `task` blocks the parent and returns the result. `bg_task`, `bg_bash` and `bg_loop` return a handle at once and push a completion nudge later.
- At most 4 `task` workers run at once (`PI_TASK_MAX_PARALLEL`, default 4); extra calls queue. `bg_task` pi workers have a separate pool per session tree (`PI_BG_MAX_PARALLEL`, default 4) that refuses extra spawns instead of queueing, and `llmc/` workers are exempt from it. A 402 on OpenRouter's in-flight credit budget killed one of six workers on 2026-10-19, and the cap shipped on 2026-10-20 (d5fb627).
- A `task` worker hit by a transient provider error is resumed up to 2 times, after a 30 s, 60 s or Retry-After backoff capped at 180 s.
- Workers never run mutating git (dotfiles#140, 2026-10-20). They edit files in a worktree the main session created, and the main session commits, merges and pushes.
- `/btw` forks the session into a read-only worker that answers while the main turn keeps running.
- `/undo` restores the files the agent changed together with the conversation.

## Which worker for which job

| You need | Use | Mechanism |
|---|---|---|
| A sub-task whose result the parent reads before continuing | `task` | Blocks the parent and returns output in the same turn. Several `task` calls in one message run in parallel. |
| Research, audit or a deep refactor that should not block you | `bg_task` | Detached `pi -p` in tmux. Returns a handle and pushes a completion nudge. |
| A polling loop, slow download or long build, past the 30 s bash-tool timeout | `bg_bash` | Detached shell in tmux, no pi process. |
| An unattended build/lint/test loop with a model ladder | `bg_loop` | `loop run` with per-iteration progress in the agent view. `loop graph run` for multi-node graphs. |
| A quick lookup that must not interrupt the running turn | `/btw` | Read-only fork of the session. The answer lands in the agent view. |
| A read-only deep dive that must finish before continuing | `task` with `explore` | No full extension load, so it starts cheaper. |
| Two or more independent research angles | several `task` calls in one turn | Parallel dispatch. Each worker writes its results and the parent synthesises. |

## The worker kinds

### task: inline subagent

`task` spawns a fresh `pi -p` process, feeds it the prompt, parses its JSON event stream for progress, and returns the final assistant text. The parent blocks until the worker exits. Workers are one-shot: there is no multi-turn conversation with a `task` subagent.

`task.ts` defines two presets, plus `general-purpose` as an alias for `general`:

| Preset | Tools | Extensions |
|---|---|---|
| `explore` | `read`, `grep`, `glob`, `docs_search`, `docs_read`, `docs_grep`, `docs_find`, `docs_summary`, `docs_sources`. No bash, no writes, no web search. | `--no-extensions --no-skills --no-prompt-templates`, then `docs.ts`, `glob.ts`, `worker-inbox.ts` and `lineage.ts` loaded back in |
| `general` | All tools; the `model` argument, else pi's configured default model | All |

Parallel dispatch: each `task` call in one turn becomes a separate subprocess. A counting semaphore caps concurrent workers at `PI_TASK_MAX_PARALLEL` (default 4) and queues the rest until a slot frees (`task-limits-core.ts`).

Incident, 2026-10-12: three parallel workers on `openrouter/~deepseek/deepseek-flash-latest` printed DSML tool-call markup as text and ran zero tools. `tool-routing.md` now names that model as unfit for workers and says to check a worker's tool count in `bg_status` before trusting its silence.

### bg_task: detached pi worker

`bg_task` is the same `pi -p` subprocess inside a detached tmux session. The tool returns the session handle within about 100 ms. When the worker finishes, the tmux wrapper updates a state file and a completion watcher pushes the result to the parent as a steer. State lives at `~/.pi/agent/bg-tasks/<name>.json`. Workers inherit the parent's extensions and skills unless `minimal: true` is set. The model is the `model` argument, else `PI_BG_DEFAULT_MODEL` on non-minimal runs, else pi's configured default (`bg-tasks.ts`).

A worker on the local llmc stack gets a 20-tool allowlist (`LLMC_DEFAULT_TOOLS`) and no MCP servers, so the single-lane engine's prompt-cache prefill stays small. With every MCP server loaded, the first request carried about 77.5k prompt tokens before the first tool ran (`bg-tasks.ts`).

Every `bg_task` prompt is prefixed with `HEADLESS_WORKER_PREAMBLE`: nobody reads the worker's messages until it finishes, git is blocked, the question tool has no UI, and it must finish or stop with a precise blocker.

### bg_bash: detached shell command

`bg_bash` runs a bash command in a detached tmux session with the same lifecycle as `bg_task` and no pi process. The command text is written to a tempfile and run as `bash <tempfile>`. Output streams to the tmux pane and to `~/.pi/agent/bg-tasks/<name>.log`, which outlives the 30 s tmux grace period after exit (`bg-tasks.ts`).

### bg_loop: self-correcting loop in the background

`bg_loop` runs `loop run --events <file>` inside tmux. The JSON event stream (`run_start`, `sensor`, `iteration_start`, `iteration`, `run_end`) drives an agent view row with iteration count, model, phase and failing sensors, and the completion nudge carries the result instead of a raw log tail. `bg_loop graph=<graph.json>` runs `loop graph run`, which orders loop manifests and shell `cmd` nodes as a dependency graph, with no approval prompts and the governor owning git. The mechanism is in the [self-correcting loop reference](/reference/self-correcting-agent-loop/).

## Lifecycle and the agent view

Every worker kind registers with a process-wide registry (`lib/agent-view-core.ts`). The `agent-view` extension renders it as a list under the editor, a port of Claude Code's agent list (dotfiles#56, plan `docs/plans/2026-10-12-pi-agent-view.md`).

Keys, with the editor empty:

| Key | Action |
|---|---|
| Down arrow | Enter the list |
| Up / down | Move between rows |
| Enter, or a click | Open the live transcript overlay |
| `x` | Stop the worker |
| Esc, or left arrow | Leave the list |

Finished rows stay for 30 s (`LINGER_MS`) and then drop. Each row shows a status glyph, elapsed time, turns, tool count and the last tool label.

Streaming: `task` and `bg_task` both emit `pi --mode json` event streams. `lib/bg-stream.ts` extracts tool calls, assistant text, token counts and errors into a transcript.

Completion nudge: when a `bg_task`, `bg_bash` or `bg_loop` finishes, the watcher pushes the final output into the parent session as a steer. It is keyed on the parent's session id, so it survives `--session` resume, and `PI_BG_NOTIFY=0` disables it. A running `bg_wait` returns early when another task finishes, so the steer is not held behind it. `bg_wait` itself blocks until a pattern matches a worker's output, the worker exits or a timeout elapses, replacing a chain of `bg_status` calls across turns.

## Steering a running worker

The agent view overlay has an input line. A message typed there reaches the viewed worker as a steer:

1. The parent (`task.ts` or `bg-tasks.ts`) appends a JSON line to a per-worker inbox file named by `PI_WORKER_INBOX` (`lib/worker-inbox-core.ts`).
2. `worker-inbox.ts` inside the worker polls the file every 300 ms, records each message with `pi.appendEntry` (the parent's transcript shows `> typed message`), and delivers it with `pi.sendUserMessage(..., {deliverAs: "steer"})`.
3. The model sees the steer after its current tool calls finish.

Nothing reaches a worker after it settles. A row whose provider `canSend` is false (finished, or spawned without an inbox) shows a read-only line instead of the input.

## Provider errors and the concurrency cap

### The 402 incident (2026-10-19)

Six parallel deepseek workers were dispatched in one turn. OpenRouter returned a 402 on one of them with the reason `in_flight_budget_exhausted`. OpenRouter reserves credit per in-flight request, so six concurrent requests consumed the reservation. The worker died and its work was lost (header of `task-limits-core.ts`).

### The fix: semaphore and retry

`task-limits-core.ts` (d5fb627, 2026-10-20, dotfiles#132) adds two mechanisms.

Concurrency cap: a FIFO counting semaphore gated on `PI_TASK_MAX_PARALLEL`. `maxParallel` reads the variable and falls back to 4 when it is unset or not a number.

Transient-error resume: when a worker's last request fails with a retryable provider error, the spawner waits and relaunches the worker from its persisted session with the prompt "Continue the task from where you left off." Up to `MAX_RESUMES` (2) retries.

| Error | Retried |
|---|---|
| 402 with in-flight wording, 429, 5xx, overload, dropped connection, timeout | Yes |
| 401, 403, 400 | No, fails at once |
| 402 without in-flight wording (out of credits) | No, fails at once |

Backoff is the `Retry-After` value when the message has one, otherwise 30 s then 60 s, clamped between 5 s and 180 s.

### Error surfacing in the stream

Before dotfiles#126, a provider failure arrived as an assistant message with empty content and `stopReason: "error"`. `extractAssistantText` dropped it, so the failure left no trace. `lib/bg-stream.ts` now runs `noteOutcome` on every assistant message, stores the `errorMessage` as `lastError` and pushes an `[error]` transcript entry. If no assistant text ever arrived, the result is `"[subagent produced no output]"`, and the caller reads `lastError` for the reason.

## Worktree isolation

Two agents in one working directory share one index, one working tree and one set of untracked files. A worktree gives each its own index and tree, and shares the object store and refs with the main tree, so a merge needs no fetch (`git-worktrees` skill, `tool-routing.md`).

### The hazard

| Mechanism | Effect on the other session |
|---|---|
| Checkpoint `git add -A` | Stages the other session's in-progress files. If the human then commits, unrelated work rides along. |
| Scope revert | Deletes an untracked file outside `writeScope`, so the other session's new file is gone. |
| Rollback to checkpoint | Restores files from the checkpoint index. Files created after the checkpoint were never in it. |

An untracked file deleted by a scope revert was never committed, so `git fsck --unreachable` finds no blob. The only copy was in the authoring session's context.

### The flow

Setup, by the main session:

1. `git worktree add .worktrees/<card>-<slug> -b agent/<card>-<slug> main` in the repo root. This is routine git and runs without a prompt.
2. Symlink `node_modules` instead of reinstalling.
3. Append `node_modules` and `.worktrees/` to the shared git exclude file so both trees stay clean.
4. Copy gitignored config (harness manifests, `.env` files) into the worktree.

The worker edits files and runs tests in its worktree and never commits. The main tree stays clean.

Finish, by the main session:

1. Review the diff with `git -C .worktrees/<card>-<slug> diff`, then `git add` and `git commit` in the worktree.
2. `cd` to the main repo root and `git merge --ff-only agent/<card>-<slug>`, or `git cherry-pick` when main has moved on.
3. `git worktree remove .worktrees/<card>-<slug>`, then `git branch -d agent/<card>-<slug>`.

`rm -rf` on a worktree directory leaves a stale entry in `.git/worktrees/`. `git worktree prune` clears it.

The pages in this series are written this way: one worktree per writer, no commits from the writer, and the parent reviews the diff, merges and removes the worktree.

## Main-session-only git

On 2026-10-20 the harness stopped letting subagents and background workers run mutating git. The data behind the decision: 4 denials in 3,833 git approval prompts over 30 days, 2 of them misclicks (`docs/plans/2026-10-20-command-git-safety.md`). The guard extensions caught the leaks, not the prompt.

The rule (dotfiles#140): workers edit files in the worktree the main session gave them, and the main session commits, merges and pushes. `git-gh-gate.ts` enforces it for any session with no UI:

```ts
// Workers (pi -p subagents, bg workers, loop agents: no UI) never run
// mutating git, routine or not: they edit files in the worktree the
// main session gave them, and the main session commits, merges and
// pushes (user decision 2026-10-20, dotfiles#140).
if (!ctx.hasUI) {
  audit("blocked");
  return {
    block: true,
    reason:
      "Mutating git/gh is main-session only (dotfiles#140): subagents and background workers edit files in the " +
      "worktree they were given and leave committing, merging and pushing to the main session. Finish the file " +
      "changes and report what is ready to commit.",
  };
}
```

The same gate blocks no-UI `write`, `edit` and `apply_patch` calls that target `.git/` paths. `HEADLESS_WORKER_PREAMBLE` repeats the rule in every `bg_task` prompt: "Mutating git ... is blocked here: leave all git operations to the parent and describe what to commit in your final message."

In the main session, routine local git (commit, push without force or delete, worktree add and remove, merge, switch, cherry-pick, revert, stash pop) runs without an approval prompt while the global git hooks are active. The pre-push gate runs gitleaks, blocked terms and sensitive-file checks on every push, and on public targets adds identifier shapes, provenance wording and an llmc review. Every auto-allowed command is logged. The tiers are in [Running agent git commands without per-command approval prompts](/reference/agent-git-without-prompts/) and the push checks in [Agent leak gates](/guides/agent-leak-gates/).

## /btw: side questions without interrupting

`/btw <question>` forks the current session into a read-only background worker. It answers from the full conversation history plus read-only lookups, and the answer lands in the agent view as a `btw` row while the main turn keeps running (`btw.ts`, dotfiles#63, reworked in dotfiles#134).

Before 2026-10-20, `/btw` sent the captured conversation to the model as a one-shot request and showed the answer in an overlay, with no tools and no way to add the answer to the conversation. The rewrite forks the session, so the worker has the parent's history and model. On a provider with prompt caching the shared prefix is served from cache: the first request of a 2026-10-20 probe read 520k cached input tokens (`btw.ts` header).

The fork's tool allowlist is `BTW_TOOLS` (`lib/btw-core.ts:14`): `read`, `grep`, `glob`, `lsp`, `webfetch`, `websearch`, `web_research`, `codesearch`, the `docs_*` readers, `session_search`, `memledger_search`, `search_messages` and the two context7 tools. No bash, no writes, no edits. The worker session persists under the parent's `subagents/` directory like `task` workers, so memledger ingests it.

| Command | Effect |
|---|---|
| `/btw <question>` | Fork and ask |
| `/btw` | List this session's side questions |
| `/btw add [n]` | Add answer n (default: the latest) to the main conversation as a user message |

## /undo: file-level undo

`/undo` restores the conversation and the files the agent changed. Restoring only the conversation leaves the files in the half-state the agent just edited, and the next turn starts on broken files (`session-undo.ts`, dotfiles#127).

Mechanism, lazy pre-image capture:

1. On `tool_call` for `write`, `edit`, `write_stream` and `apply_patch`, the extension records the bytes on disk before the tool runs, the first time a path is touched in a turn.
2. On `tool_result`, it records the bytes after.
3. Pre-images live in a content-addressed shadow store outside the project: `~/.local/state/pi-undo/<session-id>/objects/<sha256>`. The root is `PI_FILE_UNDO_DIR`.
4. On `/undo`, it compares each touched file's current bytes with the post-image. An unchanged file gets its pre-image back. A file changed since the agent's edit (by a human or another session) is skipped with a warning.
5. It then forks the conversation before the most recent user message and restores that prompt into the editor.

Limits:

- bash writes are not snapshotted, only the four file tools.
- Skipped: gitignored files, `node_modules`, `.git`, build directories, files over 5 MiB, and anything outside the session cwd.
- The in-memory index is empty after a pi restart, so `/undo` falls back to a conversation-only fork.
- With no UI, `/undo` refuses instead of restoring files silently.

`PI_NO_SESSION_UNDO=1` disables the extension. `PI_FILE_UNDO_OFF=1` keeps the conversation fork and drops the file restore.

The same decision as text:

1. A side question while the main turn runs goes to `/btw`.
2. Work whose result the parent reads before continuing goes to `task`: `explore` when it is read-only, `general` when it needs full tools, one call per independent angle.
3. A plain shell command (polling, build, download) goes to `bg_bash`.
4. A self-correcting loop or loop graph goes to `bg_loop`.
5. Any other long delegated work goes to `bg_task`.
