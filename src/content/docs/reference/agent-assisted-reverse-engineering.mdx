import { Aside } from "@astrojs/starlight/components";

A shipped binary has no source, and the questions about it concern behaviour its authors never documented. This page covers giving a coding agent a decompiler it can drive as tools - a reverse-engineering MCP server backed by headless Ghidra - and the workflow that lets it answer "which protocol messages does this client handle" and "does the public documentation miss anything".

The scope is static analysis of software the analyst is entitled to study: interoperability, protocol documentation, one's own tooling. Mechanisms are read from the harness source and the reverse-engineering skill as of 2026-10-20, with versions and checksums copied from the installer. A re-check on 2026-10-31 found the server pin and tool count had moved (see Evidence); the 2026-10-20 figures below stay labelled with their date. The worked example is read from the author's Soulseek parity research notes of 2026-10-19.

TL;DR:

- The decompiler is exposed as agent-callable tools, so the model reads pseudocode and cross-references instead of explaining a binary from a strings dump.
- The server exposes ~170 tools (2026-10-20), all `deferred`: found through tool search when a task needs them, not declared every turn.
- Ghidra 12.1.4 is installed by a script that checks a sha256 before unzipping, on top of JDK 21. Re-running is idempotent.
- The skill is vendored verbatim from the server's package and bumped together with the server pin.
- The worked example built a feature-parity matrix from the official Soulseek client's binary and two open-source clients, and found a server message code the public protocol documentation omits.
- A worker stops a helper process by recorded PID. `pkill -f` matches the worker's own command line and kills the worker.

## Which tool for which job

| You have | Reach for | Why |
|---|---|---|
| A question about a shipped binary or package (what protocol codes it handles, what a function does), for software you may study | The RE MCP server over headless Ghidra | Pseudocode, assembly and cross-references are the raw evidence, and the agent can query them as tools |
| An ordinary source repository, asking how the code behaves | Normal repo tools: read, grep, LSP | Source is authoritative and cheaper; the skill's own routing says to skip RE for complete source |
| A rarely-used tool capability that only some sessions need | `exposure: deferred`, found via tool search | Declared schemas are a per-turn prompt cost on every request |
| A worker that must stop a helper process it started (a headless analysis run gone long) | Record the PID to a file and kill by PID | `pkill -f` matches the worker's own command line and kills the worker |

## What static analysis answers

Reverse engineering applies when the artifact is the only source of truth. In the worked example the question was what the official Soulseek client can do and which protocol messages each feature uses, and the vendor publishes none of it. Without a decompiler an agent can read strings and guess. With one it can name the symbol a message code reaches and read the pseudocode.

The skill's boundary is the same: static analysis of software the analyst is entitled to study, never executing the target binary, no licence-circumvention work, no copied or pirated commercial software. The official client's Linux build is analysed as a shipped artifact (it ships unstripped, with debug symbols) and is never run.

## Why deferred

The REA server exposes roughly 170 tools[^rea]. Every declared tool adds its name, description and parameter schema to each outgoing request. A worker's first request used to carry about 77.5k prompt tokens with 139 tool schemas loaded across every MCP server, and a local single-lane engine re-prefilled all of it on every cache miss (measured in [Which model runs which agent work](/reference/agent-model-routing/)).

Most turns need no reverse engineering, so declaring it every turn taxes all of them. With `"exposure": "deferred"` the server's tools stay out of the per-turn list and the model fetches them through tool search. The entry keeps a `description` for the search to match: "native binaries via Ghidra (pseudocode, asm, xrefs), JS/Electron, .NET, APKs, SQLite, websites". The server is also registered `"enabled": false` globally, and a project that does RE work carries a per-project override (`mcp.json` entry and `VENDORED.md`, read 2026-10-31).

## Installing Ghidra

The installer script (`bin/re-tools-install`) pins both pieces:

- Ghidra 12.1.4[^ghidra], matching the 12.1.x line the server's provider accepts. The zip is `ghidra_12.1.4_PUBLIC_20260921.zip`, sha256 `ddac49f903da9d5bac833e5cc79395098b9c33cfd3279be5f31bd00387d2d4db`, checked before unzipping.
- A JDK 21+ on PATH, enforced up front with `command -v javac`.

The script downloads to a pinned directory, verifies the checksum, unzips into an install tree and symlinks a stable path, so `GHIDRA_INSTALL_DIR` points at whichever version is current. Re-running skips what is already in place. The same script pins a Lua 5.x bytecode decompiler the same way, for targets that bundle Lua plugins rather than native code.

<Aside type="note">
A pinned URL to a release asset still moves when upstream retags. The checksum catches a changed or truncated download, and the script re-checks it on every run.
</Aside>

## The vendored skill

The server's package ships a skill: routing instructions telling the agent which tool to open for which target (native ELF, APK, managed assembly, archive). It is vendored verbatim into the harness's skill tree, with a provenance file recording the source and the update procedure.

The skill and the server pin carry the same version, and bumping one means bumping both and re-copying the skill. The provenance file does both in one commit: unpack the new package, copy the skill files over, check the diff, then bump the `rea-agents` pin in `mcp.json` and in the provenance file itself. A skill edited out of band can describe capabilities the running server lacks and point the agent at tools that changed.

The skill's routing sets three rules:

- Installing the skill supplies instructions only. Registering the server and installing the engines are separate steps with separate failure modes.
- The first tool depends on the artifact: `open_binary` for a native binary or archive, a JS/Electron path for an extracted app, a managed-assembly path for a .NET artifact. Target-free tools take their own explicit path.
- Big artifacts get a summary view first, then a focused follow-up on the item that answers the question.

## The headless workflow

Headless Ghidra (`analyzeHeadless`) runs the analysis and dumps results with no window, so the whole loop fits inside the agent's normal tools. For the worked example:

1. Bind the official client's build through `open_binary`, then take the `binary_overview` metadata and symbol inventory.
2. Search symbols for the names the questions point at - here, the dispatch table entries each protocol message code reaches.
3. Decompile the reached function to read what it does, and cross-reference callers to see who relies on it.
4. Record each finding as a row of a coverage matrix, with the evidence (symbol, code, offset) attached.

Every conclusion is marked as observation, inference or unknown. Static analysis establishes that a symbol exists and what its decompiled body does, not that a code path runs at a particular time.

## Worked example: a Soulseek feature-parity matrix

The author builds a Soulseek client, and wanted it to reach feature parity with the official desktop client rather than staying an automation-only tool. The reference is the official client's shipped Linux build[^soulseek] - a closed binary, analysed statically. Two open-source clients (Nicotine+[^nicotine] and slskd[^slskd]) were inventoried from source for the same feature list, to see what a complete client does with each protocol message.

Because the official build ships unstripped, the symbol table carries 10,894 symbols with names attached, which turns "what does code 128 do" into a direct symbol lookup. The result is a parity matrix with one column per client (the official reference, the two open-source clients, and the author's own) and one row per feature, marked Y / partial / missing, with the protocol codes each feature still needs.

Two findings came from the binary alone, absent from the public protocol documentation[^slskproto]:

### Server code 128, Distributed Delivery Report

The public protocol document numbers the server messages it covers and skips 128 entirely. The binary has a `Server::DNetDeliveryReport(int)` symbol that the dispatch table routes code 128 to, decoding a single 32-bit value. The reference client only logs it, so the author's client can ignore it.

### An obfuscated peer connection

Decompilation of the connect path recovered how peers advertise a second real port and XOR the traffic on it with a 4-byte key rotated per block. The open-source clients do not implement it. Recovered from decompilation but not tested against a live peer, so the implementation is gated on a live handshake test.

Each "codes / notes" cell of the matrix names the exact server or peer message an incomplete feature needs next. The binary was downloaded against a pinned checksum and only strings-scanned or symbol-read, never executed.

The official build ships with symbols intact, which turned most questions into a symbol lookup. A stripped or packed target would need more decompilation per question, with the same workflow.

## Stopping a helper process by PID

A worker running the headless analysis needed to stop an `analyzeHeadless` run it had started, and ran `pkill -f analyzeHeadless`. The worker's own command line contains its prompt, and the prompt named the Ghidra tool, so `pkill -f` matched the worker and killed it with exit 143 (SIGTERM). The work was lost.

The fix is to record the PID when the helper starts (`... & echo $! > pidfile`) and kill by that PID. A pattern kill (`pkill -f`, `killall`) is safe only when the pattern cannot appear in the killer's own prompt, and an agent's prompt usually names the tool it is about to run.

## What carries over to another harness

The server name, the 170-tool count, the Ghidra 12.1.4 pin and the Soulseek specifics belong to this setup. These carry over:

1. A decompiler exposed as tools lets the agent query the binary instead of guessing from strings.
2. A pinned version plus a checksum verified before use lets a finding be re-checked against the same decompiler.
3. A capability that a minority of turns need goes behind tool search, with a description the search can match.
4. Guidance is vendored next to the server and bumped with it.
5. Findings end as a coverage matrix with per-row evidence.

```dot
digraph {
  rankdir=TB; bgcolor="transparent"; nodesep=0.3; ranksep=0.5;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=diamond, margin="0.1,0.05"];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];

  start [label="Question about how\nsoftware behaves", shape=box, style=rounded];
  q_src [label="Source\navailable?"];
  q_ent [label="Entitled to\nstudy it?"];
  q_proc [label="Worker starts a\nhelper process?"];
  r_src [label="Read, grep, LSP.\nNo RE server.", shape=box, style=rounded];
  r_stop [label="Stop. No RE.", shape=box, style=rounded];
  r_re [label="Load the RE tools via tool search;\nstatic analysis on headless Ghidra\n(pinned version + checksum)", shape=box, style=rounded];
  r_pid [label="Record its PID; kill by PID,\nnever pkill -f", shape=box, style=rounded];
  r_done [label="Distil findings into\na coverage matrix", shape=box, style=rounded];

  start -> q_src;
  q_src -> r_src [label="yes"];
  q_src -> q_ent [label="no"];
  q_ent -> r_stop [label="no"];
  q_ent -> r_re [label="yes"];
  r_re -> q_proc;
  q_proc -> r_pid [label="yes"];
  q_proc -> r_done [label="no"];
  r_pid -> r_done;
}
```

1. Source is available: use normal repository tools (read, grep, LSP). Reverse engineering is the heavier fallback, reserved for when the artifact is the only source of truth.
2. No source, and you are not entitled to study the artifact: stop.
3. No source, and you may study it: load the RE tools through tool search and analyse the artifact statically on headless Ghidra installed from a pinned version plus a verified checksum. Overview first, then focused decompilation; the target is never executed.
4. A worker that starts a helper process records its PID and kills by PID. A `pkill -f` pattern matches the worker's own argv and kills the worker instead.
5. Findings end as a coverage matrix with per-row evidence.
