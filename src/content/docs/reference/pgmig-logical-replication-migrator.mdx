pgmig is a Postgres-to-Postgres migrator built on native logical
replication[^pg-logical], published at
[github.com/erfianugrah/pgmig](https://github.com/erfianugrah/pgmig).[^pgmig-repo]
It creates a publication on the source, a subscription on the target, streams the
initial copy and the ongoing changes, checksums the two sides, and stops the world
for the few seconds it takes to drain lag, resync sequences, and drop the
subscription.[^pgmig-readme] This page is the reference for the tool's own
decisions: what the replication carries, what the schema pre-step has to restore
first, where the cutover gates sit, how the reconcile proves the copy, and what
the separate `pg_upgrade` rehearsal lab does.

The two task-sequenced guides are the implementation of this page:
[moving a project to another region](/guides/supabase-region-migration-e2e/)
runs the pipeline cross-region,[^region-guide] and
[upgrading to a new Postgres major version](/guides/supabase-postgres-major-upgrade-e2e/)
runs it into a new PG 17 project or rehearses the upgrade in the lab.[^upgrade-guide]

Naming: the tool is `pgmig` now, was `sbshift` until 2026-09-28, and was `pgshift`
before the 2026-07-03 rename recorded in `CHANGELOG.md`. Older notes that say
either name are the same program.

**TL;DR**

- **Logical replication carries table rows and nothing else.** No DDL, no roles,
  no extensions, no sequences, no `auth`/`storage` schemas. The schema pre-step
  (`bootstrap`) restores the first three; the rest is a documented hand-off
  (RUNBOOK section 6).
- **The `auth.users` FK is what breaks the copy if you skip the pre-step.** A
  `public.<table>.user_id` reference into `auth.users` rejects every child row
  until the referenced auth rows exist on the target.
- **Sequences do not replicate, so `cutover` `setval()`s every owned sequence
  from the write-stopped source.** Without it the next serial or IDENTITY insert
  collides with a replicated primary key. It is a no-op on uuid and text keys.
- **The gates are a lag drain to zero, a clean chunked checksum, and a
  quiescent source.** `watch` aborts on WAL bloat or a lost slot on its own; the
  lag gate refuses to close if writes are still arriving.
- **From a Supabase source, the subscription connection needs
  `statement_timeout=0`.** The `postgres` role is capped at 2 min, the target's
  tablesync worker runs the initial COPY outside pgmig's pinned settings, and a
  table whose copy takes longer restarts forever. pgmig has added the option
  itself since 2026-11-09; any other subscriber needs it added by hand.
- **At 3.65 GB from Postgres 15 to 17, pgmig's cutover took 1.6 s with no writer
  running (measured 2026-11-09).** The copy took 196.9 s and reconciled
  identical. The in-place upgrade at the same size lost 52 of 691 acknowledged
  probe writes sent during it, so writes have to stop for its whole run.
- **New Postgres 17 projects subscribing to one source at the same time can
  collide on a table-sync slot name.** 24 of 26 new 17.11 projects shared one
  `system_identifier`, and 3 of 3 concurrent pairs with matching slot names left
  one target's table in `f` at the end of its wait bound (40 minutes in RR10, 10
  in RR11) with the source's row count while every call succeeded (supabase-lab
  RR10 and RR11, 2026-11-10). Subscribe new targets one at a time, each after
  every earlier target has every table `r`, and read `pg_subscription_rel` on
  each rather than row counts.
- **The point of no return is repointing the app, not the cutover.** Before it,
  `teardown` plus re-enabled source writes is lossless. After it, rollback loses
  every write the target took unless reverse replication was set up first.
- **`pg_upgrade` rehearsal is a separate workflow.** It needs no
  `migrate.config.yaml` and no billable project: it captures the source, times a
  real `pg_upgrade --link` in Docker, and proves the result identical with the
  same checksum engine `reconcile` uses.

```dot
  source -> target [label="initial copy + WAL stream"];
  pre -> target [label="before replicate"];
  target -> app [label="repoint after cutover"];

```

Text fallback, the same pipeline in order:

1. `bootstrap` restores roles, extensions and schema onto the target, and with
   `--with-auth-data` the `auth` rows the FKs need.
2. `replicate` creates the publication, the slot and the subscription
   (`copy_data=true`), so the initial copy starts against a schema that already
   exists.
3. `watch` polls until every table is `srsubstate='r'` and aborts if the slot or
   the WAL watchdog trips.
4. The app stops writing to the source.
5. `reconcile` checksums both sides; `cutover` drains lag, resyncs sequences and
   drops the subscription.
6. The app is repointed at the target. The source is never written to again.

## Which move is this

| Move | Downtime | Reconfiguration after | Pick when |
|---|---|---|---|
| Logical replication (pgmig) | the lag drain, seconds | new project: new ref, new API keys, new JWT secret, the whole non-data surface | the downtime budget is smaller than a dump-and-restore window, or the move doubles as a region change |
| Dump and restore | the copy time | same new-project list | the database is small, or the pipeline is not worth rehearsing |
| Supabase clone (Restore to a new project) | the restore window | same new-project list, minus storage bytes | rehearsal, not a migration - the clone is a copy of a backup |
| `pg_upgrade` rehearsal lab | n/a - rehearsal only | n/a | you want the blocker audit and a downtime estimate without creating a billable project |

Logical replication is the only one of the four that needs the target to exist
with a loadable schema *before* the copy starts, which is why the pre-step is a
first-class command rather than a suggestion.

## What replicates, and what the pre-step carries

| Artifact | Carrier | Note |
|---|---|---|
| Table rows and the changes to them | `replicate` + `watch` | the only thing logical replication carries |
| Schema: tables, views, functions, triggers, RLS policies | `bootstrap` | pre-step; for a Supabase source it excludes the roughly 27 managed schemas and filters the cluster-level objects a plain dump still emits |
| Roles and permissions | `bootstrap` | `pg_dumpall --roles-only --no-role-passwords`, so custom LOGIN roles arrive without passwords |
| Extensions | `bootstrap` | enabled on the target before the schema load; `doctor` diffs the two sides and prints the `CREATE EXTENSION` statements still missing |
| `auth` row data | `bootstrap --with-auth-data`, or a manual dump/restore | the `auth.users` FK pre-step; `auth.schema_migrations` is excluded because the target carries its own ledger |
| Sequences | schema DDL for the object, `cutover` for the value | values do not replicate; a no-op for uuid and text primary keys |
| Generated columns (for example a STORED `tsvector`) | recomputed on the subscriber | excluded from the reconcile hash, because hashing them reports a mismatch that is not one |
| Project config, integration secrets, billable infra, Edge Functions, storage objects | `config-sync`, `provision`, `functions`, `storage` | a separate surface from the data plane; the JWT signing secret and API keys are never copied |
| Org settings, org members and roles, entitlements | nothing | read-only on the Management API; the only org-level action is claiming a project into another org |
| Read replicas, custom domains, realtime publications, custom role passwords | hand work | no clean API path; recreate or re-enter after cutover |

The exhaustive version of this table, including every dashboard surface and its
API endpoint, is the repository's `MIGRATION-SCOPE.md`.[^pgmig-scope]

<Aside type="caution" title="The copy fails row by row, not loudly">

Every FK from a replicated table into `auth.users` is checked on the target at
insert time. If the referenced auth rows are not there yet, the initial copy
rejects those child rows and the failure surfaces as a table that never reaches
`srsubstate='r'`, not as a preflight error. `doctor` flags any cross-schema FK
before you start; `bootstrap --with-auth-data` is the fix.

</Aside>

## The pipeline

| Command | What it does | Gate behaviour |
|---|---|---|
| `doctor` | Readiness report: connection shape, versions, `wal_level`, replica identity, extension diff, cross-schema FKs, foreign slots, SQL-level GUC overrides | read-only; `--source-only` for before the target exists |
| `bootstrap` | Target preparation: extensions, roles, schema, optionally auth rows | preview by default; `--confirm` mutates |
| `preflight` | Hard-gate checks: `CREATE SUBSCRIPTION` grant, replication capacity, a replica identity on every published table | fails closed |
| `replicate` | Empty publication plus `ADD TABLE` (never `FOR ALL TABLES`, which needs superuser), slot, subscription with `copy_data=true` | re-running issues `REFRESH PUBLICATION` for a newly added table |
| `watch` | Polls `pg_subscription_rel` until every table is `r`, with live copy percentage | aborts on retained WAL over the watchdog threshold or slot `wal_status='lost'`; rising apply or sync error counts only log a warning, and the sync timeout (`watchdog.syncTimeoutMin`, 240 min by default) ends the wait |
| `reconcile` | Chunked checksum, 256 buckets by default: one scan per side, bucket by primary-key hash, drill only the mismatched buckets | authoritative only after writes stop |
| `cutover` | Samples WAL LSN twice, drains lag, `setval()`s every owned sequence, drops the subscription | refuses without the writes-stopped assertion on the autonomous path |
| `teardown` | Drops subscription, slot, publication in that order | idempotent |
| `verify` | Post-migration advisor health gate on the target | fails closed if the advisors are unreachable |

`run` chains the phases for automation: `run --through reconcile --json` exits 0
only if preflight, replicate, watch and reconcile all passed, and `status
--require-synced` is the wait loop for a script that needs the copy ready.

<Aside type="caution" title="A Supabase source cancels any initial copy that runs past two minutes">

On a Supabase source the `postgres` role has no `statement_timeout` of its own,
and the timeouts page gives its default as "`postgres`: none (capped by default
global timeout to be 2min)".[^sb-timeouts] The subscription CONNECTION is dialled
by the target's tablesync worker, outside the pgmig pools that pin
`statement_timeout = 0`, so a table whose initial COPY runs longer than two
minutes is cancelled and starts again, indefinitely. It never reaches
`srsubstate='r'`. The target logs `could not receive data from WAL stream: ERROR:
canceling statement due to statement timeout`, the source logs `canceling
statement due to statement timeout`, and `sync_error_count` in
`pg_stat_subscription_stats` rises with each restart. On 2026-11-09, at
4,000,000 documents on 20 GB disks, `documents` never synced in two runs. In the
second, which read the logs before teardown, the cancellations came every 120 s
from 08:43:58 to 09:14:02 UTC: 16 restarts (`sync_error_count` 16), the other
three tables `r`, and `watch` warning until the harness's 30 min sync
limit.[^pgmig-pg17-live]

pgmig's `replicate`[^pgmig-replicate] now passes the CONNECTION through
`withNoStatementTimeout()`,[^pgmig-no-timeout] which adds
`options=-c statement_timeout=0` unless the string already sets a
`statement_timeout`. On an older pgmig, put `?options=-c%20statement_timeout%3D0`
on `SOURCE_REPLICATION_URL` (set it to the source direct URL if unset; pgmig
otherwise dials `SOURCE_DB_URL`). With any other tool, or a hand-rolled
`CREATE SUBSCRIPTION`, add it to the connection string yourself. Both halves of
the cause sit outside pgmig - the cap on the Supabase source, the tablesync
worker in Postgres - so any logical replication from a Supabase source whose
initial COPY of a table runs past two minutes meets the cap. That is reasoned from the mechanism; only pgmig's subscription was run.

```sql
CREATE SUBSCRIPTION my_sub
  CONNECTION 'postgresql://postgres:<password>@db.<ref>.supabase.co:5432/postgres?options=-c%20statement_timeout%3D0'
  PUBLICATION my_pub;
```

</Aside>

## The schema pre-step

`bootstrap` is the answer to "logical replication carries rows only".[^pgmig-runbook]
In order:

1. Enable the non-default extensions the source has and the target lacks.
2. Restore roles from a roles-only dump. Supabase's reserved roles are filtered
   out the same way `supabase db dump --role-only` filters them, so only your
   application roles are created - and they arrive with no passwords.
3. Restore the schema: DDL, RLS policies, functions, triggers.
4. With `--with-auth-data`, dump and restore the `auth` schema rows with
   `session_replication_role = replica`, so FK triggers are deferred during the
   load rather than checked per row. `auth.schema_migrations` is excluded: the
   managed target grants the `postgres` role SELECT only on it, and it has its
   own migration history.

The manual equivalent for a non-Supabase pair is a `pg_dumpall --roles-only`
plus a `pg_dump --schema-only`, restored with `ON_ERROR_STOP=1`, with any
cross-schema reference data loaded under `session_replication_role = replica`.
`doctor` gives you the same diff either way.

Two failure modes recur in the window. A part-way `bootstrap` can
be recovered by running the auth-data dump and restore commands it printed rather
than re-applying the whole schema, because a re-run re-plans the schema restore
against tables that now exist. And any custom LOGIN role reaches the target with
`rolpassword` NULL, so every service using one needs
`ALTER ROLE <name> WITH PASSWORD '...'` before it is repointed.

## Sequences, and why cutover resyncs them

A sequence is schema, so the pre-step creates it on the target and carries the
value it held at dump time. Rows inserted on the source between `bootstrap` and
the write stop replicate with their explicit primary keys, which the sequence on
the target never sees. The first insert after cutover then picks a value the
sequence has already handed out, and the primary-key unique index rejects it.

`cutover` closes that gap by resynchronising every sequence owned by a replicated
column, using the write-stopped source as the authority. Serial and IDENTITY
columns are covered; uuid and text primary keys have no sequence to resync, so
the step is a no-op for them. The companion upgrade guide records the check that
proves it - an insert after cutover returns the next id rather than colliding.

## The cutover gates

The tool owns the data-plane gates; your dashboards own the app-tier ones. Decide
the app-tier numbers before the window, from a baseline.

| Phase | Data plane (the tool) | App tier (your dashboards) |
|---|---|---|
| Initial copy | retained WAL under `watchdog.maxRetainedWalMb`, slot active, `wal_status` still `reserved` or `extended`, apply and sync error counts flat | source CPU, disk IOPS and latency headroom; connections not near saturation |
| Reconcile | zero mismatched buckets | - |
| Lag drain | lag reaches 0 inside `--max-lag-wait` (300 s by default), the source WAL reads as quiescent | the app is confirmed read-only or down; no write retries still hitting the source |
| After the repoint | the cutover log shows a `setval` per sequence | target p95 and p99 within your margin of the baseline, error rate flat, pool not spiking on retries |

The hard stops, in the tool's own words: `watch` aborts on retained WAL over the
threshold and immediately on `wal_status='lost'`; a lag drain that times out
means writes were not actually stopped, so do not proceed; any reconcile mismatch
means the cutover is not finished, whatever the lag says. Those are not advisory.

**Never re-enable writes on the source after the repoint.** Two databases
accepting writes is split-brain, and nothing in the pipeline reconciles it.

## Reconcile, and why the hash is comparable cross-region

`reconcile` scans each side once, buckets rows by a hash of the primary key,
and compares bucket checksums. Only the buckets that differ are drilled, and the
report names the rows as `missing_on_target`, `extra_on_target` or `hash_diff`.
Full-table mode is available for small tables and is not the default because a
single aggregate scan of a real database is both slower and less specific about
where the difference is.

The comparison only works if both sides render the same row values the same way.
The row hash is taken over the row's text form, which depends on `TimeZone`,
`DateStyle`, `IntervalStyle`, `extra_float_digits` and `bytea_output`. Every
connection in both pools therefore pins those settings identically and sets
`statement_timeout = 0`, so a cross-region run compares values and not two
machines' display conventions.[^pgmig-skill] The subscription's CONNECTION is
dialled by the target and belongs to neither pool, which is why it carries its own
`statement_timeout=0` from a Supabase source (the caution under
[the pipeline](#the-pipeline)).

Two consequences: timestamptz comparisons are stable across regions, and a STORED
generated column has to be excluded from the hash - the subscriber recomputes it,
and hashing it would report a mismatch on every row that has one.

## The pg_upgrade rehearsal lab

This is a separate workflow from the migration pipeline. It needs no
`migrate.config.yaml` and no Supabase project, and it exists to put a number on
the in-place upgrade window before you take one. The underlying step is
`pg_upgrade --link`.[^pg-upgrade]

| Step | Command | What it produces |
|---|---|---|
| Audit | `upgrade doctor --to <version>` | read-only readiness report: extensions deprecated on the target major, `reg*` columns referencing system OIDs, foreign replication slots, roles on md5 password storage, and a downtime estimate from the database size. Exit 1 on a hard blocker |
| Capture | `upgrade capture --out-dir capture --max-gb <n>` | roles, schema and data dumped locally with a `manifest.json`; refuses to capture past the size limit unless forced; `--with-auth-data` for a Supabase source |
| Lab | `upgrade lab --capture-dir capture --runs 3 --keep` | starts an old-version and a new-version container, snapshots the old data directory, runs `pg_upgrade --link` N times with a fresh snapshot per run, then `ANALYZE`, and prints the timings. `--keep` leaves both containers up for the verify step; `--seed-gib` inserts fixture data instead of real data; `--prod-bytes` extrapolates the production window |
| Verify | `upgrade verify` | pre-upgrade copy at `SOURCE_DB_URL` against the upgraded cluster at `TARGET_DB_URL`, through the same chunked-checksum reconcile, plus extension versions, auth schema sanity and md5-role status. Exit 0 only when the data is identical |

The lab is the only phase that needs Docker; the audit and the capture run
anywhere `psql` does. Because verify is the reconcile engine, a pass there means
the same thing a pass before cutover means - the two sides checksum identical
under the same GUC pinning.

## Rollback, by phase

| Phase | Position | What rollback costs |
|---|---|---|
| A: before writes stop | the source has served continuously, the target is a throwaway | free: `teardown` removes the replication objects and the source is untouched |
| B: writes stopped, app not repointed | the target has taken no application writes | still lossless: `teardown`, then re-enable writes on the source and bring the app up unchanged |
| C: app repointed | the target is authoritative and nothing streams back | roll forward, accept the loss window and re-apply it by hand, or use the reverse path below. Re-enabling writes on both sides is split-brain |

Reverse replication keeps phase C lossless. It is a second config with the source
and target swapped, distinct slot, publication and subscription names, and
`copyData: false` - the data already matches, so only new changes stream back.
Set it up after `reconcile` passes and before the repoint; roll back inside the
window by stopping writes on the target, draining the reverse lag, repointing at
the source, and tearing down both directions. It is not active-active: only one
side ever takes application writes.

## Postgres 15 to 17 live runs, 2026-11-09

pgmig's research note records a move from Postgres 15 to 17 at two sizes, and
the platform's in-place upgrade at the same sizes for comparison.[^pgmig-pg17-live]
Shape: throwaway projects on a Team-plan organisation, ap-southeast-1, Small
compute. The source and the in-place subject were created with
`postgres_engine: "15"` (PostgreSQL 15.19); the pgmig target took the platform
default (PostgreSQL 17.11). The seed puts a STORED tsvector on `documents`, the
copy bottleneck the evidence table names. One run per size, so every figure
below is n = 1 (a first 3.65 GB in-place attempt reached ACTIVE_HEALTHY at
695.5 s and lost its survival check to `getaddrinfo ENOTFOUND`).

pgmig, 15.19 to 17.11, with no writer running and no app repoint in the harness:

| Step | 50,000 documents (0.06 GB) | 4,000,000 documents (source 3.65 GB) |
|---|---|---|
| Seed | not recorded | 643.1 s |
| Initial copy (`replicate` + `watch`) | 5.4 s | 196.9 s; 4 of 4 tables `r`, WAL retained 10MB at the end |
| Reconcile, 256 buckets | 0.8 s, identical (4 tables) | 62.6 s, identical: `users` 50000, `documents` 4000000, `events` 4000000, `audit` 400000 |
| Cutover (the write-stop window before the app repoint) | 1.6 s | 1.6 s; lag drained to 0.0 KB |
| Insert after cutover | id 50001: the sequence resync prevented a collision | id 4000001 |

The 50,000-document run predates the `statement_timeout` fix; its 5.4 s copy
stayed under the 2 min cap. The 4,000,000-document column is the re-run with the
fix, 09:16 to 09:40 UTC on 20 GB disks. Before it, on the default disk the seed failed
after about 6 minutes with `cannot execute INSERT in a read-only transaction`
(SQLSTATE 25006), the platform making the database read-only as the volume
filled; two runs on 20 GB disks without the fix never finished `documents`
(the caution under [the pipeline](#the-pipeline)). In the 50,000-document run,
`doctor` warned on the Small 17 target: `max_worker_processes=6` (asks for 16 or more),
`max_logical_replication_workers=4` for 4 tables (asks for 5 or more), and
`pg_stat_statements` 1.10 on the source against 1.11 on the target.

The in-place runs upgraded 15.19 to 17.11 (target image
`supabase-postgres-17.11.0.018`). Eligibility answered `eligible: true`,
`duration_estimate_hours: 1` at both sizes. A 1 s probe writer inserted numbered
rows through the session pooler throughout, and a 2 s sampler opened a fresh
pooler connection each time. At 3.65 GB the project reached ACTIVE_HEALTHY
633.1 s after the POST (337.4 s at 0.06 GB). 53 of 458 acknowledged probe writes
at 0.06 GB and 52 of 691 at 3.65 GB were absent on 17, every one acknowledged by
the last 15.19 restart before 17.11 answered, which matches supabase-lab
upgrade-integrity UI03 on Micro (2026-10-23 and 10-26,
[RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/2f7df19/experiments/upgrade-integrity/RUNLOG.md)).
The time from `9_completed_upgrade` to ACTIVE_HEALTHY grew from 20.4 s at
0.06 GB to 296 s at 3.65 GB while 17.11 was already answering; what that tail
is was not separated.

Side by side at 3.65 GB, one run each:

| | pgmig | In-place upgrade |
|---|---|---|
| Writes must stop for | 1.6 s of cutover, plus the app repoint | the whole upgrade, from before the POST: the first lost write was acknowledged at +272.9 s and 17.11 first answered at +344.6 s |
| Client-visible outage in the run | none measured (no writer, no repoint in the harness) | longest failed sample run 35.1 s (+235.3 s to +270.4 s) |
| Acknowledged writes lost | none possible after a drained cutover (reconcile identical) | 52 of 691 |
| What changes for the app | new project URL, keys and connection strings | nothing |

Not measured:

- An app writing through the pgmig cutover, a repoint, or a source with Auth
  users or Storage objects to carry.
- Any compute larger than Small, any region but ap-southeast-1, more than one
  completed run per size, databases larger than 3.65 GB.
- Whether the in-place tail scales linearly past 3.65 GB, and what the Data API
  does during it.

Every project was deleted by its harness's teardown; cost was not metered.

Postgres names each table-sync slot
`pg_<subscription oid>_sync_<table oid>_<system identifier>`, and all three
values are read on the subscriber, while the slot itself is created on the source.
The code appends the system identifier "to avoid slot_name collision with
subscriptions in other clusters".[^pg-tablesync-name] Two subscribers whose three
values match therefore compute the same slot name on one source, as RR10's two
targets did: `pg_17650_sync_17643_7703759698107299042`. The names come from
Postgres, so any tool that subscribes with `copy_data=true`, pgmig's `replicate`
included, gets the same names; that is reasoned from the code, not run with pgmig.

On new 17.11 projects the identifier repeated. 24 of 26 reported
7703759698107299042 and 2 reported 7703760980994770283, so every project read
shared its identifier with at least one other (RR10's two targets and a fourth
project, all read by hand; RR11a in runs 1 to 4). That holds for one region and one
organisation: RR11's projects and RR10's two targets were in ap-southeast-1 on one
Team-plan organisation, at the default size (RR11) or Small (RR10), and the fourth
project's size, region and organisation were not recorded. The 15.19 sources
reported 7703759990361338896 (RR10, RR11 runs 1 to 3) and 7703761001322865815
(RR11 run 4).

The OIDs have to match as well. After the same setup steps, 10 of the 16
subscribed targets (RR10's two, RR11 runs 2 to 4) had subscription/table OIDs
17650/17643 and five other combinations came up, so which targets would match was
not known until each target's table existed. On all 16 the subscription OID was
the table OID plus 7.

Every target in these pairs had the same `system_identifier`; the slot values
column gives the subscription/table OIDs.

RR10 and RR11 run 3 that target still missed the rows written afterwards at the
30 s read; in run 4 that target (T3) was `r` with 501,000 rows by then, and the
target missing rows at the 30 s read was T5, from the one-at-a-time pair. No call
failed: every `CREATE SUBSCRIPTION` answered HTTP 201 through the query endpoint
or ran without error in a session. RR10 has log evidence of the collision: at
09:33:03 UTC the source's walsender logged `replication slot
"pg_17650_sync_17643_7703759698107299042" already exists`, from 09:34:54 every
attempt logged `does not exist`, about every 5 s to the end of the read window at
09:38:37 UTC, and at 10:18 UTC A's tablesync
worker was still starting and exiting with code 1 about every 5 s while its apply
worker stayed up
([manual reads](https://github.com/erfianugrah/supabase-lab/blob/b339e99/experiments/replica-routing/out/2026-11-10/rr10-manual-reads.md)).
That B's cleanup dropped the slot is inference from the timing. RR11 searched no
log for slot errors, so its two collisions are inferred from the states and
counts. Concurrent pairs whose OIDs differed did not collide (RR11 run 2, and the
controls in runs 3 and 4).

Postgres drops a table-sync slot when that table reaches sync-done ("Cleanup the
tablesync slot", in the sync-done branch[^pg-tablesync-cleanup]), so a target
started after every earlier target has every table `r` cannot meet an earlier
target's sync slot. That rests on the Postgres code and one incidental case: in
RR11 run 2, T3 (17650/17643) subscribed after T2 (17650/17643, the same
`system_identifier`) had every table `r`, and T3 was `r` by the 16 s check and
held 501,000 rows at the 30 s read. The pairs RR11 ran as one-at-a-time in runs 2
and 3 had different OIDs, and run 4's matching pair started while an earlier
matching target was stuck.

Run 4's states read as slot stealing. This is a reading of states; no log was
searched for slot errors. T3, stuck in `f` after the concurrent pair, was `r` with
501,000 rows by the 30 s read. T4, which subscribed while T3 was stuck, never
reached `r` in its 10-minute bound but was `r` by the 30 s read. T5 started at
T4's bound, was the last subscribed target with the same values (T6 had the same
`system_identifier` and table OID but was not subscribed), and ended in `f` with
500,000 rows. The reading is that a
stuck target keeps retrying, takes the next same-named slot when it is created,
finishes, drops it and strands the newer target. One at a time therefore holds
only while no earlier target with the same values is stuck. A target that
recovers this way would start from the newer slot's point and miss writes made in
between; that is inference as well, and nothing was written on the source in that
window.

A stuck target's row count matched the source's in all three collisions, so read
the state on each target instead:

```sql
-- no rows once every table on this target is ready
select srrelid::regclass, srsubstate from pg_subscription_rel where srsubstate <> 'r';
```

Then write a marker row on the source after the last subscription and read it
back on every target.

The same RR11 runs counted whether `CREATE SUBSCRIPTION`, connection string and
password included, reached the target's Postgres log. `log_statement` was read
on 7 of the 14 subscribed targets in runs 2 to 4 (one each in runs 2 and 3, all
five in run 4) and was `ddl` on all 7. Every target that did not set `log_statement` logged the
statement with the password, 11 of 11; `set log_statement = 'none'` in the same
session first kept it out on 3 of 3. Runs 2 and 3 do not separate the setting from
the connection path, because their targets that ran the `set` were also the only
ones in a session-pooler session. Run 4's T4 is the like-for-like control: the
same session-pooler path without the `set`, and it was logged. Run 4's T5, with
the `set`, had 422 Postgres log rows in the hour, so its logs were readable. The
module counted rows and printed no log text. RR10's A logged the same statement
with the password in plain text (hand read; `log_statement` was not read there).
pgmig's `replicate` at `cd29532` puts the source connection URL, which carries the
password, in the CONNECTION and sets `log_statement` nowhere in `src/`, so on a
target with `log_statement` `ddl` its statement would be logged too; that is read
from the code, not run.

```sql
-- one session on the target (RR11 used a session-pooler session), both statements in it
set log_statement = 'none';
create subscription my_sub
  connection 'postgresql://postgres:<password>@db.<source-ref>.supabase.co:5432/postgres?options=-c%20statement_timeout%3D0'
  publication my_pub;
```

Not settled by RR10 and RR11: recovering a stuck table on purpose
(`refresh publication`, or dropping and recreating the subscription); one at a
time with matching names and no stuck target beyond run 2's T2 then T3, one
instance; writes during a slot-steal window; `set log_statement` from the SQL
Editor or the query endpoint; `alter subscription ... connection`; more than two
concurrent targets with matching slot names; table sizes other than RR11's 500,000
rows (about 0.5 GiB, scaled from RR10's 3.9 GiB for 4,000,000 rows; not read in
RR11) and RR10's 4,000,000 rows.

## A source with network restrictions on (RR12)

Network restrictions apply to all connection routes, pooled or direct,[^sb-netrestrict]
and the IPv4 address page says that when a database makes outbound connections,
the outbound address "is not static and cannot be guaranteed".[^sb-ipv4] RR12
(replica-routing, 2026-11-11, two runs) asked which address a source sees when
another project's subscription connects to its direct host, and what a
restriction does to a subscription already streaming. It used three throwaway
projects on the Team-plan organisation at the default compute size in
ap-southeast-1, a source S on `postgres_engine: "15"` (15.19) and targets T and T2
on the default (17.11). S held `rr12_t` with 1,000 rows, published; T subscribed
over S's direct host on port 5432. Restrictions were applied with
`POST /v1/projects/{ref}/network-restrictions/apply`, and the documentation ranges
192.0.2.0/24 and 2001:db8::/32 stood for every other address. Both artifacts name
lab commit `b339e99`, which predates the module; run 1 used an earlier version and
ended with `The operation timed out.` before RR12g (by elimination, during RR12f's
call), and the committed module is run 2's with the RR12g query fixed after it
([RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/RUNLOG.md);
facts for [run 1](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-11/run-2026-11-11T04-29-45-868Z.facts.md)
and [run 2](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-11/run-2026-11-11T04-34-58-170Z.facts.md)).

Each project's database host had one AAAA record and no A record. With S open,
T's `CREATE SUBSCRIPTION` returned 201 and T held 1,000 rows at the first check;
on S, `pg_stat_replication` listed `rr12_sub_t` streaming, with `client_addr` the
address T's own database host, `db.<target ref>.supabase.co`, resolves to (the
text cast renders it as a /128). The subscriber connected from its own IPv6
address, and that is the address the source's restriction judged.

| Step (both runs unless stated) | Source allows | Result |
|---|---|---|
| RR12c | every address | T subscribed and held 1,000 rows at the first check; S's `pg_stat_replication` listed the walsender serving T with `client_addr` T's own address |
| RR12d | 192.0.2.0/24 and 2001:db8::/32 | 20 s later T's walsender was still on S, streaming, and 100 rows inserted on S were on T at the first check. A walsender that was already streaming was still on S 20 s after the
restriction's apply call, in two runs; RR12d did not read whether the restriction
was in force at that read. After T disabled and re-enabled its subscription it had
not reconnected 60 s later; once its own /128 was allowed it held every row by the
10 s (run 1) and 5 s (run 2) checks. No error source was read for the missing
reconnect: RR12g, the step meant to read the subscribers' Postgres log lines,
returned no data (run 1 ended before it, and run 2's query named `postgres_logs`
as a table). T2's `CREATE SUBSCRIPTION` hung instead of failing at
`connect_timeout`, and in run 2 a statement timeout ended it at 120 s.
Why `connect_timeout` did not apply was not checked, and that the restriction
blocked T2 at all is inference, as T2 was not tried with S open; RR13 run 1 later
saw a second target's `CREATE SUBSCRIPTION`, with no `connect_timeout` in its
connection string, end in the same `57014` statement timeout with the source open
([below](#a-source-with-the-ipv4-add-on-rr13)).

The address to allow is the AAAA record of the target's own database host, as a
/128 in the IPv6 list. On the source, while the subscription streams, RR12c's read
shows it:

```sql
select client_addr::text, application_name, state from pg_stat_replication;
```

Resolving the AAAA record of `db.<target ref>.supabase.co` gives the same address
(RR12c compared the two). No run changed the target's instance, so whether that
address moves on a restart, resize, pause and restore or upgrade is open, and
re-checking it after any of those is a design choice taken from the docs'
outbound-address line rather than a result.

Not measured in RR12: a source with the IPv4 add-on (the restrictions page says
only IPv4 CIDRs are needed then; RR13 below ran a source with the add-on but kept
2001:db8::/32 in the IPv6 list); whether a target's address changes on restart,
resize, pause and restore or upgrade; a subscription through the session pooler; a
walsender's survival under a restriction beyond 20 s; the subscriber's log lines
for the blocked connection (RR12g); a target in another region.

On a source with the add-on, the address to allow is the target's outbound IPv4,
which its database host's DNS does not show. The target can read it itself, which

```sql
create extension if not exists pg_net;
select net.http_get('https://api.ipify.org');                 -- returns a request id
select content from net._http_response where id = <id>;       -- a few seconds later
```

## Decision guide

```dot
digraph {
  rankdir=LR; bgcolor="transparent"; nodesep=0.3; ranksep=0.7;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];
  q [label="what is being moved?"];
  data [label="rows, into an\nexisting schema"];
  all [label="a whole project\nto another region"];
  ver [label="a Postgres major\nversion, in place"];
  rep [label="replicate -> watch\n-> reconcile -> cutover"];
  pre [label="bootstrap first,\nthen replicate"];
  lab [label="upgrade doctor ->\ncapture -> lab -> verify"];
  q -> data [label="same schema"];
  q -> all [label="new project"];
  q -> ver [label="no new project"];
  data -> rep;
  all -> pre -> rep;
  ver -> lab;
}
```

Text fallback:

1. A Postgres major-version change in place, no new project - the `pg_upgrade`
   rehearsal lab, then the upgrade itself.
2. A whole project to another region or a new major version as a new project -
   `bootstrap` first, then the replication pipeline; this is the region guide.
3. Data only, into a schema you already created and control - `replicate` onward,
   with the pre-step done by your own tooling.
4. Small database, downtime acceptable - dump and restore, and skip the pipeline.

## Evidence

| Claim | How it was checked |
|---|---|
| Logical replication carries rows, not DDL, roles, extensions or sequences | Postgres logical replication documentation, and pgmig's own scope document (`MIGRATION-SCOPE.md`, commit `ba5f88c`) |
| `bootstrap` restores extensions, roles and schema, and `--with-auth-data` adds the `auth` rows with FK triggers deferred | pgmig `README.md` and `docs/RUNBOOK.md` section 6 (documented procedure); exercised live on 2026-07-30 per the region guide's measured run |
| `auth.schema_migrations` is SELECT-only for the `postgres` role on a managed target | RUNBOOK section 6, recorded as verified 2026-07-30; reproduced in the upgrade guide's gotchas |
| A sequence collision follows a skipped resync, and `cutover` closes it | The companion upgrade guide's sequence check (an insert after cutover returns the next id after 300 seeded rows) |
| `watch` aborts on the WAL watchdog and on `wal_status='lost'` | pgmig `README.md` command table and the scale harness's `WATCHDOG_FIRE=1` negative mode, which exits non-zero if the abort does not fire |
| A write that continues through cutover makes the lag gate fail | The scale harness's `WRITE_THROUGH_CUTOVER=1` mode, which asserts the `lag did not drain` failure |
| A STORED generated column is the initial-copy bottleneck | pgmig's large-scale rehearsal, reported in `README.md` and repeated in the companion upgrade guide (about 7x slower copy) |
| Cross-region row hashes match only because the GUCs are pinned | pgmig `skills/pgmig/SKILL.md` and the reconcile implementation; the cross-region pass itself is the region guide's measured run |
| DDL on the source stalls the stream until the same DDL is applied on the target | supabase-lab W15, cited in both companion guides (about 6.1 s to resume with backfill) |
| `watch` warns on rising apply or sync error counts and does not abort on them | [`src/steps/watch.ts`](https://github.com/erfianugrah/pgmig/blob/ba5f88c/src/steps/watch.ts) at `ba5f88c` (a `log.warn`, then the sync timeout); measured 2026-11-09, when `watch` warned through `sync_error_count` 16 until the harness's 30 min limit ([research note](https://github.com/erfianugrah/pgmig/blob/cd29532/docs/research/2026-11-09-pg15-to-17-live.md)) |
| From a Supabase source, a subscription without `statement_timeout=0` cancels an initial COPY longer than 2 min and restarts it | Measured 2026-11-09, 4,000,000 documents, two runs on 20 GB disks that never synced `documents`; the second read the logs: the target and source log lines every 120 s, `sync_error_count` 16; the re-run with [`withNoStatementTimeout()`](https://github.com/erfianugrah/pgmig/blob/cd29532/src/db.ts) synced in 196.9 s ([research note](https://github.com/erfianugrah/pgmig/blob/cd29532/docs/research/2026-11-09-pg15-to-17-live.md)). The 2 min cap is documented on the [Supabase timeouts page](https://supabase.com/docs/guides/database/postgres/timeouts); that it hits any subscriber is reasoned from the mechanism |
| pgmig's write-stop window from 15.19 to 17.11 was 1.6 s at 0.06 GB and at 3.65 GB, reconcile identical | Measured 2026-11-09, one run per size, Team-plan organisation, Small, ap-southeast-1, no writer running and no app repoint ([research note](https://github.com/erfianugrah/pgmig/blob/cd29532/docs/research/2026-11-09-pg15-to-17-live.md)) |
| The in-place upgrade loses writes acknowledged by the last 15.19 restart | Measured 2026-11-09, 2 of 2 runs with a completed survival check, one per size (53 of 458 at 0.06 GB, 52 of 691 at 3.65 GB); agrees with supabase-lab upgrade-integrity UI03 ([RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/2f7df19/experiments/upgrade-integrity/RUNLOG.md)) |
| A multi-GB seed on a default-size disk turns the database read-only (SQLSTATE 25006) | Measured 2026-11-09, the 4,000,000-document seed, failed after about 6 minutes ([research note](https://github.com/erfianugrah/pgmig/blob/cd29532/docs/research/2026-11-09-pg15-to-17-live.md)) |
| New 17.11 projects share a `system_identifier`, so two targets whose OIDs also match compute the same table-sync slot name on one source | Measured 2026-11-10: 24 of 26 projects one value and 2 of 26 another (RR10 hand read, RR11a runs 1 to 4), 25 of them in ap-southeast-1 on one Team-plan organisation and RR10's fourth project's size, region and organisation not recorded; subscription/table OIDs 17650/17643 on 10 of 16 subscribed targets ([RR10 RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/b339e99/experiments/replica-routing/RUNLOG.md), [RR11 RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/RUNLOG.md)). The name format is `ReplicationSlotNameForTablesync` in Postgres 17's [tablesync.c](https://github.com/postgres/postgres/blob/f2acab53482cfd444c8ac23d317f90ad6f6b1a7f/src/backend/replication/logical/tablesync.c#L1276-L1299) |
| Concurrent targets with matching slot names leave one table in `f` at the end of the wait bound with its count equal to the source's, and no call fails | Measured, 3 of 3 pairs: RR10 (one run, 3.9 GiB, 40-minute bound) and RR11 runs 3 and 4 (500,000 rows, 10-minute bound). Log evidence only in RR10 ([manual reads](https://github.com/erfianugrah/supabase-lab/blob/b339e99/experiments/replica-routing/out/2026-11-10/rr10-manual-reads.md)); RR11's two are inferred from states and counts ([run 3](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-10/run-2026-11-10T12-41-03-975Z.facts.md), [run 4](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-10/run-2026-11-10T13-24-53-642Z.facts.md)) |
| Subscribing one target at a time avoids the collision while no earlier target with the same values is stuck | The Postgres code drops the slot at sync-done ([tablesync.c](https://github.com/postgres/postgres/blob/f2acab53482cfd444c8ac23d317f90ad6f6b1a7f/src/backend/replication/logical/tablesync.c#L306-L345)); one incidental measured case, RR11 run 2's T2 then T3 ([facts](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-10/run-2026-11-10T12-36-39-047Z.facts.md)). Run 4's states at the 30 s read (T3 recovered, T5 in `f`) are measured; reading them as slot stealing is inference, as no log was searched |
| `set log_statement = 'none'` in the same session keeps the `CREATE SUBSCRIPTION` password out of the target's Postgres log | Measured 2026-11-10, RR11f runs 2 to 4: 11 of 11 targets without the `set` logged it, 0 of 3 with it; run 4's T4 is the same session-pooler path without the `set`. Counts only, no log text printed ([RR11 RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/RUNLOG.md)) |
| A subscriber connects from its own database host's IPv6 address, and a restricted source admits it once that /128 is allowed | Measured 2026-11-11, RR12c to RR12e, two runs, ap-southeast-1, one Team-plan organisation ([run 1](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-11/run-2026-11-11T04-29-45-868Z.facts.md), [run 2](https://github.com/erfianugrah/supabase-lab/blob/6b30084/experiments/replica-routing/out/2026-11-11/run-2026-11-11T04-34-58-170Z.facts.md)).
