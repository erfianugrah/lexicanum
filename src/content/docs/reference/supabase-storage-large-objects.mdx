What Supabase Storage does with a 2 GiB object over the S3 endpoint, the REST read paths and TUS, which of the S3 headers an existing client sends are enforced and which are accepted and ignored, and where a self-hosted stack answers differently from a managed project. For anyone moving large objects, resumable uploads or an S3 client onto Storage. The claims under test come from the S3 compatibility page[^sb-s3-compat], the resumable uploads page[^sb-resumable], the file limits page[^sb-file-limits] and the Storage server source.

Every figure marked measured comes from the [supabase-lab](https://github.com/erfianugrah/supabase-lab) harness, [experiments/storage-surface](https://github.com/erfianugrah/supabase-lab/tree/5f7ce52/experiments/storage-surface), run on 2026-10-12. One module, `SS03`, runs the SS03, SS04 and SS05 rows against one target per run; SS06 is the row-by-row diff of those runs and SS07 is a read of the Management API. Managed: one throwaway Pro-org project per run in `ap-southeast-1`, created and deleted by the module, Storage server 1.80.2, reached on two hosts, the gateway `<ref>.supabase.co` and the direct storage host `<ref>.storage.supabase.co`, with S3 in the session-token form and the `service_role` JWT[^sb-s3-auth]. Self-hosted: the [self-hosted-defaults](/reference/supabase-self-hosted-defaults/) rig at its pinned supabase/supabase commit on Docker Desktop for macOS, one fresh stack per run, one host (the Envoy gateway at `localhost:8000`), S3 with the stack's protocol keys. The client was the AWS SDK for JavaScript v3 and tus-js-client 4.3.1 under Node, from one laptop. Fixtures were generated from fixed seeds: `big` 2 GiB (128 parts of 16 MiB), `mid` 64 MiB, a gzip stream of 256 MiB of random bytes, and a 64x64 PNG.

Which run backs which figure. Managed figures are from run 2 ([`run-2026-10-12T08-47-30-825Z`](https://github.com/erfianugrah/supabase-lab/blob/5f7ce52/experiments/storage-surface/out/2026-10-12/run-2026-10-12T08-47-30-825Z.facts.md)), except the cache-state and timing cells of SS03d and SS03k, which are from run 4 ([`run-2026-10-12T10-15-37-476Z`](https://github.com/erfianugrah/supabase-lab/blob/5f7ce52/experiments/storage-surface/out/2026-10-12/run-2026-10-12T10-15-37-476Z.facts.md)), a re-run of those two rows with a fresh key per path and host. Run 3, made before run 4, repeats part of its rows and lost DNS near the end. Run 1 is superseded by a harness bug and is not cited. Each self-hosted variant ran the full battery once; `sh-s3@v1.80.2` also ran SS03d and SS03k a second time as the control. Anything not marked measured is cited to the documentation as fetched on 2026-10-12 or to the Storage server source, and was not run.

TL;DR:

- Multipart and resume work on every target. Per-part ETags equal the local part MD5 (128 of 128); a new process finds an unfinished upload with ListMultipartUploads and ListParts and completes it. The final ETag follows the backend: the AWS form `-128` on managed and on self-hosted MinIO, the object MD5 on the self-hosted file backend.
- Single ranges return 206 with the right bytes everywhere. A multi-range request or a `Bytes=` unit with a capital B sent to S3 GetObject on managed returns 200 and the whole object, 2 GiB for `big`. `Accept-Ranges` is absent on every S3 response.
- On managed, S3 GetObject enforces `If-Match` and `If-Unmodified-Since` (412). The CDN read paths answer from cache and ignore a wrong `If-Match` on a HIT. After an overwrite through S3, `/object/authenticated` served the pre-overwrite bytes from cache. S3 HeadObject ignored every conditional header on every target.
- Accepted and ignored on every target: conditional PUTs (the object is overwritten), wrong checksums and a wrong `Content-MD5` (the body is stored), and SSE-C, `AES256` and `aws:kms` headers (an SSE-C object is readable without its key).
- The CDN cached and served the 2 GiB object intact. In one probe per direction, `/object/public` and `/object/authenticated` share one cache entry per host on a public bucket; signed URLs have their own; the gateway and the direct host do not share. A cold 1 KiB range of the 2 GiB object answered with response headers within 1,718 ms (total 1,728 ms), managed run 4, one sample per cell; one repeat read took 31,521 ms.
- TUS: 5 and 8 MiB chunks completed with the right bytes (the docs say 6 MiB only), a resume after SIGKILL completed, also from the gateway to the direct host, and an existing key without `x-upsert` answered 409 (the docs say 400). `Upload-Expires` was 24 hours on managed, 1 hour on self-hosted MinIO and absent on the self-hosted file backend.
- Self-hosted at the pinned Storage 1.74.0 ignores `If-Match` and drops `Content-Encoding: gzip`; with the image at 1.80.2, S3 GetObject and presigned GET enforce `If-Match` and `If-Unmodified-Since` as managed does (412), and the REST read paths differ, because managed answers 200 or 206 from cache. `Content-Encoding: gzip` matches managed on every path. Envoy echoes the Origin and exposes `*`; managed sends `Access-Control-Allow-Origin: *` and no expose list on GET.

1. On managed the client reaches Storage through either host. REST reads (signed URL, `/object/public`, `/object/authenticated`) pass through the CDN and carry a `cf-cache-status` of MISS, HIT or REVALIDATED; S3 and presigned S3 reads carry `DYNAMIC`, so the origin answers them.

## Which do I pick

| You need | Use | Why (measured unless marked) |
|---|---|---|
| To upload a 2 GiB object with resume | S3 multipart with 16 MiB parts, or TUS | Both resumed from a new process on every target; S3 via ListMultipartUploads + ListParts, TUS from the stored upload URL |
| To check an upload landed intact | A SHA-256 of a GET, or per-part ETags against local part MD5s | Wrong `x-amz-checksum-*` and `Content-MD5` values were accepted and the body stored |
| A ranged read that must reflect the current object | S3 GetObject or a presigned S3 GET | `DYNAMIC` on managed, so the origin answers; it enforced `If-Match` at 1.80.2 |
| A cacheable ranged read | `/object/public` or `/object/authenticated` | MISS then HIT; the two share one cache entry per host on a public bucket |
| To replace an object that readers fetch through the CDN | A new key | `/object/authenticated` served the pre-overwrite bytes from cache after an S3 overwrite; the resumable uploads page advises new paths too[^sb-resumable] |
| "Create only if absent" | A check in your own code, or TUS without `x-upsert` | PutObject `If-None-Match: *` overwrote on every target; TUS without `x-upsert` answered 409 |
| Data encrypted under a key you hold | Client-side encryption | SSE-C headers were accepted and ignored; a client-side AES-256-GCM object round-tripped by chunk-aligned ranges |
| A browser multipart upload | S3 UploadPart from the page | Managed exposes `etag` on UploadPart responses; GET responses expose no ETag or Content-Range |
| Self-hosted parity with managed on gzip and `If-Match` | The Storage image at 1.80.2 | 1.74.0 drops `Content-Encoding` and ignores `If-Match`; at 1.80.2 `Content-Encoding` matches managed on every path and S3 GetObject enforces `If-Match` as managed does, while the REST read paths differ (managed answers 200 or 206 from cache) |

## Multipart: ETags, resume and abort

| Row (SS03a, SS03b) | Managed | Self-hosted, all four |
|---|---|---|
| Per-part ETag equals the local part MD5 | 128/128 | 128/128 |
| ListParts after 40 parts | `200`, 40 parts, 40 ETags match | same |
| Client process exits after 40 parts; a new process | ListMultipartUploads finds the upload, ListParts returns 40, 88 more parts uploaded, CompleteMultipartUpload `200` | same |
| SHA-256 of a full GET equals the fixture | true, 2147483648 bytes | true |
| Final ETag | AWS multipart form, MD5 of the part MD5s, `-128` | `sh-s3@*` the same; `sh-file@*` the object MD5 |
| AbortMultipartUpload | ListParts after it `404 NoSuchUpload`; the upload is gone from ListMultipartUploads | same |

The ETag form follows the backend and not the version. The same split shows on single uploads: one 64 MiB PutObject with a known length got `"b5d87668321e5b89a5adfed51e705c60-4"` on managed and `sh-s3`, and the object MD5 on `sh-file`. An unknown-length PutObject (chunked transfer encoding) got the `-4` form on managed and `sh-s3`. The compatibility page makes no statement about ETag form.

SS03j, information only, one sample each from one laptop: the 2 GiB multipart upload to the direct host took 208.3 s and the download from the gateway 58.1 s (managed run 2). That is not a throughput figure.

## Range reads

Single ranges (the first 1 KiB, a 4 KiB middle range, suffix `-1024`, open `N-`) returned 206 with the right `Content-Range` and bytes on `mid` and `big`, on S3 and REST, on every target (SS03c). The rows that differ:

| Request | Managed | `sh-file` 1.74.0 / 1.80.2 | `sh-s3` 1.74.0 / 1.80.2 |
|---|---|---|---|
| `Accept-Ranges` on S3 HeadObject and GetObject | absent | absent | absent |
| `Accept-Ranges` on a REST 206 | absent | `bytes` | `bytes` |
| Past EOF, S3 | `416 InvalidRange` | `416 InvalidRange` | `416 S3Error` / `416 InvalidRange` |
| Past EOF, REST | `416`, `Content-Range: bytes */67108864`, empty body | `416` JSON | `500` JSON / `416` JSON |
| `bytes=0-9,20-29`, S3 | `200`, whole object | `416 InvalidRange` | `200`, whole object |
| `bytes=0-9,20-29`, REST | `206`, `multipart/byteranges` | `416` | `200`, whole object |
| `Bytes=0-9` (capital unit), S3 | `200`, whole object | `416` / `206 bytes 0-9` | `200`, whole object |
| `Bytes=0-9`, REST | `206 bytes 0-9` | `416` / `206 bytes 0-9` | `200`, whole object |

On managed the REST answer to a multi-range or a capital-unit request differs from the S3 answer on the same object, and the S3 answer matches `sh-s3`. The `multipart/byteranges` body and the case-insensitive unit on managed REST therefore come from the layer in front of the origin; that is inference from the pattern, since the CDN serves REST reads and not S3 reads. A client that sends a multi-range request to S3 GetObject on managed or `sh-s3` receives the whole object with status 200, which for `big` is 2 GiB.

The compatibility page lists Range and PartNumber as supported on GetObject.[^sb-s3-compat] Range holds for single ranges. PartNumber is in the checksums section below.

## The CDN cache by read path

SS03d reads one 1 KiB range at offset 1 MiB through every read path and host; SS03k reads whole objects. The first design read keys that earlier rows had already warmed, so run 4 gives every path and host its own server-side copy (`CopyObject` to a fresh key, deleted after its two reads) and the first read is the first request for that key anywhere. Every read returned 206 with the right bytes on every target and host. Managed cache state, run 4, `mid` and `big` alike:

| Path | First read, fresh key | Repeat read |
|---|---|---|
| S3 presigned GET | `DYNAMIC` | `DYNAMIC` |
| Signed URL | `MISS` | `REVALIDATED` |
| `/object/public` | `MISS` | `HIT` |
| `/object/authenticated` | `MISS` | `HIT`, except the direct-host repeat on `big`, `MISS` |

The signed-URL repeat answered `REVALIDATED` here, where the [data residency page](/reference/supabase-data-residency/) recorded `HIT` for a repeat of the same signed URL on 2026-08-20; this run used a 2 GiB object and a fresh key per path, and the difference was not investigated.

Time for the 1 KiB range of `big`, time to response headers and total, milliseconds, managed run 4:

| Path | Gateway, cold | Gateway, repeat | Direct, cold | Direct, repeat |
|---|---|---|---|---|
| Presigned | 185 / 186 | 160 / 160 | 197 / 197 | 158 / 159 |
| Signed URL | 272 / 283 | 111 / 111 | 282 / 312 | 109 / 110 |
| Public | 389 / 395 | 87 / 87 | 319 / 330 | 86 / 86 |
| Authenticated | 1718 / 1728 | 102 / 102 | 337 / 363 | 31521 / 31527 (`MISS`) |

A cold ranged read of the 2 GiB object answered within 1,718 ms to headers on every path, while whole 2 GiB reads in SS03k took 53,064 to 155,110 ms from this vantage, so for a 1 KiB range on a MISS the headers arrived before a whole-object fetch could have finished (inferred; mechanism not measured). One repeat read, `/object/authenticated` on the direct host, was a MISS that took 31,521 ms for 1 KiB; in run 3 the same cell was a HIT at 116 ms. A request queued behind the edge filling the whole object after the first MISS would fit that wait. It is one sample and the mechanism was not measured. The self-hosted control has no cache: every cold and repeat timing was 4 to 105 ms locally.

### Does one path warm another

Fresh key per probe, `mid`, a public bucket, managed:

| First read, then | Run 4 | Run 3 |
|---|---|---|
| Authenticated, then public, same host | `MISS` -> public on the gateway `206 HIT` | not measured (copy timed out) |
| Public, then authenticated, same host | `MISS` -> authenticated on the gateway `206 HIT` | same |
| Authenticated, then signed URL, same host | `MISS` -> signed URL on the gateway `206 MISS` | not measured |
| Authenticated on the gateway, then on the direct host | `MISS` -> authenticated on the direct host `206 MISS` | same |
| Public on the gateway, then on the direct host | `MISS` -> public on the direct host `206 MISS` | same |

On a public bucket, in one probe per direction, `/object/public` and `/object/authenticated` share one cache entry per host. Signed URLs have entries of their own (one direction probed), and the gateway and the direct storage host do not share. The same probes on a private bucket were not run in this lab; the [data residency page](/reference/supabase-data-residency/) records a separate, earlier measurement of private-object caching across users. The S3 SDK cells do not record the cache header; the presigned S3 GET shows `DYNAMIC`.

## Conditional reads

SS03e, a 1 MiB object. The managed CDN columns are the CDN's answers for a cached object: when these were sent, every conditional GET after the control read on the signed, public and authenticated paths showed `HIT`, and every HEAD on them `REVALIDATED`. S3 and presigned reads are `DYNAMIC`, the origin's answer. The cold-cache case of a conditional read was not measured.

| Request | Managed S3 / presigned | Managed signed, public, authenticated | Self-hosted 1.74.0 (file, s3) | Self-hosted 1.80.2 (file, s3) |
|---|---|---|---|---|
| GET `If-None-Match` = ETag | `304` | `304 HIT` | `304` | `304` |
| GET `If-Match` wrong | `412 PreconditionFailed` | `200 HIT` | `200` | `412 PreconditionFailed` |
| GET `If-Modified-Since` = Last-Modified | `304` | `304 HIT` | file `200`, s3 `304` | `304` |
| GET `If-Unmodified-Since` yesterday | `412 PreconditionFailed` | `200 HIT` | `200` | `412 PreconditionFailed` |
| GET other ETag + `If-Modified-Since` = Last-Modified | `200` | `200` | file `200`, s3 `304` | file `200`, s3 `304` |
| S3 HEAD, any of the above | `200` | - | `200` | `200` |
| HEAD on the signed URL | - | `304` for If-None-Match and If-Modified-Since, `200` for a wrong If-Match and If-Unmodified-Since, `REVALIDATED` | If-None-Match `304`, If-Match and If-Unmodified-Since `200`; If-Modified-Since file `200`, s3 `304` | as GET: `412` for a wrong If-Match and If-Unmodified-Since, `304` for If-None-Match and If-Modified-Since |
| HEAD on public and authenticated | - | as the signed URL, `REVALIDATED` | `200` for every condition | `200` for every condition |

S3 HeadObject ignored every conditional header on every target; the compatibility page lists all four as supported on HeadObject.[^sb-s3-compat] RFC 9110 has a recipient ignore `If-Modified-Since` when `If-None-Match` is present[^rfc9110-ims], so "other ETag + If-Modified-Since" should be 200. Managed and the file backend answer 200; the `sh-s3` targets answer 304. The Storage server passes conditional reads to its S3 backend, so the `sh-s3` answers here (and `If-Modified-Since` 304 at 1.74.0) may be MinIO's rather than the Storage server's. Read those cells as "self-hosted with MinIO". Managed answers 200; its backend is not observable here, though its `-128` multipart ETag form matches `sh-s3`.

Ranged reads with a wrong `If-Match`, after two warming reads of the same range:

| Path | Managed (run 2) | Self-hosted 1.74.0 | Self-hosted 1.80.2 |
|---|---|---|---|
| Presigned S3 | `412`, `DYNAMIC` | `206` | `412` |
| Signed URL, public, authenticated | `206 HIT`, 1024 bytes | `206` | `412` |

### After an overwrite

The module read `cond-overwrite.bin` twice through `/object/authenticated` with a range, overwrote it through S3, then asked for the same range with `If-Match` set to the first version's ETag:

| Path | Managed | Self-hosted 1.74.0 | Self-hosted 1.80.2 |
|---|---|---|---|
| `/object/authenticated` | `206 HIT`, 100 bytes, first-version bytes | `206`, second-version bytes | `412` |
| S3 GetObject | `412 PreconditionFailed` | `206`, 100 bytes, second-version bytes | `412 PreconditionFailed` |
| `/object/public` | `206 MISS`, 100 bytes, second-version bytes | `206`, second-version bytes | `412` |

On managed, `/object/authenticated` served the pre-overwrite bytes from the cache (inferred: the If-Match matched the cached copy), and the public URL, on a MISS, returned the new bytes with status 206 although they no longer matched the If-Match ETag. The Storage server at 1.80.2 enforces If-Match on every path on self-hosted, which has no cache; on managed only the S3 paths, which the CDN does not cache, give the origin's answer. The resumable uploads page warns that an overwrite takes time to propagate to the edge and recommends a new path.[^sb-resumable] Not measured: how long the stale copy stays served, and whether a different `Range` or a fresh signed URL avoids it. The [image transformations page](/reference/supabase-image-transformations-billing/) records stale variants after an overwrite on the render path.

<Aside type="caution" title="A cache HIT is not a precondition check">
On managed, a wrong `If-Match` on a signed URL, `/object/public` or `/object/authenticated` got `200` or `206` from cache. A client that relies on `412` to detect a changed object has to read through S3 GetObject or a presigned S3 GET.
</Aside>

## Conditional writes

Identical on every target (SS03f, no key differs in SS06):

| Request on an existing key | Measured |
|---|---|
| PutObject `If-None-Match: *` | `200`, overwritten |
| PutObject `If-Match` with a stale ETag | `200`, overwritten |
| CompleteMultipartUpload `If-None-Match: *` | `200`, overwritten |
| CreateMultipartUpload `If-None-Match: *` | `200`, upload id returned |
| UploadPartCopy `x-amz-copy-source-if-match` wrong | `200`, ETag returned |

The compatibility page lists no conditional headers on PutObject, marks the `x-amz-copy-source-if-*` conditions supported on CopyObject and unsupported on UploadPartCopy.[^sb-s3-compat] Measured: the write conditions are accepted and ignored, so an "only create if absent" or "only replace this version" PUT overwrites. CopyObject's copy-source conditions were not tested.

## Checksums, attributes and part numbers

Identical on every target (SS03g; in SS06 only the unknown-length PutObject ETag differs):

| Request | Measured |
|---|---|
| PutObject `x-amz-checksum-sha256` correct / wrong | `200`, stored, both; no checksum echoed |
| PutObject `Content-MD5` correct / wrong | `200`, stored, both |
| PutObject `x-amz-checksum-crc32` wrong (header) | `200`, stored |
| aws-chunked body with a trailing `x-amz-checksum-crc32`, correct / wrong | `200`, stored, both |
| SDK default (`x-amz-checksum-crc32` as a header for a buffer body) and `requestChecksumCalculation: WHEN_REQUIRED` | `200`, both |
| HeadObject / GetObject `ChecksumMode: ENABLED` | `200`, no SHA-256 or CRC32 returned |
| GetObjectAttributes | `200`, `application/octet-stream`, 262144 bytes of object body: the request fell through to GetObject |
| UploadPart with SHA-256 correct / wrong | `200`, both |
| HEAD `?partNumber=1` on the 128-part object | `200`, `Content-Length` 2147483648, the whole object and not part 1 |

The compatibility page marks `Content-MD5` unsupported on PutObject and UploadPart and lists no checksum headers on PutObject.[^sb-s3-compat] Measured, "unsupported" means accepted and not checked: a corrupted body sent with a correct client checksum would be stored. The page lists partNumber as supported on HeadObject; it returned the whole object's length.

## Server-side encryption headers

Identical on every target (SS03l; the one SS06 difference is the wording of a cell, `200` against `200 accepted (upload id)`):

| Request | Measured |
|---|---|
| PutObject with SSE-C headers | `200`, no SSE response headers; GET without the key `200` and the plaintext bytes |

The compatibility page marks SSE unsupported and GetBucketEncryption unimplemented.[^sb-s3-compat] Measured: the headers are accepted and ignored. ## Whole reads of a gzip object and a 2 GiB object

SS03k reads two objects whole through presigned S3, signed URL, `/object/public` and `/object/authenticated` on both hosts, first and repeat: the 256 MiB gzip stream, stored through S3 PutObject with `ContentEncoding: gzip`, and `big`. The requests sent `Accept-Encoding: gzip, deflate, br`, through raw `node:http` so nothing decompressed the body. Every read returned the stored bytes with the full length (`Content-Length` 268517089 for the gzip object, 2147483648 for `big`) and no `Transfer-Encoding`: 16 of 16 cells per object on managed in run 4, and 8 of 8 on every self-hosted target.

Cache state of the repeat whole read on managed, run 4:

| Path | gzip object, gateway / direct | `big`, gateway / direct |
|---|---|---|
| Presigned | `DYNAMIC` / `DYNAMIC` | `DYNAMIC` / `DYNAMIC` |
| Signed URL | `MISS` / `MISS` | `MISS` / `HIT` |
| Public | `HIT` / `HIT` | `HIT` / `HIT` |
| Authenticated | `HIT` / `HIT` | `HIT` / `HIT` |

The edge cached and served the 2 GiB object intact. Signed URLs re-fetched the whole object on three of four repeat reads; their ranged repeats in SS03d were `REVALIDATED`. The targets differ only in the header on the gzip object:

| Target | `Content-Encoding` on every read of the gzip object |
|---|---|
| Managed (1.80.2) | `gzip` |
| `sh-file@v1.80.2`, `sh-s3@v1.80.2` | `gzip` |
| `sh-file@v1.74.0`, `sh-s3@v1.74.0` | absent |

At 1.74.0 a gzip object is served as opaque bytes with no encoding header, and no `Content-Encoding` header is sent, so a client that decodes by header would not decode it (not measured); at 1.80.2 the header comes back. Neither the edge nor the origin re-encoded or truncated anything. A client that decodes (fetch, a browser) would see the decompressed body; that is a client property and was not measured.

## Reading the numbers

- Managed is one full run (run 2) plus the SS03d and SS03k re-run (run 4); run 1 stopped part-way and is not cited. Each self-hosted variant is one full run, and `sh-s3@v1.80.2` also has the SS03d and SS03k control. Most rows are statuses and headers, deterministic reads, but n = 1 cannot separate a flaky answer from a stable one; the `sh-file@v1.74.0` 413 (uncaptured operator note) against 503 (captured) at the upload limit is one that moved.
- The timing cells are single samples from one laptop to `ap-southeast-1`. The 208.3 s upload and 58.1 s download of `big`, and the 53,064 to 155,110 ms whole reads, describe this vantage on this day.
- The cache cells describe a public bucket, objects up to 2 GiB, and keys read seconds apart. Eviction, objects past 2 GiB and warming on private buckets were not measured; the SS05d reads on a private bucket were one cold read per user.
- What generalises is the contract: which headers are enforced, which are ignored, and that the CDN answers REST reads from cache before the origin sees a precondition. The version split (1.74.0 against 1.80.2) is tied to the tags tested; a later Storage release can move any row.

## What to do about it

| Practice | Evidence | Module |
|---|---|---|
| Raise the global file size limit before a large upload. | At the default 52428800: S3 `413`, REST `400` with body 413, multipart refused at part 4. | SS03i |
| Verify uploads by per-part MD5s or a SHA-256 of a GET. | Wrong `x-amz-checksum-*`, `Content-MD5` and aws-chunked CRC32 values were stored; per-part ETag = part MD5, 128/128. | SS03a, SS03g |
| Do not compare a final multipart ETag across backends. | `-128` on managed and `sh-s3`, the object MD5 on `sh-file`; a TUS upload of the same bytes gets `-342`. | SS03a, SS04c |
| Resume multipart with ListMultipartUploads and ListParts. | A new process found the upload, read 40 parts, uploaded 88 and completed; SHA-256 matched. | SS03b |
| Send one range per request with a lowercase `bytes=` unit. | Multi-range and `Bytes=0-9` to S3 GetObject returned `200` and the whole object (2 GiB for `big`) on managed and `sh-s3`. | SS03c |
| Do not gate range requests on `Accept-Ranges`. | Absent on every S3 response and on managed REST 206s; single ranges still `206`. | SS03c |
| Read through S3 GetObject when a 412 must be enforced on managed. | S3 `412`; signed, public and authenticated answered a wrong `If-Match` with `200`/`206` from cache. | SS03e |
| Write a new key instead of overwriting an object served through the CDN. | After an S3 overwrite `/object/authenticated` served first-version bytes `206 HIT`. Duration not measured. | SS03e |
| Enforce create-if-absent in your own code. | PutObject `If-None-Match: *` and stale `If-Match` overwrote on every target. | SS03f |
| Encrypt client-side when data must be unreadable without your key. | SSE-C object readable without its key; AES-256-GCM chunks decrypted from ranged reads. | SS03l, SS05a |
| Set the content type on upload. | No sniffing: ciphertext and PNG without a type were stored as `application/octet-stream`. | SS05c |
| In a browser, read ETags from UploadPart only. | Managed exposes `etag` on UploadPart and no headers on GET; Envoy's `*` does not cover credentialed requests. | SS03h |
| Do not use PutBucketCors or GetBucketCors. | PutBucketCors on a new name created a bucket; GetBucketCors returned a listing. | SS03h |
| Match S3 errors on the XML code, REST errors on body `statusCode`. | S3 XML is `text/plain` on managed, `application/xml` self-hosted; REST errors are HTTP 400. | SS03i |
| Store the TUS upload URL so a crashed client can resume. | Resume after SIGKILL at offset 125829120 completed; gateway to direct host also completed. | SS04b |
| Send `x-upsert: true` on TUS overwrites; handle 409. | An existing key without it answered `409` (the docs say 400). | SS04d |
| Read `Upload-Expires` from the creation response. | 24 h managed, 1 h self-hosted MinIO, absent on the self-hosted file backend. | SS04d |
| Pin self-hosted Storage at 1.80.2 when If-Match or gzip objects matter. | 1.74.0 ignored `If-Match` and dropped `Content-Encoding: gzip`; at 1.80.2 S3 GetObject and presigned GET enforced `If-Match` as managed does (the REST paths differ) and `Content-Encoding: gzip` matched managed on every path. | SS06 |
| Self-hosted: address S3 at exactly the `STORAGE_PUBLIC_URL` host. | `127.0.0.1:8000` got `403 SignatureDoesNotMatch` where `localhost:8000` got `200`. | rig, SS03 target row |
| Self-hosted on macOS: keep the file backend on a named volume. | The default bind mount failed a 1 KiB upload with `500` (no extended attributes). | rig, SS03 target row |
| Ask about customer-managed keys outside the Management API. | 169 operations; the only encryption match is `PUT /v1/projects/{ref}/pgsodium`. | SS07b |

## Decision guide

```dot
digraph {
  rankdir=TB; bgcolor="transparent"; nodesep=0.35; ranksep=0.55;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];

  root [label="Large object on Storage", shape=hexagon];
  up   [label="Upload", shape=diamond];
  rd   [label="Read", shape=diamond];
  mp   [label="S3 multipart\n(resume via ListParts;\nverify part MD5s)"];
  tus  [label="TUS\n(store the upload URL;\nx-upsert or 409)"];
  s3   [label="S3 GetObject / presigned\n(DYNAMIC; 412 enforced at 1.80.2)"];
  cdn  [label="public / authenticated\n(MISS then HIT; shared entry)"];
  key  [label="new key per version"];

  root -> up;
  root -> rd;
  up -> mp  [label="an S3 client"];
  up -> tus [label="a browser or\ntus client"];
  rd -> s3  [label="must reflect the\ncurrent object"];
  rd -> cdn [label="cacheable,\nrepeat reads"];
  cdn -> key [label="objects that change"];
}
```

1. Upload from an S3 client: multipart in 16 MiB parts; resume with ListMultipartUploads and ListParts; check part ETags against local MD5s.
2. Upload from a browser or a TUS client: store the upload URL for resume; send `x-upsert: true` to overwrite, otherwise expect 409.
3. Read where the bytes must be current or a precondition must hold: S3 GetObject or a presigned S3 GET, which the CDN does not cache.
4. Read for cacheable repeat traffic: `/object/public` or `/object/authenticated`, and give a changed object a new key, since the cache served pre-overwrite bytes.
