Logs Ingest on Supabase is billed per byte across every service, at \$0.50 per GB after 20 GB included on paid plans.[^sb-logs-ingest] This page measures where those bytes come from: how much each kind of client request writes to the project logs, and how much the Postgres logging settings a project owner can change add on top. It is for whoever has to explain a logs line on an invoice, or decide which change on their side moves it.

The LV01 and LV02 rows ran on 2026-10-15 from one macOS machine in Singapore (Bun 1.3.14) against throwaway projects in `ap-southeast-1` on a Pro-plan organisation, one project per module run, created and read back through the Management API from the same machine; the client actions went straight to the project API. LV01 ran twice (`run1`, `run2`) with 100 actions per row; LV02 ran three times (`run1` to `run3`) with 50 requests or statements per condition. The figures are quoted from the [RUNLOG](https://github.com/erfianugrah/supabase-lab/blob/f7e86f3/experiments/logs-volume/RUNLOG.md) of the [logs-volume experiment](https://github.com/erfianugrah/supabase-lab/tree/f7e86f3/experiments/logs-volume/), and redacted copies of the run artifacts are linked in [Modules](#modules). Rows marked documented come from the public pages cited at the claim and were not run. LV03 (2026-11-09) and LV04 and LV05 (2026-11-10) ran once each from the same machine on a Team-plan organisation (Postgres 17.11, PostgREST 14.18), each on a project created with no `desired_instance_size` (compute size not read back); their figures are in the [RUNLOG at the later commit](https://github.com/erfianugrah/supabase-lab/blob/cb476ee/experiments/logs-volume/RUNLOG.md).

Size is a proxy throughout. Metered ingest bytes are not readable with a personal access token (the organisation usage route answered 401, [observability surface](/reference/supabase-observability-surface/)), so "bytes" here is the length of a row's `event_message` plus every key and value in its `log_attributes` map, as the logs endpoint returns it. The figures compare actions with each other; they do not predict the GB on an invoice.

**TL;DR:**

- A REST read or single-row write produced about 0.9 `edge_logs` rows per request; a REST GET row is 1807 bytes. A 100-row bulk insert produced one row.
- An Edge Function call with no console output wrote about 3,019 bytes in 2.81 rows: a `function_edge_logs` row plus a Boot and a Shutdown row in `function_logs`. Each ~100-character `console.log` line added about 520-540 bytes.
- `auth.getUser()` wrote 2,604 bytes per call; `auth.getClaims()` with an ES256 token wrote 27 bytes per call (2 rows for 100 calls).
- Public Storage reads served from the CDN cache are logged: 100 reads with 99 `cf-cache-status: HIT` produced 99 (`run1`) and 90 (`run2`) `edge_logs` rows.
- 100 Realtime broadcast messages over an open WebSocket wrote no `realtime_logs` or `edge_logs` rows (both runs; `run2` 0 rows and 2 bytes per message after idle subtraction).
- On a new project (`log_statement=ddl`, `log_min_duration_statement=-1`) REST GETs and SQL `select` statements wrote 0 `postgres_logs` rows. Of `postgres`, `authenticator` and `anon`, only settings on `authenticator` logged REST requests: `log_statement=all` added 4,405 bytes per REST request and `log_min_duration_statement=0` added 9,026 bytes.
- A role setting on `postgres` reached new direct sessions at once and had not reached new sessions through the shared pooler 75-453 s later. `alter role authenticator reset all` returned OK and cleared nothing.

## Which change moves which source

| Source in the logs | What writes it | Lever on the project side | Measured here |
|---|---|---|---|
| `edge_logs` | every HTTP request to the project API, cache hits included | send fewer requests: client or app caching, Realtime in place of polling, bulk writes, fewer round trips | LV01b-d, LV01h-j |
| `auth_logs` | Auth server calls such as `getUser` | verify the JWT locally with `getClaims` | LV01h, LV01i |
| `function_edge_logs`, `function_logs` | every Edge Function invocation, plus the function's own console output | fewer invocations; remove debug `console.log` | LV01e-g |
| `postgres_logs` | Postgres itself, per the logging settings in force | reset `log_statement`, `log_min_duration_statement`, `pgaudit.log` where raised; avoid `RAISE LOG` in hot functions | LV02 |
| `pgbouncer_logs`, background `postgres_logs` | the platform, with no client traffic | none | LV01a |
| `realtime_logs` | not seen per message in either LV01 run | - | LV01k, LV01l |

Text version of the diagram:

1. A REST, Auth or Storage request to the project API wrote up to one `edge_logs` row at the gateway (0.83-0.97 per request; 1807 bytes for a REST GET), including Storage reads served from the CDN cache; an Edge Function call wrote a `function_edge_logs` row instead.
2. Behind the gateway, PostgREST logs in as `authenticator` and switches to `anon` or `authenticated`; at defaults Postgres wrote no `postgres_logs` row for a REST GET (LV02a), and one row per call for a function that runs `RAISE LOG` (LV02i).
3. An Auth call writes an `auth_logs` row (608 bytes for `getUser`) as well as its gateway row.
4. An Edge Function call writes a `function_edge_logs` row and a Boot and a Shutdown row in `function_logs`, plus one row per console line.
5. A Realtime broadcast message on an already open WebSocket wrote no `realtime_logs` or `edge_logs` row.

## Per client action

Measured, LV01 `run2`, 100 actions per row (LV01d n = 1), sequential, one project. `run1` values in brackets where it measured the same thing. Keys: the legacy anon key for REST GETs, Edge Functions and Realtime; the legacy service_role key for REST inserts and Storage setup; no key for the public Storage reads; a password-signed-in user with an ES256 access token for the Auth rows. Per-action figures for the non-function rows subtract the idle rate from LV01a.

| Row | Action | Rows per action | Bytes per action | Where the bytes are |
|---|---|---|---|---|
| LV01b | REST GET, anon key | 0.91 (0.85) | 1659 (1520) | `edge_logs`, 1807 bytes per row |
| LV01c | REST insert, service_role key, one row per request | 0.92 (0.88) | 1610 (1525) | `edge_logs` |
| LV01d | REST insert, service_role key, 100 rows in one request (n = 1) | 1 `edge_logs` row (1) | 1771 (1771), `edge_logs` only | one row in both runs; all sources 2047 (1554), the difference is `pgbouncer_logs` idle-subtraction noise |
| LV01h | `auth.getUser()`, signed-in user | 1.98 (1.89) | 2604 (2343) | `edge_logs` plus one `auth_logs` row of 608 bytes |
| LV01i | `auth.getClaims()`, same user, ES256 token | 0.03 (0.03) | 27 (27) | 1 `auth_logs` and 1 `edge_logs` row for the 100 calls |
| LV01j | Storage public object, no key, same object | 0.97 (1.12) | 1014 (1144) | `edge_logs`; responses 1 MISS, 99 HIT in both runs; `run1` 1.12 includes 0.06 late `function_logs` and 0.06 `pgbouncer_logs` rows |
| LV01k | Realtime broadcast over an open WebSocket | 0 | 2 | 100 of 100 messages received |
| LV01e | Edge Function, anon key, no console output | 2.81 | 3019 | `function_edge_logs` 0.91 rows; `function_logs` Boot:95 Shutdown:95 |
| LV01f | Edge Function, one ~100-character `console.log` | 3.88 | 3622 | Boot:97 Log:100 Shutdown:97 |
| LV01g | Edge Function, ten `console.log` lines | 12.77 | 8221 | Boot:93 Log:1000 Shutdown:93 |

The `Rows per action` and `Bytes per action` columns are all-sources totals - the idle-subtracted sum across log sources - for every row except LV01d, whose figure is `edge_logs` only and gives its all-sources total beside it. The `Where the bytes are` column names the source the figure is read from, and the prose below quotes the `edge_logs`-only counts where they differ.

100 rows written one per request produced 91 `edge_logs` rows (LV01c, `run2`); 100 rows written in one request produced 1 (LV01d).

### Edge Functions

A silent invocation still wrote rows, even when the function printed nothing: a gateway row in `function_edge_logs` and two lifecycle rows in `function_logs`, Boot and Shutdown. The 100 sequential calls in LV01e (`run2`) produced 95 Boot and 95 Shutdown rows, which suggests nearly every call started its own worker (inferred from the event types). Each ~100-character console line then added about 520-540 bytes: LV01f minus LV01e is 1,482 - 940 bytes of `function_logs` per invocation, and LV01g gives (6,150 - 940) / 10.

Shutdown rows arrived up to about 3.5 minutes after the request (an exploratory probe of 20 invocations with 20 Boot and 20 Shutdown rows, not archived). Counting `function_logs` by time window therefore undercounts: `run1` did that and attributed 0.98 `function_logs` rows per invocation, and the late rows (event type not recorded in `run1`) showed up in later windows. `run2` counts by `log_attributes['function_id']` from the start of each phase, and that is the figure above.

### Auth: getUser against getClaims

`getUser()` calls the Auth server, and each call wrote an `edge_logs` row and an `auth_logs` row, 2,604 bytes in `run2`. `getClaims()` verifies the token locally against a cached JWKS when the project signs with asymmetric keys, and calls the Auth server when it signs with the legacy symmetric secret.[^sb-server-client] New projects issued ES256 user tokens here, and 100 `getClaims()` calls wrote 1 `auth_logs` and 1 `edge_logs` row in total. The request path of those two rows was not recorded; a JWKS fetch is what the docs describe. A server that calls `getUser()` on every request adds about 2,604 bytes to each request (derived from LV01h).

### Caching and Storage

Public Storage reads served from the CDN cache are logged. The same 1 KB object, fetched 100 times with no query string, came back 1 MISS and 99 HIT (`cf-cache-status`) in both runs and produced 99 (`run1`) and 90 (`run2`) `edge_logs` rows, about 1 KB each: a CDN cache HIT still wrote an `edge_logs` row. A cache in the client, the application or the project owner's own CDN keeps the request from reaching the project at all; that follows from LV01b, where each request reaching the gateway is one row, and was not separately measured.

### Realtime against polling

100 broadcast messages over an open WebSocket, all received, wrote no `realtime_logs` or `edge_logs` rows (LV01k, both runs), and two subscribed clients idling for 180 s wrote nothing attributable to them (LV01l: every source at or below the idle rate in `run2`; `run1` had 1 `edge_logs` row and 70 late `function_logs` rows in the 186 s window). The same updates fetched by polling cost a gateway row per poll: one client polling every 5 seconds sends 17,280 requests a day, which at LV01b's 1,659 bytes is about 28.7 MB (10^6 bytes) a day, or 0.86 GB over 30 days, per open client (derived from LV01b, not measured as a polling run). Realtime Postgres Changes were not measured.

### Idle background

With no client traffic, a project wrote at a rate of 520 `pgbouncer_logs`, 40 `postgres_logs` and 60 `function_logs` rows an hour (both runs), extrapolated from one 180 s window, about 4.2 MiB a day (`run1` 4.4). The 3 `function_logs` rows in that window are probably Shutdown rows from the setup's warm-up invocations (not determined). No setting for the `pgbouncer_logs` and `postgres_logs` background was found (not tested).

### Row completeness

Not every request produced a row the run could find. For 100 marked REST GETs, `edge_logs` held 84 (`run1`) and 92 (`run2`) rows, unchanged after a 300 s tail in `run2`; `function_edge_logs` counts per 100 invocations were 86-94 across both runs, and Boot counts were 93-97 (`run2`). Whether that is sampling, loss, or arrival later than the run waited is not determined. Read every per-request row count on this page as covering about 83-97 of every 100 requests (lowest: LV01h `run1`, 83 `edge_logs` rows).

## Postgres logging settings

The `postgres` role can change `log_statement`, `log_min_duration_statement` and `pgaudit.*` at role level through supautils; `log_connections` and `log_disconnections` are listed as CLI-only project settings.[^sb-custom-pg-config] The logs-ingest page lists `log_statement`, `log_min_duration_statement`, `log_connections`, pgAudit, and `RAISE NOTICE` / `RAISE LOG` in functions as the volume sources a project owner controls.[^sb-logs-ingest] On a new project the defaults were `log_statement=ddl`, `log_min_duration_statement=-1`, `log_min_messages=warning` and `log_connections=off`, and the platform roles `supabase_auth_admin`, `supabase_storage_admin` and `supabase_admin` carry `log_statement=none` at role level (read on a dev project, not archived).

Measured, LV02 `run3`, 50 anon REST requests and 50 SQL statements per path per condition. Settings were applied with `alter role ... set` from a `postgres` session through the shared pooler (session mode, 5432); REST traffic waited 45 s after each change, longer than PostgREST's default 30 s `db-pool-max-idletime`,[^pgrst-config] so PostgREST should open a new pool connection (not measured; the platform's own value was not read). LV05b (2026-11-10) later found idle pool connections kept past 330 s, so how these settings reached REST requests after 45 s is open; see [When an `authenticator` setting takes effect](#when-an-authenticator-setting-takes-effect). `run1` and `run2` gave the same REST rows per request except `run1` LV02e (0.02); bytes were within 16 bytes per request of `run3`. The direct path was measured in `run3` only.

| Row | Setting | `postgres_logs` per REST request | Per SQL statement, direct connection | Per SQL statement, shared pooler (session mode, 5432) |
|---|---|---|---|---|
| LV02a | defaults | 0 | 0 | 0 |
| LV02b | `postgres` `log_statement=all` | 0 | 1.02 rows, 621 bytes | 0 (session reported `log_statement=ddl`) |
| LV02c | `authenticator` `log_statement=all` | 4.02 rows, 4405 bytes | 0 | 0 |
| LV02d | `anon` `log_statement=all` | 0 | 0 | 0 |
| LV02e | `postgres` `log_min_duration_statement=0` | 0 | 1.02 rows, 661 bytes | 0 (session reported `log_min_duration_statement=-1`) |
| LV02f | `authenticator` `log_min_duration_statement=0` | 8.1 rows, 9026 bytes | 0 | 0 |
| LV02g | `postgres` `pgaudit.log=all` | 0 | 1.02 rows, 681 bytes | 0 (session reported `pgaudit.log=none`) |
| LV02h | defaults, RPC with `RAISE NOTICE` | 0 | - | - |
| LV02i | defaults, RPC with `RAISE LOG` | 1 row, 1336 bytes | - | - |

The role that matters for REST requests is `authenticator`, the role PostgREST logs in as. The same `log_statement=all` on `anon`, the role it switches to per request, logged nothing in three runs. Against LV01b's 1,659 bytes for a REST GET, `log_statement=all` on `authenticator` takes a request to about 6,064 bytes (3.7x) and `log_min_duration_statement=0` to about 10,685 bytes (6.4x); the ratios combine figures from two modules on different projects and are derived. `authenticated`, `service_role` and database-level settings were not tested.

A role setting on `postgres` reached new direct sessions at once and had not reached new sessions through the shared pooler 75-453 s later. In LV02b, e and g, each "new" pooled session reported the pre-change value of the setting under test, with a backend age that grew by about 75 s per condition across all conditions, from 75 s to 453 s (`run2` and `run3`), which fits one reused server connection, and logged nothing. When the pooler opens a fresh server connection, and the setting with it, was not measured.

`alter role authenticator reset all` returned OK and left `log_statement=all` in place, in all three runs; `alter role authenticator reset log_statement` removed it. At defaults `RAISE NOTICE` wrote nothing, because `log_min_messages=warning` sits above it, and `RAISE LOG` wrote one row per call.

### When an `authenticator` setting takes effect

A role setting applies to connections opened after the change, and PostgREST serves requests from a pool of connections it keeps open.[^pgrst-pool] PostgREST documents a 30 s `db-pool-max-idletime` and a 1,800 s `db-pool-max-lifetime`;[^pgrst-config] the values a hosted project runs are not readable from the project. Measured once each on 2026-11-10 with service_role-key traffic (LV04, LV05):

| Module | What ran | Result |
|---|---|---|
| LV05b | 8 concurrent RPC calls, then no traffic, DDL or NOTIFY for 330 s | the 8 pool connections stayed at all 33 samples, 0 to 327 s |
| LV04d | steady traffic (a point read about twice a second, a 300 ms RPC every 10 s), then `alter role authenticator set log_min_duration_statement = '200ms'` | the first duration row for the 300 ms RPC came 1,750 s later; the two pool connections were replaced at 1,792 s and 1,797 s of age |
| LV05c | the same setting under steady traffic, then `notify pgrst, 'reload config'` | the same 8 connections 90 s later; 0 duration rows |
| LV05d | then `notify pgrst, 'reload schema'` | 0 of the 8 left after 90 s; 18 duration rows from 3 s after the NOTIFY; 179 point reads and 18 RPC calls, all `200` |
| LV04e | `reset log_min_duration_statement`, then `pg_terminate_backend` on the `authenticator` connections from a `postgres` session | `postgres` is a member of `pg_signal_backend`; 2 of 2 terminated; 299 point reads and 15 RPC calls in the next 150 s, all `200`; 0 duration rows from 10 s after |

Under steady traffic a setting on `authenticator` waited for the pool's connection lifetime, about 30 minutes, and `notify pgrst, 'reload schema'` applied it within the next 90 s. The undo behaves the same way: after the `reset` in LV04e, connections opened since the change kept logging (6 rows in 60 s) until they were terminated. These are single runs at low request rates; the cost of `reload schema` on a large schema and pool behaviour at production concurrency were not measured. LV02's 45 s idle wait applying `authenticator` settings is not explained by LV05b.

### What the Postgres logs keep for a slow or timed-out Data API call

With `log_min_duration_statement` set on `authenticator`, the duration row for an RPC call carried PostgREST's statement and, in `log_attributes['parsed.detail']`, the bind values: `Parameters: $1 = '{"ms":300}', $2 = '1000', $3 = '0'` (LV05d), so request bodies reach `postgres_logs`. An anon-key call cancelled by the anon role's statement timeout answered HTTP `500` `57014` after 3,040 ms and left one row, `canceling statement due to statement timeout`, with `parsed.user_name` `authenticator`, `parsed.sql_state_code` `57014` and the statement in `parsed.query` with `$1` placeholders and no values (LV05a). Both measured 2026-11-10, one run each. Supabase's timeouts guide has a Logs Explorer query that lists both kinds of row.[^sb-timeouts]

### Finding the slow query in a time window without a drain

`pg_stat_statements` counters are cumulative, so an answer for one window needs two readings. LV03 (2026-11-09, one run, Postgres 17.11, pg_cron 1.6.4, pg_stat_statements 1.11) ran a pg_cron job every 30 seconds that copied the current database's `pg_stat_statements` rows and the non-idle client backends of `pg_stat_activity` into tables and kept 3 hours; the SQL is `SETUP` in [`lv03-snapshot-rca.ts`](https://github.com/erfianugrah/supabase-lab/blob/cb476ee/experiments/logs-volume/tests/lv03-snapshot-rca.ts). Over 120 s of three concurrent loops of a slow RPC (a `like '%abc%'` count over 1,000,000 rows) on top of point reads, the difference between the snapshots bracketing that window put the slow RPC first, 333,978.6 ms over 485 calls, and it was not in the top 5 for the baseline window before it (LV03b). The activity snapshots caught it in flight 12 times, under `usename` `authenticator`, so the query text is what identifies the call (LV03c).

| Module | `pg_stat_statements` rows per snapshot | Job run time | Snapshot table bytes per snapshot |
|---|---|---|---|
| LV03d | 705.9 | 22.6 ms average, 42.8 ms max, 15 runs | about 71.5 KB (1,073,152 bytes after 15) |
| LV04f | 4,911.8 (`pg_stat_statements.max` 5000, filled with 6,000 distinct statements) | 82.0 ms average, 103.5 ms max, 10 runs | 453,018 |

At 30 s that is 360 snapshots per 3 hours, about 26 MB at LV03's statement count and about 163 MB with `pg_stat_statements` full (derived). A stats reset or restart inside a window and the job's effect on a busy database were not measured.

## Decision guide

```dot
digraph {
  rankdir=TB; bgcolor="transparent"; nodesep=0.3; ranksep=0.5;
  fontname="Helvetica,Arial,sans-serif";
  node [fontname="Helvetica,Arial,sans-serif", fontsize=11, shape=box];
  edge [fontname="Helvetica,Arial,sans-serif", fontsize=9];
  start [label="logs ingest higher than expected"];
  which [label="which source carries the rows?"];
  edge_ [label="edge_logs / auth_logs:\ncount requests reaching the project"];
  fn [label="function_logs:\ncount invocations and console lines"];
  pg [label="postgres_logs:\nread role settings on authenticator and postgres"];
  bg [label="pgbouncer_logs only:\nplatform background, no lever"];
  start -> which;
  which -> edge_ [label="gateway"];
  which -> fn [label="functions"];
  which -> pg [label="Postgres"];
  which -> bg [label="idle"];
}
```

Text version of the decision guide:

1. Group the project's rows by `source` first; the lever depends on which one carries the volume.
2. `edge_logs` and `auth_logs`: count the requests reaching the project. Per-request `getUser` (LV01h) and single-row writes (LV01c) are the measured multipliers; polling and refetching on every render follow from LV01b's row per request and were not measured.
3. `function_logs`: count invocations and console lines per invocation. Each ~100-character line is about 520-540 bytes; each silent call is about 3,019 bytes.
4. `postgres_logs`: read `pg_db_role_setting` for `authenticator` and `postgres`, and search hot functions for `RAISE LOG`. At defaults REST GETs and `select` statements wrote 0 rows here; `RAISE LOG` wrote 1 row per call.
5. `pgbouncer_logs` and a few `postgres_logs` rows an hour with no traffic are platform background.

## What to do about it

| Practice | Evidence | Module |
|---|---|---|
| Group logs by `source` before changing anything. | Each source has a different lever; the gateway, function and Postgres rows above move independently. | LV01, LV02 |
| Replace polling with Realtime where updates are pushed. | A REST GET is about 0.9 `edge_logs` rows and 1,659 bytes; 100 broadcast messages wrote none. | [LV01](https://github.com/erfianugrah/supabase-lab/blob/f7e86f3/experiments/logs-volume/tests/lv01-request-footprint.ts) b, k |
| Batch writes into one request. | 100 single-row inserts produced 91 `edge_logs` rows (`run2`); one 100-row insert produced 1. | LV01c, LV01d |
| Verify auth with `getClaims()` on projects with asymmetric signing keys. | `getUser` wrote 2,604 bytes per call; `getClaims` wrote 27 bytes per call (2 rows per 100 calls). | LV01h, LV01i |
| Cache in the client or app; do not rely on the Storage CDN to cut logs. | 99 CDN cache hits of 100 still produced 90-99 `edge_logs` rows; client and app caching not measured. | LV01j |
| Gate Edge Function `console.log` behind a debug flag. | Each ~100-character line added about 520-540 bytes; a silent call wrote about 3,019. | LV01e-g |
| Count Edge Function rows by `function_id`, not by time window. | Shutdown rows landed up to about 3.5 minutes late; the windowed count was 0.98 `function_logs` rows per call in `run1` against 1.9 by id in `run2`. | LV01e, `run1` and `run2` |
