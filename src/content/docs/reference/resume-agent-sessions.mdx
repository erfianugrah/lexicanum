Both coding-agent harnesses on this workstation resume per directory: `pi -c` and `claude -c` open the newest session for the current directory, and each harness's picker lists only its own sessions. `resume` is a CLI that indexes the session files of both harnesses, lists them newest first from any directory, and starts the chosen one in the directory it started in. It is for anyone running more than one harness, or one harness across many repos, who has typed `pi -c` in the wrong directory.

Everything below was read from the `resume` source at v0.4.0 (commit `56ef6c7`, 2026-11-05) and measured on the same day on the WSL2 dev box (16 threads, Go 1.27.3, fzf 0.74.5). The first version of this page described v0.3.0 (commit `920a7e6`, 2026-10-21); the search, filter-mode, live-session and missing-directory sections are new in v0.4.0. The section on stored sessions describes v0.6.0 (tag `v0.6.0`, same day), which added listing, restore, relocation and merge from the session store. The repo is private, so file names are cited as text rather than links. Harness behaviour is cited from each harness's docs; where a claim was observed rather than documented, the evidence table at the end says so.

## TL;DR

- The machine held 1,565 session files (1,560 pi, 5 Claude Code) under 233 directories, about 2.7 GiB in total.
- The default list shows 345 of them, from 43 directories. The other 1,220 are pi workers (1,062), one-shot `pi -p` runs (156) and Claude Code SDK sessions (2); `--all` shows them.
- Both harnesses append to one JSONL file per session, so the index stores size, mtime and a byte offset per file.
- A run where nothing changed only stats the files: 24-31 ms in-process, 26-32 ms end to end for `resume ls`, a completion or one picker keystroke.
- An index built from scratch took 0.47-0.48 s with the files in the page cache.
- The search is the CLI's, not fzf's: every word must appear in the path, the title, any prompt, the branch or the ID, and the picker re-runs that search on every keystroke.
- Resuming means `cd` into the session's original directory, then `pi --session <file>` or `claude --resume <id>`, run in a subshell so a shell function named `pi` or `claude` still runs.
- The optional vim keymap for fzf is built from `unbind`/`rebind` and `change-prompt`, and reads the current mode back from `$FZF_PROMPT`.
- Search is not resume, but restore closes the gap: the memory store also keeps every pi session file byte for byte, and v0.6.0 lists the 1,574 interactive sessions whose files are gone from this disk, restores one on demand, relocates it when its directory is gone, and merges two copies of one session that continued apart.

## Which tool for which lookup

| You want | Use | Scope |
|---|---|---|
| The newest session in this directory | `pi -c`, `claude -c` | One harness, this directory[^pi-sessions][^cc-cli] |
| Any session of one harness | pi `/resume` then Tab; Claude Code picker then Ctrl+A | One harness, every directory[^cc-picker] |
| Any session of either harness, from the shell, searching paths and prompt text, with tab completion | `resume` | Both harnesses, this machine |
| A pi session whose file was pruned from this machine | `resume` (rows marked `⇣`): restores it, then resumes | pi, every host that syncs to the store |
| Text from any session on any host, any client | memledger search | Every client, every host; search only |

pi's picker has a Current Folder / All toggle on Tab (observed in the pi 1.3.0 picker; the docs describe its search, sort and named-only filters but not the scope toggle)[^pi-sessions]. Claude Code's picker shows the current worktree by default; Ctrl+W widens it to every worktree of the repo and Ctrl+A to every project on the machine[^cc-picker]. Each picker still lists only its own harness, opens only from inside that harness, and searches titles rather than the text of every prompt. The memory store is covered in [A cross-client memory store for coding agents](/reference/agent-memory-store/); it holds the text of sessions older than the 30-day local retention, but neither harness can resume from it.

## Where each harness keeps sessions

Read from live files on 2026-10-21; neither format is a documented interface, so the parsers are written against what the files contain.

| | pi | Claude Code |
|---|---|---|
| Root | `$PI_CODING_AGENT_SESSION_DIR`, else `~/.pi/agent/sessions` | `$RESUME_CLAUDE_DIRS` (colon list), else `$CLAUDE_CONFIG_DIR`, else `~/.claude`; then `projects/` |
| File | `<encoded-cwd>/<timestamp>_<id>.jsonl` | `<encoded-cwd>/<id>.jsonl` |
| Working directory | `cwd` in the first line, `{"type":"session",...}` | The first `cwd` seen on a user line. Later lines change when the user changes directory; the file stays under the launch directory |
| Title | Latest `session_info.name` | `custom-title`, else `ai-title`, else legacy `summary` |
| User turn | `type:message` with `message.role:user` | A line with `"type":"user"` that is not meta, sidechain or a tool result |
| Headless | Workers under `<encoded-cwd>/<parent-id>/subagents/` | `entrypoint:"sdk-cli"` |
| Resume command | `cd <cwd> && pi --session <file>` | `cd <cwd> && claude --resume <id>` |

Three details in that table shaped the parser in `internal/session/parse.go`:

- pi writes `"type"` as the first key of every line. Claude Code writes it first only on metadata lines (`ai-title`, `custom-title`, `summary`, `last-prompt`); user lines put it after `parentUuid`, `cwd` and others. The parser checks the first 96 bytes for metadata types and the whole line for `"type":"user"`. Nested JSON inside message content is escaped (`\"type\"`), so a raw byte match on the unescaped key only finds the top-level one.
- Claude Code tool results are user lines too, and can be megabytes. Once the working directory is known they carry nothing the index needs, and the parser skips them before decoding.
- Claude Code's `subagents/agent-*.jsonl` files are sidechain transcripts that `claude --resume` does not open, so they are not indexed at all. pi workers (since 2026-10-19 they persist under the parent's `subagents/` directory, see [Subagents, worktrees, and parallel agent work](/reference/agent-subagents-and-worktrees/)) are resumable and are indexed as headless.

`resume` starts both harnesses in the original directory. pi needs it: its `--session` accepts a path or an ID and searches the current project first, offering to fork a match from another project[^pi-cli]. Claude Code since v2.1.223 searches every project for a session ID passed to `--resume`[^cc-cli], so it would find the session from anywhere; `resume` still changes directory first so both harnesses behave the same way.

## What the default list hides

| Hidden by default | Count on 2026-11-05 | Rule |
|---|---|---|
| pi workers (`task`, `bg_task`) | 1,062 | File under a `subagents/` directory |
| One-shot `pi -p` runs | 156 | pi session with one prompt and no name |
| Claude Code SDK sessions | 2 | `entrypoint:"sdk-cli"` |
| Sessions with no prompt | 0 | No user turn parsed |

The pi rule is a heuristic, marked `simplify:` in `session.go`. pi records nothing in the session file that separates print mode from interactive mode. Interactive sessions on this harness get a name from the `session-auto-title` extension after the first turn; print-mode runs never do. So "one prompt, no name" is treated as a probe. An interactive session abandoned after one prompt, before the title arrived, is hidden too, and `--all` brings it back. Claude Code draws the same line itself: `claude --continue` and the picker skip `-p` and Agent SDK sessions[^cc-cli].

## The index

`internal/session/index.go` globs the session roots, then for each file:

1. Cached size and mtime unchanged: reuse the cached entry without opening the file.
2. File grew and the byte just before the cached offset is still a newline: seek to the offset and parse only the new lines. Any other byte there means the file was rewritten rather than appended to, and it is parsed from byte 0.
3. File shrank or was rewritten: parse from byte 0.
4. File gone: drop the entry.

Files that need parsing go to a worker pool sized to `GOMAXPROCS`. The parser consumes only complete lines and returns the offset just past the last newline, so a harness caught mid-write leaves its partial last line for the next run, and incremental parsing never sees half a JSON object. The first and last prompts are clipped to 400 characters each for the preview. Search needs every prompt, so a third field, `Prompts`, holds all of them whitespace-collapsed, 200 characters each, appended until it reaches 2,000 characters; on this machine that grew the index from 1.96 MB to 2.43 MB and left a warm run within a millisecond of what it was. The cache is written atomically (temp file and rename) with mode 0600, because it holds prompt text. A failed write costs only a slower next run. A `cacheVersion` constant discards caches written by an older parser.

The memory store's ingest uses the same byte-offset checkpoint, so it does not re-read a 30 MB file to find four new lines.

| Measured 2026-11-05 | Value | How |
|---|---|---|
| Session files | 1,565 (1,560 pi, 5 Claude Code), 233 directories | `resume ls --all -n 0 --json` piped to `jq` |
| Bytes on disk | 2.5 GiB pi, 238 MiB Claude Code | `du -sh` on both roots |

## Naming a session

`internal/session/filter.go` resolves the one argument `resume` takes, in this order:

1. A path ending in `.jsonl` that matches an indexed file.
2. A full session ID.
3. An ID prefix: at least 4 characters, and either a digit, a `-`, or 8 or more characters. One match resumes it; several open the picker over the matches. Without the digit rule, ordinary words made of hex letters (`cafe`, `added`, `face`) were taken as IDs and resumed whichever session happened to start with them.
4. Anything else is a query: every word must appear, case-insensitively, in the session's full path, title, any prompt, branch or ID. `dir:WORD` (or `d:WORD`) matches the path only, and `!WORD` excludes sessions containing the word anywhere. One match resumes it without opening fzf; several open the picker with the query typed in.

The path is searched because titles are the part people forget: `resume infra/r` lists every session started under `~/infra/r*`, and `resume kailh dir:logbook` finds a session by one word of one prompt plus the repo it ran in.

Listings show each ID cut to its shortest unique prefix, at least 8 characters. A fixed 8-character cut collides because pi IDs are UUIDv7: the first 48 bits are a Unix timestamp in milliseconds[^uuidv7], so the first 8 hex digits (32 bits) change about once every 65 seconds, and two sessions started within that window share them.

## Searching from the picker

fzf can only search what it shows. `--nth` selects among the fields left after `--with-nth`, so a row that displays age, harness, directory and title gives fzf nothing to match a prompt or a full ID against[^fzf-man]. v0.3.0 filtered with the CLI's matcher and then passed the same words to fzf as `--query`, and fzf filtered the result again against the visible row. `resume kailh`, a word that appeared only in one session's first prompt, matched one session in the CLI and none in fzf, and `--exit-0` turned that into a silent exit 130.

v0.4.0 runs fzf with `--disabled`, which turns off its filtering, and binds `change:reload(resume __list ... -- {q})`, so every keystroke re-runs the CLI's search and fzf only draws the rows. Rows highlight the matched words in the title and directory; a session that matched only through prompt text gets a dim snippet after the title (`> ...switchs, omron, kailh`), so the reason it is listed is visible.

ctrl-r cycles a filter, the way atuin cycles its filter modes[^atuin]: `all` (the flags as given), `repo` (sessions inside the git repository of the current directory, found by walking up for `.git` without running git), and `dir` (the current directory and below). The mode shows in the border above the prompt, `[ repo ~/infra/resume ]`, and a temp state file carries it between the `transform-border-label` that switches it and the `reload` that reads it. It stays out of the prompt because the vim keymap reads the prompt to know its own mode. `filter_mode` in the config picks the starting mode, and a start mode with no match widens to `all`.

## Stored sessions: list, restore, relocate, merge

memledger's ingester stores every complete line of every pi session file as a compressed blob keyed by its sha256, plus a per-file manifest of line hashes, so a file can be rebuilt byte for byte after its local copy is pruned[^memstore]. v0.5.0 and v0.6.0 make `resume` the client of that store.

Listing. Two PostgREST reads, the stored files (`raw_files`) and the pi session rows (`sessions`), joined on the session key, give 3,563 stored files; the ones whose session ID is not on disk are merged behind the local list and marked `⇣`. On this machine that is 1,574 interactive sessions, 1,990 with `--all`. The listing is cached next to the index for 10 minutes, and only `ls`, `show` and the start of the picker may refresh it; a picker keystroke and TAB read the cache only. Reading the cache made a warm `resume ls` go from about 28 ms to 38 ms. A failed refresh is not retried for a minute: before that back-off, an unreachable store cost a 3 s client timeout on every run.

Restore. Resuming a stored session rebuilds its file with `memledger raw cat` and checks the byte count against the store before writing. On its own host with its directory present, the file goes back to its original path; `cmp` against the store showed it identical. It is written to a temp file and hard-linked into place, so it can never replace an existing file.

Relocate. When the session's directory is gone, `resume` refuses and names the options: `-f` restores it into the current directory, and `--clone` clones the repository it ran in (recorded in the store at capture) to the old path first. Relocation rewrites three things and leaves every other byte as history: the header's `cwd`, the `cwd` section of the stored system prompt, and the header's `parentSession`. A session whose directory had been wiped was restored with `-f` into a scratch directory; `pi -p` on it reported the new working directory, recalled the task, and appended to the file in place, 14 lines to 23. A session from another host is restored as a relocated copy and forked with `pi --fork`, because one session ID continuing on two hosts would diverge.

Merge. Two copies of one session that continued apart share a prefix and then branch. pi stores a session as a tree of entries and resumes from the last entry in the file, so a merge is the union of both copies' entries with the chosen branch last. `resume merge ID [--from FILE] [--leaf newest|local|other]` writes the local header, the entries both copies hold (matched by entry ID), then both branches. In a test, one session got the codeword FIG-22 in one copy and KIWI-9 in the other; after the merge with the newest branch last, pi listed PLUM-4471 and KIWI-9, and with `--leaf local` it listed PLUM-4471 and FIG-22. The previous file stays as `<file>.pre-merge`.

Claude Code sessions and a second host are not done: neither is logged in on this machine, so those halves wait for the Mac.

## Live sessions

`resume last` used to pick the session open in the terminal next door, since that is the newest one. pi keeps no file descriptor open on its session file, so a lookup through `/proc/<pid>/fd` finds nothing. `internal/session/live.go` lists the `pi` and `claude` processes instead, from one of two sources: on Linux it scans `/proc/[0-9]*`; on macOS, which has no `/proc`, it runs one `ps -axww -o pid=,args=` and, only when that finds a harness process, one batched `lsof -b -n -P -a -d cwd -p PIDS -Fpn` for their working directories, each with a 3 s timeout (v0.7.0, commit `8751699`). Both sources apply the same matching rules:

- A command line that names the session (`pi --session <file>`, `claude --resume <id>`) marks that session.
- Otherwise each harness process marks the newest session of that harness in its working directory; `-p` processes pair with headless or probe sessions first, so a worker in the same directory does not take the interactive session's mark.

Live sessions get a green dot in the picker and in completion, `resume last` skips them and names each one it skipped on stderr, and resuming one explicitly warns and continues. A failed `ps` or `lsof` means no markers rather than an error.

The macOS listing costs about 0.25 s, and fzf reloads the list on every keystroke. The picker therefore lists processes once when it opens, writes a snapshot and passes it to each reload (`__list --live FILE`); a reload went from 238 ms to 9.7 ms, the median of 7 alternating runs each, with identical rows. Before v0.7.0 the check returned nothing on macOS.

## Launching through the user's shell

The first version exec'd the harness binary found on `PATH`. On this machine `claude` is also a zsh function that fetches API keys from the password manager before running the real binary, and the exec skipped it. v0.2.0 moved the launch into the shell:

```zsh
resume() {
  local f rc cmd
  f=$(mktemp "${TMPDIR:-/tmp}/resume.XXXXXX") || return 1
  RESUME_EMIT_FILE=$f command resume "$@"
  rc=$?
  cmd=$(<"$f")
  command rm -f -- "$f"
  [[ $rc -eq 0 && -n $cmd ]] || return $rc
  ( eval "$cmd" )
}
```

With `RESUME_EMIT_FILE` set, the binary writes `cd <dir> && <argv>` (each word shell-quoted) to that file instead of calling `syscall.Exec`. The function runs it in a subshell, so shell functions and aliases resolve, the harness gets the terminal, and the calling shell's directory does not change. The picker and `ls`/`show`/`-p` output go straight to the terminal; only the launch command goes through the file. Without the integration, `resume` still works and execs the binary directly.

If the session's directory no longer exists, `resume` exits 1 and prints the command it would have run. v0.3.0 printed a warning and started the harness in the current directory, where the agent then read and wrote the wrong tree. `-f` keeps that behaviour for when it is what you want.

## Completion in recency order

Completion lists sessions newest first, and a typed word narrows by ID prefix when it is one, otherwise by text, so `resume dotfiles<TAB>` offers the sessions started in the dotfiles repo and inserts the chosen ID. Both shells ask the binary for the list (`resume __complete -- <word>`), which returns `<id>\t<display>` rows in recency order. Keeping that order, and the hits, in the shell took seven workarounds:

| Problem | Fix |
|---|---|
| zsh replaced a text query with the longest common prefix of the matching IDs (`01a1`), losing the query | `compstate[insert]=menu` when the word is not an ID prefix and there are several hits |
| fzf-tab sorts every list unless the `sort` style is false[^fzf-tab]; in testing it also ignored the unsorted group from `compadd -V` | `zstyle ':completion:*:resume:*' sort false` |
| fzf re-ranks by match score | `--no-sort` in the fzf-tab flags, read from `resume __fzf-flags tab` at TAB time so a config edit applies without a new shell |
| zsh-autosuggestions' completion strategy suggested a second session ID after the first | Once a bare word is on the line, completion offers nothing more: `resume` takes one ID or query |
| fzf-tab pre-fills its fzf query with the typed word, and fzf filtered the CLI's hits again against the visible row: `resume 01a1ab<TAB>` showed 0 of 4 | `zstyle ':fzf-tab:complete:resume:*' query-string first`, which starts fzf with an empty query |
| fzf-tab inserted nothing for a single first-word match (`resume kailh<TAB>`) | fzf-tab skips inserting when the completion function returns non-zero, and the function ended with `_describe` for command names, which returns 1 when no command matches. It now returns whether any match was added (`compstate[nmatches]`) |
| bash has no menu completion | With several hits, the completion function runs fzf itself (`resume __pick`), then prints `\e[5n`; the terminal's `\e[0n` reply is bound to `redraw-current-line`, the trick fzf's own bash completion uses |

## A vim keymap from fzf bind and unbind

fzf has one keymap. Typed letters go into the query unless bound to an action, and its man page lists `unbind(...)`, `rebind(...)`, `change-prompt(...)`, `transform(...)` and the `FZF_PROMPT` variable that a transform command can read[^fzf-man]. `keys = vim` in `~/.config/resume/config` builds two modes from those (`internal/cmd/fzf.go`):

- Normal-mode keys (`j k g G h l w b 0 $ x D J K p q`, plus `y` in the picker) are bound to fzf actions, and the keys that return to insert mode (`i a A I S /`) are bound to "unbind the normal list, change to the insert prompt", after an optional cursor move. Insert mode starts by unbinding the whole list, so those letters type into the query.
- esc in insert mode rebinds the list and changes to the normal prompt.
- esc, ctrl-d, ctrl-u, ctrl-f and ctrl-b mean different things in each mode (ctrl-d is delete-char in insert, half-page-down in normal). Each is bound to a `transform` that compares `$FZF_PROMPT` with the normal prompt and prints the action for the current mode.

The mode is never stored anywhere except the prompt string, so `prompt` and `normal_prompt` must differ, and an `--prompt` in `fzf_opts` breaks vim mode. The picker sets `--with-shell` to `sh -c` so the transforms and the preview run in a POSIX shell rather than the user's login shell. fzf-tab mode cannot do that, because fzf-tab's own preview needs zsh, and it leaves `/` alone because fzf-tab uses it for continuous completion. Print-the-command is `print(print)+accept`: fzf prints a `print` line before the selection, and the binary checks for it. `--expect` would have been simpler, but an `--expect` key cannot also type into the query, and in vim mode `y` has to type in insert mode.

## Gotchas and lessons learned

| Gotcha | What happened | Rule now |
|---|---|---|
| Exec skips shell functions | The `claude` zsh function that injects API keys never ran | Launch through the shell function and `RESUME_EMIT_FILE` |
| Claude Code's `cwd` moves | Later lines carry the directory the user changed into; the file stays under the launch directory | Take the first `cwd` seen |
| Partial last line | A harness writing while `resume` reads leaves half a JSON object at EOF | Parse complete lines only, store the offset past the last newline |
| UUIDv7 prefixes | Sessions started within a minute share their first 8 hex digits | Shortest unique prefix, minimum 8 |
| esc then a key | Sent faster than the terminal's escape timeout, the pair reads as alt+key | Same as vim; tests send keys about 0.3 s apart in tmux |
| Testing completion | Pressing Enter on a `resume <id>` line launches the harness on a real session | Completion tests drive `zsh -f -i` under `zpty` and capture `$BUFFER` from a widget; never send Enter |
| A mistyped command | `resume lsit` is a query that matches nothing | Exit 2, the same code as a usage error |
| fzf filtering what the CLI already filtered | A query that matched a prompt, an ID or the full path found nothing in fzf, which only sees the row | fzf runs `--disabled`; the CLI re-runs its search on each keystroke |
| Hex words as IDs | `resume cafe` resumed a session whose ID started with `cafe` | An ID prefix needs a digit, a `-` or 8 characters |
| Missing directory | The agent started in the current directory and worked on the wrong tree | Exit 1 unless `-f` |
| A completion function's exit status | fzf-tab drops the candidates when it is non-zero; plain zsh does not care | Return `compstate[nmatches] > 0` |
| The store's `updated_at` | It is the store's own write time; a re-ingest stamped most rows with one day in October | Sort stored sessions by `ended_at` (set for pi since 2026-11-05), else `started_at` |
| A stored file that is still on disk | Sessions run with a custom session directory are outside the scanned roots, so they looked pruned | A stored row whose own-host file exists is listed as local |
| HTML escaping in Go's JSON encoder | `json.Marshal` writes `<cwd>` as `\u003ccwd\u003e`, so the relocation match failed | Encode with `SetEscapeHTML(false)` |

1. Session file not on this machine: a pi session is listed by `resume` with `⇣` and restored on resume; for anything else, search memledger, read what it holds, start a new session.
2. The newest session in the current directory: `pi -c` or `claude -c`.
3. Already inside the right harness: its own picker, widened to every directory.
4. Anything else, including "which harness was that in": `resume`, `resume <words>` or `resume <TAB>`.
