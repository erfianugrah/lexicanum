# Docs layout: reading width vs wide tables and diagrams (2026-11-10)

Question from the owner: the site's prose ran up to ~190 characters per
line on a wide monitor, but Starlight's default single 45rem column
squeezes the tables and Graphviz diagrams this corpus is full of. What
layout keeps text readable and gives tables and diagrams room? The answer
shipped as house Starlight kit 0.1.25 (lexicanum#82).

Raw dumps: `raw/2026-11-10-layout/docs-sites.md` (13 docs sites measured
with Playwright at 390/1280/1600/1920/2560px), `raw/2026-11-10-layout/videos.md`
(six YouTube typography/hierarchy tutorials, transcribed),
`raw/2026-11-10-layout/written-sources.md` (Tufte CSS, GOV.UK, Butterick,
Every Layout, Comeau and Mulligan breakout grids, GitLab Pajamas). The
reading-width and contrast evidence is in `2026-11-10-typography.md`.

## What was tried first and rejected (same day)

| Attempt | Why it was rejected |
|---|---|
| 34rem prose cap, left-aligned in a column up to 96rem (kit 0.1.22) | half of a wide screen empty |
| Prose on a centred axis, tables/code breaking out on both sides (0.1.23) | a zigzag of left edges between prose, tables and diagrams |
| Tables and code sized each to its own content | every block a different right edge |
| Starlight's single 45rem column for everything | the shape the site had moved away from: tables and diagrams squeezed |

All four were reverted (kit 0.1.24) before the research below.

## What established docs sites do (measured)

From `docs-sites.md`, spot-checked by the parent on MDN and Starlight at
1920 and 2560px (paragraph, table and code block share left edge and
width):

| Pattern | Sites | Chars per line | Wide blocks |
|---|---|---|---|
| One fixed column for everything | Tailwind, Supabase, Next.js, Starlight, Material for MkDocs | 95-148 | same width as prose |
| Wide area, prose and blocks capped together | Stripe, MDN, Rust Book, Cloudflare, Fly.io, GitHub Docs | 98-107 | same width as prose |
| No cap | Kubernetes, Vercel | up to 170 | same as prose |

No surveyed site lets tables run wider than its prose. Heading scales:
h1 2.2-2.5x body, h2 ~1.5x, h3 1.2-1.25x; more space above a heading than
below (32-60px above, 0-24px below).

The videos agree on 50-70 characters for body text, big steps between
heading levels, and whitespace as the grouping cue; none addresses wide
tables. The written sources name two patterns that keep a measure and give
blocks room: Tufte's one left edge with fullwidth figures, and GOV.UK's
two-thirds text column with tables at full width.

## What shipped (kit 0.1.25)

The owner A/B'd a two-width layout against the 45rem single column and
picked it, with the docs heading scale:

- Running text (paragraphs, lists, quotes, asides, section headings,
  references) on a reading column centred in the content area.
- Tables, code blocks, diagrams and card grids fill the whole content
  column, all at one width.
- Page title and kicker on the wide column's left edge, so a long title
  stays on one line.
- Right sidebar only as wide as its table of contents (Starlight gives it
  half of the leftover space).
- Fluid by viewport between 1280 and 2560px: body 18 -> 20px, reading
  column `clamp(38rem, 28.5rem + 11.875vw, 50rem)`, content column
  `clamp(60rem, 46vw, 72rem)` (shipped at 100rem in kit 0.1.25, cut to
  84rem in 0.1.26 because the wide blocks ran nearly twice the text
  width, then 72rem in 0.1.28 with the reading column widened to
  `clamp(38rem, calc(24rem + 17.5vw), 52rem)`, so tables sit at about 1.4x
  the text at 2560px instead of 1.75x),
  sidebar `clamp(15rem, 12.5vw, 20rem)`.
- Line height 1.6 (was 1.75) and one empty line, the line height, between
  paragraphs (was 12px, 0.4 of a line): a paragraph break read as one more
  line wrap (kit 0.1.26).
- h2 27px / h3 22px, 3rem / 2.25rem above, 1rem / 0.5rem below.
- Inline code is an inline block (moves to the next line whole; only a
  span longer than a line wraps); table cells keep words whole and break
  code; every table is wrapped in `div.table-scroll` so the few whose
  words cannot fit scroll instead of widening the page.

Measured on the final build (Playwright, dark, five pages):

| Viewport | Body | Chars per line | Reading column | Content column | Sidebar |
|---|---|---|---|---|---|
| 390 | 18px | 45 | 350 | 350 | - |
| 1280 | 18px | 79 | 608 | 728 | 240 |
| 1440 | 18.25px | 81 | 627 | 888 | 240 |
| 1600 | 18.5px | 81 | 646 | 960 | 240 |
| 1920 | 19px | 83 | 684 | 998 | 240 |
| 2560 | 20px | 87 | 760 | 1331 | 320 |

The table is kit 0.1.26. Kit 0.1.28 (live since 2026-11-10 evening):
1440 -> 82 chars / 636px text / 888 column, 1600 -> 83 / 664 / 960,
1920 -> 88 / 720 / 960, 2560 -> 95 / 832 / 1152; 1280 and 390 unchanged.
0.1.25 shipped content columns of 1000/1200/1600.

Over all 179 pages at 390, 1280, 1920 and 2560px: no page scrolls
sideways and no block spills past the content column (re-run on kit
0.1.28 over 180 pages: still clean). Of 1,330 tables (1,340 by 0.1.28),
15 scroll inside their wrapper at 1280px and 1 at 1920px (0 before the
84rem cap). No short
word (a header like MEDIAN) splits inside a table cell. `house check`
passes all eight steps on five pages; its `type-measure` maximum moved
from 80 to 90 characters (100 since 0.1.28) to hold the chosen measure (WCAG 1.4.8 says 80;
the measured docs sites run 95-107).
